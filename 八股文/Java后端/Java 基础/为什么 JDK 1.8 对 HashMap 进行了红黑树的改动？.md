# 为什么 JDK 1.8 对 HashMap 进行了红黑树的改动？

## 回答重点

JDK 1.8 引入红黑树是为了解决**哈希冲突严重时查找性能退化**的问题。

JDK 1.7 及之前，`HashMap` 用链表处理冲突，一旦冲突多了，链表变长，查找复杂度从 $O(1)$ 退化成 $O(n)$。更严重的是，攻击者可以故意构造大量哈希冲突的 `key`，让 `HashMap` 变成一条超长链表，查询直接卡死，这就是所谓的哈希碰撞攻击。

JDK 1.8 的做法是：正常情况还是链表，但链表长度达到 8 且数组长度达到 64 时，自动转成红黑树，查找复杂度降到 $O(\log n)$。反过来，红黑树节点数降到 6 以下时，又退化回链表。

## 扩展知识

### 树化的两个条件

链表转红黑树要同时满足两个条件：

1. 链表长度 >= 8
2. 数组长度 >= 64

如果链表长度到了 8 但数组长度不到 64，`HashMap` 会选择扩容而不是树化。原因很简单：小数组冲突多是正常的，扩容后槽位变多，冲突自然就散开了。这时候树化纯属浪费，扩完容可能链表就剩两三个元素了，白折腾一趟。

### 为什么是 8 和 6

为什么树化阈值定成 8？`HashMap` 源码注释给出了数学依据：在负载因子 0.75 的情况下，单个桶里出现 8 个以上元素的概率只有千万分之六，概率极低。

![20220219202956.png](Z:/Public/images/20220219202956_mianshiya.webp)

换句话说，正常使用 `HashMap` 几乎不会触发树化，只有在数据分布极端不均匀或者遭受攻击时才会。8 这个数字是个很好的分界点：小于 8 时链表遍历也很快，没必要付出红黑树的内存代价；大于 8 时冲突确实严重了，值得用红黑树来保底。

退化阈值定成 6 而不是 8，是为了**留个缓冲区间，避免反复横跳**。想象一下，如果树化和退化都用 8，一个桶里有 8 个元素，刚树化完，删一个变 7 个，退化成链表；再加一个变 8 个，又树化。来回折腾性能开销很大。定成 6 就留了 2 个元素的缓冲，不会因为一两次增删就反复切换。

### 为什么不全用红黑树

红黑树节点占用的内存是链表节点的两倍。TreeNode 要额外存父节点、左右子节点、颜色标记这些字段，而链表节点只需要一个 next 指针。

![20220219202947.png](Z:/Public/images/20220219202947.webp)

在大多数场景下，`HashMap` 的冲突都很少，链表长度普遍在 1-3 之间。这时候用红黑树纯粹是浪费内存，遍历三四个节点的链表，性能跟红黑树查找没什么区别。所以 JDK 的设计是：默认用链表，只有在真正需要时才升级成红黑树。

### 红黑树的特性

红黑树是一种自平衡二叉搜索树，通过颜色标记和旋转操作保证树的高度不会超过 2log(`n`+1)，从而保证查找、插入、删除的时间复杂度都是 $O(\log n)$。

`HashMap` 里的红黑树还有个特殊处理：节点同时保留了链表的 next 指针。这样在遍历整个 `HashMap` 时，还是可以像遍历链表一样顺序访问，不用做中序遍历。

## 面试官追问

#### 提问：哈希碰撞攻击具体是怎么实现的？怎么防御？

详细解答可以看：[什么是 Hash 碰撞？怎么解决哈希碰撞？](https://www.mianshiya.com/question/1821481519536611330)

回答：攻击者构造大量 `hashCode` 相同的 `key` 发送给服务端，让 `HashMap` 退化成链表。比如在 JDK 1.7，String 的 `hashCode` 是公开算法，攻击者可以预先计算出一批碰撞的字符串。防御手段有几个：JDK 1.8 引入红黑树是治本的方案；另外可以对用户输入做限制，比如限制 POST 参数数量；Tomcat、Jetty 这些容器也加了参数个数上限的配置。

#### 提问：红黑树的旋转操作是什么意思？为什么需要旋转？

回答：红黑树插入或删除节点后可能破坏平衡性，通过左旋和右旋来重新平衡。左旋就是把一个节点的右子节点提上来，自己变成左子节点；右旋反过来。旋转不改变二叉搜索树的性质，只调整树的形状，让左右子树高度差保持在可控范围内。`HashMap` 里具体的旋转逻辑在 `TreeNode` 的 `balanceInsertion` 和 `balanceDeletion` 方法里。

#### 提问：`ConcurrentHashMap` 也有红黑树吗？实现上有什么不同？

回答：有的，JDK 1.8 的 `ConcurrentHashMap` 也引入了红黑树，树化阈值同样是 8。不同点在于并发控制：`HashMap` 的树化过程不加锁，`ConcurrentHashMap` 用 synchronized 锁住当前桶的头节点，保证树化过程的线程安全。另外 `ConcurrentHashMap` 的 TreeBin 封装了红黑树的根节点，还维护了一个读写锁状态来优化并发读。
