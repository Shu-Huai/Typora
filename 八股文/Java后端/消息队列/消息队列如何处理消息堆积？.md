# 消息队列如何处理消息堆积？

## 回答重点

消息堆积是指消息生产速度远大于消费速度，导致大量消息积压在队列中。处理时要先定位消费变慢的原因：如果是 Bug 先修复，同时临时扩容；如果是消费能力不足，则优化消费逻辑。

常见提升消费能力的方法：

1. **增加消费者线程数量**，提高并发消费能力。
2. **增加消费实例**，在分布式系统中水平扩展消费者。
3. **优化消费者逻辑**，减少 I/O 和单条消息处理时间，使用批量处理。

扩展消费实例时要注意，Topic 对应的分区或队列数必须大于等于消费实例数，因为一个分区或队列通常只会分配给一个消费实例。

还可以进行限流和降级：对生产端限流，降低生产速率；对非关键消息丢弃或延迟处理，只保留高优先级消息。

## 扩展知识

### 优化消费者逻辑

- **批量消费**：一次读取多条消息，减少网络开销，提高处理效率。Kafka 可通过 `max.poll.records` 控制，RocketMQ 可通过 `consumeMessageBatchMaxSize` 控制。
- **异步消费**：将消息交给线程池异步处理，主线程继续拉取下一批，但要配合手动提交 offset 和业务幂等，避免消息丢失或重复。
- **优化数据库操作**：使用数据库连接池、SQL 优化、缓存以及批量插入或更新，减少单条消息的数据库访问次数。

### 临时扩容队列

- Kafka 可以增加 Partition 数量，同时扩展消费者实例。分区数只能增加不能减少，扩容前要评估后续维护成本。
- RocketMQ 可以动态增加队列数，扩容后检查消费者是否感知到新队列，必要时重启客户端。
- RabbitMQ 可以通过 Exchange 将消息路由到多个队列，每个队列配置一个消费者，积压消化后再撤掉临时队列。

### 限流与降级

生产端可以使用**令牌桶**或**漏桶算法**限制发送速率。Kafka 可调整 `linger.ms` 和 `batch.size`，让生产者攒批发送；业务层也可以使用 Guava `RateLimiter`。

消费端要区分消息优先级：核心业务必须处理，非核心消息可以暂时丢弃或发送到延迟队列。RabbitMQ 原生支持优先级队列，Kafka 和 RocketMQ 可以使用不同 Topic 区分优先级，并给高优先级 Topic 分配更多消费者。

### 堆积监控和告警

- Kafka 重点监控 consumer lag。lag 超过 10 万条可以告警，超过 100 万条需要紧急处理。
- RocketMQ 控制台可以查看每个队列的堆积量，也可以通过 MQAdmin 定时采集。
- 监控最老未消费消息的存活时间，例如超过 10 分钟仍未消费，说明消费能力不足，需要扩容或排查。

### 不同 MQ 的堆积处理思路

| MQ | 主要处理方式 |
| --- | --- |
| Kafka | 增加分区数和消费者数，优化 consumer lag |
| RocketMQ | 增加队列数，扩容消费者，检查消费进度 |
| RabbitMQ | Exchange 分流到多个队列，为队列增加消费者 |

## 面试官追问

#### 提问：消费者重启或者崩溃了，堆积的消息会丢吗？

回答：通常不会丢，消息仍保存在 Broker 中。Kafka 的消息持久化在磁盘上，Consumer Group 的消费位点也会持久化，消费者重启后从上次 offset 继续消费。RocketMQ 的消息存在 CommitLog 中，消费进度存在 ConsumerOffset 中。前提是 Broker 正常、消息没有过期。

#### 提问：消息堆积会不会把磁盘撑爆？怎么处理？

回答：有这个风险。Kafka 可以配置 `log.retention.hours` 和 `log.retention.bytes` 控制保留时长和大小；RocketMQ 默认消息保留 72 小时，也可以调整。堆积严重时要尽快消费，或临时扩容磁盘，对过期消息允许清理，但根本方案仍是提升消费能力。

#### 提问：消费者处理一条消息要 1 秒，QPS 要求 1 万，怎么设计？

回答：单条处理 1 秒而要求 1 万 QPS，需要约 1 万个并发处理。假设单机 100 个消费线程，就需要约 100 台消费者机器，Topic 分区数至少 100 个，每个消费者绑定一个分区。更好的方式是先通过批量处理、异步 I/O 等手段降低单条耗时。

#### 提问：顺序消费场景下消息堆积了怎么办？

回答：顺序消费不能随意增加消费者，因为一个分区只能被一个消费者消费。应先提升单个消费者的处理速度，或增加分区数并同步增加消费者；还可以缩小严格顺序的范围，例如按订单 ID 路由到不同分区，只保证分区内顺序、分区间并行。
