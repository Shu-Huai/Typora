# 简述下消息队列核心的一些术语？

## 回答重点

消息队列的核心术语围绕消息的“生产 - 存储 - 消费”链路展开。

![消息队列核心术语](Z:/Public/images/vQ72NFcy_FtHA9vrxVv_mianshiya.webp)

以下是所有主流 MQ 都通用的基础术语：

1. **生产者 Producer**：发消息的一方，比如订单服务下单成功后往 MQ 里丢一条“订单创建”的消息。
2. **消费者 Consumer**：收消息的一方，库存服务订阅这条消息后去扣减库存。
3. **Broker**：消息队列的服务端，专门负责接收、存储、投递消息。
4. **消息 Message**：生产者和消费者之间传递的数据单元，通常包含消息体和一些元信息（如 ID、时间戳、属性等）。

以上四个概念是所有 MQ 都有的。但再往下的术语，不同 MQ 的消息模型差异很大，需要分开讲。

## 扩展知识

### 三种 MQ 的消息模型差异

三种主流 MQ 的核心模型完全不同，这导致了术语体系的差异：

- **RabbitMQ**：Exchange-Queue 模型，消息先到 Exchange，通过路由规则分发到 Queue。
- **Kafka**：Topic-Partition 模型，消息按 Topic 组织，Partition 是最小存储和并行单元。
- **RocketMQ**：Topic-MessageQueue 模型，跟 Kafka 类似但底层存储结构不同。

### RabbitMQ 核心术语

**Exchange（交换机）**：生产者不直接把消息发到队列，而是发到 Exchange，Exchange 根据路由规则把消息分发到绑定的队列。有四种类型：

- Direct：按 Routing Key 精确匹配。
- Fanout：广播给所有绑定的队列。
- Topic：按 Routing Key 的通配符模式匹配。
- Headers：按消息头属性匹配（用得少）。

**Queue（队列）**：消息的最终存储位置，消费者直接从 Queue 消费。一个 Queue 里的一条消息只会被一个消费者消费（竞争消费模式）。

**Binding（绑定）**：Exchange 和 Queue 之间的关联关系，定义了消息的路由规则。

**Routing Key（路由键）**：生产者发消息时带上的标签，Exchange 根据它决定消息路由到哪个 Queue。

**vhost（虚拟主机）**：逻辑隔离单元，类似命名空间，不同 vhost 的 Exchange 和 Queue 互不可见，适合多租户场景。

RabbitMQ 不需要独立的命名服务，生产者和消费者直接配置 Broker 地址连接即可。

### Kafka 核心术语

**Topic（主题）**：消息的逻辑分类，生产者往某个 Topic 发消息，消费者订阅 Topic 来消费。

**Partition（分区）**：Topic 的物理拆分单元。一个 Topic 可以配多个 Partition，每个 Partition 是一个独立的有序日志文件，Partition 之间并行处理提高吞吐量。

**Offset（消费位点）**：每条消息在 Partition 里的唯一编号，从 0 递增。消费者记住当前消费到的 Offset，重启后从该位置继续消费。Offset 存储在 Broker 内部的 `__consumer_offsets` 这个特殊 Topic 里。

**Consumer Group（消费组）**：同一个消费组内的消费者共同分摊 Topic 的所有 Partition，一个 Partition 只分配给组内一个消费者。不同消费组各自维护独立的 Offset，互不影响。

![Kafka 消费者组](Z:/Public/images/l5bcUviB_dNJl9Zyu0B_mianshiya.webp)

**ISR（In-Sync Replicas）**：和 Leader 保持同步的副本集合。只有 ISR 内的副本才有资格竞选新 Leader，保证数据不丢。

**Leader / Follower**：每个 Partition 有一个 Leader 负责读写，多个 Follower 负责同步数据做备份。

Kafka 早期依赖 **ZooKeeper** 做 Broker 的服务发现和元数据管理，2.8 版本后引入 **KRaft 模式**，可以不再依赖 ZooKeeper。

### RocketMQ 核心术语

**Topic（主题）**：和 Kafka 一样，消息的逻辑分类。

**MessageQueue**：Topic 下的存储队列，功能上等价于 Kafka 的 Partition，用来提高并发度。但底层实现不同——同一个 Broker 上所有 MessageQueue 的消息其实写在同一个 **CommitLog** 文件里，通过 **ConsumeQueue** 索引来区分不同队列。

**Tag（消息标签）**：RocketMQ 特有的二级分类机制。比如 Topic 是“订单消息”，Tag 可以是“创建”“支付”“取消”，消费者可以按 Tag 过滤只消费感兴趣的消息，不用为每种类型单独建 Topic。

**Offset（消费位点）**：和 Kafka 一样，每条消息在 MessageQueue 里都有一个 Offset 编号。集群消费模式（CLUSTERING）下 Offset 存在 Broker 端，由 Broker 统一管理；广播消费模式（BROADCASTING）下 Offset 存在消费者本地，每个消费者各自维护自己的进度。

**Consumer Group（消费组）**：跟 Kafka 类似，同组内消费者分摊 MessageQueue，不同组各自独立消费。

**Producer Group（生产者组）**：这是 RocketMQ 相对独有的概念。Kafka 的生产者没有“组”的概念，但 RocketMQ 的生产者需要归属一个 Producer Group，主要用于事务消息的回查——如果发事务消息的生产者宕机了，Broker 会找同组的其他生产者来回查本地事务状态。

**NameServer**：RocketMQ 自己实现的轻量级命名服务，管理 Broker 的地址路由信息。各个 NameServer 节点之间互相独立不通信，Broker 会向所有 NameServer 注册，生产者和消费者随便连其中一个就能拿到完整的路由表。

### 通用机制类术语

以下概念三种 MQ 都有，只是实现方式不同：

**ACK（消息确认）**：消费者处理完消息后给 Broker 发确认信号。Broker 收到 ACK 后才认为消息消费成功。没收到 ACK 的消息会被重新投递，保证消息不会因为消费者宕机而丢失。

**消息重试（Retry）**：消息消费失败后会自动重试投递，重试多次仍失败才进死信队列。

**死信队列 DLQ（Dead Letter Queue）**：反复消费失败的消息最终会被扔到死信队列里，方便事后排查和人工处理。RabbitMQ 通过 DLX（Dead Letter Exchange）实现，RocketMQ 自动生成 `%DLQ%` 队列，Kafka 没有原生支持需要自行实现。

## 面试官追问

#### 提问：Kafka 的 Partition 和 RocketMQ 的 MessageQueue 有什么本质区别吗？

回答：功能上没区别，都是为了提高并发度把 Topic 拆成多个存储单元。主要差异在实现细节上，Kafka 的 Partition 是物理隔离的，每个 Partition 对应磁盘上一个独立的日志目录。RocketMQ 的 MessageQueue 是逻辑概念，同一个 Broker 上所有队列的消息写在同一个 CommitLog 文件里，通过 ConsumeQueue 索引来区分不同队列。

#### 提问：消费组里的消费者数量超过分区数会怎么样？

回答：多出来的消费者会空闲，分不到任何分区。比如 Topic 有 4 个分区，消费组里塞了 6 个消费者，那有 2 个消费者会一直闲着没活干。所以消费者数量一般不要超过分区数，超过了也是浪费资源。

#### 提问：RabbitMQ 为什么没有 Consumer Group 的概念？

回答：架构设计不一样。RabbitMQ 是基于 AMQP 协议的传统消息队列，用 Exchange 和 Binding 来做消息路由，消费者直接绑定到队列上消费。如果想实现类似消费组的效果，可以让多个消费者绑定同一个队列，队列会自动把消息轮询分发给这些消费者。
