# 消息队列设计成推消息还是拉消息？推拉模式的优缺点？

## 回答重点

**推模式（Push）**：Broker 主动将消息推送给消费者。

- 优点：实时性好，消息到达 Broker 后可以立即送达，消费者使用简单。
- 缺点：难以控制消费速度，生产速度大于消费速度时容易导致消费者过载。

**拉模式（Pull）**：消费者主动从 Broker 拉取消息。

- 优点：消费者可以根据自身负载控制拉取频率，避免过载，也更适合批量处理。
- 缺点：拉取频率低会造成消息延迟，频繁拉取又会产生大量无效请求。

RocketMQ、Kafka 都选择了拉模式，但底层使用**长轮询**弥补实时性问题：消费者拉取时若有消息，Broker 立即返回；没有消息则暂时保持请求，等消息到达后再返回，超时后消费者重新请求。RocketMQ 的 PushConsumer 看起来像推模式，实际上也是框架封装的自动拉取。

## 扩展知识

### 推拉模式讨论的对象

通常所说的推拉模式，是指 Consumer 和 Broker 之间的交互。Producer 与 Broker 之间默认是推模式，即生产者把消息推给 Broker。

如果让 Broker 主动从 Producer 拉取，生产者就必须本地保存消息等待 Broker 拉取，消息可靠性将依赖大量生产者；而 Broker 可以通过持久化和多副本集中保证消息可靠性，因此生产者通常直接推消息给 Broker。

### 推模式

推模式由 Broker 主导发送，优点是实时性高、消费者使用简单。但推送速率难以适应不同消费者的处理速率：当生产速度大于消费速度时，消费者可能“爆仓”。Broker 还需要维护每个消费者的状态并动态调整推送速率，增加自身复杂度。

因此推模式适合消息量不大、消费者处理能力强且实时性要求高的场景。

### 拉模式

拉模式的主动权在消费者，消费者可以根据自身情况停止拉取、降低频率或一次拉取一批消息。Broker 只负责存储和响应请求，结构更简单，批量发送也更合理。

拉模式的主要问题是：

- **消息延迟**：消费者不能请求太频繁，否则会产生大量无效请求。
- **忙请求**：长时间没有消息时，消费者仍可能不断发起空请求。

### 长轮询

RocketMQ 和 Kafka 都通过长轮询优化拉模式。消费者发起拉取请求时，若暂时没有消息，Broker 会 hold 住请求；当对应队列或分区有新消息时，Broker 唤醒请求并返回消息；达到超时时间后请求结束，消费者再次发起拉取。

长轮询在实时性和 Broker 压力之间取得了平衡，避免了频繁空轮询。

### RocketMQ 中的长轮询

RocketMQ 的 PushConsumer 只是披着推模式外衣的拉模式。后台线程会根据 Topic 队列数和消费者数量做负载均衡，生成拉取请求，由拉取线程不断向 Broker 请求数据。

Broker 没有消息时会暂存拉取请求；消息写入后唤醒等待请求并重新处理，默认长轮询时间约为 30 秒。这样消息到达时可以立即返回，不必等下一次固定间隔的轮询。

### Kafka 中的长轮询

Kafka 的 `poll` 请求可以配置等待时间。消费者没有消息时会等待到超时，Broker 端也会建立延迟拉取操作；消息到达后立即满足请求，否则到期返回。Kafka 通过这种方式减少空请求，同时保持较好的实时性。

### 推拉模式对比

| 特性 | 推模式 | 拉模式 |
| --- | --- | --- |
| 主动方 | Broker | Consumer |
| 实时性 | 高 | 普通拉取较低，长轮询可接近推模式 |
| 流量控制 | Broker 较难控制 | 消费者自主控制 |
| 过载风险 | 消费者容易过载 | 可按能力拉取 |
| 批量消费 | 不够灵活 | 更适合批量处理 |
| Broker 复杂度 | 需维护消费者状态 | 相对简单 |
| 代表产品 | ActiveMQ 等 | Kafka、RocketMQ |

## 面试官追问

#### 提问：拉模式下消费者挂了一段时间再重启，会不会丢消息？

回答：不会。消息保存在 Broker 中，消费者维护消费位移，重启后从上次位移继续拉取。只要消息尚未过期或删除，就可以继续消费，这也是拉模式让消费者状态与 Broker 解耦的好处。

#### 提问：长轮询请求一直 hold 住不会有问题吗？

回答：一般会设置超时时间，RocketMQ 默认约 30 秒，Kafka 也可配置。超时后连接断开，消费者重新发起请求；Broker 挂掉时消费者感知连接断开并连接其他节点，因此 Broker 要做集群部署。

#### 提问：为什么 Kafka 和 RocketMQ 选择拉模式，推模式真的不行吗？

回答：推模式不是不能用，但拉模式更适合消息队列。消息队列有持久化需求，消费者又有快有慢，Broker 只需保存消息，消费者按能力来取即可。推模式需要维护每个消费者的状态和推送速率，会增加 Broker 复杂度。

#### 提问：长轮询和 WebSocket 有什么区别？

回答：长轮询仍基于 HTTP 请求，服务端暂不响应，数据到达后返回，响应完成连接就断开，客户端再发新请求。WebSocket 握手后建立独立长连接，服务端可以主动推送。WebSocket 更适合实时聊天和通知，长轮询更适合消息队列的拉取场景。
