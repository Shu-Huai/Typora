# 消息队列如何处理重复消息（保证消息的幂等性）？

## 回答重点

消息队列里重复消息是不可避免的，只能靠消费端做**幂等处理**，保证同一条消息消费多少次结果都一样。

两种主流方案：

1. **基于唯一标识去重**：给每条消息分配全局唯一 ID，可以用 UUID、雪花算法生成的 ID 或业务单号。消费者收到消息后先拿这个 ID 去 Redis 或数据库查询，查到了说明处理过了，直接返回；没查到就执行业务逻辑，然后把 ID 存进去。
2. **利用业务本身的幂等性**：比如转账场景用订单号做数据库唯一索引，重复插入会触发唯一约束，不会真的多扣一次钱。也可以设计严格的状态机，订单从“待支付”变成“已支付”后，再来一条支付成功消息时检查状态，不符合条件就丢弃。

## 扩展知识

### 什么是幂等性

幂等性是指一个操作执行一次和执行一百次，最终结果都一样。HTTP 里的 PUT 方法就是幂等的，不管对同一个资源 PUT 多少次，结果都相同。

例如：

```sql
UPDATE t1 SET money = 150 WHERE id = 1 AND money = 100;
```

第一次执行，money 从 100 变成 150；第二次执行时 `money = 100` 匹配不上，影响行数为 0，money 仍然是 150，这就是幂等。

### 为什么消息重复不可避免

![消息重复产生原因](Z:/Public/images/DJHgPEpD_image_mianshiya.webp)

生产者发消息到 Broker，Broker 写入成功但响应超时，生产者以为失败后重发一次，Broker 中就会有两条一样的消息。想完全避免重复就得放弃 Broker 的响应确认，但这样消息可靠性又没有保障，所以生产端会产生重复。

消费者拉到消息，业务逻辑执行完、事务也提交了，正要更新 offset 告诉 Broker“我消费完了”时消费者宕机。另一个消费者接替后发现 offset 没更新，就会把刚才那条消息再消费一遍，所以消费端也会产生重复。

对于大多数业务场景，**消息重复无法从源头消除**，只能在消费端做幂等兜底。

### 基于 Redis 的去重方案

最简单的做法是用 Redis 存已处理的消息 ID：

```java
public boolean processMessage(Message msg) {
    String msgId = msg.getMsgId();

    // SETNX 原子操作，key 存在返回 false
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent("msg:" + msgId, "1", 7, TimeUnit.DAYS);

    if (!success) {
        // 消息已处理过，直接返回
        log.info("重复消息，跳过处理: {}", msgId);
        return true;
    }

    try {
        // 执行真正的业务逻辑
        doBusiness(msg);
        return true;
    } catch (Exception e) {
        // 业务处理失败，删除 Redis key 以便重试
        redisTemplate.delete("msg:" + msgId);
        throw e;
    }
}
```

Redis 方案性能高、实现简单。设置 7 天过期时间可以自动清理历史数据，减少内存占用。缺点是 Redis 和数据库是两个存储，存在一致性问题；如果写 Redis 成功但业务处理失败，需要删除 Redis 中的 `key`。

### 基于数据库的去重方案

在数据库里建立去重表：

```sql
CREATE TABLE msg_dedup (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    msg_id VARCHAR(64) NOT NULL,
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_msg_id (msg_id)
) ENGINE=InnoDB;
```

消费消息时先往去重表插入一条记录：

```java
public void processMessage(Message msg) {
    String msgId = msg.getMsgId();

    try {
        // 利用唯一索引做去重
        msgDedupMapper.insert(msgId);
    } catch (DuplicateKeyException e) {
        // 消息已处理过
        log.info("重复消息，跳过处理: {}", msgId);
        return;
    }

    // 执行业务逻辑
    doBusiness(msg);
}
```

如果去重表插入和业务逻辑在同一个事务里，要么都成功要么都回滚，能保证一致性。但这种方案每条消息都要多一次数据库写入，高并发场景下去重表可能成为瓶颈。

### 利用业务特性做幂等

很多场景不用额外建立去重表，利用业务数据本身就能做幂等。

**版本号方案**：消息里带上数据的版本号。

```sql
UPDATE account
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;
```

第一次执行，version 从 5 变成 6，余额扣减成功；第二次执行同样的消息时，version 已经是 6，条件匹配不上，影响行数为 0，不会重复扣款。

**状态机方案**：订单状态按“待支付 → 已支付 → 已发货”的顺序流转。

```java
public void handlePaySuccess(String orderId) {
    Order order = orderMapper.selectById(orderId);

    if (order.getStatus() != OrderStatus.PENDING_PAY) {
        // 状态不对，说明已经处理过或者订单状态异常
        log.info("订单状态不是待支付，跳过处理: {}", order.getStatus());
        return;
    }

    // 更新订单状态
    orderMapper.updateStatus(orderId, OrderStatus.PAID);
}
```

这种方案不需要额外存储，业务逻辑本身就是幂等的。

## 面试官追问

#### 提问：Redis 去重如果 Redis 挂了怎么办？

回答：Redis 挂了会导致去重失效，重复消息可能被处理多次。如果业务对重复非常敏感，可以用 Redis 集群保证高可用，或者退化成数据库去重。更稳妥的做法是 Redis 只做第一道防线快速过滤，业务逻辑层面再加一道保险，比如用数据库唯一索引兜底。

#### 提问：去重表数据量太大怎么清理？

回答：设计时就要考虑清理策略。最简单的是按时间清理，消息超过 7 天或 30 天基本不会再重复投递，可以用定时任务批量删除过期数据。如果数据量特别大，可以按天或按月分表，直接删除过期表比逐条删除效率高得多。

#### 提问：Kafka 的幂等生产者能彻底解决重复消息问题吗？

回答：不能。Kafka 0.11 之后支持幂等生产者，原理是给每个生产者分配 PID，每条消息带上序列号，Broker 根据 PID + 序列号去重。但这只能保证单个生产者会话内不重复，生产者重启后 PID 会变，跨会话的重复仍然防不住；而且消费端重复消费的问题还得靠消费者自己做幂等。

#### 提问：分布式事务场景下怎么保证幂等？

回答：如果使用 TCC 模式，Try、Confirm、Cancel 三个阶段都要设计成幂等的。例如扣库存的 Try 阶段记录冻结记录而不是直接扣减，重复 Try 时检查冻结记录是否已存在。Seata 等分布式事务框架会维护分支事务状态，但业务接口本身仍建议设计成幂等，防止框架层面出问题。
