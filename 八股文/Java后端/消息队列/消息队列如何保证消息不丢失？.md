# 消息队列如何保证消息不丢失？

## 回答重点

保证消息不丢失需要**生产、存储、消费**三个环节共同配合，任何一个环节出问题消息都可能丢。

![消息可靠性](Z:/Public/images/6clAinyW_b71e1c36-50f7-43d8-93a7-8f9a027986d3_mianshiya.webp)

1. **生产阶段**

生产者发完消息后必须等 Broker 返回确认，如果 Broker 返回失败或者超时没响应，生产者得重试发送。同步发送要处理返回值，异步发送要在回调里处理失败情况。

2. **存储阶段**

Broker 收到消息后必须先把消息持久化到磁盘再返回成功。如果消息还在内存里就告诉生产者“收到了”，机器一断电消息就没了。集群部署的场景下，最好配置成消息同步到至少 2 个副本后再返回确认。

3. **消费阶段**

消费者必须在业务逻辑真正执行完之后再给 Broker 发 ACK。千万别拿到消息就立刻返回确认，万一处理到一半消费者宕机了，这条消息就真丢了。

![消息确认与重试](Z:/Public/images/6ujxpzCZ_image_mianshiya.webp)

如果消费者持续处理失败，消息队列会自动重试投递。重试多次还是失败的消息会被扔到死信队列里，方便事后排查，避免消息彻底丢失（Kafka 没有原生死信队列，需要自行实现）。

## 扩展知识

### RabbitMQ 的保障机制

**生产阶段：Publisher Confirm**

RabbitMQ 不用传统的同步返回值，而是通过 **Confirm 模式**保证消息到达 Broker。

开启 Confirm 模式后，Broker 会异步回调通知生产者消息是否成功写入。还可以配合 `mandatory` 参数，当消息无法路由到任何队列时触发 `ReturnCallback`，避免消息被静默丢弃。

```java
// 开启 confirm 模式
channel.confirmSelect();
channel.addConfirmListener((deliveryTag, multiple) -> {
    // 消息成功到达 Broker
}, (deliveryTag, multiple) -> {
    // 消息投递失败，需要重发或记录
});
```

**存储阶段：持久化 + Quorum Queue**

三个东西都要持久化：

- **Exchange 持久化**（`durable=true`）
- **Queue 持久化**（`durable=true`）
- **消息持久化**（`deliveryMode=2`）

三者缺一不可，任何一个没配持久化，重启后消息就没了。

集群场景下，传统的**镜像队列（Mirrored Queue）**已逐步被 **Quorum Queue** 取代。Quorum Queue 基于 Raft 协议实现多副本同步，写入需要多数节点确认，比镜像队列更可靠。

**消费阶段：手动 ACK**

RabbitMQ 默认是自动 ACK（`autoAck=true`），必须设为手动 ACK，业务处理完再调用 `basicAck`。

处理失败调用 `basicNack` 或 `basicReject`，可以选择重新入队或丢弃。

```java
channel.basicConsume(queue, false, (consumerTag, delivery) -> {
    try {
        processMessage(delivery.getBody());
        channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
    } catch (Exception e) {
        // requeue=true 重新入队，false 进死信队列
        channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, true);
    }
}, consumerTag -> {});
```

### RocketMQ 的保障机制

**生产阶段：同步发送或异步发送带回调**

RocketMQ 提供同步、异步、单向三种发送方式。保证不丢必须用**同步发送**或**异步发送带回调**，检查 `SendStatus` 是否为 `SEND_OK`。

RocketMQ 独有的**事务消息**机制可以保证本地事务和消息发送的原子性：先发 half 消息，执行本地事务，再提交或回滚消息。Broker 还会定时回查事务状态，防止生产者宕机导致消息悬而未决。

```java
// 事务消息发送
TransactionSendResult result = producer.sendMessageInTransaction(msg, null);
// Broker 会回调 checkLocalTransaction 方法检查事务状态
```

**存储阶段：刷盘策略 + 主从同步**

- **同步刷盘（SYNC_FLUSH）**：写磁盘后再返回，可靠但慢。
- **异步刷盘（ASYNC_FLUSH）**：写 PageCache 就返回，快但断电可能丢。

集群部署时配置 **SYNC_MASTER** 模式，主从同步完成后才返回确认。官方推荐 SSD + 异步刷盘 + 主从同步，兼顾性能和可靠性。

**消费阶段：重试队列 + 死信队列**

消费失败返回 `RECONSUME_LATER`，消息进入 **%RETRY%** 重试队列，默认重试 16 次（间隔从 10s 递增到 2h）。16 次全失败进入 **%DLQ%** 死信队列，需要人工介入处理。

### Kafka 的保障机制

**生产阶段：acks + 幂等生产者**

Kafka 通过 `acks` 参数控制确认级别：

- `acks=0`：发完不管，最不可靠。
- `acks=1`：Leader 写入就返回，Leader 挂了未同步的消息会丢。
- `acks=all`：所有 ISR 副本写入才返回，必须配合 `min.insync.replicas>=2`，否则 ISR 只剩 Leader 一个节点时 `acks=all` 等于 `acks=1`。

Kafka 0.11+ 支持**幂等生产者**（`enable.idempotence=true`），通过 ProducerID + SequenceNumber 在 Broker 端去重，解决重试导致的消息重复问题。

```java
Properties props = new Properties();
props.put("acks", "all");
props.put("enable.idempotence", "true");
props.put("retries", Integer.MAX_VALUE);

// Broker/Topic 端配置
// min.insync.replicas = 2
// unclean.leader.election.enable = false
```

**存储阶段：多副本 ISR 机制**

Kafka 的可靠性核心不在刷盘（默认依赖 OS PageCache，不强制每条刷盘），而在**多副本复制**。关键配置组合：

- `replication.factor >= 3`：每个分区至少 3 个副本。
- `min.insync.replicas = 2`：至少 2 个副本同步成功才算写入成功。
- `unclean.leader.election.enable = false`：禁止非 ISR 副本竞选 Leader，防止数据丢失。

这三个参数是 Kafka 防丢的铁三角，缺一不可。

**消费阶段：手动提交 Offset**

必须关闭自动提交（`enable.auto.commit=false`），业务处理完后手动调用 `commitSync()` 或 `commitAsync()`。自动提交可能在消费者处理到一半宕机时已经提交 offset，导致消息丢失。

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processMessage(record);
    }
    consumer.commitSync(); // 处理完再提交
}
```

### 三种 MQ 的可靠性对比

| 项目 | RabbitMQ | RocketMQ | Kafka |
| --- | --- | --- | --- |
| 生产确认 | Publisher Confirm | SendStatus / 事务消息 | `acks=all` + 幂等 |
| 存储可靠 | 持久化三件套 + Quorum Queue | 同步刷盘 + SYNC_MASTER | ISR + min.insync.replicas |
| 消费确认 | 手动 basicAck | CONSUME_SUCCESS | 手动 commitSync |
| 死信机制 | DLX（Dead Letter Exchange） | `%DLQ%` 死信队列 | 无原生支持，需自行实现 |

### 可靠性与性能的权衡

三个阶段都配置成最高可靠性，消息肯定不会丢，但性能会下降很多。同步刷盘要等磁盘 IO，多副本同步要等网络传输，这些都会增加延迟。

![可靠性与性能权衡](Z:/Public/images/psl7Fbrw_H9XV6VJZqp_mianshiya.webp)

实际业务中要根据场景做取舍：

1. 订单支付等核心业务，必须用同步刷盘 + `acks=all` + 消费完成后 ACK，丢一条都不行。
2. 用户行为日志、监控数据等场景，偶尔丢几条问题不大，可以用异步刷盘 + `acks=1` 换取更高吞吐量。

## 面试官追问

#### 提问：生产者重试发送会不会导致消息重复？

回答：会。生产者发消息超时后重试，但其实第一次 Broker 已经收到了，只是响应慢了，这就会产生重复消息。Kafka 0.11+ 支持幂等生产者和事务，在 Broker 端直接去重；RocketMQ 和 RabbitMQ 没有 Broker 端去重能力，需要消费端做幂等，比如用消息唯一 ID 做去重表，或者把业务逻辑设计成幂等操作。

#### 提问：同步刷盘和异步刷盘性能差多少？

回答：差距很大，具体数字取决于硬件配置。一般来说异步刷盘 TPS 能到几万甚至十几万，同步刷盘可能只有几千。同步刷盘的瓶颈在于每条消息都要等磁盘 IO 完成。RocketMQ 官方建议用 SSD + 异步刷盘 + 主从同步兼顾性能和可靠性；Kafka 则主要靠多副本复制保障数据安全。

#### 提问：消费者处理失败进入死信队列后怎么处理？

回答：死信队列里的消息需要人工介入。一般做法是写专门的消费者订阅死信队列，分析失败原因，修复问题后把消息重新投递到原队列，或者直接做补偿处理。RabbitMQ 需要提前配置 DLX 和绑定关系；RocketMQ 自动生成 `%DLQ%` 队列；Kafka 需要自行把失败消息发到专门的 Topic 来模拟死信队列。
