# 消息队列如何保证消息的有序性（顺序性）？

## 回答重点

保证消息有序性的常见方法如下：

**单一生产者和单一消费者**：使用单个生产者发送消息到单个队列，并由单个消费者处理，确保消息按照生产者的发送顺序消费。这种方法简单，但容易成为性能瓶颈。

**分区与顺序键（Partition Key）**：在支持分区的消息队列中（如 Kafka、RocketMQ），通过 Partition Key 将消息发送到特定分区。每个分区内部有序，因此相同 Partition Key 的消息可以按顺序消费。例如使用订单号作为 Partition Key，将同一订单的所有消息路由到同一分区。

**顺序队列（Ordered Queue）**：一些消息队列支持顺序队列，消息在队列中的存储顺序与投递顺序一致。使用单个顺序队列可以保证按顺序消费，也可以用多个顺序队列并通过规则分配消息，提高并发处理能力。

## 扩展知识

### 不同消息队列的顺序性保证

**Kafka**：消息在分区内部有序。生产者指定分区或使用相同 Key，使同一类消息进入同一分区；消费端使用单线程读取特定分区即可保证顺序。

**RabbitMQ**：通过单个队列保证消息顺序。需要并发时，可以使用 Message Grouping 或自定义路由策略，将同一业务逻辑的消息发送到相同队列。

**RocketMQ**：支持顺序消息。生产者使用 `MessageQueueSelector` 选择目标队列，例如按订单 ID 对队列数取模；消费者使用顺序消费模式从同一队列按顺序读取。

### 有序消息之全局有序

如果要保证消息的**全局有序**，只能由一个生产者往 Topic 发送消息，Topic 内部只能有一个队列（分区），消费者也必须单线程消费这个队列。

不过一般不需要全局有序，即使同步 MySQL Binlog，通常也只需要保证单表消息有序。

### 有序消息之部分有序

绝大部分有序需求是部分有序。可以将 Topic 划分成多个队列，通过特定策略把消息发往固定队列，每个队列对应一个单线程消费者。这样既满足同一业务 Key 的顺序，又能利用多个队列并发处理。

### Kafka 顺序消息示例

假设要保证同一订单 ID 的消息按顺序消费，将相同的业务 Key（订单 ID）发送到同一个分区即可。

#### 生产者代码

```java
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
String orderId = "order-123";

for (int i = 1; i <= 5; i++) {
    String value = "Order Step " + i + " for " + orderId;
    // 相同 orderId 会发送到同一个分区
    ProducerRecord<String, String> record =
            new ProducerRecord<>(TOPIC, orderId, value);
    producer.send(record).get();
}
```

#### 消费者代码

```java
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList(TOPIC));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
    for (ConsumerRecord<String, String> record : records) {
        System.out.printf("Consumed message: %s from partition: %d, offset: %d%n",
                record.value(), record.partition(), record.offset());
    }
}
```

### RocketMQ 顺序消息示例

通过 `MessageQueueSelector` 将相同订单 ID 的消息发送到同一个队列：

```java
String orderId = "order-123";
for (int i = 1; i <= 5; i++) {
    String body = "Order Step " + i + " for " + orderId;
    Message message = new Message("OrderTopic", body.getBytes(StandardCharsets.UTF_8));

    producer.send(message, (mqs, msg, arg) -> {
        String id = (String) arg;
        int index = Math.abs(id.hashCode() % mqs.size());
        return mqs.get(index);
    }, orderId);
}
```

消费者端使用顺序消费模式，从同一个 MessageQueue 按顺序读取消息。

### RabbitMQ 顺序消息示例

RabbitMQ 中可以使用单个队列、单个消费者保证顺序：

```java
try (Connection connection = factory.newConnection();
     Channel channel = connection.createChannel()) {
    channel.queueDeclare(QUEUE_NAME, true, false, false, null);

    DeliverCallback deliverCallback = (consumerTag, delivery) -> {
        String message = new String(delivery.getBody(), "UTF-8");
        System.out.println("Received: " + message);
        // 业务处理完成后手动确认
        channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
    };
    channel.basicConsume(QUEUE_NAME, false, deliverCallback, consumerTag -> { });
}
```

对于顺序性要求高的业务，通常只使用一个消费者。需要提升性能时，可以根据订单 ID 等业务 Key 做哈希，将消息分配到多个队列，每个队列只由一个消费者处理。

### RabbitMQ 多队列 + 顺序消费

生产者根据业务 Key 的哈希值选择队列：

```java
String orderId = "order-123";
int numberOfQueues = 3;
int queueIndex = Math.abs(orderId.hashCode() % numberOfQueues);
String queueName = QUEUE_PREFIX + queueIndex;

channel.queueDeclare(queueName, true, false, false, null);
for (int i = 1; i <= 5; i++) {
    String message = "Order Step " + i + " for " + orderId;
    channel.basicPublish("", queueName, null, message.getBytes("UTF-8"));
}
```

每个消费者固定处理一个队列，保证该队列内的消息按顺序消费，同时通过多个队列提升并发能力。

## 面试官追问

#### 提问：消费端多线程消费怎么保证顺序？比如 Kafka 消费者组里多个消费者怎么处理？

回答：Kafka 的分区是消费的最小并行单位，一个分区同一时间只能被消费者组里的一个消费者消费。只要业务 Key 相同的消息落到同一个分区，即使消费者组里有多个消费者，也不会出现同一个分区被多个消费者抢占。想提升并发，就增加分区数量，让更多消费者并行处理不同分区。

#### 提问：生产者发送失败重试会不会导致乱序？

回答：会。例如消息 A 发送失败并重试时，消息 B 已经发送成功，A 重试成功后就可能排在 B 后面。Kafka 可以把 `max.in.flight.requests.per.connection` 设为 1，保证同一时间只有一个请求在飞，但吞吐量会下降；更好的办法是开启幂等生产者，配合 `acks=all` 和 `retries`。

#### 提问：RocketMQ 消费失败重试会不会破坏顺序？

回答：RocketMQ 顺序消费模式下，某条消息消费失败会阻塞当前队列并不断重试，后面的消息要等它处理完才能继续。顺序得到保证，但一条持续失败的消息会卡住整个队列，因此应设置合理重试次数，超过次数后进入死信队列人工处理。

#### 提问：分区数量怎么定？太多太少有什么问题？

回答：分区太少，消费者再多也无法提升并发，因为一个分区只能被一个消费者消费；分区太多则会增加日志文件、文件句柄和 Leader 选举开销，并延长 Broker 重启恢复时间。一般可以让分区数等于消费者数，或设置为消费者数的整数倍。
