# 什么是循环依赖（常问）？

## 回答重点

循环依赖其实就是**两个或多个 Bean** 互相引用，形成了一个闭环。简单说就是**我中有你，你中有我**，或者像是**先有鸡还是先有蛋**的死锁问题。

就好比：

- A 说：“我要干活，但我得先拿到 B 的工具。”

- B 说：“我也要干活，但我得先拿到 A 的工具。”

![](Z:/Public/images/VagJkJyh_658dafbb-f354-41e0-97e9-896759a20c94_mianshiya.webp)

结果就是：**A 等 B，B 等 A，谁也动不了，这就卡死了**。

在 Spring 中，最典型的场景就是：

- Spring 正在创建 Bean A，发现它依赖 B，于是去创建 B；

- 结果创建 B 的时候，发现它又依赖 A。

这时候 A 还在**娘胎**里（正在创建中，还没完全生成好），B 拿不到 A 的引用，所以就不知道该怎么办了。

不过这里要**分两种情况**（更详细的介绍看扩展知识中的内容）：

- 如果是**构造器注入**：这种是无解的，Spring 会直接抛出 `BeanCurrentlyInCreationException` 错误，因为连对象实例都 new 不出来。

- 如果是 **Setter 或字段注入**：Spring 是可以通过三级缓存机制来解决的，简单说就是先把半成品的 A 暴露出来给 B 用，但这属于框架的兜底策略。

## 扩展知识

### 循环依赖的三种场景

```java
// 场景一：字段注入循环依赖，Spring 能解决
@Service
public class OrderService {
    @Autowired
    private UserService userService;
}

@Service
public class UserService {
    @Autowired
    private OrderService orderService;
}

// 场景二：构造器注入循环依赖，Spring 解决不了
@Service
public class OrderService {
    private final UserService userService;
    
    public OrderService(UserService userService) {
        this.userService = userService;
    }
}

@Service
public class UserService {
    private final OrderService orderService;
    
    public UserService(OrderService orderService) {
        this.orderService = orderService;
    }
}

// 场景三：自己依赖自己，Spring 也能解决
@Service
public class CacheService {
    @Autowired
    private CacheService self;  // 用于调用自身的事务方法
}
```

构造器注入为什么解决不了？因为构造器执行时对象还没创建出来，连个内存地址都没有，压根没办法提前暴露给别的 Bean。而 setter 注入是先 new 出空对象，再填充属性，所以能把这个空壳子先暴露出去。

### Spring Boot 2.6 之后的变化

Spring Boot 2.6 开始，**默认禁止循环依赖**，启动时直接报错。官方认为循环依赖本身就是设计问题，不应该靠框架兜底。

如果老项目升级后报错，可以在配置里临时打开：

```yaml
spring:
  main:
    allow-circular-references: true
```

但这只是临时方案，长期还是要重构代码消除循环依赖。

### 如何避免循环依赖

总结有下图：

![](Z:/Public/images/jQeQy2N7_jRYqZmM62C_mianshiya.webp)

**实际开发中最推荐的是拆分职责**。比如 OrderService 和 UserService 互相依赖，大概率是有一部分逻辑既不属于订单也不属于用户，应该抽出来放到独立的服务里。

用 `@Lazy` 是最简单的临时方案：

```java
@Service
public class OrderService {
    @Autowired
    @Lazy  // 延迟到真正使用时才注入
    private UserService userService;
}
```

## 面试官追问

#### 提问：为什么 Spring 官方在 2.6 版本默认禁止循环依赖？

回答：循环依赖本质上是设计问题，说明两个类的职责边界没划清楚。靠框架兜底只是掩盖问题，不是解决问题。而且三级缓存有性能开销，还会导致 Bean 的创建顺序不可预测。官方的态度很明确：与其让框架帮你擦屁股，不如从源头消灭问题。

#### 提问：如果必须用构造器注入，又存在循环依赖，怎么处理？

回答：两种思路。第一种是用 `@Lazy` 注解让其中一个参数延迟加载，这样构造器执行时不会真的去创建依赖对象，只是生成一个代理。第二种是重构代码，把互相依赖的部分抽成第三个类，打破循环。绝大多数场景下，循环依赖都能通过重构消除。

#### 提问：自己注入自己有什么实际用途？

回答：主要用在事务场景。同一个类里 A 方法调 B 方法，B 方法上的 `@Transactional` 不会生效，因为没走代理。注入 self 之后通过 `self.methodB()` 调用，就能走代理让事务生效。不过更优雅的做法是把 B 方法拆到另一个 Service 里。
