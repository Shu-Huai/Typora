# 为什么 Java 新生代被划分为 S0、S1 和 Eden 区？

## 回答重点

核心目的是**提高内存利用率**，同时保留复制算法避免碎片的优点。

新生代对象朝生夕死，用复制算法最合适。最朴素的做法是把内存一分为二，每次只用一半，GC 时把存活对象复制到另一半再清空原区域。问题是空间利用率只有 50%，太浪费了。

HotSpot 的解法是划出三块区域：一个 Eden 区 + 两个 Survivor 区。对象优先分配在 Eden，GC 时把 Eden 和其中一个 Survivor 里存活的对象一起复制到另一个 Survivor，然后清空 Eden 和原 Survivor。默认比例 8:1:1，实际可用空间达到 90%，比一分为二的 50% 高出一大截。

Eden 区占 80%，S0 和 S1 各占 10%。对象分配在 Eden，GC 时把 Eden 和当前 Survivor（如 S0）中存活的对象复制到另一个 Survivor（S1），清空 Eden 和 S0。下次 GC 时把 Eden + S1 的存活对象复制到 S0，交替使用两个 Survivor。

## 扩展知识

### 复制算法为什么适合新生代

IBM 有个统计数据，新生代 98% 以上的对象熬不过一次 GC。这意味着复制算法每次只需要搬运极少量存活对象，效率非常高。对比标记-清除或标记-整理，那些算法要遍历整块内存做标记再清理或压缩，GC 停顿时间长得多。

### 两个 Survivor 为什么缺一不可

只留一个 Survivor 会出问题。假设 GC 后存活对象直接留在 Eden，下次分配新对象时，新老对象混在一起，没法用复制算法整理，只能退化成标记-整理，效率大打折扣。

两个 Survivor 的好处是永远有一块是空的，GC 时把存活对象统一复制过去，内存天然紧凑，没有碎片。

### 如果 Survivor 放不下怎么办

老年代兜底。GC 后存活对象超出 Survivor 容量，超出部分直接晋升到老年代。

如果老年代也放不下，不同收集器有不同处理方式：

1. CMS 会触发一次 CMS 回收，回收后空间仍然不够则退化成 Serial Old 做 Full GC
2. G1 会触发 Mixed GC，把新生代和部分老年代 Region 一起回收

### 比例可以调吗

可以通过 `-XX:SurvivorRatio` 调整。默认值是 8，表示 Eden:S0:S1 = 8:1:1。

如果业务对象存活率特别高，比如大量缓存场景，可以适当调大 Survivor 比例避免对象过早晋升老年代。反过来，如果对象几乎都是用完就扔的，Eden 可以更大一些。

## 面试官追问

#### 提问：为什么默认比例是 8:1:1 而不是其他数字？

回答：这是 HotSpot 根据经验值定的。IBM 研究发现新生代 98% 的对象活不过一次 GC，10% 的 Survivor 足够装下那 2% 的存活对象。同时 90% 的空间可用于分配，兼顾了利用率和安全边际。实际生产中可以根据 GC 日志调整。

#### 提问：对象什么时候会从 Survivor 晋升到老年代？

回答：两种情况。第一种是年龄达到阈值，每熬过一次 Minor GC 年龄加 1，默认到 15 就晋升，可以通过 `-XX:MaxTenuringThreshold` 调整。第二种是动态年龄判断，如果 Survivor 中相同年龄对象总大小超过 Survivor 空间一半，年龄大于等于这个值的对象直接晋升，不用等到 15。

#### 提问：Survivor 区太小会有什么问题？

回答：频繁触发担保晋升，大量对象直接进老年代，导致老年代很快填满，Full GC 频率上升。严重时会出现“过早晋升”现象，本来该在新生代被回收的对象跑到老年代占着坑，最终引发 Full GC 风暴。
