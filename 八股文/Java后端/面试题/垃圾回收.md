# 垃圾回收

## JVM 垃圾回收概述

### 1. 为什么需要垃圾回收（GC）

- Java 使用 **自动内存管理**，绝大多数对象分配在堆上，由垃圾回收器负责回收不再使用的对象。
- 如果不回收：
  - 堆空间会被无用对象占满，最终导致 `OutOfMemoryError`。
  - 频繁创建/销毁对象的系统（Web 服务、微服务、游戏服务器等），GC 设计是否合理直接影响 **吞吐量、延迟和稳定性**。

### GC 重点解决的问题

#### 哪些对象是垃圾？  

—— 即“对象是否还存活”的判定策略（引用计数、可达性分析、三色标记等）。

#### 怎么回收这些垃圾？  

—— 回收算法：标记清除、标记整理、复制、分代收集等。

#### 如何在吞吐量、停顿时间、内存利用率之间平衡？  

—— 不同 GC（Serial、Parallel、CMS、G1、ZGC、Shenandoah 等）只是这些基本思想的不同工程实现。

## 对象存活判定

### 引用计数法

> “引用计数是否为 0” 作为对象是否存活的基础判断之一，但存在循环引用缺陷，所以 **Java 一般不会单独采用**。

#### 基本原理

每个对象维护一个 **引用计数器**：
- 有一个地方引用它 → 计数 +1  
- 有一个引用失效 → 计数 -1

当计数变为 0 时，说明再也没有地方能访问到该对象，它就可以被回收。

#### 缺点：循环引用问题

场景：对象 A 引用 B，B 也引用 A，其他地方都不再引用 A、B。

此时：
- A 的计数为 1（被 B 引用）  
- B 的计数为 1（被 A 引用）  

虽然这两个对象 **实际上已不可达**，但计数不为 0，永远不会被回收 → **内存泄漏**。

#### 应用现状

- 许多系统（如 Python、Objective-C 的 ARC）会使用引用计数配合其他机制（如循环检测）使用。
- **HotSpot JVM 并不采用引用计数作为主要 GC 判活策略**，而是采用 **可达性分析**。

### 可达性分析（Reachability Analysis）

> Java / JVM 的主流对象判活方法。

#### 核心思想

把堆中的对象看作一个 **有向图**：  
- 对象是图中的节点  
- 引用是有向边

从一组特定的起点（**GC Roots**）出发，沿着引用链进行遍历：
- **能被遍历到** 的对象视为 **存活对象**。  
- **遍历不到** 的对象，就是垃圾。

#### GC Roots 的典型来源（Java）

常见根节点包括但不限于：

- 虚拟机栈（栈帧中）引用的对象：  
  - 各个线程中正在执行的方法的局部变量、参数等。
- 方法区中静态属性引用的对象。
- 方法区中常量引用的对象（如字符串常量池中的对象引用）。
- 本地方法栈中 JNI（Native 方法）引用的对象。
- JVM 内部的一些特殊结构引用的对象（如系统类加载器引用的对象等）。

> **GC 的本质问题变成：从 GC Roots 出发，哪些对象最终“够不着”。**

## 三色标记法（Tri-Color Marking）

> 三色标记是对可达性分析的一种 **过程抽象模型**，大量并发/增量 GC 实现（如 CMS、G1、ZGC 等）在设计时都会用到这一思想。

### 三种颜色的含义

- **白色**：尚未被 GC 访问到的对象  
  - 起始时，所有对象都在白色集合里。
  - 扫描结束时，白色集合中的对象即为 **不可达对象（垃圾）**。

- **灰色**：  
  - 已被发现并标记为可达，但**它的引用还没完全扫描完**。
  - 换句话说：灰色对象本身是存活的，但它可能还会指向更多需要扫描的对象。

- **黑色**：  
  - 已被访问且其内部引用已全部扫描过。
  - 黑色对象及它所有已遍历到的引用对象都被视为 **存活**。

### 标记过程（抽象）

1. 初始：所有对象为 **白色**；GC Roots 入队，设为 **灰色**。
2. 循环：
   - 从灰色集合中取出一个对象 `X`：
     - 扫描 `X` 的所有引用：
       - 如果引用指向的对象是白色，将其置为灰色，并加入灰色集合。
     - `X` 扫描完成后，将 `X` 置为 **黑色**。
3. 当灰色集合为空时：
   - 所有黑色对象 = 可达对象  
   - 仍为白色的对象 = 不可达对象 → 垃圾

## 并发标记中的两个核心问题

### 浮动垃圾（Floating Garbage）

> “并发标记时产生的新垃圾，当前这次无法清理，只能等下次 GC。”

#### 形成原因

- 在 **并发标记** 阶段，GC 与用户线程（Mutator）同时工作。
- 假设某对象在标记时仍然是可达的（被认为“活着”），但之后应用代码不再引用它，但这次 GC 的标记阶段已经过去了。
- 结果：该对象仍被视为“黑色”，这次不会被回收，但在下一次 GC 中会被识别为垃圾。

#### 1.2 影响

浮动垃圾会导致本次 GC 后堆中仍残留一部分短期垃圾，但 **一般是可接受的设计权衡**：
- 换来的是更短的停顿时间、更高的并发度。
- 浮动垃圾不会永久存在，下次 GC 会清理。

### 漏标问题（Missed Marking）

> 核心风险：**白色对象被误认为不可达而错误回收，造成“仍在被使用的对象被 GC 掉”（致命错误）。**

#### 漏标产生的典型场景

假设在并发标记期间发生如下变化：

1. 某个已经被扫描为 **黑色** 的对象 `B`，在用户线程的操作下，**新建了一个对白色对象 `W` 的引用**（黑 → 白的引用新增）。
2. 同时，原本灰色/黑色对象中唯一指向 `W` 的引用被删掉或改变。
3. 对于 GC 来说：
   - `B` 已被标记为黑色，不会再扫描。
   - `W` 仍然是白色，但实际仍可从 GC Roots 通过 `B` 访问到。
4. 最终：GC 会把 `W` 当作白色垃圾回收掉，但应用仍在用它 → **严重内存错误**。

#### 如何避免：写屏障（Write Barrier）

为了在并发标记时保持 **三色不变式**，需要在对象引用变化时做“拦截和记录”：

常见两种思想：
1. **增量更新（Incremental Update）**：  
   - 当黑色对象新增指向白色对象的引用时，通过写屏障把目标对象重新加入灰色集合。  
   - 破坏的规则被重新补救。

2. **快照-at-the-beginning（SATB）**：  
   - 以标记开始时的堆引用图为快照；写屏障在引用变更时记录“旧引用”。  
   - GC 会保证所有在快照中**曾经可达**的对象都被标记，避免漏标。

不同 GC 实现会选择不同策略：
- CMS 多用增量更新。
- G1 / ZGC 采用 SATB 思想。

## 垃圾回收算法

> 接下来讨论的是 **“如何回收”**，不再区分并行/并发，只看算法思路。

### 标记-清除（Mark-Sweep）

#### 基本流程

1. **标记阶段**：  
   - 从 GC Roots 开始遍历，**标记所有存活对象**。
2. **清除阶段**：  
   - 扫描整个堆，把 **未标记（白色）对象全部回收**，释放空间。

#### 优点

- 实现简单。
- 不需要移动对象，适合不便移动的场景（如含有大量大对象、需要保持对象地址稳定）。

#### 缺点

- **内存碎片严重**：
  - 回收后的空闲区域是不连续的，小碎块多。
  - 对于需要大连续内存的对象分配会失败，甚至导致 **频繁 GC 或 Full GC**。
- 分配性能较差：
  - 需要维护空闲列表（free `list`），分配时要寻找合适大小的空闲块。

### 标记-整理（Mark-Compact）

> 又称“标记-压缩算法”，是对标记-清除的改进。

#### 基本流程

1. 仍然先从 GC Roots **标记所有存活对象**。
2. 然后让所有存活对象向堆的一侧 **“紧缩/压缩”**：
   - 把存活对象移动到一端，保持相对顺序。
   - 再一次性清理边界以外的内存空间。

#### 优点

- **消除内存碎片**：回收后得到连续的大块内存。
- 对象分配可以使用 **指针碰撞（Bump-the-pointer）**，效率非常高。

#### 缺点

- 需要**移动对象**：
  - 需要更新所有指向这些对象的引用，成本更高。
  - 垃圾回收停顿时间更长。

> 因此标记整理常用于 **老年代**，特别是并行或压缩型 GC 中（如 Parallel Old、G1 的部分阶段）。

### 复制算法（Copying）

> 复制算法在 **新生代（Young Generation）** 中使用非常广泛。

#### 基本思想

- 将内存空间按比例分为两个大小相等的区域：
  - `From` 区
  - `To` 区
- 每次只使用其中一个作为活动区（例如 `From`），当发生 GC 时：
  1. 从 GC Roots 和 `From` 区标记存活对象。
  2. 将存活对象“**顺序复制**”到 `To` 区。
  3. 清空 `From` 区。
  4. 交换 `From` 和 `To` 的角色。

#### 优点

- 无内存碎片：因为活对象按顺序复制，`To` 区是一块连续空间。
- 分配速度极快：只需移动一个指针（指针碰撞）。
- 对于“存活率很低”的区域（很多短命对象），复制成本实际很低。

#### 缺点

- **空间利用率低**：总有一半空间空着，用于做待复制的目标区域。
- 对存活对象较多时，复制成本高。

> Java 新生代并不是 1:1 划分，而是采用 **Eden + 两块 Survivor 区** 的方式，在空间利用率和复制效率之间折中。

## 分代收集算法（Generational Collection）

> Java 垃圾回收的核心思想：**“不同年龄的对象用不同策略”**。

### “弱分代假说”与“强分代假说”

- **弱分代假说**：大部分对象“朝生暮死”，很快就会被回收。
- **强分代假说**：存活时间越长的对象，越不容易死。
- 由此带来两个设计：
  - 年轻对象 → 更适合 **频繁、快速的回收**。
  - 老年对象 → 更适合 **较低频率但更彻底的回收**。

### Java 堆的典型分代结构（以 HotSpot 为例）

- **新生代（Young Generation）**
  - Eden 区
  - Survivor 区：`S0`（From） 和 `S1`（To）
- **老年代（Old Generation）**
  - 存放多次 GC 后仍然存活的对象。

> 有的 GC 实现还会有 **元空间 / 永久代（MetaSpace / PermGen）** 存放类元数据，这部分不在本文重点讨论。

## 典型 GC 流程示意（结合图片内容）

### 新生代（Young GC / Minor GC）流程

> 新生代采用 **复制算法** + 三个区（Eden + From + To）。

#### 分配与触发

1. 大多数新对象在 Eden 区创建。
2. 当 Eden 空间不足时，触发一次 **Young GC**（也叫 Minor GC）。

#### 回收步骤（简化理解）

1. 以 GC Roots 以及 **老年代中对新生代对象的引用** 为起点，标记新生代中存活的对象。
2. 将存活对象从：
   - Eden 区
   - Survivor From 区  
   复制到 Survivor To 区（或直接晋升到老年代，见后述）。
3. 复制完成后：
   - 清空 Eden 和 Survivor From。
   - Survivor To → 变成新的 From 区。
   - 原来的 From 区 → 变成新的 To 区（空）。

#### 对象年龄与晋升（Promotion）

- 每次 Minor GC 中，在 Survivor 区仍存活的对象 **年龄 +1**。
- 当满足以下任意条件之一时，对象会 **晋升到老年代**：
  1. 对象年龄达到阈值（默认约为 **15**，可由参数 `-XX:MaxTenuringThreshold` 决定）。
  2. Survivor 区空间不足（可能触发“动态年龄判定”提早晋升）。
  3. 大对象（如大数组）可能直接在老年代分配（由 GC 策略决定）。

### 老年代回收（Full GC）

> 当老年代空间不足时，会触发 **Full GC**（也可能同时清理新生代）。

#### 触发原因（常见）

- 老年代空间不足：
  - 新生代晋升过多。
  - 老年代内部碎片过多导致无法分配大对象。
- 显式调用 `System.gc()`（具体是否触发由 JVM 决定）。
- 元空间/永久代空间不足（在某些版本中）。

#### Full GC 的算法选择

- 传统上：老年代多使用 **标记-清除 + 标记-整理** 的组合：
  - 先标记存活对象。
  - 根据实现选择直接清除，或进行整理压缩。
- 不同 GC：
  - Parallel Old：并行标记–整理。
  - CMS：并发标记–清除（但会产生碎片）。
  - G1：分区式 + 标记–复制/整理的组合思想。

## 关键优化与工程实现要点

### 写屏障与记忆集（Remembered Set）

- 为了让 **分代收集** 生效，老年代引用新生代对象时需要记录，以便 **Young GC 时能从老年代正确找到 GC Roots**。
- 实现方式之一：
  - 通过写屏障在“老年代对象写入新生代引用”时，将该引用记录在 **记忆集（RSet）** 或卡表（Card Table）中。

### 停顿时间 vs 吞吐量权衡

- 单线程 GC（Serial）：
  - 实现简单，但停顿长，适合单核或对停顿不敏感的场景。
- 多线程并行 GC（Parallel）：
  - 追求高吞吐，但仍可能产生较长停顿。
- 并发 GC（CMS、G1、ZGC、Shenandoah）：
  - 尽量把工作移到与应用线程并发的阶段，减少 Stop-The-World 时间。
  - 需要复杂的写屏障、三色标记、快照等机制保证正确性。
