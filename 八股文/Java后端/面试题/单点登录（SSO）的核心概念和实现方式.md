# 单点登录（SSO）的核心概念和实现方式

单点登录（Single Sign-On，SSO）解决的是“用户在多个系统中反复登录”的问题。它的核心目标是：用户只需要在统一身份认证中心完成一次登录，就可以访问多个相互信任的业务系统，而不必在每个系统中分别输入账号和密码。

在企业内部系统、互联网开放平台、集团多应用平台中，SSO 都非常常见。例如，一个企业可能同时有 OA、CRM、财务系统、工单系统、数据平台和后台管理系统。如果每个系统都维护一套独立账号和密码，用户体验会很差，运维成本也会很高。因此，企业通常会引入统一身份认证中心，由它集中完成登录、身份校验、凭证签发和登录状态维护。

需要注意的是，SSO 不是某一个具体技术，而是一种身份认证架构。JWT、Session、CAS、SAML、OAuth2、OpenID Connect 等都可以参与 SSO 的实现，但它们和 SSO 不是同一个概念。

## 为什么需要单点登录

### 多系统独立登录的痛点

在没有单点登录之前，企业内部经常是每个系统各自维护用户表、登录页、密码策略和权限体系。这样会带来几个明显问题。

首先是用户体验差。员工访问 OA 系统需要登录一次，访问 CRM 又要登录一次，进入财务系统还要再次登录。系统越多，重复登录越频繁。

其次是账号密码管理混乱。不同系统可能有不同密码规则、不同过期策略、不同重置流程。用户容易忘记密码，运维和管理员也需要频繁处理账号重置、权限开通和离职回收。

第三是安全治理困难。每个系统都自己处理登录，就意味着每个系统都要单独实现密码校验、登录风控、验证码、多因素认证、登录日志和账号锁定。一旦某个系统实现不规范，就可能成为安全短板。

第四是权限和身份不统一。员工入职、转岗、离职时，需要在多个系统中同步账号状态。如果某个系统忘记禁用离职员工账号，就会留下安全风险。

### SSO 的基本目标

SSO 的目标是把分散在各个业务系统中的登录能力收敛到统一身份认证中心。

用户第一次访问业务系统时，如果没有登录，会被重定向到统一认证中心。认证中心完成账号密码、多因素认证、验证码、扫码登录等校验后，生成登录状态和身份凭证。业务系统拿到认证中心签发的凭证后，就可以识别用户身份，并为用户建立本系统内的登录状态。

当用户之后访问其他业务系统时，其他系统同样会把用户重定向到认证中心。由于用户浏览器中已经存在认证中心的登录态，认证中心可以识别出用户已经登录，于是直接给新的业务系统签发凭证，用户无需再次输入账号密码。

因此，SSO 的关键不是“所有系统共用一个密码”，而是“所有系统都信任同一个认证中心”。

## SSO 的核心架构与登录流程

### 三个核心角色

SSO 架构中通常有三个核心角色。

#### 用户浏览器

用户浏览器负责访问业务系统、跳转到认证中心、保存 Cookie，并在不同系统之间完成重定向。SSO 很大程度上依赖浏览器的跳转和 Cookie 机制来维持认证中心的登录状态。

#### 业务系统

业务系统也可以称为应用系统、服务提供方、客户端应用、Service Provider 或 Relying Party。它本身不直接处理用户密码，而是把登录请求交给统一认证中心。业务系统只需要验证认证中心返回的凭证，并在本系统中建立局部会话。

例如 OA、CRM、财务系统、后台管理系统都可以是业务系统。

#### 统一认证中心

统一认证中心也可以称为身份提供方、认证服务器、Identity Provider 或 Authorization Server。它负责用户认证、登录状态维护、凭证签发、令牌校验、单点登出、多因素认证、登录风控等能力。

在企业内部，它可能是自研统一登录平台，也可能是 Keycloak、CAS、Okta、Azure AD、Authing、Auth0 等身份系统。在互联网开放登录中，微信、GitHub、Google 等也可以扮演认证或授权中心的角色。

### 首次访问系统 A 的登录流程

假设用户第一次访问业务系统 A，此时用户在系统 A 中没有登录状态。

完整流程通常如下：

1. 用户访问系统 A 的受保护页面。
2. 系统 A 检查本地 Session 或登录态，发现用户未登录。
3. 系统 A 将用户浏览器重定向到统一认证中心，并携带回调地址、应用标识、状态参数等信息。
4. 用户在统一认证中心完成登录，例如输入账号密码、扫码确认或通过多因素认证。
5. 认证中心校验通过后，在认证中心自己的域名下写入登录态 Cookie。
6. 认证中心生成一次性凭证，例如 ticket 或 authorization code。
7. 浏览器被重定向回系统 A 的回调地址，并携带该凭证。
8. 系统 A 后端拿凭证去认证中心校验，或用 code 换取 token。
9. 系统 A 确认用户身份后，创建系统 A 自己的局部 Session。
10. 用户正式进入系统 A。

这里需要注意：认证中心的登录态和业务系统的登录态通常是两层状态。

认证中心保存的是“用户已经在统一认证中心登录”。业务系统保存的是“用户已经在当前业务系统登录”。这两个状态相关，但不完全相同。

### 再访问系统 B 时为什么不需要重新登录

当用户访问业务系统 B 时，系统 B 发现用户在自己这里没有登录状态，于是也会把用户重定向到统一认证中心。

此时关键点在于：用户之前登录系统 A 时，已经在认证中心域名下留下了登录态 Cookie。当浏览器再次访问认证中心时，会自动带上这个 Cookie。认证中心识别到用户已经登录，就不再要求用户输入账号密码，而是直接给系统 B 签发新的凭证。

系统 B 拿到凭证后，向认证中心校验凭证或换取 token，确认用户身份，然后建立系统 B 自己的局部 Session。对用户来说，这个过程可能只是浏览器短暂跳转，甚至几乎无感，因此就实现了“一次登录，多系统通行”。

### SSO 不是简单共享 Cookie

很多人会误以为单点登录就是“多个系统共享一个 Cookie”。这种理解不够准确。

如果多个业务系统都在同一个主域名下，例如：

```text
oa.example.com
crm.example.com
finance.example.com
```

理论上可以通过设置父域 Cookie，也就是 `.example.com`，让多个子系统共享某些登录状态。但这种方式有明显限制：

- 只适合同一主域名下的系统；
- 安全隔离较弱；
- Cookie 过大或泄露会影响多个系统；
- 不适合跨公司、跨平台、跨顶级域名的场景；
- 很难优雅支持第三方登录和开放授权。

真正通用的 SSO 通常不是简单共享业务系统 Cookie，而是让所有业务系统都信任统一认证中心，通过重定向、凭证签发和服务端校验来完成登录。

## SSO 的常见实现方式与面试回答

### Session 模式

Session 模式是最容易理解的 SSO 实现思路。

用户在统一认证中心登录成功后，认证中心保存一份全局登录 Session，并在认证中心域名下写入 Cookie。业务系统需要登录时，就把用户重定向到认证中心。认证中心根据 Cookie 判断用户是否已经登录，如果已登录，就给业务系统签发一个临时 ticket。业务系统拿 ticket 到认证中心校验，校验通过后创建自己的局部 Session。

这种方式的典型代表是 CAS（Central Authentication Service）。CAS 的基本思路是：业务系统不直接处理密码，而是依赖认证中心签发和校验 ticket。

Session 模式适合企业内部系统，逻辑直观，服务端可控性强，也方便做集中登出、账号禁用和权限回收。缺点是认证中心需要维护登录状态，对服务端存储和集群共享有一定要求，通常需要 Redis 等集中式存储来保存会话状态。

### JWT 模式

JWT（JSON Web Token）是一种令牌格式，不是 SSO 本身。它可以用来承载用户身份、过期时间、签发方、受众、权限范围等信息，并通过签名保证令牌没有被篡改。

在 SSO 场景中，认证中心可以在用户登录成功后签发 JWT，业务系统通过验证 JWT 的签名和声明信息来识别用户身份。由于 JWT 可以自包含用户信息，业务系统不一定每次都要访问认证中心，这有利于提高系统扩展性。

但 JWT 也有明显注意点：

- JWT 一旦签发，在过期前通常不容易主动失效；
- 如果令牌泄露，攻击者可能在有效期内冒用身份；
- 不能把敏感信息直接放进 JWT；
- 需要合理设置过期时间、刷新机制和黑名单机制；
- 浏览器端存储 JWT 时要考虑 XSS 和 CSRF 风险；
- 多系统之间要校验 issuer、audience、过期时间和签名算法。

因此，不能简单说“用了 JWT 就是 SSO”。JWT 只是 SSO 架构中可能使用的一种令牌表达形式。

### OAuth2 与 OpenID Connect

OAuth2 本质上是授权框架，重点解决“第三方应用如何在用户授权后访问资源”的问题。严格来说，OAuth2 不是专门的身份认证协议。

OpenID Connect（OIDC）是在 OAuth2 基础上扩展出来的身份认证协议。它在 OAuth2 的授权流程之上增加了 ID Token 和用户身份信息，使业务系统可以确认“当前登录用户是谁”。

在现代互联网和大厂实践中，跨平台登录通常会使用 OAuth2 + OpenID Connect 的思想。例如用户使用 GitHub、Google、微信等账号登录第三方系统时，大致流程是：

1. 第三方系统把用户重定向到平台认证授权页面。
2. 用户在平台完成登录并授权。
3. 平台返回 authorization code 给第三方系统。
4. 第三方系统后端用 code 换取 access token、`id` token 等。
5. 第三方系统校验 token，获取用户身份。
6. 第三方系统建立自己的本地登录态。

这里的关键是：OAuth2 更偏授权，OIDC 才明确解决身份认证。面试中如果说“大厂 SSO 通常结合 OAuth2”，最好进一步补充“在登录认证场景中通常会结合 OpenID Connect”。

### SAML 模式

SAML（Security Assertion Markup Language）也是一种常见的企业级 SSO 协议，尤其在传统企业软件、海外 SaaS、企业身份系统中很常见。

SAML 的核心是由身份提供方签发包含用户身份信息的断言，业务系统验证断言后为用户建立登录态。它和 OIDC 的目标相似，都是让业务系统信任统一身份提供方，只是协议格式和生态不同。

在新系统中，OIDC 更常见；在很多传统企业级系统中，SAML 仍然大量存在。

### 单点登出

SSO 不只要考虑单点登录，还要考虑单点登出。

用户从某个系统退出时，可能有两种语义：

- 只退出当前业务系统；
- 退出统一认证中心，并让所有业务系统都失效。

如果只是退出当前业务系统，那么只需要清除当前业务系统的局部 Session。如果要实现全局退出，则需要清除认证中心登录态，并通知或触发其他业务系统清理本地 Session。

单点登出比单点登录更复杂，因为各个业务系统都有自己的局部登录态。实现方式可能包括前端重定向通知、后端回调通知、token 失效、session 黑名单、短 token 有效期配合刷新机制等。

### 安全设计要点

SSO 是企业身份入口，一旦设计不当，会影响所有接入系统。因此需要重点关注安全设计。

常见安全要点包括：

- 全链路使用 HTTPS；
- 回调地址必须白名单校验，防止开放重定向；
- OAuth2/OIDC 流程中使用 state 防止 CSRF；
- OIDC 中使用 nonce 防止重放攻击；
- authorization code 应该短期有效且只能使用一次；
- 公共客户端应使用 PKCE；
- token 设置合理过期时间；
- refresh token 需要安全存储和轮换；
- JWT 必须校验签名、issuer、audience、exp 等字段；
- 不在前端长期保存高权限 token；
- 业务系统要有自己的局部会话和权限控制；
- 管理后台、财务系统等高风险系统可以要求二次认证或多因素认证。

### 面试中的完整回答

可以这样回答这个问题：

> 单点登录解决的是用户在多个系统中反复登录的问题。它的核心不是某个具体技术，而是一种统一身份认证架构。多个业务系统不再各自维护登录逻辑，而是统一信任一个身份认证中心。用户只要在认证中心登录一次，就可以访问多个接入系统。
>
> SSO 通常有三个核心角色：用户浏览器、业务系统和统一认证中心。用户首次访问系统 A 时，系统 A 发现用户未登录，就把浏览器重定向到认证中心。用户在认证中心完成账号密码、扫码或多因素认证后，认证中心建立自己的全局登录态，并给系统 A 签发一次性凭证。系统 A 校验凭证成功后，建立自己的本地 Session，用户就可以访问系统 A。
>
> 当用户再访问系统 B 时，系统 B 也会重定向到认证中心。由于浏览器中已经有认证中心的 Cookie，认证中心能识别用户已经登录，于是直接给系统 B 签发新的凭证。系统 B 校验后建立本地 Session，用户不需要再次输入账号密码。这就是一次登录、多系统通行的基本原理。
>
> 实现方式有很多种。企业内部系统常见的是 Session + ticket 模式，例如 CAS。认证中心维护全局 Session，业务系统通过 ticket 校验用户身份。JWT 也可以用于 SSO，但 JWT 只是令牌格式，不等于 SSO 本身。它适合承载身份声明和权限信息，但要注意过期、吊销、泄露和签名校验问题。跨平台、大厂开放登录中更常见的是 OAuth2 + OpenID Connect。OAuth2 主要解决授权问题，OIDC 在 OAuth2 基础上补充身份认证能力，因此更适合做登录。
>
> 真正完整的 SSO 还要考虑安全和治理，例如 HTTPS、回调地址白名单、state、nonce、PKCE、token 过期、refresh token 轮换、单点登出、多因素认证、权限同步和账号生命周期管理。
>
> 所以，SSO 的本质是统一身份认证中心加多个业务系统之间的信任关系。JWT、Session、CAS、OAuth2、OIDC、SAML 都只是不同实现手段。面试中不能把 JWT 和 SSO 直接划等号，也不能把 OAuth2 简单说成登录协议；更严谨的说法是，企业 SSO 常用 CAS、SAML、OAuth2/OIDC 等协议或方案实现，具体选型取决于系统边界、跨域需求、安全要求和接入生态。

### 总结

单点登录的核心是统一认证和信任传递。

它不是让所有系统共享一张用户表那么简单，也不是简单共享 Cookie，更不是“用了 JWT 就是 SSO”。SSO 的关键在于：业务系统把登录认证交给统一认证中心，认证中心完成用户身份校验并签发可信凭证，业务系统验证凭证后建立自己的局部登录态。

从实现方式看：

- 企业内部系统可以使用 Session + ticket，例如 CAS；
- 前后端分离系统可以结合短期 token 和刷新机制；
- 跨平台开放登录通常使用 OAuth2 + OpenID Connect；
- 传统企业 SaaS 集成中经常使用 SAML；
- JWT 可以作为令牌格式参与实现，但不是 SSO 本身。

一个成熟的 SSO 系统不仅要让用户少登录几次，还要统一身份入口、降低账号管理成本、增强安全治理能力，并为多系统权限控制、审计、登出和账号生命周期管理提供基础。
