# 为什么有了 HTTP 还需要 WebSocket

## 引言

HTTP 是目前 Web 世界最重要的应用层协议，但它最初是为**“文档请求-响应”**设计的，而不是为**实时双向通信**设计的。

随着 IM 聊天、股票行情、在线协作编辑、在线游戏等场景的普及，传统 HTTP 的通信模型暴露出明显短板——这就是为什么后来会出现 WebSocket，并逐渐成为实时通信的“标配”方案。

## HTTP 的核心痛点

### 请求-响应模型：服务器被动

HTTP 是**无状态、单向请求-响应**协议：  
- 一次通信总是由**客户端发起请求**，服务器**被动返回响应**。  
- 服务器不能主动推送消息给浏览器，只能“等你来问”。

在实时场景中的问题：
- 实时通知、聊天消息、新行情价格等，一旦只靠客户端“隔一会儿来问一下”，就会出现：
  - 要么问得太勤 → 资源浪费；
  - 要么问得太慢 → 延迟大、体验差。

### 头部开销大：频繁通信时极不经济

- 每次 HTTP 请求都需要带完整的请求行 + 请求头（方法、URL、Cookie、User-Agent、各种自定义 header 等）。
- 在**高频小数据**场景（例如每秒几十条行情、心跳）中：
  - 真正的业务数据可能只有几百字节；
  - 但 HTTP 头部却可能占到整个包的 20%～30% 甚至更多。
- 结果：
  - 带宽浪费、服务端解析压力大；
  - 很难做到**低开销、低延迟的实时通信**。

> 总结：HTTP 的“被动响应 + 头部重”的特性，天然不适合高频、低延迟、双向实时通信。

## 轮询方案：在 HTTP 之上的妥协

在 WebSocket 出现之前，为了在浏览器里“硬凑出”实时效果，人们在 HTTP 之上设计了几种轮询类方案。

### 定时轮询（Short Polling）

#### 原理

- 浏览器用 `setInterval` 等定时器，每隔 N 秒向服务器发一次 HTTP 请求：“有新消息吗？没有就返回空，有就返回数据。”

#### 优点

- 实现极其简单：
  - 前端：一个定时器 + 一个 Ajax 请求；
  - 后端：一个普通的 HTTP 接口。

#### 缺点

1. **大量无效请求**
   - 绝大部分请求的返回都是“没有新数据”。
   - 白白浪费带宽和服务器 CPU/IO。
2. **延迟和资源无法兼得**
   - 想实时 → 轮询间隔设得很短（比如 1s），请求暴增；
   - 想省资源 → 间隔设得很长（比如 30s），用户感知延迟巨大。
3. **不可控的系统压力**
   - 用户一多，每人每秒一个请求，服务端 QPS 直接飙升，难以支撑。

**适用场景**

- 极少数**遗留系统、低并发、非核心**场景；
- 不推荐在现代系统的核心链路中使用。

### 长轮询（Long Polling）

#### 原理

- 客户端发起请求后，服务器**不立刻返回**：
  - 如果有新数据 → 立刻返回；
  - 如果暂时没有数据 → 挂起连接，一直等，直到**有新数据**或**超时**（例如 30 秒）。
- 客户端收到响应后**立即再发起下一次请求**，形成“假持久连接”。

#### 优点

- 大幅减少“空响应”：
  - 有数据才返回，没数据就挂着；
  - 相比定时轮询，CPU/带宽浪费少很多。
- 易于在现有 HTTP 基础上实现：
  - 无需新协议，前后端都是普通 HTTP 逻辑。

#### 缺点

1. **不是“真正的持久连接”**
   - 每次返回或超时后，都要**重新建立一次 HTTP 连接**；
   - 连接建立 + TCP 三次握手 + TLS 握手（如 HTTPS）本身就有开销。
2. **服务器连接压力大**
   - 对每个客户端都要维持一个“挂起请求”，本质是维护大量**半闲置连接**；
   - 高并发场景下内存、线程、连接数压力巨大。
3. **实现复杂度提升**
   - 服务端需要额外的**连接管理 + 超时管理**逻辑；
   - 容易出现资源泄露、超时策略不当等问题。

#### 适用场景

- 作为 WebSocket 的**降级方案**：
  - 某些老旧浏览器环境；
  - 某些中间件不支持 WebSocket 穿透的网络环境。
- 不适合高并发、高实时性的核心业务。

## WebSocket：为实时双向通信而生

### WebSocket 的设计目标

WebSocket 的目标是：在浏览器与服务器之间提供一个**真正的、全双工、持久的通信通道**，同时兼顾：

- **低延迟**：消息可以即时双向推送；
- **低开销**：头部极小，适合高频传输小数据包；
- **与 HTTP 共存**：握手阶段沿用 HTTP，便于穿透代理、防火墙、负载均衡。

### 核心特点

#### 一次握手，长期连接

- 基于 HTTP 发起**一次握手**；
- 成功后升级为 WebSocket 协议；
- 之后长时间复用该 TCP 连接进行双向通信。

#### 真·全双工

- 客户端可以主动发消息；
- 服务器也可以随时主动推送消息；
- 两边互不阻塞，真正的双向对等通信。

#### 协议头开销极低

- 单个数据帧的头部通常只有 2–10 字节；
- 对比 HTTP 动辄成百上千字节的请求头，节省非常可观。

#### 保持长连接 + 心跳机制

- 通过 ping/pong 心跳保持连接活性，及时发现断线；
- 比反复新建/销毁 HTTP 连接更加高效。

### 典型适用场景

- IM 聊天、协同编辑；
- 实时行情、大盘监控、实时看板；
- 在线游戏、实时互动课；
- Web 端监控控制台、终端 WebShell 等。

## WebSocket 的握手流程（与 HTTP 的关系）

> 关键点：WebSocket 不替代 HTTP，它是**基于 HTTP 握手、然后升级为新协议**。

### 客户端发起升级请求

浏览器通过普通 HTTP 请求发起“协议升级”：

- 请求方法：`GET`
- 关键请求头：
  - `Upgrade: websocket` —— 请求升级为 WebSocket；
  - `Connection: Upgrade` —— 表示本次连接要升级；
  - `Sec-WebSocket-Key` —— 一段随机 Base64 字符串，用于服务端校验；
  - `Sec-WebSocket-Version: 13` —— WebSocket 版本号。

示例（简化版）：

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
