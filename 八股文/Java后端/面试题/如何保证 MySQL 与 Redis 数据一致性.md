# 如何保证 MySQL 与 Redis 数据一致性

> 目标：在保证系统高性能的前提下，让 **MySQL（主存储）** 与 **Redis（缓存 / 计数器）** 数据在可接受范围内保持一致。

## 背景：为什么会不一致？

在典型的互联网系统中，一般都会采用：

- **MySQL**：作为权威数据源（System of Record），负责持久化、复杂查询、事务。[[MySQL]]
- **Redis**：作为缓存或计数器，负责高 QPS、低延迟访问。[[Redis简介]]

两者彼此独立，当存在“**一份数据，两份存储**”时，就不可避免出现：

- MySQL 已更新，但 Redis 还是旧值；
- Redis 已更新，但 MySQL 还没来得及同步；
- 写请求中途失败，只更新了一边。

这就像超市里：**价签和库存系统对不上**——顾客看到 10 件，可系统实际只剩 5 件，产生投诉。

> 结论：**缓存与数据库之间永远会存在一个不一致窗口**，真正能做的是 **控制窗口的大小、出现概率、影响范围**。

## 一致性级别与设计思路

常见的一致性级别：

- **强一致性**：写成功后，所有读请求都能立刻看到新值。  
- **最终一致性**：允许短暂不一致，但在一段时间内最终会收敛到同一值。
- **弱一致性**：只保证大致正确，短时间内存在较大偏差，例如实时播放量、点赞数。

通常做法：

- 对 **交易、金额、库存扣减** 等关键数据，需要尽量接近强一致。
- 对 **点赞、播放量、排行榜** 等统计型数据，只需最终一致或弱一致。

## 方案一：旁路缓存（Cache-Aside）模式

[[Redis缓存问题#旁路缓存模式]]

> 读多写少，优先推荐的通用方案。

<img src="Z:\Public\images\image-20251201211911775.png" alt="image-20251201211911775" style="zoom:50%;" />

### 核心思想

#### 读流程（Cache-Aside / Lazy Loading）：

先查 Redis  
- 命中：直接返回。
- 未命中：查询 MySQL，得到结果后写入 Redis，并返回。

#### 写流程（关键！）：

1. **先更新 MySQL**
2. **再删除 Redis 对应缓存键**（注意是删除，而不是直接更新缓存）。

下次读请求命中缓存失败，再从 MySQL 读取最新数据写入 Redis，从根源上避免脏数据。

### 为什么“删除缓存”比“更新缓存”更安全？

如果采用“**更新 MySQL + 更新 Redis**”的方式，在高并发下会出现如下时序：

1. 请求 A 更新 MySQL（值更新为 100），**暂未更新 Redis**；
2. 请求 B 更新 MySQL（更新为 80），并立刻更新 Redis = 80；
3. 请求 A 再更新 Redis = 100（旧值），把 B 的新结果覆盖了。

最终 Redis 中是 **错误的旧值 100**。  

而采用“**更新 MySQL + 删除缓存**”：

1. B 更新时间较晚，它删除缓存；
2. A 即使晚到，也只会再删一次缓存；
3. 下一个读请求从 MySQL 重建缓存，一定是 **最新值**。

多数工程实践与文档都推荐：**数据库更新成功后删除缓存，而不是直接改缓存值**。

### 并发与“缓存双删”优化（可选）

极端情况下可能出现：

1. 读线程 R 发现缓存不存在，从 MySQL 读到旧值；
2. 写线程 W 更新了 MySQL 新值并删除缓存；
3. R 把旧值写回 Redis，产生短时间脏数据。

常见优化：

```text
写请求：
1）更新 MySQL
2）删除缓存
3）短暂 sleep（比如 50~200ms）
4）再次删除缓存（补偿）
```

这种“**缓存双删**”操作能降低并发读写交错时产生脏数据的概率，但会增加 Redis QPS，需要结合业务权衡。

### 优缺点与适用场景

**优点：**

- 实现简单，业务入侵少；
- 在读大于写场景下效果极佳；
- 只要删除缓存成功，下一次读取一定是 MySQL 最新数据。

**缺点：**

- 删除缓存后第一次读会打到 MySQL，可能出现瞬时压力高峰（可配合缓存预热、读写分离缓解）。
- 仍存在极短时间的不一致窗口。

**适用场景：**

- **读多写少**：商品详情页、用户资料、配置数据等；
- 数据正确性要求较高，但能接受非常短时间内的不一致。

## 方案二：MQ 异步更新（写 Redis，异步刷 MySQL）

> 目标：在高频写场景下，**强提升写性能**，同时保证最终一致性。

<img src="Z:\Public\images\image-20251201211931365.png" alt="image-20251201211931365" style="zoom:50%;" />

### 场景举例：直播点赞 / 实时计数器

直播间点赞、弹幕计数等场景：

- 每秒上万次写请求；
- 用户只需要看到 **“大致正确的实时数值”**；
- MySQL 如果同步参与每次写，将成为性能瓶颈。

问题描述：

- 原方案：点赞同步更新 MySQL，导致 MySQL CPU 90%+，响应时间 > 500ms；
- 优化后：改为 **Redis 实时写 + MQ 异步同步 MySQL**，响应时间降为 50ms 以内。

### 核心流程

**写点赞请求：**

1. 写入 Redis（自增计数或设置值）；
2. 发送一条 MQ 消息（包括业务主键、增量 / 新值、消息 ID 等）；
3. 立即返回给用户（Redis 已是最新值）。

**MQ 消费者：**

1. 从 MQ 拉取消息；
2. 做 **幂等性校验（根据消息 ID / 去重表 / Redis Set）**；
3. 更新 MySQL（累加或覆盖）；
4. 标记该消息已处理，确保重试不会导致重复计数。

这样，Redis 始终是 **最快更新** 的，而 MySQL 在几十毫秒～几百毫秒内完成同步，形成 **最终一致性**。

### 一致性与幂等关键点

#### 消息可靠投递

- MQ 需至少保证 “At-Least-Once”；
- 业务方需可接受同一消息被消费多次。

#### 消费者幂等

- 典型做法：
    - 消息中携带全局唯一 ID；
    - 消费前先查“幂等表 / Redis Set”是否已处理；
    - MySQL 更新使用 `UPDATE ... SET cnt = cnt + delta` 等幂等写法。

#### 最终一致性容忍度

- 一般 Redis → MySQL 延迟在 50～200ms；
- 对于“点赞总数”、“播放量”这类数据，用户几乎无感。

### 优缺点与适用场景

#### 优点

- 用户写请求只打到 Redis + MQ，响应极快；
- MySQL 写压力骤降，瓶颈前移到 MQ 与 Redis；
- 适合高并发写场景。

#### 缺点

- 系统复杂度明显上升（MQ 集群、消息轨迹、失败补偿、幂等表）；
- 只能保证**最终一致性**，无法做到强一致。

#### 典型适用场景

- 直播点赞、观看人数、文章阅读 / 点赞计数；
- 实时排行榜中使用的各类计数器。

## 方案三：双写 TCC 方案（强一致）

<img src="Z:\Public\images\image-20251201211837586.png" alt="image-20251201211837586" style="zoom:50%;" />

> 目标：**牺牲部分性能和复杂度，换取强一致性**，适用于转账、支付等金融级场景。

### TCC 模式简介

TCC（Try-Confirm-Cancel）是一种分布式事务模式，将整个事务拆分为三步：

- **Try**：预留资源 / 冻结状态（检查并锁定可用余额、库存等）；
- **Confirm**：确认执行（真正扣减余额、写入 Redis 与 MySQL 等），只要 Try 成功一般不会失败；
- **Cancel**：回滚（释放 Try 阶段占用的资源）。

在 MySQL + Redis 一致性场景中的抽象：

1. **Try**
    - 在 MySQL 中预留或锁定相关记录；
    - 在 Redis 中标记“事务进行中”，防止被其他线程并发修改。
2. **Confirm**
    - 最终更新 MySQL 的真实值；
    - 同步写入 Redis；
    - 解除锁定。
3. **Cancel**
    - 回滚 MySQL 中预留的变更；
    - 清理 Redis 中的事务标记 / 回退值。

### 特点

#### 优点

- 能够实现“**要么两边都成功，要么两边都失败**”；
- 更适合服务拆分后的跨系统事务（支付、账户、订单系统分别独立）。

#### 缺点：

- 实现复杂度高：每个参与方都要实现 Try/Confirm/Cancel 三套接口；
- 要考虑幂等、防悬挂、空回滚等问题；
- 性能较普通本地事务差，一般会带来 20%～30% 的额外开销。

### 适用场景

- **金融转账 / 支付扣款 / 充值提现**；
- 跨账户资金划转、里程 / 积分扣减等需要**绝对准确**的业务。

对商品评论、点赞、新闻阅读量等普通业务，**不建议动用 TCC**，成本远大于收益。

## 方案四：数据回写（Write-Behind + 聚合回刷）

> 目标：在“极端高频写”场景下，把大量小写操作聚合成少量批量更新。

### 核心流程

1. **所有写请求先写 Redis**
    - 比如：把某篇文章的点赞次数累加到 Redis 的计数器上；
2. Redis 定期或达到阈值后将增量写回 MySQL：
    - 根据配置：
        - “每累积 N 次再刷一次 DB”；
        - 或“每隔 T 分钟批量刷一次 DB”；
3. 刷库动作可以：
    - 写在后台任务（定时 Job）里；
    - 或通过 MQ 把增量投递给“写库服务”，统一合并写入批量 SQL。

这是一种典型的 **Write-Behind（写后回写）+ 批量更新** 思路。

### 参数设计

假设：

- 每分钟有 1000 次点赞；
- 将“增量写 MySQL”设为：**累积 200 次或每 5 分钟刷一次**。

则：

- 原来 1000 次写全部落到 MySQL；
- 现在最多只写 5 次（1000 / 200 向上取整）；
- MySQL 写压力约降低 95%+。

参数选择原则：

- **阈值太小**（如 50 次）：MySQL 写压力仍较大；
- **阈值太大**（如 10000 次）：MySQL 数据更新过慢，可能与 Redis 显著不一致。

一般需要结合：

- 实际写入 QPS；
- 用户能接受的延迟（例如“播放量晚几分钟增加”通常可接受）。

### 一致性特征 & 注意点

- Redis 始终是“最新”的，MySQL 是延迟更新的“准实时”快照；
- 如果服务在写回前宕机，可能丢失一小段时间内的增量，需要结合：
    - Redis 持久化（AOF）、
    - 或把增量追加到 MQ 中，再异步落库，来提高可靠性。

### 适用场景

- **超高频计数类数据**：
    - 视频播放量、文章阅读量、榜单热度值；
- 业务只关心“趋势”和“排序”，不追求每一刻的精确值。

## 四种方案对比与选型建议

| 方案                     | 一致性                 | 性能表现         | 实现复杂度 | 典型场景                           |
| ------------------------ | ---------------------- | ---------------- | ---------- | ---------------------------------- |
| 旁路缓存（Cache-Aside）  | 接近强一致（短暂窗口） | 读性能好，写稍慢 | 低         | 商品详情、用户信息、配置等读多写少 |
| MQ 异步更新              | 最终一致               | 写性能极高       | 中-高      | 直播点赞、实时计数器、高频写场景   |
| 双写 TCC                 | 强一致                 | 性能一般         | 很高       | 金融转账、扣款、资金类关键业务     |
| 数据回写（Write-Behind） | 弱 / 最终一致          | 写性能极高       | 中         | 播放量、排行榜、日志计数等聚合数据 |

### 实用选型建议

1. **大部分业务：优先使用 “旁路缓存 + 删除缓存”**
    - 简单、可靠、社区经验丰富。
2. **写多读少、允许短暂不一致：考虑 “写 Redis + MQ 异步刷 MySQL”**
    - 同时做好幂等处理与监控。
3. **极端高频聚合写：采用 “Redis 聚合 + 定期回写（Write-Behind）”**
    - 注意持久化与丢数据风险。
4. **只有真正金融级强一致需求时，才考虑 “TCC / 分布式事务”**
    - 谨慎评估团队成本与性能开销。

## 工程实践中的通用注意事项

1. **尽量把 MySQL 作为权威数据源**
    - Redis 只是缓存或“加速层”，需要时可以从 MySQL 重新构建。
2. **所有方案都要考虑幂等性（Idempotency）**
    - 重试 / 消息重复 / 定时任务重复执行时不能造成数据翻倍。
3. **为关键数据建立监控与对账机制**
    - 定期比对 Redis 与 MySQL 的关键指标（总量差、异常偏差）；
    - 遇到明显偏差时自动触发修复脚本或预警。
4. **不要盲目追求“最复杂的方案”**
    - 大部分电商 / 内容系统，**旁路缓存模式 + 少量异步优化就够用**；
    - 复杂方案（TCC、全链路 MQ）适合系统规模足够大且确有刚需的场景。
