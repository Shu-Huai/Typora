# 如何合理地设置 Java 线程池的线程数？

## 回答重点

线程数怎么设，关键看任务是 **CPU 密集型**还是 **I/O 密集型**。

CPU 密集型任务，比如加解密、压缩、复杂计算，CPU 一直在干活，这时候线程开太多没意义，线程切换反而浪费时间。经验值是 `CPU 核心数 + 1`，多出来的 1 个是为了应对偶发的页缺失等中断。

I/O 密集型任务，比如读数据库、调远程接口、读文件，线程大部分时间在等 I/O 返回，CPU 闲着。这时候可以多开线程，让 CPU 在等待期间去处理其他任务。经验值是 `CPU 核心数 * 2`，甚至更多。

但这两个公式只是起点，不是答案。实际生产环境里，一台机器上跑着好几个服务，每个服务还有多个线程池，算出来的理论值根本用不上。正确的做法是根据业务压测结果不断调整，观察 CPU 利用率、响应时间、队列堆积情况来确定最优值。

## 扩展知识

### 理论公式的局限

网上流传的几个公式：

1. CPU 密集型：线程数 = CPU 核心数 + 1

2. I/O 密集型：线程数 = CPU 核心数 * 2

3. 通用公式：线程数 = CPU 核心数 * (1 + 等待时间/计算时间)

这些公式的问题在于假设太理想化：假设只有这一个线程池，假设任务类型单一，假设系统资源独占。现实情况是一台机器上可能跑着 Tomcat、Dubbo、定时任务各自的线程池，每个池子都按公式算一遍加起来早超标了。

### 实战中怎么定线程数

实际项目里定线程数的正确姿势：

1. 先用经验值跑起来，比如 I/O 密集型先设成 CPU 核心数 * 2

2. 做压测，逐步加大并发，观察 CPU 利用率、平均响应时间、队列堆积数

3. CPU 利用率 70%-80% 左右比较健康。太低说明线程数可以加，太高说明要减或者瓶颈在 CPU

4. 观察队列堆积，如果队列经常满说明线程数不够或者下游扛不住

5. 看响应时间 P99，如果突然飙高可能是线程切换太频繁或者 GC 问题

### 动态线程池

既然线程数很难一次算准，那能不能运行时动态调整？答案是可以的。

ThreadPoolExecutor 提供了 setCorePoolSize 和 setMaximumPoolSize 方法，可以在运行时修改线程数。配合配置中心就能实现动态调参，不用重启服务。

美团开源的 DynamicTp、Hippo4j 这些动态线程池框架就是基于这个原理。它们还加上了监控告警，线程池快满了能自动通知，方便及时扩容。

```java
// 运行时调整线程池参数
ThreadPoolExecutor executor = (ThreadPoolExecutor) Executors.newFixedThreadPool(10);
// 动态修改最大线程数
executor.setMaximumPoolSize(50);
// 动态修改核心线程数
executor.setCorePoolSize(20);
```

使用动态线程池的注意点：修改核心线程数会立即生效，但如果新值比当前线程数小，多余的线程不会立刻销毁，要等空闲超时才回收。

### 不同场景的经验值

1. Web 服务处理 HTTP 请求：典型 I/O 密集型，Tomcat 默认最大 200 线程，一般够用。如果下游调用多、RT 长，可以适当调大

2. 消息消费：看消费逻辑，如果只是解析消息写数据库，I/O 密集型，线程可以多开。如果有复杂计算，适当减少

3. 定时任务：看任务特点，批量导出这种 I/O 密集可以多线程，报表计算这种 CPU 密集别开太多

4. RPC 服务端：Dubbo 默认 200 线程，大部分场景够用。如果处理逻辑重可以调小，避免压垮下游

### Java 21 虚拟线程

Java 21 正式发布的虚拟线程改变了线程池的玩法。虚拟线程创建成本极低，几乎可以无限创建，不用再纠结线程数怎么设。遇到 I/O 阻塞时虚拟线程会自动挂起，让出底层的平台线程去执行其他任务。

但虚拟线程不是银弹。CPU 密集型任务用虚拟线程没有优势，因为 CPU 本身就是瓶颈。另外虚拟线程和 synchronized 配合还有一些坑，可能导致 carrier thread 被 pin 住。

## 面试官追问

#### 提问：你说 CPU 密集型任务线程数设成核心数加 1，为什么要加 1？

回答：加 1 是为了应对偶发的页缺失或其他中断。当某个线程因为页缺失被阻塞去磁盘读数据时，多出来的那个线程可以顶上，保证 CPU 不会空转。不过实际影响很小，设成核心数也没问题。

#### 提问：怎么判断一个任务是 CPU 密集还是 I/O 密集？

回答：看任务执行期间 CPU 在不在干活。用 top 或者 jstack 看线程状态，如果大部分时间是 RUNNABLE 说明 CPU 在算，是 CPU 密集型；如果大部分时间是 WAITING 或 TIMED_WAITING 说明在等 I/O，是 I/O 密集型。还可以算等待时间和计算时间的比值，比值越大越偏 I/O 密集。

#### 提问：线程池线程数设太大会有什么问题？

回答：三个问题。第一是内存占用，如果每个线程默认 1MB 栈空间，1000 个线程就是 1GB。第二是上下文切换开销，线程太多 CPU 光切换就忙不过来，真正干活的时间反而少了。第三是资源竞争加剧，比如数据库连接池就那么多连接，线程多了都在抢，反而更慢。

#### 提问：压测时 CPU 利用率一直上不去，可能是什么原因？

回答：几种可能。第一是瓶颈在 I/O，比如下游接口慢、数据库查询慢，线程都在等 I/O，CPU 没活干。第二是锁竞争严重，线程都卡在 synchronized 或 Lock 上排队。第三是线程数太少，并发上不去。第四是压测工具本身的瓶颈，压力根本没打上去。要结合 jstack 看线程状态来定位。
