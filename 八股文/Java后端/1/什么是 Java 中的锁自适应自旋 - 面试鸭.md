# 什么是 Java 中的锁自适应自旋？ - 面试鸭 | 2026最新面试题+详细答案解析

## 回答重点

**自适应自旋**是 synchronized 重量级锁的一个优化手段：线程竞争锁失败时不会立刻阻塞，而是先自旋一会儿等锁释放。自旋的时间不是写死的，JVM 会根据上次自旋的结果动态调整。

具体逻辑是这样的：线程抢锁失败后，不是立刻挂起，而是原地空转几圈看看锁能不能释放。如果上次自旋很快就拿到锁了，JVM 认为这次自旋也很可能成功，就允许多转几圈；如果上次白转了半天最后还是阻塞了，JVM 就认为这锁可能竞争比较激烈，这次少转甚至不转，直接阻塞。

为什么要搞自旋？因为线程阻塞和唤醒的成本很高，要涉及用户态和内核态的切换。如果持锁线程很快就释放了，自旋一下就能拿到锁，省去了上下文切换的开销。但自旋也不是没代价，CPU 在空转，所以需要自适应机制来平衡。

## 扩展知识

### 自旋发生在哪个阶段

自旋只发生在**重量级锁**阶段。轻量级锁 CAS 失败后不会自旋，而是直接膨胀成重量级锁。自旋是在已经膨胀成重量级锁之后，线程竞争失败时的一个优化动作。

很多资料说轻量级锁 CAS 失败会自旋，这其实是错的。翻 HotSpot 1.8 源码就能看到，轻量级锁 CAS 失败直接调用 inflate 方法进行锁膨胀，压根没有自旋的代码。

### 为什么需要自适应

最早的自旋锁是固定次数的，比如 10 次。但问题是不同场景差异太大：有的锁持有时间极短，转两圈就释放了；有的锁持有时间很长，转 100 圈也拿不到。固定次数要么浪费 CPU，要么白白阻塞。

自适应自旋通过历史数据来预测未来：如果某个锁经常能自旋成功，说明持锁时间短，值得多转几圈；如果经常自旋失败，说明持锁时间长或竞争激烈，不如早点阻塞省 CPU。

### 怠速停车的比喻

可以把自旋理解成怠速停车。如果你知道一会儿就要出发，怠速等着比熄火划算，因为熄火后再点火启动有成本。但如果要等很久，一直怠速就太费油了，不如熄火。

自适应就是根据经验判断要等多久：上次怠速一会儿就出发了，这次多怠一会儿；上次怠了半天还是熄火了，这次早点熄火。

### JVM 参数

自适应自旋在 HotSpot 中是默认开启的。相关参数有：

1）`-XX:PreBlockSpin`(jdk7中移除了)：设置自旋次数上限，默认 10 次
2）`-XX:+UseSpinning`：开启自旋锁
3）`-XX:-UseSpinning`：关闭自旋锁

不过一般不需要手动调这些参数，JVM 的默认策略已经做了比较好的平衡。除非你非常了解应用的锁竞争模式，否则瞎调可能适得其反。

### 和 ReentrantLock 的区别

ReentrantLock 也有自旋的概念，但实现不太一样。ReentrantLock 用的是 AQS 框架，在入队阻塞之前会先尝试几次 CAS 抢锁，这也算是一种自旋。不过 AQS 的自旋策略相对固定，没有 synchronized 那种基于历史数据的自适应调整。

如果对锁的公平性有要求，或者需要可中断、超时等高级功能，用 ReentrantLock；如果只是普通的同步需求，synchronized 配合 JVM 的自适应自旋已经够用了，而且写起来更简单。

## 面试官追问

#### 提问：自旋次数太多会有什么问题？

回答：自旋是 CPU 空转，次数太多就是白白浪费 CPU 时间。如果一个线程自旋了很久还拿不到锁，这段时间本来可以让给其他线程干活，现在全浪费了。特别是在 CPU 核心数少的机器上，一个线程空转会直接影响其他线程的执行。所以 JVM 会有自旋次数上限，超过就直接阻塞。

#### 提问：自适应自旋怎么判断上次自旋是否成功的？

回答：JVM 会在每个 ObjectMonitor 上记录自旋的统计信息，包括最近几次自旋是成功拿到锁了还是最后阻塞了。这些信息存在 Monitor 对象里，下次自旋时会参考这些历史数据来决定自旋多久。具体实现可以看 HotSpot 源码里 ObjectMonitor 的 _SpinFreq、_SpinClock 等字段。

#### 提问：JDK 15 废弃偏向锁之后，对自旋有什么影响？

回答：没有直接影响。偏向锁是解决无竞争场景的，自旋是解决轻度竞争场景的，两个优化点不一样。废弃偏向锁之后，无竞争场景会直接走轻量级锁，有竞争就升级到重量级锁，重量级锁里的自适应自旋机制还是照常运作。 ...
