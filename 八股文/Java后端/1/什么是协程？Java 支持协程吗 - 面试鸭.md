# 什么是协程？Java 支持协程吗？ - 面试鸭 | 2026最新面试题+详细答案解析

## 回答重点

**协程**是用户态的轻量级线程，不由操作系统内核调度，而是由程序自己在用户空间里管理。创建和切换成本极低，内存占用只有几 KB，不像线程那样动辄 1MB。

Java 从 21 开始正式支持协程，叫做**虚拟线程**，是 Project Loom 的成果。19 和 20 是预览版，21 才转正。

虚拟线程的用法很简单：

```java
// 启动单个虚拟线程
Thread.startVirtualThread(() -> {
    System.out.println("Hello from a virtual thread!");
});

// 用线程池跑 10 万个并发任务
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> Thread.sleep(100));
    }
}
```

同样的代码用传统线程池跑 10 万并发，服务器早就 OOM 了，换成虚拟线程跑起来毫无压力。

>

通俗解释一下

你可以把**线程**想象成公司的正式员工：

- 成本高：每个人都要占工位（栈内存大，约 1MB），入职离职手续麻烦（创建销毁慢）。

- 归老板管：操作系统（OS）就是老板，老板让你干你就干，让你停你就得停（抢占式调度），切换任务时还要开会交接（上下文切换开销大）。

而**协程**就像是外包临时工：

- 成本极低：自带小板凳就能干活（栈内存极小，几 KB），招之即来挥之即去。

- 归项目组管：程序自己就是组长（用户态调度）。组长发现 A 临时工在等快递（IO 阻塞），立马让他去旁边休息，换 B 临时工上来干活，根本不需要惊动大老板（OS）。

所以在同样的服务器配置下，你可能只能养 1000 个“正式员工”（线程），但可以养 100 万个“临时工”（协程）。这就解决了高并发下的资源瓶颈问题。

## 扩展知识

### 虚拟线程的实现原理

要搞懂虚拟线程，得先理清三个角色：

虚拟线程是 Java 堆里的普通对象，可以创建几百万个。平台线程是传统的 Java 线程，1:1 绑定操作系统内核线程，数量有限。载体线程是动态角色，当平台线程正在执行某个虚拟线程时，这个平台线程就叫载体线程。

调度器是一个 ForkJoinPool，默认线程数等于 CPU 核心数，负责把虚拟线程分配给空闲的载体线程执行。

![xuni.drawio.png](https://pic.code-nav.cn/mianshiya/question_picture/1783388929455529986/TRxUrk0w_xuni.drawio_mianshiya.webp)

核心机制是**挂载**和**卸载**：

1）虚拟线程需要执行时，调度器把它挂载到一个空闲的载体线程上，载体线程开始跑虚拟线程里的代码

2）虚拟线程遇到阻塞操作时，JVM 把它的栈状态存回堆内存，从载体线程上卸载下来，载体线程空出来去执行别的虚拟线程

3）阻塞结束后，调度器找一个空闲的载体线程把这个虚拟线程重新挂载上去继续跑，不一定是原来那个载体

传统线程遇到 IO 阻塞会死等，整个线程被占用。虚拟线程遇到阻塞就让出载体，载体可以同时服务很多虚拟线程，这就是能扛百万并发的原因。

### 协程的三大核心特性

**轻量级**：内存占用只有几 KB 到几十 KB，栈是动态增长的，用多少分配多少。线程的栈创建时就固定分配 1MB，即使用不上也占着。单机跑百万协程没问题，线程几千个就到极限了。

**用户态调度**：线程由操作系统内核调度，是抢占式的，随时可能被打断。协程由 JVM 调度，是协作式的，只在 yield、await 或阻塞 IO 这些显式让出点才会切换，能减少上下文切换开销。

**高并发**：传统的线程池 + 阻塞 IO 模型，几千并发线程资源就耗尽了。协程用户态调度开销极低，轻松扛住十万到百万级并发。

### 协程与线程的对比

对比维度传统线程虚拟线程/协程调度者操作系统内核，抢占式JVM 用户态，协作式上下文切换涉及内核态切换，开销大纯用户态，几百纳秒阻塞行为占用整个 OS 线程只挂起当前协程，载体继续干活并发规模几千个到上限百万级没压力内存占用固定 1-8 MB 栈初始几 KB，动态增长编程模型阻塞式代码写着舒服但扛不住量阻塞式写法 + 高并发两全其美

### 虚拟线程的适用场景和坑点

适合的场景是 IO 密集型任务，比如 HTTP 请求、数据库查询、RPC 调用。这类任务大部分时间在等响应，用虚拟线程可以在等待时让出载体去服务其他请求。

不适合 CPU 密集型任务，比如大量计算、加解密、压缩。这类任务没有阻塞点让虚拟线程卸载，载体线程被一直占用，和普通线程没区别。

![](https://pic.code-nav.cn/mianshiya/question_picture/1843904816956411905/q3u5tu3K_3yPkrWwRrQ_mianshiya.webp)

有个坑要注意：synchronized 同步块里如果有阻塞操作，虚拟线程没法卸载，会把载体线程一起卡住，这叫 pinning。解决办法是把 synchronized 换成 ReentrantLock。JDK 21 的版本对这个问题做了一些优化，但还是建议用 ReentrantLock。

## 面试官追问

#### 提问：虚拟线程和 CompletableFuture 异步编程有什么区别？什么时候该用哪个？

回答：CompletableFuture 是回调式异步，代码拆成一段一段用 thenApply、thenCompose 串起来，嵌套多了可读性很差。虚拟线程可以用同步阻塞的写法达到异步的效果，代码看起来是顺序执行的，实际上遇到阻塞会自动让出 CPU。能用虚拟线程的场景优先用虚拟线程，代码简洁太多。CompletableFuture 适合需要组合多个异步结果的复杂场景，比如并行调用三个接口然后合并结果。

#### 提问：虚拟线程能完全替代线程池吗？

回答：不能完全替代。IO 密集型任务用虚拟线程很香，但 CPU 密集型任务还是得用传统线程池。虚拟线程的优势在于阻塞时能让出载体，CPU 密集型任务没有阻塞点，虚拟线程就是个普通的线程池，反而因为调度开销可能更慢一点。另外混合型任务也要注意，如果一个任务大部分时间在计算，少量时间做 IO，用传统线程池可能更合适。

#### 提问：虚拟线程里用 ThreadLocal 会有什么问题？

回答：ThreadLocal 在虚拟线程里会膨胀。传统线程池复用几十个线程，ThreadLocal 顶多占几十份内存。虚拟线程数量可能是百万级，每个虚拟线程都有自己的 ThreadLocal 副本，内存占用会爆炸。解决办法一是改用 ScopedValue，这是 JDK 21 引入的替代方案，生命周期更可控。二是用完立即 remove，不要让值一直挂着。

#### 提问：怎么判断一个虚拟线程有没有被 pin 住？

回答：可以加 JVM 参数 -Djdk.tracePinnedThreads=full，运行时会打印被 pin 住的虚拟线程堆栈。一般是 synchronized 块里做了阻塞操作导致的，把 synchronized 换成 ReentrantLock 就能解决。生产环境可以用 JFR 事件 jdk.VirtualThreadPinned 来监控。
