# RabbitMQ 中的持久化队列与非持久化队列有什么区别？ - 面试鸭 | 2026最新RabbitMQ 面试题+详细答案解析

## 回答重点

RabbitMQ 提供了两种队列类型：持久化队列和非持久化队列。它们的主要区别在于消息在 RabbitMQ 中的存储方式以及遇到服务器重启或者崩溃时的行为。

1）**持久化队列**：消息会被存储到磁盘上，即使 RabbitMQ 服务器重启或崩溃，消息也能被保留下来。所以，通过持久化队列，我们可以确保消息不会丢失。但需要注意的是，持久化队列也会略微影响性能，因为将消息写入磁盘比仅在内存中操作要慢。

2）**非持久化队列**：消息只存储在内存中，当 RabbitMQ 服务器重启或崩溃时，这些消息会丢失。这种队列的优势在于其高性能，适用于不特别关心数据持久性的应用场景。

## 扩展知识

除了持久化队列和非持久化队列的基本区别，还有一些实际场景和实现细节可以分享：

1）**队列声明**：
当我们声明队列时，可以通过设置 `durable` 参数来指定队列的持久化行为。对于持久化队列，`durable` 参数设置为 `true`，而非持久化队列，`durable` 参数设置为 `false`。例如，在 Python 中使用 `pika` 库可以这样声明：

```python
channel.queue_declare(queue='task_queue', durable=True)  # 持久化队列
```

2）**消息持久化**：
即使队列设置为持久化，为了完全确保消息的持久化，消息本身也需要被标记为持久化。可以将 `delivery_mode=2` 添加到消息属性中：

```python
channel.basic_publish(exchange='',
                      routing_key='task_queue',
                      body=message,
                      properties=pika.BasicProperties(
                          delivery_mode=2,  # make message persistent
                      ))
```

3）**应用场景**：

- **持久化队列场景**：
1）金融交易系统：需要保证任何情况下消息不会丢失。
2）订单处理系统：确保订单消息在系统故障后依旧存在。

- **非持久化队列场景**：
1）日志系统：日志消息可以丢失且更在意处理速度。
2）临时通知：消耗过后的通知无需保存。

4）**性能影响**：
持久化会消耗更多的资源、导致吞吐率下降和消息延迟的增加。因此在需要高性能的场景中可能会选择非持久化队列。

5）**磁盘 I/O**：
消息写入磁盘的过程不仅仅可通过 `durable` 参数和 `delivery_mode` 设置，还可以通过 `confirm` 模式来优化，确保消息在达到磁盘前不会被消费者处理。使用 `confirm` 模式可以获得消息何时完全持久化的信息。
