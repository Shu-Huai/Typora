# HTTP 中 GET 和 POST 的区别是什么？ - 面试鸭 | 2026最新计算机网络面试题+详细答案解析

## 回答重点

从 HTTP 规范的语义来看，GET 用于获取资源，不应该改变服务器状态；POST 用于提交数据，通常会产生副作用，比如创建或更新资源。

不过在实际应用中，因为浏览器和服务器的实现，两者有一些明显的差异：

1）参数传递方式不同：GET 把参数拼在 URL 上，长度受浏览器和服务器限制，一般在 2KB 左右。POST 把参数放在请求体里，理论上没有大小限制，更适合传大块数据。当然 POST 也能在 URL 上带参数，只是不常见。

2）安全性有区别：GET 的参数直接暴露在 URL 里，会被浏览器历史记录、服务器日志、代理缓存记下来，不适合传密码这类敏感信息。POST 把数据藏在请求体里，看起来安全一点，但本质上还是明文，真要安全得靠 HTTPS。

3）幂等性不同：按规范 GET 是幂等的，同一个请求发 10 遍结果都一样；POST 不是幂等的，发 10 遍可能创建 10 条数据。但实际开发中，有人拿 GET 搞提交、拿 POST 搞查询，那就得具体看代码逻辑了。

4）缓存机制不同：GET 请求能被浏览器和 CDN 缓存，适合图片、静态页面这类不常变的资源。POST 请求默认不缓存，每次都会打到服务器。

## 扩展知识

### 为什么会有这些区别

HTTP 协议设计的时候就给不同方法定了不同的语义。GET 被定义为"安全方法"，意思是只读不写，不应该对服务器产生副作用，所以浏览器敢放心地缓存 GET 响应、允许用户刷新重试。POST 被定义为"非安全方法"，每次请求都可能改变服务器状态，所以浏览器在刷新 POST 页面时会弹确认框。

URL 长度限制其实不是 HTTP 协议规定的，RFC 里压根没说 URL 最长多少。限制来自浏览器和服务器的实现：IE 限制 2083 字符，Chrome 大概 2MB，Nginx 默认 4KB，Tomcat 默认 8KB。所以跨端传大数据用 GET 就是在给自己挖坑。

### RESTful 设计中的角色分工

在 RESTful 架构里，HTTP 方法有明确分工：

1）GET 负责查询：`GET /users/123` 获取用户详情，`GET /orders?status=pending` 查待处理订单

2）POST 负责创建：`POST /users` 创建新用户，请求体带用户信息

3）PUT 负责全量更新：`PUT /users/123` 替换整个用户数据

4）PATCH 负责部分更新：`PATCH /users/123` 只改某几个字段

5）DELETE 负责删除：`DELETE /users/123` 删除这个用户

### 浏览器的特殊处理

浏览器对 GET 和 POST 有一些特殊行为要注意：

1）重定向会改方法：服务器返回 301、302 时，浏览器会把 POST 自动改成 GET 再发。如果你 POST 提交表单后服务器 302 跳转，请求体数据就丢了。想保持 POST 方法得用 307 状态码。

2）预检请求：跨域 POST 带自定义头或 JSON body 时，浏览器会先发一个 OPTIONS 预检请求问服务器允不允许，GET 简单请求就没这事。

3）历史记录处理：GET 请求能被收藏、能分享链接、能用浏览器后退按钮。POST 请求后退时会弹"重新提交表单"的确认框，用户体验差。

### 编码格式差异

GET 请求只能用 URL 编码，特殊字符得转成 `%XX` 格式，中文一个字可能变成 9 个字符。

POST 请求支持多种 Content-Type：

1）`application/x-www-form-urlencoded`：表单默认格式，键值对用 & 连接

2）`multipart/form-data`：上传文件必须用这个，数据按分隔符切块

3）`application/json`：前后端分离项目的主流选择，结构清晰好解析

### 网络层面的细微差异

在某些网络库或浏览器实现中，POST 请求可能会分两次发：先发请求头等服务器返回 100 Continue，再发请求体。GET 通常一次发完。不过这个行为不是强制的，现代浏览器基本都是一次发完。

HTTP/2 里 GET 和 POST 都走同一个 TCP 连接，多路复用，区别更小了。

## 面试官追问

#### 提问：你说 POST 比 GET 安全，那如果我抓包的话，POST 的数据能看到吗？

回答：当然能看到。HTTP 不管 GET 还是 POST 都是明文传输，用 Wireshark、Fiddler 这类工具抓包，请求体里的内容一览无余。POST "安全"只是说不会出现在 URL 里、不会被浏览器缓存，仅此而已。真正的安全得靠 HTTPS，请求和响应全程加密，中间人拿到的就是一堆乱码。

#### 提问：那为什么表单提交推荐用 POST 而不是 GET？

回答：主要三个原因。第一，GET 有长度限制，表单数据稍微多点就超了。第二，GET 参数在 URL 里会被浏览器历史、服务器日志记下来，用户密码这类敏感数据暴露风险太大。第三，GET 请求能被缓存、能被预加载，万一表单是个转账操作，浏览器预加载一下钱就没了。

#### 提问：GET 请求能带 body 吗？

回答：HTTP 协议没禁止，但不推荐。RFC 7231 明确说 GET 请求的 body "没有定义的语义"，意思是服务器可以直接忽略。实际上很多服务器框架收到 GET 带 body 也确实不处理。Elasticsearch 早期用 GET 带 body 做查询，后来也支持了 POST 方式，就是因为兼容性太差。

#### 提问：POST 请求能被缓存吗？

回答：HTTP 协议允许缓存 POST 响应，只要响应头带了合适的 Cache-Control 和 Expires。但现实中几乎没人这么干，因为 POST 语义就是"有副作用的操作"，缓存它没意义还容易出问题。浏览器和 CDN 默认也不缓存 POST。硬要缓存的话，一般是把 POST 换成 GET，或者在应用层自己实现缓存逻辑。 ...
