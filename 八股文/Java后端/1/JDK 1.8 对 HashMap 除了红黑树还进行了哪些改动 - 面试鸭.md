# JDK 1.8 对 HashMap 除了红黑树还进行了哪些改动？ - 面试鸭 | 2026最新Java 热门面试题 200 道+详细答案解析

## 回答重点

JDK 1.8 对 HashMap 除了引入红黑树，还有三个重要改动：**哈希函数简化**、**扩容机制优化**、**头插法改尾插法**。

1）哈希函数简化：1.7 的 hash 函数经过四次异或运算，1.8 只做一次，把 key 的 hashCode 高 16 位和低 16 位异或一下就完事了。这样既保证了高低位都能参与索引计算，又减少了运算开销。

2）扩容不再逐个取模：1.7 扩容时每个元素都要重新算一遍 `hash % newCapacity`，1.8 利用了一个巧妙的特性，元素要么留原位，要么挪到「原位置 + 老数组长度」，通过一次位运算就能判断，省去了大量取模计算。

3）头插法改尾插法：1.7 插入新节点直接往链表头部塞，扩容时链表会倒过来。多线程环境下，两个线程同时扩容可能把链表搞成环，CPU 直接跑满死循环。1.8 改成尾插法，扩容后顺序不变，避免了成环问题。

## 扩展知识

### 哈希函数的演进

1.7 的 hash 函数长这样：

```java
static int hash(int h) {
    h ^= (h >>> 20) ^ (h >>> 12);
    return h ^ (h >>> 7) ^ (h >>> 4);
}
```

1.8 简化成了这样：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

为什么能简化？因为 1.8 引入了红黑树兜底，就算哈希冲突严重，链表长度超过 8 也会转成红黑树，查询效率从 O(n) 变成 O(log n)。有了这层保障，hash 函数就不用那么拼命地去打散分布了，JDK 开发者在速度、实用性、哈希质量之间做了权衡，选择了更简单的实现。

### 扩容机制的优化细节

按照常规思维，扩容时每个元素都得重新算一遍 `hash & (newCapacity - 1)` 来确定新位置。1.7 就是这么干的，但 1.8 发现了一个规律：数组长度永远是 2 的幂次方，扩容就是翻倍。

假设老数组长度 16，二进制是 `010000`，新数组长度 32，二进制是 `100000`。用来取模的掩码分别是 `001111` 和 `011111`，差别就在第 5 位。

所以判断一个元素该留原地还是搬新家，只需要看它 hash 值的第 5 位是 0 还是 1：

- 第 5 位是 0：新旧掩码算出来的索引一样，留原地

- 第 5 位是 1：索引变成「原位置 + 16」

刚好可以拿老数组长度 `010000` 去跟 hash 做与运算，结果是 0 就留原地，非 0 就搬到新位置。这样整条链表的节点可以一次性分成两拨，分别挂到两个位置，不用每个节点单独算索引了。

### 头插法的死循环问题

1.7 用头插法，新节点直接插到链表头部，不用遍历到尾巴，插入是 O(1)。但扩容时迁移节点也是从头开始取、往头上插，导致链表顺序会反过来。

![20220219203032.png](https://pic.code-nav.cn/mianshiya/question_picture/1783397053004488705/20220219203032_mianshiya.webp)

假设线程 A 和线程 B 同时扩容，A 刚把节点 1 指向节点 2，还没来得及断开旧连接，B 又把节点 2 指向节点 1，环就形成了。后面任何 get 或 put 操作遍历到这条链表，就会陷入死循环。

1.8 改成尾插法，扩容后链表顺序保持不变，从根源上避免了成环的可能。

不过话说回来，**改成尾插法之后 HashMap 就彻底线程安全了吗？** 并没有。多线程同时 put 还是可能丢数据，红黑树的树化和反树化过程也有并发问题。想要线程安全，老老实实用 ConcurrentHashMap。

## 面试官追问

#### 提问：为什么说 HashMap 数组长度必须是 2 的幂次方？

>

详细解答可以看：[为什么 HashMap 在 Java 中扩容时采用 2 的 n 次方倍？](https://www.mianshiya.com/question/1780933294754394113)

回答：为了用位运算替代取模。`hash % length` 在 length 是 2 的幂次方时，等价于 `hash & (length - 1)`，位运算比取模快得多。同时 length - 1 的二进制全是 1，能保证 hash 的低位都参与运算，分布更均匀。

#### 提问：1.8 的 HashMap 在什么情况下链表会转红黑树？

>

详细解答可以看：[为什么 JDK 1.8 对 HashMap 进行了红黑树的改动？](https://www.mianshiya.com/question/1780933294771171329)

回答：两个条件都得满足：链表长度大于等于 8，并且数组容量达到 64。如果链表长了但数组还不到 64，会优先扩容而不是树化，因为小数组树化意义不大，扩容反而能更好地打散数据。

#### 提问：红黑树什么时候会退化回链表？

回答：当红黑树节点数减少到 6 个以下时，会退化成链表。这里用 6 而不是 8 是为了避免频繁的树化和反树化，中间留了个缓冲区间。

#### 提问：ConcurrentHashMap 1.8 和 1.7 的锁机制有什么区别？

>

详细解答可以看：[Java 中 ConcurrentHashMap 1.7 和 1.8 之间有哪些区别？](https://www.mianshiya.com/question/1780933294813114369)

回答：1.7 用的是分段锁 Segment，每个 Segment 继承 ReentrantLock，默认 16 个 Segment 意味着最多 16 个线程并发写。1.8 抛弃了 Segment，直接在数组的每个槽位上用 CAS + synchronized 做细粒度锁，锁的粒度从段级别降到了节点级别，并发度大幅提升。 ...
