# 为什么 HashMap 在 Java 中扩容时采用 2 的 n 次方倍？ - 面试鸭 | 2026最新27 届校招 Java 热题+详细答案解析

## 回答重点

HashMap 的容量必须是 2 的 n 次方，核心原因有两个：**位运算替代取模**和**扩容时高效迁移**。

计算元素在数组中的位置时，HashMap 用的是 `(n - 1) & hash` 这个位运算公式。只有当 n 是 2 的次方时，`n - 1` 的二进制低位全是 1，这样 & 运算才能让 hash 值的低位完整保留，保证索引均匀分布。比如 n = 16 时，`n - 1 = 15`，二进制是 `0000 1111`，hash 值跟它 & 一下，低 4 位原封不动拿来当下标。

![hashmapsuoyin.drawio.png](https://pic.code-nav.cn/mianshiya/question_picture/1783388929455529986/podapRiP_hashmapsuoyin.drawio_mianshiya.webp)

如果用取模运算 `hash % n`，CPU 要做除法，比位运算慢得多。在高并发场景下，每秒几十万次 get/put 操作，这点性能差距就很可观了。

```java
// HashMap 源码中的索引计算
int index = (n - 1) & hash;  // 位运算，效率高
// 等价于 hash % n，但前提是 n 必须是 2 的次方
```

## 扩展知识

### 为什么 n-1 的低位必须全是 1

假设数组长度不是 2 的次方，比如 n = 10，`n - 1 = 9`，二进制是 `1001`。这时候拿 hash 值跟它 & 运算，中间那两个 0 的位置永远出不来 1，意味着下标 2、3、6、7 这些位置永远不会被映射到，数组利用率直接砍半，冲突概率飙升。

### rehash 时的迁移优化

扩容时最耗时的就是把老数组的元素搬到新数组。传统做法是每个元素重新算一遍 `hash % newSize`，JDK 1.8 利用 2 的次方这个特性做了个很巧妙的优化。

因为新容量是老容量的 2 倍，二进制上就是高位多了一个 1。比如从 16 扩到 32：

1）老容量 16，二进制 `0001 0000`，`n - 1 = 0000 1111`
2）新容量 32，二进制 `0010 0000`，`n - 1 = 0001 1111`

两者的差别就在第 5 位。所以判断一个元素该不该挪位置，只需要看它 hash 值的第 5 位是 0 还是 1：

1）第 5 位是 0：新下标 = 老下标，不用动
2）第 5 位是 1：新下标 = 老下标 + 老容量

```java
// JDK 1.8 扩容时的位运算判断
if ((e.hash & oldCap) == 0) {
    // 留在原位置
} else {
    // 迁移到 原位置 + oldCap
}
```

一个 & 运算就能决定元素去向，比重新取模快多了。而且链表上的元素可以一次性分成两拨，分别挂到新旧位置，不用一个个搬。

### 指定容量时的自动修正

如果你 `new HashMap(10)`，HashMap 不会真的用 10 作为容量，而是自动向上取整到最近的 2 的次方，也就是 16。这个修正逻辑在 `tableSizeFor` 方法里：

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

通过 5 次无符号右移和或运算，把最高位 1 右边的所有位都填成 1，最后加 1 就得到 2 的次方。比如传入 10，经过处理变成 15，加 1 得 16。

## 面试官追问

#### 提问：如果我就是想用一个非 2 次方的容量，能不能绕过这个限制？

回答：绕不过。HashMap 内部强制把你传的值修正成 2 的次方，`tableSizeFor` 方法会在构造时自动执行。就算你用反射改了 table 数组的长度，后续扩容还是会按 2 倍来，而且 `(n - 1) & hash` 这个索引计算逻辑是写死的，非 2 次方容量会导致大量哈希冲突，得不偿失。

#### 提问：ConcurrentHashMap 也是用 2 的次方容量吗？原理一样吗？

回答：一样的，ConcurrentHashMap 底层索引计算也是 `(n - 1) & hash`，扩容时同样利用高位判断元素迁移位置。JDK 1.8 及之后 ConcurrentHashMap 用 CAS + synchronized 锁，但容量设计这块跟 HashMap 完全一致。

#### 提问：位运算比取模快多少？有没有具体的性能数据？

回答：在 x86 架构上，整数除法指令大概需要 20-40 个时钟周期，而位与运算只要 1 个周期，差了一两个数量级。实际业务里单次操作感知不到，但 HashMap 作为最常用的集合，一个请求可能触发几百次 get/put，积少成多就很明显了。像 Netty 这种高性能框架，内部大量使用位运算来优化热点路径。
