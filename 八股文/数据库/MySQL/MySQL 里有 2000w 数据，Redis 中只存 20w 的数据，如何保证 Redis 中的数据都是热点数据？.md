# MySQL 里有 2000w 数据，Redis 中只存 20w 的数据，如何保证 Redis 中的数据都是热点数据？

## 回答重点

核心思路是 **缓存预热 + 热点探测 + 淘汰策略**，让 Redis 动态保留访问频率高的数据。

1. 配置 `maxmemory`，根据内存上限选择 LRU 或 LFU 淘汰策略。内存不足时自动淘汰冷数据，让热点数据留下。
2. 通过埋点或热点探测系统统计 `key` 的访问频率，主动将高频数据加载到 Redis。
3. 系统上线或发布时根据业务经验、历史日志进行缓存预热，避免冷启动时请求集中打到数据库。

整体流程就是：**预热打底、探测补充、淘汰兜底**。

## 扩展知识

### 京东 hotkey 的设计思路

在业务代码中硬编码热点 `key` 无法应对热点变化。hotkey 采用实时探测：每个业务服务的 client 将访问 `key` 上报到 worker 集群，worker 统计访问频率，超过阈值后判定为热点并推送给各 client。client 收到后将热点数据放入 JVM 本地缓存，后续请求甚至无需访问 Redis。

![hotkey 架构](Z:/Public/images/JqQEOgAo_GCZueiY8sF_mianshiya.webp)

这种架构可以将热点流量分流到本地缓存，降低 Redis 压力。worker 集群应部署多实例，避免热点探测服务自身成为单点。

### LRU 和 LFU 的区别

Redis 4.0 之前主要使用 LRU，4.0 开始支持 LFU：

| 策略 | 依据 | 适用场景 | 缺点 |
| --- | --- | --- | --- |
| LRU | 最后访问时间 | 热点变化快、有时效性，如新闻和活动页 | 无法识别长期高频但短期未访问的数据 |
| LFU | 访问次数 | 长期稳定热点，如爆款商品和搜索词 | 需要维护计数并进行衰减 |

LRU 淘汰最近最久未访问的数据，但 Redis 使用的是**近似 LRU**：随机采样若干 `key`，淘汰样本中最老的一个。`maxmemory-samples` 默认是 5，调大可提高精度但会增加开销。

LFU 按访问次数淘汰低频 `key`，同时对历史访问次数进行衰减，避免过去的热点永久占用内存。

### 缓存预热的做法

1. **定时任务**：凌晨将预判热点（例如销量 Top 1000 商品）批量写入 Redis。
2. **应用启动预热**：通过 Spring `ApplicationRunner` 或 `CommandLineRunner`，在应用启动完成后加载热点数据。
3. **日志分析预热**：使用历史访问日志和大数据平台计算热点 `key`，再批量写入 Redis。

预热应分批进行，避免一次性写入过多数据导致 Redis 被打满或频繁触发淘汰。

## 面试官追问

### 提问：LRU 和 LFU 应该如何选择？

热点变化快、具有明显时效性的业务适合 LRU；热点较稳定、长期高频访问的业务适合 LFU。实际生产中常见 `volatile-lfu` 或 `allkeys-lfu`，具体取决于是否只允许淘汰带过期时间的 `key`。

### 提问：hotkey 的 worker 集群挂掉怎么办？

worker 通常是无状态的，重启后重新积累统计数据。挂掉期间热点探测会暂停，但业务仍可访问 Redis；client 已识别的热点本地缓存仍可使用，只是新热点不会及时更新。因此应部署多 worker 做高可用。

### 提问：20 万这个容量如何确定？

主要根据 Redis 可用内存和单条数据大小估算。例如分配 10 GB 内存、每条数据平均 50 KB，理论上约可保存 20 万条。实际还要预留 1.2～1.5 倍内存空间应对碎片、对象开销和复制缓冲区，并避免将 Redis 使用率打满，通常控制在 `maxmemory` 的 80% 左右。
