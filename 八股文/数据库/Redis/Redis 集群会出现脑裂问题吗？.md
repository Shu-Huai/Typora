# Redis 集群会出现脑裂问题吗？

## 回答重点

会。网络分区时，Redis 集群可能出现多个主节点同时提供写入服务，导致数据不一致。

典型过程是：主节点与从节点、哨兵之间网络中断，但主节点本身仍在运行；哨兵认为主节点失联，选举从节点升级为新主。此时旧主和新主同时接受写请求。网络恢复后，旧主会被降级为从节点并同步新主数据，期间写入旧主的数据可能被覆盖丢失。

![Redis 脑裂](Z:/Public/images/VHf2Tcvo_redisnaolie.drawio_mianshiya.webp)

可使用以下参数降低风险：

- `min-slaves-to-write`：主节点写入前至少需要多少个有效从节点。
- `min-slaves-max-lag`：从节点允许的最大复制延迟秒数。

例如 `min-slaves-to-write=2`、`min-slaves-max-lag=10`，主节点只有在至少 2 个从节点延迟不超过 10 秒时才接受写入。被网络隔离的旧主因缺少有效从节点，会拒绝写入。

## 扩展知识

### 什么是脑裂

脑裂是网络分区后，集群被分成多个互不通信的部分，每一部分都误以为自己是完整集群并选出自己的“主节点”，从而对同一数据做出冲突决策。根本原因是网络分区。

### Redis 中的脑裂过程

1. 主节点与哨兵、从节点发生网络分区。
2. 哨兵无法联系主节点，发起故障转移。
3. 某个从节点被提升为新主，集群暂时存在两个主节点。
4. 客户端向不同主节点写入，数据出现分歧。

### 为什么参数也不能完全避免脑裂

`min-slaves-to-write` 和 `min-slaves-max-lag` 只能降低概率。例如故障转移期间旧主暂时仍有足够从节点，且复制延迟低于阈值，它仍可能接受写入。选出新主后，旧主切换为从节点，选举期间写入的数据仍可能被覆盖。

![脑裂风险窗口](Z:/Public/images/gVjeypUb_WF8kkJLBUt_mianshiya.webp)

### 生产环境建议

1. 部署奇数个节点，例如 3 个或 5 个；按实际拓扑配置 `min-slaves-to-write` 和 `min-slaves-max-lag`。
2. 合理设置哨兵 `down-after-milliseconds`，避免过短导致网络抖动误触发，也避免过长导致故障恢复慢，通常可从 5～10 秒开始压测调整。
3. 客户端做好重试和幂等，关键写入同时落库或投递消息队列。
4. 金融级场景可使用 `WAIT` 等待副本同步，或选择 TiKV、数据库等支持强一致性的存储。

### 与 ZooKeeper 的对比

ZooKeeper 使用 ZAB，写入需要多数节点确认，天然更强调强一致；Redis 更偏向 AP，优先保证性能和可用性，通过异步复制实现最终一致。缓存场景可以接受少量丢失，但分布式锁和关键交易场景需要谨慎评估。

## 面试官追问

### 提问：脑裂恢复后如何处理脏数据？

旧主会被降级为从节点并执行全量或部分同步，旧主期间写入的数据可能直接被覆盖，没有自动冲突合并机制。关键数据应同步落库或进入消息队列，恢复后再通过对账脚本补回缺失数据。

### 提问：`min-slaves-to-write` 设置为从节点总数会怎样？

数据安全性更高，但任何一个从节点故障都可能让主节点拒绝写入，可用性显著下降。通常设置为从节点数量的一半多一点，例如 3 个从节点设为 2，5 个从节点设为 3。

### 提问：为什么 Redis 不像 ZooKeeper 使用 Paxos 或 Raft 保证强一致？

Redis 面向高性能缓存和高并发读写，每次写入都等待多数派确认会显著增加延迟；ZooKeeper 存储配置和元数据，数据量小、写入少，可以承受强一致协议的成本。两者设计目标不同。
