# Redis 在生成 RDB 文件时如何处理请求？

## 回答重点

Redis 通常通过 `BGSAVE` 生成 RDB 快照，核心机制是 **fork 子进程**。主进程 fork 出子进程后继续处理客户端请求，子进程遍历内存数据并写入磁盘。

流程如下：

1. 客户端发起 `BGSAVE`。
2. 主进程 fork 子进程，这一步会造成短暂阻塞。
3. fork 完成后，主进程恢复处理请求。
4. 子进程在后台遍历内存并写入 RDB 文件。
5. 子进程完成后退出并通知主进程。

因此生成 RDB 期间 Redis 通常不会停止服务，主要影响是 fork 瞬间的毫秒级延迟。

## 扩展知识

### 快照期间数据能修改吗？

可以。主进程仍然接收并执行写命令，快照一致性由**写时复制（Copy-On-Write）**保证。

fork 时，子进程不会完整复制主进程内存，而是复制页表。父子进程暂时指向相同的物理内存页：

![写时复制原理](Z:/Public/images/cASYQdyk_image_mianshiya.webp)

当主进程修改某个内存页时，操作系统才复制该页，主进程在副本上修改，而子进程继续读取原来的页面：

![写时复制过程](Z:/Public/images/HCjbjSF3_image_mianshiya.webp)

因此子进程最终写出的 RDB 反映的是 fork 时刻的数据状态，不会被后续写操作污染。

![RDB 快照一致性](Z:/Public/images/S45bV9Ti_APUItvSVe9_mianshiya.webp)

### 高峰期执行 RDB 的风险

1. **内存膨胀**：写并发很高时，大量内存页被修改，写时复制可能使内存占用接近翻倍。16 GB 数据集最坏可能需要预留约 32 GB 内存。
2. **磁盘 I/O 压力**：子进程需要把整个数据集写入磁盘，可能影响 AOF 刷盘和其他系统进程。
3. **fork 阻塞**：虽然只复制页表，但实例很大时页表本身也很大，fork 可能造成几十到上百毫秒的阻塞。

生产环境通常在低峰期执行 `BGSAVE`，或让从节点负责 RDB，主节点专注于处理业务请求。

## 面试官追问

### 提问：fork 为什么会阻塞主进程？不是只复制页表吗？

页表也需要占用内存并被复制。Redis 使用虚拟内存，通常每个页面为 4 KB；实例越大，页表越大，复制页表所需时间越长。20 GB 级实例 fork 可能阻塞几十到上百毫秒。

### 提问：RDB 生成到一半机器宕机怎么办？

Redis 会先写临时文件，完成后再通过原子 `rename` 替换正式的 `dump.rdb`。如果中途失败，旧的完整 RDB 不会被半成品覆盖，重启时仍可加载上一次成功的快照。

### 提问：`BGSAVE` 和 `SAVE` 有什么区别？生产上用哪个？

`SAVE` 由主进程同步生成 RDB，期间不能处理请求；`BGSAVE` fork 子进程异步生成，主进程仍可服务。生产环境应使用 `BGSAVE`，`SAVE` 只适合停机维护、紧急备份或关机前落盘。
