# Redis 的持久化机制有哪些？

## 回答重点

Redis 主要提供 **RDB** 和 **AOF** 两种持久化机制，Redis 4.0 之后还支持将两者结合的混合持久化。

- **RDB**：在某个时间点把整个内存数据保存为二进制快照，文件小、恢复快，适合备份和灾难恢复；但两次快照之间的数据可能丢失。
- **AOF**：按顺序记录每条写命令，数据安全性高；但文件较大，恢复时需要重放命令，速度相对较慢。
- **混合持久化**：AOF 重写时先写入 RDB 快照，后续增量命令再以 AOF 格式追加，兼顾恢复速度和数据安全性。

## 扩展知识

### RDB 持久化详解

RDB 通过 fork 子进程生成快照。主进程继续处理请求，子进程将内存数据写入临时文件，写完后再替换旧的 `dump.rdb` 文件。

触发方式：

1. **`save`**：在主线程中生成 RDB，期间 Redis 阻塞，通常只用于停机维护。
2. **`bgsave`**：后台生成 RDB，通过 fork 子进程完成，是生产环境常用方式。

`bgsave` 流程：

1. 检查是否已有 AOF 或 RDB 子进程运行。
2. 调用 `rdbSaveBackground`。
3. fork 子进程并生成 RDB 文件。
4. 主进程继续处理客户端请求。
5. 子进程写完后用新文件替换旧文件并退出。

![RDB 持久化流程](Z:/Public/images/ZQrKLTCy_HRQ70xeAb3_mianshiya.webp)

fork 使用**写时复制（Copy-on-Write）**：创建子进程时父子进程共享内存，只有某一方修改内存页时才复制该页，避免立即复制整份数据。

### AOF 持久化详解

AOF 将每条写命令追加到文件末尾，Redis 重启时重新执行这些命令即可恢复数据。它比 RDB 更安全，但文件更大，恢复速度更慢。

### AOF 写回策略

| 策略 | 说明 | 特点 |
| --- | --- | --- |
| `always` | 每条命令执行后立即 `fsync` | 最安全，但性能最差 |
| `everysec` | 每秒 `fsync` 一次 | 默认策略，性能与安全性折中，最多丢约 1 秒数据 |
| `no` | 由操作系统决定刷盘时机 | 性能最好，但可能丢失更多数据 |

即使设置 `always` 也不能绝对保证不丢数据，因为 Redis 通常是先执行命令，再将命令写入 AOF；如果两者之间进程崩溃，命令仍可能丢失。

### AOF 重写机制

AOF 会随着写操作不断膨胀。同一个 `key` 被 SET 多次时，历史命令大多没有意义。AOF 重写会根据当前内存状态生成最精简的新 AOF 文件。

流程如下：

1. 主进程 fork 子进程。
2. 子进程根据内存快照生成新的 AOF 文件。
3. 重写期间，主进程的新写命令同时追加到旧 AOF 和重写缓冲区。
4. 子进程完成后，主进程把重写缓冲区追加到新 AOF。
5. 用新文件原子替换旧文件。

![AOF 重写](Z:/Public/images/PRsIuzOQ_image_mianshiya.webp)

可以手动执行 `BGREWRITEAOF`，也可以通过以下参数自动触发：

- `auto-aof-rewrite-min-size`：允许重写的 AOF 最小大小，默认 64 MB。
- `auto-aof-rewrite-percentage`：相对上次重写后文件的增长百分比。

### 混合持久化

Redis 4.0 引入混合持久化，通过 `aof-use-rdb-preamble` 开启。AOF 重写时，先将当前内存数据以 RDB 格式写在新 AOF 文件开头，再将重写期间的增量命令以 AOF 格式追加在后面。

恢复时先加载 RDB 部分，再回放增量 AOF 命令，因此比纯 AOF 恢复更快，同时比纯 RDB 更安全。

### Redis 7.0 的 MP-AOF

Redis 7.0 之前，AOF 重写可能造成缓冲区重复、主进程 CPU 额外消耗以及同一份数据重复写磁盘等问题。MP-AOF 将单个 AOF 拆成多个文件：

- **base file**：基础文件，类似某个时间点的快照。
- **incremental files**：增量文件，记录基础文件之后的写操作。
- **manifest file**：清单文件，管理 base 和 incremental 文件。

![MP-AOF 文件结构](Z:/Public/images/S75VQa4K_image_mianshiya.webp)

重写期间的新命令直接写入新的增量文件，子进程独立生成新的 base 文件；完成后更新 manifest，旧文件再异步删除。

### AOF 文件修复

AOF 因系统崩溃出现损坏时，可以使用以下命令修复：

```bash
redis-check-aof --fix appendonly.aof
```

该工具会截断文件末尾不完整的命令，使 AOF 恢复到一致状态。

## 面试官追问

### 提问：生产环境一般如何配置持久化？

大多数场景使用混合持久化，并将 AOF 写回策略设为 `everysec`，兼顾恢复速度和数据安全。同时定期生成 RDB 并备份到异地存储。只有对数据安全要求极高且能接受性能下降时，才考虑 `always`。

### 提问：RDB 的 fork 会阻塞主线程吗？

会，但通常是微秒到毫秒级。fork 需要复制页表，实例内存越大阻塞时间越长；写时复制避免了立即复制全部数据，但 fork 期间父进程写入较多时，会产生更多内存页复制。

### 提问：AOF 重写期间 Redis 挂掉会怎样？

旧 AOF 文件仍然存在。新文件只有在完整写入并追加重写缓冲区后才会原子替换旧文件，因此重写中途崩溃通常仍使用旧 AOF 恢复。

### 提问：为什么 Redis 不使用传统 WAL，而使用 AOF？

传统 WAL 通常先写日志再修改数据，而 Redis 先修改内存再写 AOF。Redis 的内存操作本身很快且通常是原子的，AOF 的主要目的在于持久化而不是事务一致性；先写日志还会增加每次操作的延迟。
