# Redis 中如何保证缓存与数据库的数据一致性？

## 回答重点

缓存与数据库的一致性，本质是两个数据源之间的同步问题，没有绝对完美的方案，只有根据实时性、性能和复杂度进行取舍。

常见方案：

1. 先更新缓存，再更新数据库：并发和失败场景容易造成不一致。
2. 先更新数据库，再更新缓存：并发更新顺序可能错乱。
3. 先删缓存，再更新数据库：读请求可能把旧值重新写回缓存。
4. **先更新数据库，再删缓存**：Cache Aside Pattern，实时性和复杂度之间的常用折中。
5. **缓存双删**：先删缓存、更新数据库，延迟后再删一次。
6. **Binlog 异步同步**：监听数据库 Binlog，通过消息队列更新缓存，最终一致性更可靠。

实时性要求高时通常选择“更新数据库后删除缓存”；一致性要求高且允许毫秒到秒级延迟时，可以采用 Binlog + 消息队列。

## 扩展知识

### 为什么通常删除缓存而不是更新缓存

1. 缓存值可能需要复杂计算，写操作时重复计算浪费资源，删除后由下次查询重建更简单。
2. 并发更新时顺序不可控。例如 A 更新为 10、B 更新为 20，但 B 的缓存更新先到、A 的后到，最终可能出现数据库为 20、缓存为 10。

### 先更新缓存再更新数据库

该方案可能出现缓存已是新值而数据库更新失败，也可能因为并发请求执行顺序不同，最终数据库与缓存不一致，因此不推荐。

### 先更新数据库再更新缓存

并发场景中，A 先更新数据库但后更新缓存，B 后更新数据库却先更新缓存，网络延迟可能导致旧值覆盖新值，同样存在不一致问题。

### 先删缓存再更新数据库

典型时序：

1. A 删除缓存，准备更新数据库。
2. B 查询缓存未命中，从数据库读到旧值 10 并回写缓存。
3. A 将数据库更新为 20。
4. 缓存仍是旧值 10。

读多写少场景尤其容易出现这种问题。

### 缓存双删

先删除缓存，更新数据库，等待一段时间后再删除一次缓存。即使读请求在中间把旧值回写，第二次删除也能清掉它。

延迟时间通常取业务读操作最大耗时再加几百毫秒，可以通过消息队列、定时任务或 Redisson 延迟队列实现：

```java
public void updateWithDoubleDelete(String key, Object newValue) {
    redis.del(key);
    database.update(newValue);
    delayQueue.send(key, 1000); // 1 秒后再次删除
}
```

### 先更新数据库再删缓存

这是业界使用最广的 Cache Aside Pattern：

1. 先更新数据库。
2. 删除缓存。
3. 后续读请求发现缓存未命中，从数据库读取最新值并回写。

它存在一个极端窗口：读请求先查到旧值，写请求更新数据库并删除缓存，读请求随后把旧值回写。但该窗口很短，且要求读写时序精确交错，实际发生概率较低，因此是性能和一致性之间性价比较高的方案。

### 通过 Binlog 异步更新缓存

使用 Canal 伪装成 MySQL 从节点订阅 Binlog，解析数据变更后发送到 Kafka 或 RocketMQ，再由消费者更新或删除 Redis。

优点是业务代码不必显式维护缓存同步，消息队列还可以重试，最终一致性更可靠。需要注意：

1. 消息要按 `key` 顺序消费。
2. 消费者必须幂等，因为消息可能重复投递。
3. 存在百毫秒到秒级延迟。

```yaml
canal.destinations = example
canal.instance.master.address = 127.0.0.1:3306
canal.mq.topic = cache-sync-topic
canal.mq.partition = 0
```

### 强一致性方案

完全不能容忍不一致的金融场景，可以使用分布式读写锁：

- 写：获取写锁 → 更新数据库 → 删除缓存 → 释放写锁。
- 读：获取读锁 → 查缓存，未命中则查库并回写 → 释放读锁。

读读不互斥，但读写、写写互斥。代价是写操作会阻塞读操作，高并发性能明显下降。

## 面试官追问

### 提问：删除缓存失败怎么办？

数据库更新成功后，将删除任务投递到消息队列，由消费者持续重试；也可以使用 Spring Retry 本地重试，例如重试 3 次、间隔 100 ms。多次失败后应告警并人工处理。

### 提问：为什么“更新数据库再删缓存”出问题概率低？

通常要同时满足缓存刚过期、读写并发，以及写操作恰好在读请求查库与回写之间完成。数据库更新一般比缓存回写耗时更长，真正的交错窗口很短；即使出现异常，下一次缓存过期后也能自动修复。

### 提问：Canal 挂掉会丢数据吗？

Canal 会记录消费位点，重启后从上次位置继续消费，因此通常不会丢失，只是产生同步延迟。为避免单点故障，可以部署 Canal 集群并使用 ZooKeeper 做高可用协调。
