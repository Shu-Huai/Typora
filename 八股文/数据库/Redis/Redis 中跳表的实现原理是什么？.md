# Redis 中跳表的实现原理是什么？

## 回答重点

跳表本质上是一个**多层有序链表**：底层链表保存所有元素，上层链表是下层的稀疏索引，通过分层将普通链表的 $O(N)$ 查找优化为平均 $O(\log N)$。

查找从最高层开始，能够向右就向右，遇到大于目标值的节点就下降一层，重复直到找到目标或确定不存在。例如查找 50，可以先从顶层快速跳到 40，再下降到下一层找到 50。

![跳表查找](Z:/Public/images/tgO89EHY_amvtq6PKdl_mianshiya.webp)

插入时先定位位置，再随机决定节点需要建立几层索引。Redis 以 25% 概率向上增加一层，因此大多数节点只有底层索引，少数节点出现在高层。删除时找到目标节点，并在各层调整前后指针。

## 扩展知识

### 跳表查询过程

普通链表查找 50 需要逐个经过 `10 → 20 → 40 → 50`。跳表可以先在高层走 `10 → 40`，再下降一层从 40 走到 50，元素越多优势越明显。跳表平均查询复杂度为 $O(\log N)$，极端情况下为 $O(N)$。

![跳表查询示例](Z:/Public/images/Snipaste_2024-05-16_20-47-44_mianshiya.webp)

### Redis 跳表的特殊设计

Redis 跳表相比标准跳表增加了回退指针，并允许多个节点拥有相同 score。Redis 7.0 的核心结构如下：

```c
typedef struct zskiplistNode {
    sds ele;                         // 元素值
    double score;                    // 排序分数
    struct zskiplistNode *backward;  // 底层回退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针
        unsigned long span;             // 跨度
    } level[];
} zskiplistNode;
```

- `ele`：ZSet 成员，使用 SDS 保存。
- `score`：排序依据。
- `backward`：只在最底层有效，指向前一个节点。
- `level[]`：保存各层的前进指针和跨度。

![Redis 跳表节点](Z:/Public/images/Snipaste_2024-05-16_21-22-05_mianshiya.webp)

回退指针用于支持 `ZREVRANGE`、`ZREVRANGEBYSCORE`、`ZREVRANK` 等反向操作。定位到起点后，沿底层 `backward` 指针反向遍历即可；该指针只存在于 level 0，无需每层都维护。

### 随机层级算法

Redis 7.0 的跳表最大 32 层，节点升层概率为 0.25：

```c
#define ZSKIPLIST_MAXLEVEL 32
#define ZSKIPLIST_P 0.25

int zslRandomLevel(void) {
    static const int threshold = ZSKIPLIST_P * RAND_MAX;
    int level = 1;
    while (random() < threshold)
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}
```

每次循环有 25% 概率增加一层、75% 概率停止，因此节点最终停留在第 `n` 层的概率为 `0.25^(n-1) × 0.75`：第 1 层约 75%，第 2 层约 18.75%，第 3 层约 4.6875%。

### 为什么使用跳表而不是红黑树

1. **实现简单**：跳表主要是链表和随机层级，红黑树需要旋转和重新着色。
2. **范围查询高效**：ZSet 经常进行排名区间查询，跳表定位后沿底层链表遍历即可。
3. **内存可控**：25% 的升层概率使每个节点平均约 1.33 层，平均指针数量低于红黑树。
4. **结构调整方便**：跳表通过概率维持整体平衡，不需要显式的平衡操作。

Redis 命令执行主要是单线程，因此并发锁并不是选择跳表的主要原因；跳表的简单实现、范围查询和可控内存才是核心考量。

## 面试官追问

### 提问：跳表的空间复杂度是多少？

空间复杂度为 $O(N)$。节点以 25% 概率升层，平均层数为 `1 / (1 - 0.25) = 1.33`，因此总指针数约为 `N × 1.33`，比普通链表多约 33% 的指针开销。

### 提问：最高层数为什么是 32 层？

32 层已足以覆盖实际数据规模。层数太多会增加每个节点的指针开销。Redis 5.0 之前曾使用 64 层，后来发现实际场景不需要这么高便调整为 32 层。

### 提问：为什么层级概率是 25% 而不是 50%？

这是空间和查询效率之间的折中。50% 会使索引过密，增加内存；25% 让平均每 4 个节点才有一个节点上升，仍能保持 $O(\log N)$ 查询，同时减少索引开销。

### 提问：插入和删除会导致索引层不平衡吗？

通常不会。节点层数由均匀随机函数决定，长期插入和删除后整体分布会趋近理论概率，因此跳表依靠概率实现平均平衡，不需要像红黑树一样通过旋转维护平衡。
