# 为什么 Redis 设计为单线程？6.0 版本为何引入多线程？

## 回答重点

Redis 早期采用单线程，主要因为瓶颈不在 CPU，而在**内存和网络 I/O**。单线程的优势是代码简单、没有锁竞争、没有线程上下文切换开销；配合 I/O 多路复用，单机也能达到 10 万级 QPS。

Redis 6.0 引入多线程，是因为高并发场景下网络 I/O 成为瓶颈。网络数据从内核复制到用户空间的过程会占用主线程，多线程可以分摊网络读写；命令执行仍由主线程串行完成，因此兼顾吞吐量与数据安全。

版本演进：

- **Redis 4.0 之前**：网络 I/O 和命令执行都在主线程。
- **Redis 4.0**：增加后台线程处理大 `key` 异步删除、AOF 刷盘等耗时任务。
- **Redis 6.0**：增加网络 I/O 多线程，命令执行仍由主线程完成。

## 扩展知识

### “单线程”具体指什么

这里的单线程主要指网络事件处理和 Redis 命令执行由一个主线程完成。Redis 仍然包含后台线程，例如：

1. `bio_close_file`：关闭大文件。
2. `bio_aof_fsync`：执行 AOF 持久化刷盘。
3. `bio_lazy_free`：Redis 4.0 引入，用于异步释放大 `key`。

### 为什么单线程反而更快

一条简单 GET 命令的 CPU 执行时间通常只有几微秒，而网络往返可能达到毫秒级，CPU 并不是主要瓶颈。多线程会引入额外成本：

1. 线程创建和销毁。
2. 上下文切换。
3. 访问共享数据时的锁竞争。
4. 更高的代码复杂度和调试成本。

因此 Redis 选择单线程命令执行配合 I/O 多路复用，和 Nginx 的设计思路类似。

### Redis 6.0 多线程的工作原理

Redis 6.0 的多线程只用于网络 I/O：

1. 主线程接收连接，并把待处理 socket 分配给 I/O 线程。
2. I/O 线程并行读取网络数据并解析命令。
3. 主线程串行执行所有命令。
4. 执行完成后，I/O 线程并行写回响应。

![Redis 6.0 多线程流程](Z:/Public/images/E3TP5i9Y_EQlflHEv1N_mianshiya.webp)

典型配置：

```bash
# redis.conf
io-threads 4
io-threads-do-reads yes
```

该功能默认关闭，通常建议在 4 核以上、网络 I/O 密集型场景中通过压测决定是否开启，吞吐量可能提升约一倍。

### 为什么命令执行不用多线程

命令执行本身通常只需几微秒，多线程收益有限，却需要为 Dict、ZSet 等数据结构增加锁，改造成本高，也会产生锁竞争。Redis 选择只并行处理网络 I/O，在提升吞吐量的同时保持命令串行执行。

### I/O 多路复用的同步等待

I/O 多路复用本质上仍是同步 I/O。`epoll_wait` 返回后，数据还需要从内核缓冲区复制到用户空间。并发连接很多时，单线程可能忙于处理这些复制操作，这正是 Redis 6.0 用 I/O 多线程分摊主线程压力的原因。

## 面试官追问

### 提问：开启多线程后 Redis 还是线程安全吗？

是的。多线程只处理网络 I/O，所有命令仍由主线程串行执行，数据结构不会被多个线程同时修改。

### 提问：`io-threads` 设置多少合适？

通常可参考 CPU 核心数，建议不超过 8 个，并结合压测调整。I/O 线程过多会产生调度和竞争开销；如果瓶颈是大 `key` 或复杂计算，增加 I/O 线程帮助不大。

### 提问：Redis 4.0 的 `UNLINK` 与 6.0 多线程有什么关系？

两者解决的问题不同。`UNLINK` 将大 `key` 的内存回收放到后台线程，避免 `DEL` 阻塞；6.0 多线程并行处理网络 I/O，提升连接并发能力，两者可以同时使用。

### 提问：Cluster 模式下使用多线程要注意什么？

Cluster 每个节点都是独立 Redis 实例，多线程配置互不影响。若机器核心数有限，I/O 线程可能与其他业务抢 CPU，建议专机部署或根据压测结果调整线程数。
