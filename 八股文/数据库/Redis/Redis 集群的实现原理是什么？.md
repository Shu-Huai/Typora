# Redis 集群的实现原理是什么？

## 回答重点

Redis Cluster 通过多个 Redis 实例分担内存和并发压力，核心是**哈希槽分片、Gossip 协议和去中心化架构**。

### 数据分片

Redis Cluster 将数据空间划分为 16384 个哈希槽，每个主节点负责其中一部分。写入 `key` 时，先用 CRC16 计算哈希值，再对 16384 取模得到槽编号，数据保存到负责该槽的节点。扩容时只需迁移部分槽位，不必重新计算全部数据。

### 节点通信

集群没有中心节点，各节点通过 Gossip 协议交换存活状态、负责槽位和拓扑信息。节点随机选择邻居传播状态，最终整个集群收敛到一致视图。

### 客户端定位数据

客户端可连接任意节点。若 `key` 不属于当前节点，当前节点返回 `MOVED` 和目标地址，客户端更新槽位缓存后直接访问目标节点。

## 扩展知识

### 为什么使用 16384 个槽

槽位信息用位图表示，16384 个槽只需 2 KB；65536 个槽则需要 8 KB。心跳包需要频繁携带槽位信息，16384 可以在通信开销与分片粒度之间折中。Redis 集群通常不会扩展到远超 1000 个节点，16384 个槽已经足够。

![槽位信息](Z:/Public/images/BcRJEuQs_image_mianshiya.webp)

### 哈希槽分片流程

1. 对 `key` 使用 CRC16 计算 16 位哈希值。
2. 对 16384 取模，得到槽编号。
3. 根据节点负责的槽区间定位目标节点。

例如三个主节点负责：Node1 为 0～5460，Node2 为 5461～10922，Node3 为 10923～16383。假设 `user:1001` 的 CRC16 结果为 12345，则槽为 `12345 % 16384 = 12345`，数据存储在 Node3。

![哈希槽分片](Z:/Public/images/38YpNUp2_image_mianshiya.webp)

### 跨节点请求

客户端连接 Node1 访问属于 Node3 的 `key` 时，Node1 返回 `MOVED`，客户端根据地址重连 Node3 并重新发送命令。槽迁移期间则可能收到临时的 `ASK` 重定向。

![MOVED 重定向](Z:/Public/images/U1hTi3Oi_image_mianshiya.webp)

### Gossip 协议

Gossip 像“八卦传播”：节点随机选择少量邻居交换信息，经过多轮后消息扩散到集群。可分为 Push、Pull 和 Push+Pull，Redis 使用混合思路。它去中心化、容错性好，但属于最终一致性，存在消息冗余和传播延迟。

## 面试官追问

### 提问：集群扩容的数据迁移会影响线上读写吗？

会有一定影响。迁移槽处于 `MIGRATING` 状态，访问正在迁移的 `key` 时，源节点返回 `ASK`，客户端临时到新节点读取。数据仍可读写，但可能多一次重定向。

### 提问：Redis Cluster 能保证强一致性吗？

不能。集群采用异步复制，主节点写成功后不必等待从节点确认，主节点刚写入就宕机时可能丢失数据。可以用 `WAIT` 等待副本确认，但会牺牲性能。

### 提问：Lua 脚本和 MGET 等多 `key` 操作还能使用吗？

可以，但相关 `key` 必须在同一个槽，否则会出现 `CROSSSLOT`。可使用 Hash Tag，例如 `{user}:1001` 和 `{user}:1002`，Redis 只对花括号内容计算哈希。

### 提问：16384 个槽会限制性能吗？

通常不会。CRC16 计算槽号和槽到节点的映射都是 $O(1)$；槽数量主要影响管理粒度和 Gossip 消息大小。节点过多会增加网络与 CPU 压力，集群规模通常建议控制在约 1000 个节点以内。
