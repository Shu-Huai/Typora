# Redis 数据过期后的删除策略是什么？

## 回答重点

Redis 通过**惰性删除 + 定期删除**共同处理过期 `key`。

- **惰性删除**：每次读写 `key` 前先检查是否过期，过期就删除并返回空。优点是不额外占用 CPU 扫描；缺点是过期后长期无人访问的 `key` 可能继续占用内存。
- **定期删除**：定时随机抽取设置了过期时间的 `key`，删除其中已过期的部分，但不会一次扫描全部 `key`，从而控制 CPU 开销。

两种策略互相补充：惰性删除可能漏清理，定期删除可能一次清理不完，组合使用才能兼顾性能与内存回收。

## 扩展知识

### 定期删除的具体流程

每轮定期删除大致按以下步骤执行：

1. 从设置了过期时间的 `key` 集合中随机抽取 20 个。
2. 删除其中已经过期的 `key`。
3. 如果过期比例超过 25%，说明过期 `key` 较多，继续抽取下一批。
4. 如果比例低于 25%，结束本轮。
5. 本轮有约 25 ms 的时间上限，超时立即结束，避免阻塞主线程过久。

![定期删除流程](Z:/Public/images/pRL4ISrf_AFUNxWg0g9_mianshiya.webp)

Redis 是单线程模型，定期删除运行时其他命令需要等待，因此必须同时控制抽样比例和执行时间。

### 内存淘汰策略

如果过期删除没有及时释放足够内存，达到 `maxmemory` 后，写入新数据会触发内存淘汰：

| 策略 | 作用范围 | 淘汰规则 |
| --- | --- | --- |
| `noeviction` | 不淘汰 | 直接报错，拒绝写入 |
| `allkeys-lru` | 所有 `key` | 最近最少使用的先淘汰 |
| `allkeys-lfu` | 所有 `key` | 使用频率最低的先淘汰 |
| `allkeys-random` | 所有 `key` | 随机淘汰 |
| `volatile-lru` | 有过期时间的 `key` | 最近最少使用的先淘汰 |
| `volatile-lfu` | 有过期时间的 `key` | 使用频率最低的先淘汰 |
| `volatile-random` | 有过期时间的 `key` | 随机淘汰 |
| `volatile-ttl` | 有过期时间的 `key` | 剩余 TTL 短的先淘汰 |

生产环境常用 `allkeys-lru` 和 `volatile-lru`。如果所有缓存数据都设置了过期时间，`volatile-lru` 可以避免误删未设置过期时间的重要数据。

### LRU 和 LFU 的区别

- **LRU** 看最近是否访问过，最久未访问的 `key` 优先淘汰。偶尔访问一次的冷 `key` 可能暂时被保留。
- **LFU** 看访问次数，访问频率低的 `key` 优先淘汰。Redis 4.0 引入 LFU，并通过访问次数衰减避免历史热点长期占用内存。

访问模式比较稳定时，LFU 通常能获得更高的缓存命中率。

### 过期时间相关命令

```redis
# 设置过期时间
EXPIRE key 60
PEXPIRE key 60000
EXPIREAT key 1735689600
PEXPIREAT key 1735689600000

# 设置值的同时指定过期时间
SET key value EX 60    # 推荐，原子操作
SETEX key 60 value

# 查看剩余时间
TTL key      # 秒；-1 表示永不过期，-2 表示 key 不存在
PTTL key     # 毫秒

# 移除过期时间
PERSIST key
```

### 过期 `key` 的存储结构

Redis 内部维护 `expires dict`，保存所有设置了过期时间的 `key`。字典的 `key` 指向实际 `key` 对象，`value` 是毫秒级 Unix 过期时间戳。惰性删除在访问前查询该字典，定期删除则从中随机抽样检查。

## 面试官追问

### 提问：主从复制时，从节点会自己删除过期 `key` 吗？

从节点不会主动删除，而是等待主节点同步 `DEL` 命令。Redis 3.2 之后，从节点读取已过期 `key` 会返回空，但 `key` 可能仍暂时存在内存中，直到主节点的删除命令同步过来。

### 提问：大量 `key` 同时过期会有什么问题？

会造成请求延迟抖动。定期删除发现过期比例较高时会继续清理，虽然有时间上限，但这段时间主线程无法处理其他命令。可以给 TTL 增加随机偏移，例如 `3600 + random(300)`，分散过期时间。

### 提问：AOF 重写时会处理过期 `key` 吗？

会。AOF 重写检查 `key` 是否过期，已过期的不会写入新 AOF；RDB 生成快照时也不会保存已过期的 `key`。这会顺便减小持久化文件体积。
