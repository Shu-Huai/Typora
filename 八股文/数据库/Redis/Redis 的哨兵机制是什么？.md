# Redis 的哨兵机制是什么？

## 回答重点

Redis Sentinel 是一套高可用监控系统，负责监控主从节点、执行自动故障转移，并通知客户端和从节点新的主节点地址。

它主要完成三件事：

1. **监控**：周期性向 Redis 节点发送 `PING`，检查存活状态。
2. **故障转移**：主节点故障时，从节点中选出一个升级为新主节点。
3. **通知**：通过配置查询和发布订阅通知客户端新主节点地址。

典型架构包含 3 个哨兵、1 个主节点和 2 个从节点。生产环境建议部署至少 3 个且为奇数个哨兵，便于投票并减少平票。

## 扩展知识

### 为什么需要哨兵

单纯主从复制只能实现读写分离，主节点宕机后不会自动切换，写请求会全部失败。哨兵可以在数秒内完成故障检测和主从切换，客户端自动连接新主节点，降低业务中断时间。

### 如何判断主节点故障

哨兵采用**主观下线**和**客观下线**两阶段判断。

#### 主观下线

每个哨兵定期向节点发送 `PING`。如果超过 `down-after-milliseconds` 仍未收到有效 `PONG`，该哨兵就认为节点主观下线。

![主观下线](Z:/Public/images/Eqx6tHT9_image_mianshiya.webp)

#### 客观下线

单个哨兵可能因网络抖动误判，因此会向其他哨兵询问状态。若同意下线的票数达到 `quorum`，则认定主节点客观下线并开始故障转移。3 个哨兵通常将 quorum 设为 2。

![客观下线](Z:/Public/images/lB8i9I6c_image_mianshiya.webp)

### 哨兵 Leader 选举

确定主节点客观下线后，需要选出一个哨兵主持故障转移：

1. 首个发现主观下线的哨兵成为候选者并先投自己。
2. 候选者向其他哨兵拉票。
3. 每个哨兵一轮只能投一票，通常先到先得。
4. 获得半数以上票数的候选者成为 Leader。

若同时有多个候选者导致平票，会等待随机时间后重新选举，因此哨兵数量应尽量设置为奇数。

### 新主节点如何选择

Leader 按以下优先级从从节点中选择新主节点：

1. `slave-priority` 越小优先级越高，值为 0 表示不参选。
2. 优先级相同时，复制偏移量 `offset` 越大表示数据越新。
3. offset 也相同时，选择 `run_id` 较小的节点。

![新主节点选择](Z:/Public/images/DJF6lnoS_B5hHyqjH5A_mianshiya.webp)

选定后，Leader 会向新主节点发送 `SLAVEOF NO ONE`，让其他从节点执行 `SLAVEOF 新主节点IP 端口`，并通过发布订阅通知客户端。

### 老主节点恢复后怎么办

老主节点恢复后，哨兵会将它配置为新主节点的从节点，让它重新同步数据，从而避免出现双主。

## 面试官追问

### 提问：哨兵为什么建议配置奇数个？配置 2 个可以吗？

不建议。两个哨兵需要至少两票才能判定故障；任意一个哨兵故障后，剩余节点无法完成客观下线和 Leader 选举。三个哨兵即使挂掉一个仍能正常投票。

### 提问：客户端如何知道主节点地址变化？

客户端可以先连接哨兵查询当前主节点，也可以订阅 Sentinel 的发布订阅频道。主从切换后，哨兵推送新地址，Jedis、Lettuce 等客户端库会自动更新连接并重连。

### 提问：哨兵能保证数据不丢吗？

不能完全保证。主从复制是异步的，主节点写成功后可能还未同步就宕机。可以使用 `min-slaves-to-write`、`min-slaves-max-lag` 限制副本数量和延迟，或用 `WAIT` 等待副本确认，但这些只能降低丢数据概率；需要强一致性时应选择更合适的存储方案。
