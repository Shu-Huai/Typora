# 对意见的回复

1. 对于测试用例中的 `username ∈ Users`，这里不符合 SOFL 形式化语言的语法。

   感谢您的指正。在此处，应该是 `username ∈ dom Users`。我们修改了测试用例，并修改了相应的表达式到 Java 语句的解析逻辑。

   我们将 `A ∈ B` 的解析保持不变，解析为 `B.contains(A)`。这将用于集合（set）的运算。

   对于 `A ↦ B ∈ C`，我们解析为 `C.entrySet().contains(pair(A, B))`，其中，`pair(A, B)` 是我们新增的一个静态方法，用于构造键值对：

   ```java
   public static Map.Entry<Object, Object> pair(Object k, Object v) {
       return new AbstractMap.SimpleEntry<>(k, v);
   }
   ```

   该方法已在表达式求值引擎（JEXL）中注册，并可在表达式中直接使用。

   我们在解析过程中做了必要的类型校验，确保 `C` 为 `Map<K, V>` 类型，并保证 `A` 与 `K`、`B` 与 `V` 类型一致。

   我们新增了对 `dom` 和 `ran` 的解析支持。其中，`dom` 表示映射中所有键的集合，`ran` 表示映射中所有值的集合。我们将 `dom M` 解析为 `M.keySet()`，并支持表达式如 `x ∈ dom M` 被转换为 `M.keySet().contains(x)`。`ran M` 被解析为 `M.values()`，并支持表达式如 `x ∈ ran M` 被转换为 `M.values().contains(x)`。

   这项修改将对系统的其他功能保持不变。

2. JEXL 执行引擎能否处理集合的运算（交、并）？

   感谢您的提问。JEXL 是Java 表达式求值的一个引擎，实现的功能是执行一个合法的 Java 表达式语句，对于不能写为一个表达式的复杂语句，需要自定义一个函数，并将该函数注册到 JEXL 执行引擎中。对于集合的交和并的操作，在 Java 的基础 API 中并没有对其的简单实现，我们需要自定义一个函数，例如

   ```java
   public static <T> Set<T> union(Set<T> a, Set<T> b) {
       Set<T> result = new HashSet<>(a);
       result.addAll(b);
       return result;
   }
   ```

   这实现了集合的并运算。

   因此，我们的程序能够处理诸如 `x ∈ A ∩ B`、`x ∈ dom A ∪ dom B` 等 SOFL 表达式。对于前一个表达式，我们将其转换为 `intersect(A, B).contains(x)`，对于后者，我们将其转换为 `union(A.keySet(), B.keySet()).contains(x)`，然后交由 JEXL 执行。

3. Process 没有输出。

    感谢您的宝贵意见。我们重新审视了 SOFL 语法规范中的 Process 部分。在 SOFL 中，每个 Process 可以存在一个或多个输出变量。在我们的项目中，涉及到对 Functional Scenario Path 的合法性的判断。该合法性有两个层面，第一，前一个 Functional Scenario 所属 Process 的输出和后一个 Functional Scenario  所属 Process 的输入应该能够连起来；第二，是根据用户初始化的变量的值和运行中的输入变量，运行时动态判断能否执行下去。另一方面，在 SOFL 中，data store 和一个 Process 的输出变量是不同的概念，应该被显式地区分开。例如，在我们的测试用例中，Login Process 中 success 应该是该 Process 的输出，而非作为 data store 处理。

    我们在之前的程序中错误地忽略了第一个层面的合法性，也错误地将data store 和输出变量混淆起来。在现在的改进版本中，我们添加了对 Process 的输出变量的解析和处理。并且，我们添加了对第一个层面的 Functional Scenario Path 的合法性判断的逻辑。

    具体而言，我们从一个 Process 块中解析提取出输出变量，并保存。在程序执行前，我们获取了 Functional Scenario Path 链路上每个 Functional Scenario 所属的 Process 的输出，并尝试校验这条链路上相邻两个 Functional Scenario 间，前一个 Functional Scenario 的输出变量是否至少有一个与后一个 Functional Scenario 的输入变量名称和类型匹配，以确保数据流的连接性，以此验证第一个层面的合法性。如果不满足，将会报错。

    同时，我们也重新设计了变量的初始化和赋值方式，并重构了部分代码，让它能够正确区分数据存储和输出，更准确地支持整个流程的执行逻辑。

    此外，我们在 GUI 上新增了一个区域，以表格的形式展示出程序执行期间，各个 Functional Scenario 的输出变量的值。

    经过修改后，我们的测试用例为：

    ```
    module PurchaseSystem
    type:
      User=string
      Response = "ok" | "not enough" | "password wrong"
    state
      Users: map User → string
      stock: map string → int
      cart: map string → int
    
    
    process Login(username: User, password: string)
    success: bool, res: Response
    pre username ∈ dom Users 
    post
      if password == Users[username] then
        success = true ∧ res = "ok"
      if password ≠ Users[username] then
        success = false ∧ res = "password wrong"
    end_process
    
    process AddToCart(success: bool, product_id: string, quantity: int) 
    res: Response, success: bool
    pre success = true ∧ product_id ∈ dom stock 
    post
      if stock[product_id] ≥ quantity then
        cart[product_id] = cart[product_id] + quantity ∧
        stock[product_id] = stock[product_id] - quantity ∧ 
        res = "ok"
      if stock[product_id] < quantity then
        cart = cart ∧ stock = stock ∧ 
        res = "not enough"
    end_process
    
    end_module
    ```

4. 你们这个程序能不能处理自定义的类型？

    感谢您的提问。我们的程序能够处理自定义类型。我们的程序除了能够处理 string、int、float、char、bool 等基本数据类型外，还支持处理 enum、map、set 和 tuple 复合类型。其中，enum 的输入格式形如 `"Ok" | "Invalid input" | "User not exist"`，map 的输入格式形如 `Users: map User → string`，set 类型形如 `Days: set of int`，而 tuple 类型形如 `Date: int * int * int`。此外，我们的程序支持自定义的类型，如我们定义一个类型 User 为： `User = string`，我们的程序能够正确识别并处理这样的类型定义。我们对此的实现方式是，通过在解析模块时统一收集这些类型定义，并在解析变量、参数和表达式时自动识别和替换为对应的真实类型结构。

    但需要注意的是，目前我们对自定义类型的处理仅支持前述的基本类型和复合类型，暂时不支持以 `composed of` 为开头的复杂类型。我们将在后续改进的版本中添加对此的支持。

5. 你们的程序不支持直接输入 Functional Scenario？

    感谢您的提问。是的，我们的程序不支持直接输入 Functional Scenario。我们的程序以一个简化的 SOFL specification 作为输入，从中提取到变量、Process、Functional Scenario（由 post 条件中的 if-then 表达式表示）等信息。随后，用户在运行时指定要执行的 Functional Scenario Path，例如 `Login_1,AddToCart_2`，程序会从解析出的 SOFLModule 中匹配并执行相应的 Functional Scenario。通过这样的设计，我们希望将“模块定义”和“路径执行”明确分离，有助于后期支持更复杂的验证任务，并且简化交互逻辑用户只需一次性输入模块内容，后续可以多次指定不同路径进行测试，无需重复输入。

    不过，我们理解直接以 `Login_1`、`AddToCart_2` 等 Functional Scenario 块作为输入，会带来更直观的交互体验。未来版本中我们会通过增加一个专门的 parser，并更新我们的 executor 逻辑，使其能够解析并处理这种输入。
