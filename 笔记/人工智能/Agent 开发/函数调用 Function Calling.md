# 函数调用 Function Calling

## 什么是 Function Calling

Function Calling，通常可翻译为**函数调用**。它的核心含义是：

[[大语言模型 LLM]] 在对话过程中，不只是输出普通文本，还可以输出一种**结构化的调用意图**，告诉外部程序：

- 要调用哪个函数
- 这个函数需要什么参数
- 参数的具体值是什么

这里要注意，**模型本身并不会真的执行函数**。真正执行函数的是你的后端程序、Agent 框架，或者某个工具运行环境。

也就是说，Function Calling 的本质不是“模型会运行代码”，而是“模型会按照约定的格式，表达它希望调用某个函数”。

例如，用户问：

> 帮我查一下北京今天的天气。

模型可能不会直接瞎猜天气，而是输出类似下面这样的结构：

```json
{
  "name": "get_weather",
  "arguments": {
    "city": "北京",
    "date": "today"
  }
}
```

然后你的程序看到这个结果后，才会：

1. 识别出模型要调用 `get_weather`
2. 解析参数 `city=北京`、`date=today`
3. 真正执行天气接口
4. 把执行结果再交还给模型
5. 模型根据工具结果生成最终回复

因此，Function Calling 可以理解为：

> **模型负责决定“调什么、怎么调”；外部系统负责真正执行。**

## 与[[工具调用 Tool Calling]] 的核心区别

最简单的理解方式是：

- **Function Calling 是更窄的概念**
- **Tool Calling 是更宽的概念**

可以记成：

> **Function Calling ⊂ Tool Calling**

也就是说，函数调用通常只是工具调用的一种具体实现形式。

### Function Calling 更强调“函数签名”

Function Calling 关注的是：

- 函数名是什么
- 参数 schema 是什么
- 参数类型是什么
- 模型该如何填参数

例如：

```json
{
  "name": "book_hotel",
  "arguments": {
    "city": "Shanghai",
    "check_in": "2026-04-10",
    "nights": 2
  }
}
```

这很像传统编程里的函数调用接口。

### Tool Calling 更强调“外部能力”

Tool Calling 关注的是：

- 模型当前需要什么能力
- 这个能力来自哪个外部系统
- 这个系统返回什么结果
- 模型如何在多个工具之间协调

因此，Tool Calling 不一定要求每个工具都长得像一个普通函数。它可能是：

- 一个搜索能力
- 一个代码执行环境
- 一个浏览器操作器
- 一个多轮工作流节点

所以，从工程视角上看，Tool Calling 更适合描述现代 Agent。

## 为什么现在更常说 Tool Calling

因为现在大家讨论的已经不只是“让模型调一个函数”，而是要让模型接入**一整套外部能力生态**。

在早期，Function Calling 这个说法很常见，因为那时大家主要在做：

- 给模型定义几个函数
- 让模型返回 JSON 参数
- 后端执行函数
- 再把结果喂回模型

这是一个比较典型的“函数接口式”用法。

但随着 Agent 体系发展，模型接入的能力越来越复杂，已经不只是几个本地函数，而可能是：

- web search
- file search
- code interpreter
- remote MCP
- computer use
- 邮件与日历系统
- 数据分析流水线

这时再只用 Function Calling 来描述，就显得太窄了。

所以现在更常见的理解是：

- **Function Calling**：一种具体的工具接入方式
- **Tool Calling**：一个更高层、更通用的总称

## 一个直观类比

可以用这个类比帮助理解：

### Function Calling 像什么？

像你在程序里定义了几个函数：

```python
def get_weather(city: str, date: str):
    pass

def search_order(order_id: str):
    pass
```

模型的任务就是根据用户问题，决定该调用哪个函数，并把参数补完整。

这很像“会读接口文档，然后自动组装请求参数”。

### Tool Calling 像什么？

像你给模型配了一个工具箱，里面有：

- 搜索工具
- 文件工具
- 日历工具
- 邮件工具
- 数据库工具
- 执行代码工具

模型要做的是：

- 判断现在该用哪个工具
- 决定工具使用顺序
- 根据上一步结果继续调用下一个工具
- 最后整合结果回复用户

这已经更像 Agent，而不只是一次简单的“函数调用”。

## 在工程里它们是怎么衔接的

虽然概念上不同，但在实际工程中，两者经常混着说，因为很多工具系统最终都会被包装成“函数签名”的样子。

也就是说，即使你从系统层面讲的是 Tool Calling，到了接口层，可能还是这样表示：

```json
{
  "name": "web_search",
  "arguments": {
    "query": "OpenAI Responses API"
  }
}
```

从外观看，它还是一个函数调用结构。

所以你会经常看到这样的现象：

- 文档里说的是 Tool Calling
- 实际传给模型的是函数定义 schema
- 模型输出的也是函数名 + 参数

这并不矛盾。

因为：

> **Tool 是能力抽象，Function 是接口表达。**

这是理解两者关系时非常重要的一点。

## 一个完整调用链示例

下面用一个最小闭环来说明。

用户说：

> 帮我查一下明天上海的天气，然后告诉我需不需要带伞。

### 第一步：模型理解任务

模型判断：需要先查天气，再根据天气结果进行语言生成。

### 第二步：模型输出工具调用意图

```json
{
  "name": "get_weather",
  "arguments": {
    "city": "上海",
    "date": "tomorrow"
  }
}
```

### 第三步：后端执行函数

后端程序真正请求天气服务，得到结果，例如：

```json
{
  "city": "上海",
  "date": "2026-04-07",
  "weather": "小雨",
  "temperature": "18~22C"
}
```

### 第四步：把工具结果喂回模型

模型拿到这个结果后，再生成最终回答：

> 明天上海有小雨，建议带伞，气温大约 18 到 22 度。

这个过程里：

- 从接口形式看，是 Function Calling
- 从系统能力看，是 Tool Calling
