# 大语言模型 LLM

## 什么是 LLM

LLM 是 Large Language Model，也就是大语言模型。简单说，它是一类用海量文本训练出来的神经网络模型。它在生成时做的事很朴素：根据已有上下文，预测下一个最可能出现的 token。

这里的 token 不是严格意义上的“字”或“单词”，而是模型内部使用的文本单位。一个汉字可能是一个 token，一个英文单词也可能被拆成几个 token。

如果只看这个目标，LLM 像是在做“语言接龙”。但当模型规模、数据规模和训练方法都上来以后，它会表现出摘要、问答、翻译、写作、代码生成、信息抽取、分类和推理等能力。这些能力不是靠人工写规则堆出来的，而是从大量语言模式里学出来的。

从系统角度看，LLM 不是数据库，也不是搜索引擎，更不是传统专家系统。它更像一个参数化的语言建模器：训练时把语言结构、常见事实、任务形式和表达习惯压进参数里；推理时再根据上下文生成输出。

## 语言建模

LLM 的基础是语言建模。所谓语言建模，就是给定前面的内容，预测后面的内容。例如：

> 今天下雨了，我出门带了把

模型更可能接出“伞”，而不是“电脑”或“冰箱”。

很多 LLM 都是自回归模型。它每生成一个 token，就把这个 token 接到上下文后面，再继续预测下一个。于是生成不是一次性写完整段话，而是一个 token 一个 token 往外吐。

这也解释了为什么翻译、摘要、对话、代码补全这些看起来不同的任务，最后都能统一成一种形式：给模型一段上下文，让它继续生成符合要求的内容。

## LLM 的基本结构

现代主流 LLM 大多基于 Transformer。GPT、Llama、Qwen、Gemma、Mistral 这些模型名字不同，但核心结构大致相近。

### Tokenizer

Tokenizer 负责把原始文本切成 token，再把 token 映射成整数 id。模型并不直接处理自然语言字符串，它处理的是数字序列。

可以把 tokenizer 近似理解成两步：

1. 按词表和切分规则把文本拆成 token。
2. 把每个 token 转成对应的 id。

它不只是查表，前面还有一层“怎么切”的规则。常见方法包括 BPE、WordPiece、SentencePiece。不同模型的 tokenizer 不同，同一句话在不同模型里的 token 数和切分方式也可能不同，这会影响推理速度、上下文占用和训练效率。

### Embedding

Embedding 层把离散的 token id 变成连续向量。换句话说，它把符号变成神经网络能计算的表示。

从计算上看，embedding 很像查表。假设词表大小是 `V`，隐藏维度是 `d_model`，那 embedding 可以看作一个 `V × d_model` 的可训练矩阵。输入某个 token id 时，模型取出矩阵中对应的一行向量。

所以 embedding 不是 tokenizer 做的事，而是模型内部的一层参数。这个“表”也不是固定的，它会在训练中被更新。

还要注意：embedding 得到的是初始 token 向量。它有一定静态语义，但还没有融合当前句子的上下文。比如“苹果”在“我买了一个苹果”和“苹果发布了新手机”里，初始 embedding 可以相同；经过后续 Transformer 层后，才会变成不同的上下文表示。

### Transformer

[[Transformer]] 是现代 LLM 的主体。它最重要的机制是[[注意力机制]]，尤其是 Self-Attention。

Self-Attention 的直觉是：模型处理当前 token 时，不只看前一个 token，而是会参考上下文里的其他位置，并决定哪些位置更重要。

比如一段长文本里，某个词的含义可能依赖很远处出现的实体、时间、条件或限定语。Self-Attention 让模型能建立这种远距离关系。

相比 RNN、LSTM，Transformer 有两个明显优势：更适合并行计算，也更擅长处理长距离依赖。这也是它能扩展到大模型训练的原因之一。

更准确地说，Transformer 做的是把 embedding 给出的初始 token 向量，逐层加工成带上下文的 token 向量。真正的上下文语义不是 tokenizer 产生的，也不是 embedding 单独决定的，而是在 Transformer 的多层计算里形成的。

### 输出层

经过多层 Transformer 后，模型会得到当前位置的隐藏状态。输出层再把这个隐藏状态映射到整个词表上，得到“下一个 token 是什么”的概率分布。

如果用贪心策略，就选概率最高的 token；如果用采样策略，就按概率分布抽样，结果会更灵活，也更不稳定。

## 从文本到向量

从输入文本到模型内部表示，可以按这条链路理解：

```text
文本 -> tokenizer -> token 序列 -> token id 序列 -> embedding -> 初始向量序列 -> Transformer -> 上下文化后的隐藏向量 -> 输出概率分布
```

这里有两个点很容易混：

1. tokenizer 不生成语义向量，它只把自然语言编码成离散符号序列。
2. embedding 不是 encoder，它只是把 id 映射成初始向量；真正做上下文建模的是后面的 Transformer 层。

## 变长输入为什么能计算

很多人刚学时会疑惑：神经网络不是要做矩阵运算吗？那输入长度不是应该固定吗？

对传统全连接网络来说，这个直觉大体没错。但 Transformer 固定的不是整句话长度，而是每个 token 的表示维度。

假设隐藏维度是 `d_model`，一句话有 `L` 个 token，那么输入形状可以理解为：

```text
L × d_model
```

其中 `d_model` 固定，`L` 可以变化。

也就是说，模型处理的不是一个固定长度的整句向量，而是一个可变长度的 token 向量序列。

例如：

- “你好”如果被切成 2 个 token，输入形状可以看成 `2 × d_model`。
- 一段长文本有 100 个 token，输入形状就是 `100 × d_model`。

模型参数主要作用在每个 token 的特征维度上，不要求每次输入的 token 数完全一样。

## Attention 的直观理解

Attention 解决的问题是：当前这个位置，应该关注上下文里的哪些内容？

例如：

> 张三把书借给了李四，因为他下周要考试。

这里“他”指张三还是李四，要靠上下文判断。Attention 可以让模型在处理“他”这个位置时，参考前面相关的人物和语义线索，而不是只看相邻词。

抽象一点说，Attention 做的是上下文加权聚合：给不同位置分配不同权重，再把这些信息合起来更新当前表示。

LLM 不是简单按顺序背文本。它在每一层里都在重新组织上下文信息。

长文理解、指代消解、条件约束、跨句信息整合，都和 Attention 有很深的关系。

## Encoder、Decoder 与 Decoder-only

embedding 和 encoder 不是一回事。

- embedding：把 token id 变成初始向量。
- encoder / decoder：对这些向量做上下文建模的 Transformer 结构。

不同模型的后半部分组织方式不同。

### Encoder-only

例如 BERT。这类模型通常使用 encoder 结构，擅长分类、抽取、判别等理解类任务。

### Encoder-decoder

例如 T5。它先用 encoder 处理输入，再由 decoder 基于 encoder 输出生成结果，常用于翻译、摘要等 seq2seq 任务。

### Decoder-only

例如 GPT、Llama、Qwen。这类模型没有独立的 encoder 堆栈，而是用一系列 decoder blocks 做自回归建模。

“decoder-only”不是说模型没有 embedding。即使是 decoder-only 模型，输入也要先经过 embedding，再进入后续 Transformer blocks。

所以更通用的说法是：embedding 后经过 Transformer 主体，得到带上下文的隐藏向量。具体到 BERT，可以说经过 encoder；具体到 GPT/Qwen/Llama，更准确的是经过 decoder blocks。

## 模型为什么像是“知道”很多东西

LLM 看起来知道很多事实，但它内部不是一个结构化知识库。它是在预训练中看过大量文本，并把语言共现、事实关联和表达模式学进了参数。

比如训练语料里大量出现“北京是中国的首都”，模型遇到“北京是中国的”时，就很容易接出“首都”。

这种知识更像分布式参数知识，不像数据库里的显式条目。

这也带来两个结果：

1. 模型能回答很多常识和公开知识，因为这些内容在训练数据里反复出现。
2. 模型会幻觉，因为它不是在查事实，而是在生成最符合上下文模式的内容。

所以 LLM 的知识能力很强，但不天然可靠。只要任务对事实准确性要求高，就需要检索、工具调用或人工校验。

## LLM 的训练过程

### 预训练

预训练是最基础、也最耗资源的阶段。这个阶段使用海量通用文本，让模型学习语言规律、句法结构、事实共现、文本风格和常见任务形式。

最常见的训练目标是：给定前文，预测下一个 token。

预训练后的模型已经有通用语言能力，但不一定会像助手一样听指令。它更像一个语言能力很强、但交互方式还没对齐的基础模型。

### 指令微调

为了让模型更适合人机交互，通常会做指令微调。这个阶段会使用大量“指令-回答”形式的数据，让模型学习按用户要求输出结果，比如回答问题、写摘要、分类、改写文本、生成代码。

经过指令微调后，模型更像助手，而不是单纯续写文本。

### 对齐

产品里的模型只会回答还不够，还要尽量有帮助、安全、稳定。对齐训练通常用来减少有害输出，改善拒答策略，让模型更符合系统规则和人类偏好。

可以粗略记成：

- 预训练解决“会不会语言”。
- 指令微调解决“会不会按要求做任务”。
- 对齐解决“输出是否适合真实使用”。

## 推理阶段在做什么

训练完成后，实际使用就是推理。推理时模型参数不会更新，它只是根据输入上下文做前向计算，得到下一个 token 的概率分布，再按解码策略生成内容。

### Temperature

Temperature 控制随机性。

温度低时，模型更倾向输出高概率、保守、稳定的内容。温度高时，输出更发散，也更容易不稳定。

### Top-p

Top-p 是一种采样策略。它只在累计概率达到某个阈值的候选 token 集合里采样。

它和 temperature 都会影响输出的稳定性和多样性。

### Context Window

Context Window 是上下文窗口，指模型一次最多能处理多少 token。

它是容量上限，不是固定输入长度。“模型支持 32K 上下文”不是说你输入一句“你好”时，系统会把它补到 32K，而是说这次请求的输入和输出加起来不能超过这个上限。

### KV Cache

自回归生成时，前面 token 的中间结果可以缓存起来，后面生成时不必重复计算。这就是 KV Cache。

它直接影响推理速度，是大模型部署里很重要的一环。

## Padding 和上下文长度

上下文长度上限和 padding 不是一回事。

上下文长度上限是模型或推理系统允许的最大序列长度，表示一次请求最多容纳多少 token。

Padding 是为了让一个 batch 里的不同样本在张量维度上对齐。GPU 更擅长处理规则形状的张量，所以同一批样本长度不同时，常常会把短样本补齐到当前 batch 里最长样本的长度。

例如一个 batch 里三句话分别是 2、6、10 个 token，常见做法是都补到 10，而不是补到模型最大上下文长度。

所以，如果只输入一句很短的话，比如“你好”，正常推理一般不会自动补到 32K。只有在批处理对齐时才会发生 padding，而且通常只补到当前 batch 的最长长度。除非用户或系统明确要求补到固定最大长度。

## 为什么 LLM 有推理能力

LLM 的推理能力不是传统符号逻辑系统那种手写规则，而是在大规模语言训练里形成的。

很多推理任务可以转成模式识别、结构映射和语言步骤生成。数学解题、代码修复、因果分析这类任务，模型往往是在大量类似数据中学到了常见解法和表达路径。

但它有边界。LLM 很擅长生成“像推理一样”的语言过程，并且在很多任务上确实有用；但这不等于它天然具备稳定的形式逻辑能力。

复杂任务里常常要接入计算器、代码执行器、数据库、搜索系统，就是为了补上纯语言推理不稳定的地方。

## 参数规模为什么重要

LLM 里的 Large，主要体现在两个方面：参数规模大，训练数据规模大。

参数越多，模型通常越有容量学习复杂模式；数据越多，模型越容易覆盖更多知识和任务形式。

但规模不是唯一因素。模型效果还会受到这些影响：

- 数据质量。
- 训练策略。
- 架构设计。
- 上下文长度。
- 对齐方式。
- 推理部署优化。
- 工具接入能力。

实际应用里不是越大越好。有时一个中等规模、速度更快、成本更低、工具接入更顺的模型，比超大模型更适合业务系统。

## LLM 的局限性

### 幻觉

模型可能生成语法流畅、逻辑看起来也合理、但事实错误的内容。这不是偶发小 bug，而是生成式模型的内在风险。

### 事实时效性有限

如果模型没有联网能力或外部检索，它的知识范围通常受训练数据时间影响。

### 长任务稳定性不足

在很长的多步骤任务里，模型可能偏离目标、遗漏约束、重复输出，或者在中间步骤累积错误。

### 计算成本高

大模型推理需要大量显存和算力。高并发场景下，部署和服务成本会很现实。

## LLM、RAG、Agent 的关系

LLM 是推理核心，但真实应用通常还要外部系统帮它补能力。

### RAG

[[检索增强生成 RAG]]，Retrieval-Augmented Generation，检索增强生成。

它先从外部知识库检索相关内容，再把结果作为上下文交给模型生成答案。

RAG 主要解决三类问题：模型知识过时、私有知识缺失、事实可靠性不足。

### Agent

[[智能体 Agent]] 是带工具调用能力的 LLM 系统。

它不只是回答文本，还会根据任务目标决定是否调用搜索、数据库、浏览器、代码执行器、办公系统等外部工具，再根据工具结果继续决策。

可以粗略记成：

- LLM：负责生成和推理。
- RAG：负责查资料。
- Agent：负责调用工具做事。

很多现代 AI 应用里，LLM 不是终点，而是核心部件。检索、工具、工作流和权限控制，才决定它能不能真正落地。

## 常见误区

第一个误区：把 LLM 当数据库。

模型不是查表回答问题，而是根据参数化模式生成输出，所以不能保证事实始终准确。

第二个误区：以为 embedding 就等于理解了上下文。

embedding 只是初始向量。真正的上下文融合发生在后续 Transformer 层。

第三个误区：把上下文长度理解成固定输入长度。

上下文长度通常是上限，不是每次都要填满的固定尺寸。

第四个误区：认为 decoder-only 模型没有“编码”能力。

decoder-only 模型没有独立 encoder 堆栈，但它仍然会通过多层 Transformer blocks 对输入做上下文建模，所以可以完成理解任务。

第五个误区：认为 LLM 真正“理解”了世界。

从工程上说，更稳妥的说法是：它学到了很强的语言模式建模能力，并在很多任务上表现出接近理解的效果，但这不等于人类式认知。

第六个误区：认为 LLM 只适合聊天。

聊天只是最容易看到的一种交互形式。更重要的应用还包括文档处理、知识问答、代码辅助、流程自动化、数据抽取、搜索增强和 Agent 系统。
