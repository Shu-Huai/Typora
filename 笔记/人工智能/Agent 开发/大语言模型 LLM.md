# 大语言模型 LLM

## 什么是 LLM

LLM，Large Language Model，大语言模型。本质上，它是一类基于海量文本数据训练出来的神经网络模型，核心任务通常是：**根据已有上下文，预测下一个最可能出现的 token**。这里的 token 不是严格意义上的“字”或“单词”，而是模型内部定义的一种离散文本单位。一个汉字可能是一个 token，一个英文单词也可能被拆成多个 token。

如果只看这个训练目标，会觉得它很简单，似乎只是“语言接龙”。但当模型规模、数据规模和训练策略发展到足够大时，模型会逐渐表现出总结、问答、翻译、写作、代码生成、信息抽取、分类、推理等复杂能力。也就是说，LLM 的能力并不是来自某条手写规则，而是来自对海量语言模式的统计学习。

从系统角度看，LLM 不是数据库，也不是搜索引擎，更不是传统专家系统。它更像一个参数化的语言建模器：把语言中的结构、模式、事实共现关系和任务形式压缩进大量参数中，然后在推理时根据上下文动态生成输出。

## LLM 的核心思想：语言建模

LLM 最核心的思想就是**语言建模（Language Modeling）**。所谓语言建模，可以理解为：给定前面的内容，预测后面的内容。例如给模型一句话：

> 今天下雨了，我出门带了把

模型需要预测下一个 token 更可能是“伞”，而不是“电脑”或“冰箱”。

如果把这个过程不断重复，模型就可以一边读入上下文，一边持续生成新内容。因此，很多 LLM 都是**自回归模型（Autoregressive Model）**：每生成一个 token，就把它接到上下文后面，再继续预测下一个。

这套机制带来两个重要特点：

1. LLM 的生成本质上是**逐 token 生成**，不是一次性把整段话同时写出来。
2. LLM 的很多能力，本质上都可以看成“下一个 token 预测”在大规模训练下涌现出来的结果。

这也是为什么很多看起来完全不同的任务，例如翻译、摘要、对话、代码补全，最后都可以统一成一种形式：给模型一段上下文，让它继续生成符合要求的后续内容。

## LLM 的基本结构

现代主流 LLM 大多建立在 Transformer 架构之上。虽然不同模型名字很多，例如 GPT、Llama、Qwen、Gemma、Mistral 等，但核心结构思想大致相近。

### Tokenizer

Tokenizer 负责把原始文本切分成 token，并映射成整数 id。模型本身并不直接理解自然语言字符串，它只处理数字序列。

例如一句中文输入到模型前，先会被 tokenizer 转成一串 token id，后续所有计算都围绕这些 id 展开。

Tokenizer 可以近似理解为两步：

1. **按词表规则切分文本**
2. **把 token 映射成 id**

因此，tokenizer 不只是简单查表，它前面还有一层“如何切分”的规则。常见做法包括 BPE、WordPiece、SentencePiece 等。不同模型采用的分词方式不同，因此同一句话在不同模型中的 token 长度和切分方式也可能不同，这会进一步影响推理速度、上下文长度和训练效率。

### Embedding

Embedding 层把离散 token id 映射成连续向量。可以把它理解为“把符号变成可以参与神经网络计算的向量表示”。

从计算上看，embedding 本质上非常接近**查表**。假设词表大小为 `V`，隐藏维度为 `d_model`，那么 embedding 可以看成一个形状为 `V × d_model` 的可训练矩阵。输入某个 token id 时，模型本质上就是取出这个矩阵中对应的一行向量。

因此，embedding 不是 tokenizer 在做的事，而是**模型内部的参数层**在做的事。它和普通查表的区别在于：这个“表”不是固定不变的，而是训练过程中不断更新的参数表。

需要注意的是，embedding 得到的是**初始 token 向量**。它带有一定静态语义，但还没有真正融合当前句子的上下文信息。比如“苹果”这个 token，在“我买了一个苹果”和“苹果发布了新手机”这两句话里，初始 embedding 可以相同，但经过后续 Transformer 层后，会变成不同的上下文表示。

### Transformer

Transformer 是现代 LLM 的核心主体。它最关键的机制是 **Attention**，尤其是 **Self-Attention**。

Self-Attention 的直觉是：模型在处理当前 token 时，不是只看前一个 token，而是会动态参考上下文中其他位置的信息，并决定“应该重点关注谁”。

例如在一句长文本里，当前词的含义可能依赖前面很远处出现的实体、时间、条件或限定语。Self-Attention 使模型能够建立这种远距离依赖关系。

相比更早期的 RNN、LSTM，Transformer 的优势主要有两点：

1. 它更适合并行计算，因此更容易扩展到超大规模训练。
2. 它对长距离依赖的建模能力更强，更适合处理复杂长文本。

更准确地说，Transformer 主体做的事情是：把 embedding 给出的“初始 token 向量”，逐层变成“融合上下文后的 token 向量”。因此，真正的上下文语义不是在 tokenizer 阶段产生的，也不是在 embedding 阶段完全决定的，而是在 Transformer 的多层计算中逐渐形成的。

### 输出层

经过多层 Transformer 处理后，模型会得到当前位置的隐藏状态，再通过输出层映射到整个词表的概率分布，判断“下一个 token 最可能是什么”。

如果使用贪心策略，就选择概率最高的 token；如果使用采样策略，就按概率分布随机选择，从而产生更灵活的生成结果。

## Token 到向量：一条更完整的数据流

从输入文本到模型内部表示，可以把整个过程整理成下面这条链路：

**文本 → tokenizer → token 序列 → token id 序列 → embedding → 初始向量序列 → Transformer → 上下文化后的隐藏向量 → 输出概率分布**

这条链路里有两个容易混淆的点：

1. **tokenizer 不负责生成语义向量**。它只负责把自然语言编码成离散符号序列。
2. **embedding 不是 encoder**。embedding 只是把 id 映射成初始向量，真正负责上下文建模的是后面的 Transformer 层。

## 变长输入是怎么成立的

很多初学者会有一个直觉：既然神经网络要做矩阵运算，那么输入维度应该固定，句子长度也应该固定。这个直觉对于传统全连接网络是对的，但对于 Transformer 不完全成立。

Transformer 中固定的，不是“整句话的长度”，而是**每个 token 的表示维度**。假设隐藏维度是 `d_model`，一句话有 `L` 个 token，那么输入形状可以理解为：

**`L × d_model`**

这里：

- `d_model` 是固定的
- `L` 是可变的

也就是说，模型处理的不是“一个固定长度的整句向量”，而是“一个可变长度的 token 向量序列”。

例如：

- “你好”如果被切成 2 个 token，那么输入形状可以看成 `2 × d_model`
- 一段更长的文本如果有 100 个 token，那么输入形状就是 `100 × d_model`

这就是为什么句子长度可以变化，而模型仍然能计算。模型参数矩阵主要作用在每个 token 的特征维度上，而不是要求整段句子的 token 数必须固定。

## Attention 的直观理解

Attention 是 LLM 中最关键的技术思想之一。它解决的核心问题是：**当前这个位置，应该关注上下文中的哪些内容？**

例如句子：

> 张三把书借给了李四，因为他下周要考试。

这里“他”到底指张三还是李四，要结合上下文关系理解。Attention 可以让模型在处理“他”这个位置时，动态参考前面相关的人物和语义线索，而不是机械地只依赖邻近词。

从更抽象的角度说，Attention 做的是一种**上下文加权聚合**：模型会给不同位置分配不同权重，再把这些信息综合起来更新当前表示。

因此，LLM 并不是简单地按顺序背文本，而是在每一层都不断重组上下文信息。

很多后续能力，例如长文理解、指代消解、条件约束、跨句信息整合，本质上都与 Attention 机制密切相关。

## Encoder、Decoder 与 Decoder-only

“embedding”和“encoder”不是同一个东西。

- **embedding**：把 token id 变成初始向量
- **encoder / decoder**：对这些向量做上下文建模的 Transformer 结构

在不同模型架构中，后半部分的组织方式不同：

### Encoder-only

例如 BERT。这类模型通常使用 encoder 结构，擅长理解类任务，如分类、抽取、判别等。

### Encoder-decoder

例如 T5。这类模型先用 encoder 处理输入，再由 decoder 基于 encoder 输出生成结果，常见于翻译、摘要等 seq2seq 任务。

### Decoder-only

例如 GPT、Llama、Qwen。这类模型没有独立的 encoder 堆栈，而是直接使用一系列 decoder blocks 进行自回归建模。

这里“decoder-only”的意思是：**Transformer 主体只有 decoder 型结构**，不是说模型里没有 embedding。即使是 decoder-only 模型，输入仍然必须先经过 embedding，再进入后续的 Transformer blocks。

因此，更通用的说法不是“embedding 后经过 encoder”，而是：

**embedding 后经过 Transformer 主体，得到带上下文的隐藏向量。**

如果具体到 BERT，可以说“经过 encoder”；如果具体到 Qwen/GPT 这类模型，更准确的说法应该是“经过 decoder blocks”。

## 为什么模型“知道”很多东西

LLM 看起来像“知道”很多事实，其实原因并不是它在内部存了一个结构化知识库，而是因为它在预训练中看过大量文本，并在参数中学习到了语言共现规律、事实关联和表达模式。

例如，如果训练语料中大量出现“北京是中国的首都”，模型在遇到“北京是中国的”这段上下文时，就很容易预测下一个 token 是“首都”。

因此，模型的“知识”更多是一种**分布式参数知识**，不是传统数据库里的显式条目。

这也解释了两个现象：

1. 模型经常能回答很多常识和公开知识，因为这些知识在训练数据中大量出现。
2. 模型也可能出现“幻觉”，因为它不是在查事实，而是在生成最符合统计模式的内容。

所以，LLM 的知识能力很强，但并不天然可靠。只要任务对真实性要求高，就通常需要外部检索、工具调用或人工校验。

## LLM 的训练过程

### 预训练

预训练是 LLM 最基础、最耗资源的阶段。这个阶段通常使用海量通用文本，让模型学习语言规律、句法结构、事实共现、文本风格和一般世界知识。

最常见的训练目标是“给定前文，预测下一个 token”。

预训练后的模型已经具备通用语言能力，但它不一定会“像助手一样”听指令。它更像一个语言能力很强、但交互行为还不完全对齐的基础模型。

### 指令微调

为了让模型更适合人机交互，通常会进行指令微调。这个阶段会构造大量“指令—回答”形式的数据，让模型学会按照用户要求输出更合适的结果，例如回答问题、写摘要、做分类、改写文本、生成代码等。

经过指令微调后，模型的风格会更接近“助手”，而不是单纯地续写文本。

### 对齐

在实际产品里，仅仅“会回答”还不够，模型还需要更有帮助、更安全、更稳定。因此通常会继续做对齐训练。

对齐的目标不是让模型更懂知识，而是让它更符合人类偏好和系统要求，比如减少有害输出、避免不当回答、提升拒答策略和交互质量。

因此可以粗略理解为：

- 预训练解决“会不会语言”
- 指令微调解决“会不会听话做任务”
- 对齐解决“输出是否适合真实使用”

## 推理阶段在做什么

训练完成后，模型进入推理阶段，也就是实际使用阶段。推理时模型不会再更新参数，而是根据输入上下文执行前向计算，输出下一个 token 的概率分布，再按照某种解码策略生成结果。

这里有几个常见概念：

### Temperature

Temperature 用来控制输出随机性。

温度低时，模型更倾向输出高概率、保守、稳定的内容；温度高时，模型更容易产生多样化和发散性的回答。

### Top-p

Top-p 是一种采样策略，表示只在累计概率达到某个阈值的候选 token 集合中采样。

它和 temperature 一样，都会影响输出的创造性与稳定性。

### Context Window

Context Window 指上下文窗口，也就是模型一次能处理的最大 token 数。

上下文长度不是“每次输入都必须达到的固定长度”，而是**模型一次最多能处理多少 token 的上限**。它更像容量上限，而不是固定输入尺寸。

因此，“模型支持 32K 上下文”并不意味着你输入一句“你好”时，系统会自动把它补到 32K。真正的意思只是：这次请求中，输入和输出加起来不能超过这个上限。

### KV Cache

在自回归生成中，前面 token 的中间结果可以缓存起来，后续生成时不必重复计算，这就是 KV Cache 的基本思想。

它直接关系到推理速度，是大模型部署中非常关键的一环。

## Padding 与上下文长度的关系

很多人会把“上下文长度上限”和“padding”混为一谈，但它们不是一回事。

### 上下文长度上限

这是模型或推理系统允许的**最大序列长度**，表示一次请求最多容纳多少 token。

### Padding

Padding 是为了让一个 batch 里的不同样本在张量维度上对齐。因为 GPU 更擅长处理规则形状的张量，所以如果同一批样本长度不同，常常会把较短样本补齐到**当前 batch 中最长的样本长度**。

例如一个 batch 中三句话长度分别为 2、6、10 个 token，那么常见做法是都补到 10，而不是补到模型最大上下文长度。

因此，如果输入只有一句很短的话，例如“你好”，正常推理下通常不会自动补到 32K。只有在批处理对齐时才会发生 padding，而且一般只补到当前 batch 的最长样本；如果用户显式要求补到某个固定最大长度，才可能补到那个长度。

## 为什么 LLM 能表现出推理能力

LLM 的推理能力并不是像传统符号逻辑系统那样由明确规则写出来的，而是在大规模语言数据训练中逐步形成的。

很多推理任务，其实都能转化为模式识别、结构映射和语言步骤生成。例如数学解题、代码修复、因果分析，模型往往是通过学习大量类似形式的数据，掌握了某些推理模板。

但这种推理有明显边界。它在“语言化的推理表达”上很强，在“严格可验证逻辑”上未必稳定。

所以，LLM 的推理能力更适合这样理解：它擅长生成**像推理一样的语言过程**，并在很多任务上确实有效，但不意味着它天然具备完全可靠的形式逻辑能力。

这也是为什么在复杂任务中，常常要引入工具，例如计算器、代码执行器、数据库和搜索系统，来弥补纯语言推理的不稳定性。

## 参数规模为什么重要，但又不是全部

LLM 中的 “Large” 主要体现在两个维度：模型参数规模大、训练数据规模大。

参数越多，模型通常就有更强的表示能力和更高的容量去学习复杂模式；数据越多，模型通常就能覆盖更广泛的知识和任务形式。

但参数规模并不是唯一决定因素。模型效果还受到很多因素影响，例如：

- 数据质量
- 训练策略
- 架构设计
- 上下文长度
- 对齐方式
- 推理部署优化
- 工具接入能力

因此，真实应用里并不是“越大越好”。有时一个中等规模、推理更快、成本更低、工具接入更完善的模型，反而比超大模型更适合业务系统。

## LLM 的局限性

### 幻觉

模型可能生成语法流畅、逻辑看似合理、但事实错误的内容。这不是偶发 bug，而是语言生成模型的内在风险之一。

### 事实时效性有限

如果模型没有联网能力或外部知识检索，它的知识范围通常受训练数据时间截断影响。

### 长任务稳定性不足

在很长的多步骤任务中，模型可能偏离目标、遗漏约束、重复输出，或者在中间步骤累积误差。

### 计算成本高

大模型推理往往需要大量显存和算力，尤其在高并发场景下，部署和服务成本是现实问题。

## LLM、RAG、Agent 的关系

LLM 是核心推理模型，但真实应用通常需要额外系统来增强能力。

### RAG

RAG，检索增强生成。

先从外部知识库中检索相关内容，再把结果作为上下文喂给模型生成答案。

它解决的主要问题是：模型知识过时、私有知识缺失、事实可靠性不足。

### Agent

Agent 是带有工具调用能力的 LLM 系统。

它不只是回答文本，还会根据任务目标决定是否调用搜索、数据库、浏览器、代码执行器、办公系统等外部工具，再根据工具结果继续决策。

### 简单理解

可以把三者关系记成：

- **LLM：大脑**
- **RAG：查资料**
- **Agent：做事**

在很多现代 AI 应用中，LLM 本身已经不是终点，而是一个推理核心，外部工具和工作流系统才是让它真正落地的关键。

## 常见误区

一个常见误区是把 LLM 当数据库。

实际上，模型不是通过“查表”回答问题，而是通过参数化模式生成输出，因此不能保证事实始终准确。

另一个常见误区是认为 embedding 已经等于“模型理解了上下文”。  
实际上，embedding 只是初始向量，真正的上下文融合发生在后续 Transformer 层中。

还有一个误区是把“上下文长度”理解成“固定输入长度”。  
实际上，上下文长度通常表示上限，而不是每次都必须填满的固定尺寸。

另一个误区是认为 decoder-only 模型没有“编码”能力。  
更准确地说，decoder-only 模型没有独立的 encoder 堆栈，但它仍然会通过多层 Transformer blocks 对输入进行上下文建模，因此依然可以完成理解任务。

还有一个误区是认为 LLM 真正“理解”了世界。

从工程上看，更准确的说法是：它学会了非常强的语言模式建模能力，并在很多任务上表现出近似理解的效果，但这不等于它具有人类式认知。

还有一个误区是认为 LLM 只适合聊天。

实际上，聊天只是最容易看见的一种交互形式。真正更重要的应用包括文档处理、知识问答、代码辅助、流程自动化、数据抽取、搜索增强和 Agent 系统。
