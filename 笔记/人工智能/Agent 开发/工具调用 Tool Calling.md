# 工具调用 Tool Calling

## 是什么

工具调用，指的是：**让模型不仅能输出自然语言，还能输出一段结构化的“调用指令”，由你的程序或平台去真正执行外部能力，再把结果回传给模型继续完成任务。**

这句话里有三个关键词：

1. **结构化指令**

   模型不是随便说一句“我想查天气”，而是按约定格式返回工具名、参数、调用 ID 等信息。

2. **外部能力**

   工具可以是天气接口、数据库查询、文件检索、浏览器、代码执行器、日历系统、邮箱系统，甚至是一整个远程 MCP 服务器。

3. **继续完成任务**

   工具调用不是终点，而是中间步骤。模型拿到工具结果后，通常还要继续推理、继续组织语言，最后才给用户答案。

所以，工具调用的本质不是“让模型自己执行函数”，而是：

> **模型负责决策，系统负责执行。**

这也是现代 Agent 系统的最小动作单元。没有工具调用，模型只能“说得像会做事”；有了工具调用，模型才开始“真的能做事”。

## 为什么工具调用这么重要

如果没有工具调用，LLM 的能力上限主要受限于训练数据和上下文。它只能依靠“已有知识 + 当前输入”去生成答案，因此会遇到三个硬问题：

### 它拿不到实时信息

比如天气、股价、新闻、订单状态、数据库中的业务数据。

这些东西不在模型参数里，也不能靠“猜”来解决。

### 它不能直接影响外部世界

比如发邮件、创建日程、修改文档、执行 SQL、调用支付接口、控制浏览器、启动一个工作流。

如果不能调用工具，模型最多只能告诉你“应该怎么做”，而不能真的替你做。

### 它无法把复杂任务拆成“思考 + 执行”闭环

真实任务往往不是一句话能完成的，而是：

- 先判断需要哪些信息
- 再去调用外部能力
- 再根据结果继续判断
- 最后给出答案或执行动作

这正是工具调用存在的原因。

所以你可以把工具调用理解成大模型应用中的第一条分水岭：

- **没有工具调用**：是一个会说话的模型
- **有工具调用**：开始变成一个能干活的系统

## 工具调用和普通 Prompt 的区别

初学者很容易误会，以为工具调用只是“把函数说明写到 prompt 里”。这不准确。

Prompt 的作用是告诉模型：

- 用户要什么
- 你该怎么回答
- 你的风格和限制是什么

而工具调用机制告诉模型：

- 你现在**可以使用哪些外部能力**
- 每个能力叫什么
- 什么时候该用
- 需要哪些参数
- 参数格式长什么样

也就是说：

> **Prompt 是任务说明，Tools 是能力清单。**

两者会共同影响模型行为，但不属于同一层。

从工程角度看，Prompt 通常是消息内容的一部分，而工具定义通常是请求体中的单独字段，比如 `tools`。所以它不是简单的自然语言描述，而是**带有 schema 的结构化配置**。

## 工具定义到底是什么

一个“工具定义”本质上是在告诉模型：

> 这里有一个可以被调用的能力，请按这个名字和这个参数结构来使用它。

一个典型的工具定义通常包含以下几部分：

### 名称 `name`

这是模型调用时使用的唯一标识。名字应当短、清晰、可区分，避免模糊。

例如：

- `get_weather`
- `search_docs`
- `run_sql`
- `send_email`

名称不要写得太抽象，例如 `process_data`、`do_task` 这种就很差，因为模型很难知道到底什么时候该用它。

### 描述 `description`

这是工具定义里非常重要的一部分。它不仅说明“这是干什么的”，还应该说明“什么时候调用、什么时候不要调用”。

例如：

- 查询指定城市天气。仅在用户明确询问天气或气温时调用。
- 检索公司知识库中的文档。仅在问题需要依赖内部文档时调用。
- 向指定邮箱发送邮件。仅在用户明确要求发送邮件时调用。

描述写得越清楚，模型越容易做出正确决策。  
你可以把 `description` 理解成“半结构化提示语”。

### 参数模式 `parameters` / schema

这通常使用 JSON Schema 表达，用来定义：

- 参数有哪些
- 每个参数是什么类型
- 哪些是必填
- 枚举值有哪些
- 是否允许附加字段

例如：

- `city: string`
- `date: string`
- `limit: integer`
- `status: enum["paid","pending","failed"]`

这个 schema 是工具调用能否稳定落地的核心。因为模型生成参数时，必须以它为约束。

### 约束和边界

成熟的工具定义还应隐含或显式表达：

- 这个工具能做什么
- 不能做什么
- 在什么前置条件下才允许调用
- 失败时应该如何处理

真正稳定的系统，靠的不是“模型足够聪明”，而是“工具边界足够清楚”。

## 一个最小例子

假设你定义一个天气工具：

```json
{
  "type": "function",
  "name": "get_weather",
  "description": "查询指定城市天气。仅在用户明确询问天气时调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名"
      }
    },
    "required": ["city"],
    "additionalProperties": false
  }
}
```

用户问：

> 上海今天天气怎么样？

此时模型不会直接伪造天气，而是更理想地返回一个工具调用请求，例如：

```json
{
  "name": "get_weather",
  "arguments": {
    "city": "上海"
  }
}
```

然后你的后端程序去真正调用天气 API，拿到结果：

```json
{
  "city": "上海",
  "weather": "多云",
  "temperature": "24°C"
}
```

最后你再把这个结果传给模型，模型输出：

> 上海今天多云，气温 24°C。

这个例子里，工具调用完整地体现了四步：

1. 用户提出任务
2. 模型决定调用工具
3. 系统执行工具
4. 模型基于工具结果生成答案

这就是最小闭环。

## 模型真正输出的是什么

这是非常关键的一点。

### 6.1 模型输出的不是“工具执行结果”

模型不会真的去运行你的 Python 函数，也不会真的去访问你的数据库。它输出的是：

> **一条结构化的调用意图**

里面一般包含：

- 工具名
- 参数
- 调用 ID
- 有时还会带调用类型等附加字段

### 普通回答和工具调用，是两种不同输出形态

当模型认为“不需要工具”时，它直接返回普通文本答案。

当模型认为“需要工具”时，它返回的是一条工具调用请求。

所以后端必须先判断：

- 这是最终答案？
- 还是中间调用指令？

这就是工具调用系统和普通问答系统最大的工程差异之一。

### 参数常常是字符串，不一定是对象

很多接口里，`arguments` 实际上是 JSON 字符串，而不是已经解析好的对象。所以你在后端常常还要做一步：

- 取出字符串
- 解析 JSON
- 校验字段

这一步非常基础，但在工程里经常是 bug 来源。

## 工具调用为什么天然是一个循环

很多人第一次接触时，会下意识把它想成：

> 发一次请求，模型要么回答，要么调一次工具，结束。

但真实系统不是这样。

工具调用通常是一个 **loop**，原因有三个。

### 模型可能连续调用多个工具

例如用户问：

> 帮我查一下明天下午上海天气，如果不下雨就帮我安排一个去浦东的外出日程，并发邮件给我自己。

这个任务至少可能涉及：

- 查天气
- 创建日历事件
- 发邮件

模型不太可能一步到位输出最终答案，而更可能逐步调用多个工具。

### 一次工具调用的结果，可能触发下一次调用

例如先调用 `search_user` 得到用户 ID，再调用 `get_orders` 查询订单，再调用 `refund_order` 发起退款。后面的工具调用依赖前面的结果，这天然是循环结构。

### 最终答案通常在所有调用之后才生成

模型先调用工具拿到数据，最后再把数据整理成自然语言，或者形成最终动作确认。

所以从后端视角看，工具调用系统最核心的不是“调 API”，而是：

> **维护一个调用循环，直到模型不再请求工具为止。**

## 后端到底应该怎么写

这是工具调用真正落地的关键。

你后端的基本职责，不是“把用户消息转发给模型”，而是做一个最小运行时。这个运行时至少要负责五件事：

### 发送请求

把以下内容发给模型：

- 用户输入
- 历史上下文
- 系统指令
- 可用工具列表
- 工具选择策略
- 必要的模型参数

### 解析模型响应

判断当前返回的是：

- 普通文本答案
- 还是工具调用请求

如果是工具调用，还要进一步解析：

- 工具名
- 参数
- 调用 ID

### 执行工具

根据工具名路由到你的业务代码：

- Python 函数
- 内部服务
- 第三方 API
- 数据库查询
- 文件系统操作
- 浏览器自动化
- 远程 MCP 服务

### 回传工具结果

执行完成后，把结果作为下一轮输入的一部分再发给模型。此时模型才能基于新拿到的信息继续推理。

### 持续循环，直到结束

伪代码如下：

```python
while True:
    response = call_model(messages, tools=tools)

    if has_tool_calls(response):
        calls = extract_tool_calls(response)

        tool_outputs = []
        for call in calls:
            args = parse_json(call.arguments)
            validate_args(call.name, args)
            result = execute_tool(call.name, args)
            tool_outputs.append(build_tool_output(call, result))

        messages = append_tool_outputs(messages, response, tool_outputs)
        continue

    final_text = extract_text(response)
    return final_text
```

这个循环的本质就是：

> **模型负责决定下一步，系统负责让下一步真的发生。*

## 错误处理比“成功路径”更重要

在真实系统里，工具调用的主要难点不在 happy path，而在失败路径。

### 工具可能调用失败

例如：

- 外部 API 超时
- 数据库连接失败
- 文件不存在
- 用户没有权限
- 参数语义不完整
- 第三方接口限流

### 失败结果也应进入模型上下文

一个成熟系统不应该一失败就直接崩掉。

更合理的做法是把失败信息包装成结构化 tool result，再交给模型继续处理。

这样模型可以：

- 向用户解释失败原因
- 要求补充参数
- 尝试备用工具
- 给出人工处理建议

### 错误处理要分层

你至少应该区分：

- **参数错误**：模型参数生成不合法
- **执行错误**：工具本身失败
- **权限错误**：用户无权执行
- **资源错误**：文件、数据库、服务不可用
- **系统错误**：你的后端 bug 或运行时异常

错误分层清楚，后续排查和日志分析才不会混乱。

## 工具调用和结构化输出的关系

工具调用几乎总是建立在结构化输出之上。

因为工具调用至少要求模型能稳定产出：

- 工具名
- 参数对象
- 调用 ID

如果没有结构化输出能力，模型就只能靠自然语言“描述它想做什么”，而你的后端会很难稳定解析。

所以可以这样理解：

- **结构化输出** 是基础能力
- **工具调用** 是结构化输出在“外部能力协作”场景下的具体应用

## Tool Calling 输出机制

### 结论

在工具调用场景下，模型输出的内容本质上是**结构化内容**，至少参数这一层通常就是 **JSON**；API 层再把这些内容包装成标准响应对象，例如 `tool_calls`。

### 核心理解

#### 模型底层始终输出 token

LLM 本质上一直是在生成 token。
这些 token 可以组成：

- 普通自然语言
- JSON
- 其他结构化文本

所以从内容层看，说“模型输出的是 JSON”在工具调用场景下基本没问题。

#### 但完整 API 返回体不等于模型原样输出

例如你看到的：

```json
{
  "choices": [
    {
      "finish_reason": "tool_calls",
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_123",
            "type": "function",
            "function": {
              "name": "get_weather",
              "arguments": "{\"city\":\"上海\"}"
            }
          }
        ]
      }
    }
  ]
}
```

这里要区分两层：

- **模型内容层**：例如 `get_weather`、`{"city":"上海"}`
- **API 协议层**：例如 `choices`、`message`、`tool_calls`、`finish_reason`

所以更准确的说法是：

> 模型生成结构化内容，API 把这些内容包装成标准响应对象。

#### API 不是先拿自然语言再猜是不是工具调用

更接近真实情况的是：

1. 你在请求里传入 `tools`
2. 服务端允许这一轮生成走“工具调用”路径
3. 模型输出了可被识别为函数调用的结构化内容
4. API 据此把响应包装成 `tool_calls`

也就是说：

> 不是“自然语言后处理猜测”，而是“结构化输出后按协议包装”。

### 能确定的部分

根据公开资料，可以基本确定：

- 工具调用由 schema 定义
- `arguments` 通常是 JSON 编码参数
- 严格结构化输出时，生成阶段会受 schema 约束
- API 最终会把结果包装成 `tool_calls` 或普通消息

### 不能确定的部分

公开资料没有完整说明：

- 服务端更底层到底如何判定“这轮属于 tool call”
- 是否用了特殊 token、隐藏标记、专门通道或其他内部机制

所以最稳妥的说法是：

> 我们知道结果形态，但不知道全部内部实现细节。
