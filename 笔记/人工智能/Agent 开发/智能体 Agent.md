# 智能体 Agent

## Agent 不是一种模型，而是一种系统形态

在很多讨论里，“Agent” 这个词容易被误解成某个新模型、某个特定框架，或者某种带有神秘色彩的“更高级 AI”。更准确的理解是：**Agent 不是模型本体，而是一种由大语言模型驱动的任务执行系统形态**。模型负责理解目标、判断下一步、整合结果；系统则负责提供工具、维护状态、执行动作、设置边界，并在合适的时候停止。

如果只看一次普通的问答调用，系统往往是“输入一段文本，输出一段文本”。而到了 Agent 这里，系统的基本单元不再只是“生成回答”，而变成了“根据当前状态选择行动”。这个行动可能是直接回答用户，也可能是调用某个工具、读取某份文档、继续追问用户，甚至把任务转交给另一个专门的 Agent。也正因为如此，Agent 的关键不在于“会不会说”，而在于**能不能在一个循环中推进任务**。

从工程视角看，Agent 更接近这样一个公式：

> Agent = [[大语言模型 LLM]] + [[工具调用 Tool Calling]] + [[状态管理 State Management]] + Loop + Guardrails

这里的每个词都不是点缀，而是系统成立所必需的部分。没有工具，模型很难真正作用于外部世界；没有状态，系统很难完成多轮、多步任务；没有循环，模型就只能一次性输出；没有边界和护栏，系统就会在权限、可靠性和安全性上失控。

## Agent 与 Workflow 的真正区别

Agent 和 [[工作流 Workflow]] 经常被放在一起讲，因此最容易混淆。两者并不是互斥的概念，也不是简单的高低级关系，但它们的核心控制逻辑确实不同。

**Workflow** 的重点在于“预定义流程”。系统的主要路径由开发者事先编排好：先做什么，再做什么，哪些条件下进入哪条分支，在哪一步结束。模型虽然也可能参与其中，但通常只是某个节点上的能力组件，例如负责分类、抽取字段、生成摘要，而不是整个流程的决策中心。

**Agent** 的重点在于“运行时决策”。开发者只给系统目标、可用工具、状态结构和一些规则约束，至于下一步是检索、追问、调用哪个工具、是否继续循环，主要由模型根据当前上下文与状态在运行时决定。

可以把二者的差异压缩成一句话：

- Workflow 更像“我规定你怎么做”。
- Agent 更像“我告诉你目标，你在边界内自己决定怎么做”。

### 一个固定流程的例子：报销单入库

假设系统的目标是把用户上传的报销票据变成财务系统可入库的数据。一个典型 Workflow 可能是：先 OCR，后字段抽取，再做格式校验，如果缺字段就提示用户补充，最后写入数据库。这个过程中哪怕使用了 LLM，它也只是出现在“抽取字段”这样的节点上。主流程是事先写死的，因此这是 Workflow。

### 一个动态决策的例子：研究型问答

如果用户要求系统“研究一下当前多 Agent 技术栈的可行方案并给出建议”，一个 Agent 可能先判断问题需要最新资料，于是调用搜索工具；看到搜索结果后又觉得官方文档更可信，于是继续检索官方资料；如果发现定义存在歧义，又可能追加检索；最后才整合出答案。开发者在写代码时并不知道它一定会搜索几次，也不知道它会先看哪家资料。这种路径在运行时才被决定，因此它更接近 Agent。

### 为什么现实系统常常既像 Workflow 又像 Agent

现实系统很少纯粹地只属于其中一端。更常见的情况是：外层是 Workflow，内层某个节点使用 Agent；或者整体是 Agent，但仍然在一些高风险步骤上加入固定护栏。也就是说，很多生产系统实际上处在一个连续谱上：

1. 完全固定的 Workflow
2. 以 Workflow 为主，但局部有 Agent 决策
3. 以 Agent 为主，但外层有约束和强制节点
4. 自主性更强的多 Agent 编排系统

因此，区分二者最实用的方法不是看宣传名称，而是看这件事：**系统的下一步主要是谁决定的**。

## Agent 的最小闭环：不是“会聊天”，而是“会推进任务”

一个最小可用的 Agent，通常包含四个最关键的环节：**Tool Calling、[[结构化输出 Structured Output]]、State、Loop**。这四个环节拼起来，系统才具备多步执行能力。

### Tool Calling：从“说”到“做”

没有 Tool Calling，模型最多只能给建议。它可以说“你应该去查询天气”“你可以打开这个网页”“建议运行这个命令”，但系统本身并不会因此发生动作。只有当模型能明确输出“我要调用哪个工具、传什么参数”，系统才真正拥有执行能力。

在这个意义上，Tool Calling 的本质不是一个 API 小功能，而是 Agent 形态成立的转折点：模型开始从“内容生成器”变成“动作选择器”。

### 3.2 Structured Output：让系统可靠接管下一步

系统不能靠猜测来判断模型当前是在回答用户，还是要调用工具，还是准备结束任务。因此，模型输出必须被约束成一种机器可解析的结构。Structured Output 的作用就在这里：它为“下一步行动”提供了清晰协议。

一个典型结构可能包括：

- 当前输出类型，是 `tool_call`、`ask_user` 还是 `final_answer`
- 如果是工具调用，工具名是什么
- 参数是什么
- 如果是最终回答，返回文本是什么

在工程上，这一层非常关键。没有结构化协议，系统会退回到脆弱的字符串匹配和提示词猜测；一旦提示词变化、输出格式漂移或上下文噪声增大，整个流程就会迅速变得不可靠。

### 3.3 State：Agent 的运行时快照

Agent 通常不是一步就能完成任务。它需要记住当前目标、已经获得的信息、缺失的信息、工具返回结果、当前所在阶段、是否需要继续追问等。所有这些并不适合仅靠原始聊天记录去维持，因此工程上通常会维护一份显式的状态对象。

一个订票 Agent 的状态，可能包含出发地、目的地、日期、乘客姓名、座位偏好、候选车次、当前步骤、缺失字段列表等。一个研究型 Agent 的状态，则可能包含查询目标、检索到的文档片段、候选事实、冲突点、待验证事项等。

状态并不是“模型记忆”的神秘化表达，而是系统刻意维护的一份运行数据结构。它是 Agent 稳定运转的基础。

### 3.4 Loop：多步执行的发动机

Agent 和普通调用最根本的差异之一，就是它通常存在一个循环。伪代码看起来经常就是这样的：

```python
while state["status"] == "running":
    action = llm_decide(state)
    result = dispatch(action)
    state = update_state(state, result)
```

这个循环并不神秘，但它意味着系统不再是一锤子买卖。模型可以在多轮里逐步推进任务：先问问题，再查资料，再根据结果决定是否继续，直到到达停止条件。

因此，Agent 的核心不应理解为“有一个 while 循环”，而应理解为：**LLM 在循环中持续产出下一步动作，系统负责执行这些动作并把结果反馈回去。**

## 4. 聊天记录、状态、记忆：三者不是一回事

在 Agent 讨论里，“上下文”“状态”“记忆”很容易混为一谈，但它们在工程上承担的职责并不相同。

### 聊天记录

聊天记录是用户和系统之间的原始消息序列。它保留了自然语言交互的全部痕迹，但天然松散、冗长、格式不稳定，不适合直接作为所有控制逻辑的基础。

### 状态

状态是系统为了驱动任务而提炼出来的结构化数据。它不追求完整复现聊天，而追求“对当前任务有用”。订票系统里的 `departure_city`、`seat_type`、`missing_fields` 就属于状态；研究型系统里的 `retrieved_chunks`、`open_questions` 也属于状态。

### 记忆

记忆通常用于跨轮次、跨任务甚至跨会话保留信息，例如用户长期偏好、历史任务结果、可复用事实等。它不一定每轮都被完整展开到主上下文里，而更常见的做法是按需检索或摘要注入。

如果不区分这三者，系统很容易出现两类问题：一类是所有信息都堆在消息历史里，导致上下文臃肿且不可控；另一类是把所有长期信息都塞进当前状态，导致状态对象不断膨胀并难以维护。

## 5. Tool Calling 的工程含义：工具不是函数名，而是能力边界

很多初学者会把 Tool Calling 理解成“模型能调用一个 Python 函数”。这不算错，但过于表层。真正重要的是：**工具决定了 Agent 能作用到外部世界的边界**。

如果系统只给模型文本生成能力，那么它最多能生成代码、生成摘要、给出建议，却无法真正修改文件、运行测试、访问网络、写入数据库。只有当系统显式暴露了这些能力，并允许模型通过结构化方式触发它们，Agent 才真正具备外部执行能力。

因此，“这个 Agent 能做什么”并不是由 Agent 这个词天然决定的，而是由以下几层共同决定：

- 模型自身的文本能力
- 系统暴露给它的工具集合
- 工具所能触达的资源范围
- 权限与安全约束
- Prompt 中规定的职责边界

这也解释了一个很常见的误区：

> 某个天气 Agent 不能写代码，并不是因为 Agent 不能写代码，而是因为这个 Agent 在设计上没有被赋予相关职责与权限。

换句话说，**Agent 的边界是系统设计出来的，不是概念天然自带的。**

## 6. 一个 Agent 可以做一件事，也可以做很多事

是否应该把系统拆成多个专长 Agent，不是一个概念问题，而是一个架构选择问题。

一个单 Agent 完全可以同时处理天气查询、新闻摘要、日程提醒、邮件归纳，只要它拥有这些工具并能在 Prompt 中被清楚地约束。这样的系统更像一个“通用助理”。它的优点是入口统一、开发速度快、用户心智简单；缺点是 Prompt 会越来越长，工具越来越多，状态也越来越复杂，模型选错工具的概率随之上升。

相反，如果把系统拆成 Weather Agent、News Agent、Coding Agent，再由一个 Router 或 Supervisor 进行分发，那么每个子 Agent 的职责会更清晰，状态与 Prompt 也更轻量，但整套系统的编排复杂度会上升。

因此，是否拆分 Agent，通常取决于以下几件事：

- 能力差异是否很大
- 工具集合是否明显不同
- 状态结构是否可以共享
- 风险边界是否需要隔离
- 调试和评估是否要求按模块独立进行

在规模较小时，一个多功能单 Agent 往往就足够；在能力和职责开始显著分化后，再拆成多个专长 Agent 通常更合理。

## 7. Guardrails：没有护栏的 Agent 不具备生产价值

很多概述在讲 Agent 时会重点介绍模型、工具和循环，却忽视了 Guardrails。实际上，在生产系统里，护栏不是可选附属物，而是系统能否上线的关键因素之一。

所谓 Guardrails，包含的内容比“安全审查”更广。它至少包括：

- 参数校验
- 工具调用权限控制
- 最大步数限制
- 超时与重试策略
- 敏感操作前的人类确认
- 对失败结果的降级处理
- 对高风险输出的结构检查

例如，一个 Coding Agent 即使拥有写文件和执行命令的能力，也未必应该被允许直接提交代码；一个邮件 Agent 也不应在未确认的情况下自动群发；一个支付相关 Agent 更不应让模型随意决定金额与收款对象。Agent 的“自主”本质上必须始终被约束在一套系统边界之中。

因此，一个工程上成熟的 Agent，从来不是“只要 LLM 很强就能自发稳定工作”，而是“系统在尽量明确的边界内让模型自主”。

## 8. 单 Agent 的运行时：真正重要的是分发层

很多人第一次自己写 Agent，会直觉地写出一段 `while running` 的代码，然后在里面堆满：

```python
if tool == "weather":
    ...
elif tool == "news":
    ...
elif tool == "coding":
    ...
```

这种写法在最小 demo 里当然可以工作，但从工程角度看，它很快会变得难以维护。更合理的方式通常是使用“工具注册表”或“统一分发器”。

工具注册表的思想很简单：系统维护一张从工具名到工具实现的映射表。LLM 输出结构化动作后，运行时只负责按名字查表、校验参数、执行工具、记录结果，而不需要把所有工具逻辑写死在主循环中。

这种分层有两个好处。第一，它让主循环保持简洁，始终围绕“决策—分发—更新状态”展开。第二，它让工具的增加与修改不会直接污染运行时主逻辑。

也因此，单 Agent 运行时最重要的不是“有没有 while”，而是**有没有一个清晰的动作分发层**。

## 9. 多 Agent：不是很多模型闲聊，而是多角色协作系统

“多 Agent” 这个词很容易让人脑补成多个模型像人一样相互聊天。现实中的工程实现通常不是这样。更准确地说，多 Agent 系统是一个**由编排器、共享状态和多个角色 Agent 共同组成的协作结构**。

多 Agent 并不意味着每个 Agent 都是平等独立的，也不意味着它们一定直接彼此对话。更常见的模式包括以下几种。

### 9.1 Supervisor / Subagents

这是最常见的形式。系统中存在一个主控 Agent，它维护全局目标与主状态，并决定何时调用哪些子 Agent。子 Agent 往往更像“高智商工具”：它们接收一段局部任务和必要上下文，完成后把结果返回给主控 Agent，由后者继续决定下一步。

这种模式的好处在于全局控制集中，适合复杂任务拆分；代价是主控 Agent 往往会承担较重的状态管理与结果整合责任。

### 9.2 Handoff

在 handoff 模式里，当前 Agent 会把控制权交给另一个 Agent，而不仅仅是“代替自己调用一个工具”。例如，客服分诊 Agent 判断当前问题属于退款流程，于是把会话转交给 Refund Agent。之后的若干轮对话可能主要由 Refund Agent 接手。

这种模式更接近“前台转接到专业坐席”，而不是“后台调用一个能力模块”。

### 9.3 Router

Router 模式强调先判断任务属于哪个专业域，然后将请求分派给对应 Agent。它更像一个智能路由层。对于多领域系统，例如法律、医疗、代码、财经四类服务并存时，这种模式很常见。

### 9.4 并行 Fan-out / 汇总 Fan-in

当任务本身可以被并行拆解时，主 Agent 或编排器会将多个子任务同时派发给多个子 Agent，再把结果统一汇总。这在研究型、多源检索型系统里尤其常见。每个子 Agent 只需要处理局部上下文，减少主上下文拥堵；最终由主 Agent 负责综合、去重、冲突消解与组织答案。

### 多 Agent 之间到底传什么

多 Agent 交互时传递的通常不是“闲聊内容”，而是三类信息：

- 子任务说明
- 必要上下文
- 结构化结果

有的系统通过消息传递来完成交接，有的系统通过共享状态或图结构来协调。无论形式怎样变化，本质都在于：**谁决定把哪一段任务交给谁，以及交接时携带哪些信息**。

## 10. MCP：协议层，不是某个具体 Agent 框架

在近年的 Agent 生态中，MCP（Model Context Protocol）越来越频繁地出现。理解它时，一个非常重要的点是：**MCP 是协议层，不是应用层框架，更不是单独一种 Agent 实现方式。**

它解决的问题并不是“怎样写一个 Agent 的 Prompt”，而是“如何以标准化方式让模型或 Agent 访问外部能力与上下文”。MCP 的核心价值，在于把原本每家各自定义、彼此不兼容的工具接入方式、资源访问方式和上下文注入方式，抽象成统一协议。

在 MCP 的语境下，经常会看到几个核心名词：

- **Tools**：供模型调用的函数式能力
- **Resources**：可供模型读取的上下文资源，如文件、数据库模式、文档片段等
- **Prompts**：由服务器提供的模板化提示或工作流入口
- **Roots**：客户端向服务器暴露的根目录或可访问空间
- **Sampling**：服务器反过来请求客户端发起模型采样的机制

从系统分层看，MCP 更接近“连接器与协议层”。它让不同工具提供方、资源提供方、客户端和 Agent 运行时之间有了更统一的协商方式，但它并不替代 Agent 自身的状态管理、运行循环和业务逻辑。

## 11. LangChain、LangGraph、Coze：应放在不同层次理解

围绕 Agent 的生态里，最容易把框架、协议、平台和产品混成一团。比较稳妥的理解方式，是按层次去看。

### LangChain

LangChain 更偏向应用开发框架，聚焦模型调用、工具使用、链式组合、Agent 抽象和生态集成。很多开发者会从它接触到 Agent 的一些常见实现形式。

### LangGraph

LangGraph 更接近一个底层编排与状态执行框架。它强调图结构、长期运行、有状态执行、节点和边的组合。相比 LangChain 中更高层的抽象，LangGraph 更适合表达复杂编排，包括循环、分支、并行和多 Agent 协作。

### Coze

Coze 更偏平台与产品化形态。它把很多 Agent 开发中常见的要素，如插件、工作流、知识库、变量节点、触发器等，包装成更低代码或可视化的操作方式。它适合作为理解“Agent 产品如何搭起来”的观察窗口，但不等同于底层原理本身。

因此，这几个词应分别放在不同问题下理解：

- 如果讨论协议互通，重点是 MCP。
- 如果讨论图式编排和有状态执行，重点是 LangGraph。
- 如果讨论高层框架与集成生态，重点是 LangChain。
- 如果讨论产品化、低代码和平台形态，Coze 更具有代表性。

## 12. 一个 Agent 项目的代码目录应如何分层

Agent 项目最怕的不是功能不够，而是职责搅在一起。最常见的坏味道，是把 Prompt、工具实现、运行循环、状态更新、业务 API 调用全都写进同一个文件。项目一开始可能还能工作，但一旦工具变多、状态变复杂、评估需求出现，代码会迅速失控。

更合理的做法，是按“运行职责”而不是“页面功能”分层。通常可以分为以下几层：

### 12.1 入口层

入口层只负责让系统启动起来，例如 HTTP API、CLI 或定时任务入口。它不应承担 Agent 运行逻辑本体。

### 12.2 Agent 定义层

这一层描述“系统中有哪些角色”。例如 WeatherAgent、NewsAgent、CodingAgent、SupervisorAgent。这里主要定义职责、可用工具集合、Prompt 入口以及输出约束，而不直接写底层 API 调用细节。

### 12.3 Runtime 层

这一层是发动机。典型模块包括：

- `loop`：主循环
- `dispatcher`：动作分发
- `state`：状态结构与更新
- `guardrails`：校验、权限、步数、异常控制

这层的核心职责是运行，而不是业务实现。

### 12.4 Tools 层

这一层存放暴露给 Agent 的动作接口。工具应该尽量是边界明确的小能力，而不是毫无限制的“万能执行器”。

### 12.5 Services 层

Services 是对底层外部依赖的封装，例如天气 API、新闻 API、Git 服务、数据库服务。通常由 Tools 层去调用 Services 层，而不是让 Agent 直接接触底层依赖。

### 12.6 Storage 与 Observability

任何稍微真实一点的 Agent 项目，都需要持久化和可观测性。前者用来保存会话、状态、检查点；后者用来记录模型调用、工具执行、错误、步数和耗时。没有这两层，系统很难调试，也很难长期运行。

## 13. 一个最小 Agent 与一个多 Agent 项目在目录上会有什么不同

在单 Agent 场景下，目录可以很小：一个入口、一个 Agent 定义、一个运行时、若干工具和测试，通常就足够了。此时最重要的是保持主循环、状态与工具注册分离。

而到了多 Agent 场景，目录的变化通常体现在两个方面。第一，会出现多个 Agent 定义，以及一个 Router 或 Supervisor。第二，状态往往不再只是单一会话状态，而会多出子任务状态、汇总结果、任务图节点状态等。此时，如果没有把运行时和角色层分开，系统会很快陷入难以维护的耦合。

## 14. 为什么说后端“知道 Agent 做了什么”，但“不预先知道它下一步想做什么”

这是理解 Agent 运行机制时一个非常关键的判断。

后端并不是完全不知道 Agent 在干什么。相反，Agent 每一次真正采取的动作，都是后端在执行、记录并写回状态的：调用了哪个工具、传了什么参数、工具返回了什么、是否报错、当前步数是多少，这些后端都知道。

后端不知道的是：**在下一轮决策发生之前，模型到底会选择哪条路径。**

这意味着 Agent 的系统控制权是分层的：

- 模型负责在边界内做运行时决策
- 后端负责提供能力、执行动作、维护状态和实施约束

也正因为如此，一个设计得当的 Agent 系统既不是“模型全权负责”，也不是“后端全写死”。它是一种决策与执行分离、能力与边界共存的形态。

## 15. 常见误解与应避免的表达

围绕 Agent 的讨论里，有一些非常常见但不够准确的说法。系统性文档里最好主动避开。

### 误解一：Agent 就是会调用工具的聊天机器人

工具调用确实是 Agent 的关键要素，但仅有工具调用还不足以构成一个稳定的 Agent。没有显式状态、没有循环、没有停止条件、没有护栏的系统，通常只是一个能偶尔调用工具的对话接口，而不是可靠的任务执行系统。

### 误解二：多 Agent 一定更高级

多 Agent 是一种拆分复杂性的方式，不是天然更强的形态。它会引入新的问题：路由、上下文裁剪、结果整合、失败传播、调试难度和成本控制。很多任务单 Agent 就足够，多 Agent 只有在职责显著分化时才真正有价值。

### 误解三：Agent 的本质是 Prompt Engineering

Prompt 很重要，但 Agent 的难点并不只在 Prompt。真正让系统落地的，往往是状态建模、工具设计、运行时分发、权限控制、失败恢复与评估体系。

### 误解四：MCP 会替代 Agent 框架

MCP 解决的是协议与接入层的问题，而不是整个 Agent 运行时的问题。它可以让工具与资源接入更标准，但不会自动替你完成状态管理、任务循环、子 Agent 协作或业务级流程设计。

### 误解五：一个 Agent 应该绝对单一职责，否则就不专业

职责清晰很重要，但这并不等于一个 Agent 只能做一种事。一个 Agent 能否承载多种任务，取决于任务相似度、工具重叠度、状态结构以及风险边界。是否拆分，应该是架构决策，而不是教条约束。

## 16. 结语：Agent 应被理解为“运行中的系统”，而不是“会说话的角色”

如果只把 Agent 看成某种更聪明的聊天模型，很容易陷入一种表面理解：仿佛只要 Prompt 写得足够像“助理”，系统就会自然出现稳定的任务执行能力。事实恰恰相反。真正决定 Agent 上限的，往往不是它说得多像，而是它的运行机制设计得是否清晰：动作如何表达、工具如何暴露、状态如何维护、边界如何设定、失败如何处理、角色如何协作。

因此，理解 Agent 最好的方式，不是把它神秘化成某种会“自主思考”的存在，而是把它放回软件系统的语境中：它是一个由语言模型驱动、借助工具与状态推进任务、并被运行时与护栏约束的执行系统。

只有在这个层面上，Workflow、Tool Calling、Structured Output、State、Multi-Agent、MCP、LangGraph、平台型工具等一整套概念，才会真正串成同一张图。
