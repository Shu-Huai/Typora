# 工作流 Workflow

在 LLM / Agent 开发语境里，**Workflow（工作流）** 不是“画一个流程图”这么简单，也不是“把几个工具串起来”这么简单。它更准确的含义是：

> **把一个任务拆成若干可执行步骤，并明确这些步骤的执行顺序、分支条件、输入输出和状态流转的一套运行逻辑。**

## Workflow 到底是什么

### 一个直接定义

<img src="http://public.file.lvshuhuai.cn/images\agent_workflow.png" alt="Agent Workflow" style="zoom:20%;" />

在 Agent 工程里，Workflow 可以理解为一层**任务编排层**。它并不直接回答“模型会不会说话”“OCR 能不能识别”“某个工具能不能调”，而是回答另一组更工程化的问题：先做什么，再做什么；在哪些条件下切换路径；失败时如何回退；整个任务在什么条件下结束。

所以，Workflow 的重点从来不是某一个节点本身有多强，而是**这些节点如何被组织成一条可执行、可恢复、可治理的流程**。你可以把它看成一个有状态的执行图：输入进入系统后，不是直接扔给一个巨大[[提示词 Prompt]]，而是按照预先设计好的步骤流动。

### 一个更工程化的理解

如果进一步抽象，Workflow 可以理解成：

> **State Machine（状态机） + Task Orchestration（任务编排） + Optional LLM Nodes（可选的 LLM 节点）**

这个表达很有用，因为它提醒我们：Workflow 的核心并不在于“用了[[大语言模型 LLM]]”，而在于“有没有明确的状态、步骤和流转关系”。LLM 在这个体系里通常只是某些节点的实现方式，有时负责分类，有时负责生成，有时负责选择工具，但它并不等于 Workflow 本身。

## 为什么需要 Workflow

如果没有 Workflow，很多 LLM 应用最终会退化成一句很长的大 prompt：让模型同时负责理解意图、补全缺失字段、调用工具、查资料、组织答案，最后再给出结果。这样做在 demo 阶段往往还能工作，但一旦进入真实业务，就会暴露出大量问题。

首先是**不可控**。模型可能跳步、漏步，也可能把本来应该先校验的事情放到后面。其次是**不可观测**。当结果错了时，你往往很难判断到底是意图识别错了、检索错了、工具参数错了，还是最后生成错了。再往后就是**不可恢复**和**不可治理**：任务中途失败时很难接着执行，权限校验、人工审批、日志审计也很难优雅地插进去。

Workflow 的价值，就在于把这些隐式过程显式化。它把不稳定的模型能力包进一个相对稳定的流程壳里，让“推理”和“执行”之间有清晰边界，也让系统具备追踪、重试、回退和审计的基础。

## Workflow 的核心组成

一个完整的 Workflow，通常离不开几个核心构件：状态、节点、路由、入口与结束条件，以及错误路径。它们不是彼此独立的小知识点，而是共同决定一条流程能否稳定运行的骨架。

### State（状态）

<img src="http://public.file.lvshuhuai.cn/images\context-window.png" alt="Conversation state | OpenAI API" style="zoom: 40%;" />

状态表示“当前任务做到哪里了”。例如在订票系统里，状态里可能既有已经拿到的信息，也有仍然缺失的字段，还可能保存上一步工具调用结果和最终待返回的答案。

```json
{
  "intent": "book_train",
  "date": "tomorrow",
  "destination": "Shanghai",
  "passenger_name": null,
  "missing_fields": ["passenger_name"],
  "tool_result": null,
  "final_answer": null
}
```

要特别注意，状态不是“模型记忆”，而是**系统显式维护的数据结构**。它的意义在于，系统可以随时知道当前掌握了什么、还缺什么、正在处于哪一阶段，以及前一步执行后留下了什么结果。没有显式状态，很多流程看上去能跑，实际上却很难恢复、很难调试。

### Node（节点）

节点是执行单元。一个节点可以是普通代码，也可以是 LLM 调用、数据库查询、OCR、Web Search、API 请求，甚至是一个需要人工确认的步骤。

理解节点时，最重要的是抓住一句话：**节点负责做事**。它应该有明确职责，而不是在一个节点里把分类、检索、生成、写库全部揉在一起。节点越清晰，整个 Workflow 越容易维护和复用。

### Edge / Router（边 / 路由）

如果说节点是“做事的人”，那边或者路由就是“决定下一步去哪里”的规则。它决定流程在不同条件下如何跳转，例如信息不完整时去追问用户，OCR 失败时切到多模态模型，或者任务已经完成时直接结束。

所以，理解 Workflow 的一个关键是：**节点做事，边决定路径**。只看节点而不看路由，看到的只是一些能力模块；把节点和路由一起看，才会看到真正的工作流。

### Entry / Exit（入口 / 结束条件）

任何 Workflow 都必须知道自己从哪里开始，又在什么条件下停止。入口常常是“收到用户请求”，也可能是“定时任务触发”或“外部系统发来事件”；结束条件则可能是“已经生成最终答案”“已经完成写库”“任务失败并返回错误说明”。

入口和结束条件看起来简单，但它们其实界定了流程的边界。边界不清，整个系统就容易变成一条一直追加逻辑、不断膨胀的长链条。

### Error Path / Fallback（错误路径 / 回退）

真实系统不能只写主流程，还必须写失败分支。OCR 可能识别失败，工具可能超时，支付请求可能报错，某些高风险动作可能还需要人工审批后才能继续。

因此，Workflow 设计里很重要的一点是：不要只思考 happy path，而要把异常路径也当成一等公民。很多系统在演示时看起来流程完整，真正上线后却问题频出，常常不是主流程设计错了，而是根本没有为异常情况留出结构化出口。

## 最初的理解

我们对话里最初形成的那个理解，其实已经非常接近一个标准 Workflow 了。它大致是这样的：用户输入文本，系统自动补当前时间；如果用户选择搜索，就调用搜索服务；如果用户上传了图片，先调用 OCR；如果 OCR 无法识别，就切到多模态 LLM；如果用户选择“深度思考”，就切换到支持 thinking 的模型，否则走普通模型。

这个理解之所以成立，是因为它已经具备了 Workflow 的几个关键特征。流程里不仅有输入预处理，还有条件判断、模型选择、工具选择、异常回退，以及最终输出。换句话说，它不是“调用几个东西”这么简单，而是**根据输入特征和运行状态，把请求路由到不同工具、不同模型和不同处理路径上的整套编排逻辑**。

所以，更准确的表述不是“Workflow 就是 if-else”，而是：Workflow 常常通过条件判断来决定路径，但它本质上是一套围绕状态和执行步骤展开的编排机制。

## Workflow 和 Tool Calling 的关系

这是最容易混淆的地方。

<img src="http://public.file.lvshuhuai.cn/images\function-calling-diagram-steps.png" alt="Function calling | OpenAI API" style="zoom: 20%;" />

### Tool Calling 是什么

[[工具调用 Tool Calling]] 关注的是：**模型如何调用一个工具**。它通常关心的是调用哪个工具、传什么参数、工具返回什么结果、这些结果又如何重新进入模型上下文。

因此，Tool Calling 更像一个局部动作机制。它描述的是某个节点内部如何完成一次工具调用闭环，而不是整个任务从开始到结束如何运行。

### Workflow 是什么

Workflow 关心的则是更大的问题：整个任务按什么顺序推进，哪些条件下分支，状态如何更新，失败时如何回退，最后什么时候结束。

所以，Workflow 更像一个全局编排结构。它不只包含 Tool Calling，也可能包含普通代码节点、条件判断节点、检索节点、人工审批节点，以及最终输出节点。Tool Calling 在这里通常只是其中一种节点能力。

### 两者不是“高级 / 低级”的关系

很多人会天然觉得，Tool Calling 由 LLM 自动发起，看起来更“智能”；Workflow 由开发者手工编排，看起来更“确定”。但这不是“高级 / 低级”的关系，而是两个不同维度的问题。

从抽象层级上看，**Tool Calling 更原子、更局部**，而 **Workflow 更宏观、更上层**。从决策主体上看，Tool Calling 往往是模型在给定边界内做局部选择，而 Workflow 往往是开发者先定义整条执行路径。

所以最稳妥的理解是：**Tool Calling 是 Workflow 里的一个节点能力**。一个系统可以在宏观上由 Workflow 编排，在局部某些节点里再让模型自主决定是否调用工具、调用哪个工具。这也是现代 Agent 系统里非常常见的模式。

## Workflow 系统的三种形态

从工程实现角度看，Workflow 系统通常有三种常见形态：代码式 workflow、可视化 workflow，以及混合式 workflow。它们面对的是同一类问题，都是在组织状态、步骤、分支和工具调用；不同之处在于，流程主要是写在代码里，还是画在画布上，或者由两者共同完成。

### 代码式 workflow

代码式 workflow 的核心特点，是开发者直接用代码来定义状态、节点、边和分支逻辑。这类系统最适合复杂业务、强定制需求、长生命周期系统，以及那些对恢复能力、日志、审计和可观测性要求较高的场景。

以 **LangGraph** 为例，它把 workflow 抽象成 graph，核心对象就是 **State、Nodes、Edges**。State 表示共享状态快照，Node 是执行逻辑单元，Edge 决定下一步跳转路径。LangGraph 还提供 Graph API 和 Functional API 两种组织方式，前者更适合显式建模执行图，后者更接近把流程写成函数。

代码式 workflow 的真正优势，不只是“能写得更复杂”，而是它能自然承接工程系统里那些迟早会出现的需求，例如循环、并行、子图、持久化恢复、流式输出、人工介入，以及细粒度测试。只要系统变得足够重要，代码式 workflow 往往就是最终会落到的形态。

### 可视化 workflow

可视化 workflow 的核心特点，是开发者通过画布、节点和连线来描述流程。它更强调低门槛、快速搭建和业务可见性，因此非常适合原型验证、中小型自动化流程，以及需要产品、运营、工程共同参与讨论的场景。

在这类系统里，workflow 往往直接表现成一张可执行流程图：节点可以是模型调用、知识检索、条件判断、代码执行、HTTP 请求或变量更新；连线则表示数据和控制流的传递。和代码式 workflow 相比，它最大的优势不在于抽象能力更强，而在于**概念更容易被看到**。

几个常见的可视化 workflow 工具可以作为代表。**FastGPT** 偏向知识库问答、AI 应用和工作流搭建，适合做问答路由、RAG、变量更新和条件分支。**Coze** 更偏应用平台，强调把插件、LLM、代码块组合成业务流程。**Dify** 提供 Workflow 和 Chatflow 两类应用形态，便于直接把流程做成可调用的应用。**Flowise** 则明确面向 AI Agents 和 LLM workflows，并引入了 Flow State 之类的概念，适合更复杂的多节点流程。

<img src="http://public.file.lvshuhuai.cn/images\flow-intro1.png" alt="img" style="zoom:50%;" />

不过，可视化 workflow 并不意味着“只是拖拖拽拽”。当流程稍微复杂起来，节点命名、变量传递、分支控制、异常处理和复用结构仍然是工程问题。它只是把这些问题放到了一个更可视、也更适合快速迭代的环境里。

### 混合式 workflow

混合式 workflow 指的是：外层流程由开发者显式编排，而内层某些节点再交给代码、Agent 或 Tool Calling 机制去动态决策。它的重点不是“把两种形式拼起来”，而是让系统在宏观上可控，在局部上保留灵活性。

这类结构在真实业务里非常常见。比如外层流程先负责输入校验、权限判断、状态恢复和结果落库；到了中间某个“复杂问题求解节点”，再让 LLM 自主决定是否调用搜索、知识库、计算器或其他工具；最后再回到固定流程继续做校验和输出。这里，workflow 负责宏观编排，agent 或 tool calling 负责局部动作选择。

从学习路径上说，混合式 workflow 其实最值得最终掌握。因为真实系统很少是“纯画布”或者“纯代码”的绝对形态。更常见的情况是：先用可视化方式快速验证需求，再把关键链路沉到代码里；或者先搭好代码骨架，再开放一部分可配置节点给业务侧使用。理解这种混合形态，才算真正进入 workflow 的工程实践层。

## Workflow 的典型结构模式

Workflow 在形式上可以变化很多，但底层反复出现的结构模式其实比较有限。理解这些模式，比死记某个平台有哪些按钮更重要。

### 顺序执行（Sequence）

最简单的模式就是顺序执行，例如“输入 → 预处理 → 检索 → 生成 → 输出”。这种模式适合步骤清晰、依赖关系单向的任务，也是很多更复杂 workflow 的骨架。

### 条件分支（Conditional Branching）

条件分支意味着流程会根据状态或输入特征走不同路径。比如有图片就走图像链路，没有图片就走文本链路；开启搜索就调用搜索服务，不开启就直接进入生成。这是最典型、也最常见的 workflow 形态。

### 循环（Loop）

循环模式常见于信息收集和错误恢复。例如信息不完整时继续追问，工具调用失败时按规则重试，审批未通过时返回修改后再进入下一轮。只要一个任务存在“直到满足某条件为止”的阶段，循环几乎就不可避免。

### 并行（Parallel / Fan-out）

有些流程为了提升效率，会并行执行多个步骤。例如同时跑多个检索源、同时解析多张图片、同时调用多个候选工具，然后再聚合结果。并行不是为了让流程看起来高级，而是为了优化时延和提高信息覆盖度。

### 人工介入（Human-in-the-loop）

在真实生产系统中，人工介入往往是必需的，而不是“系统不够智能”的妥协。像写数据库、发邮件、转账、删数据这类高风险动作，常常需要在执行前暂停，等待人工审核或确认后再继续。这类设计决定了 workflow 能不能真正上线，而不只是停留在 demo。

## Workflow 的底层思维方式

学习 Workflow，真正要掌握的不是某个平台的按钮位置，而是一套更稳定的思考顺序。

### 第一步：先想“要自动化的过程”

不要先想模型，不要先想 prompt，也不要先想某个框架支持多少节点。第一步应该是先把真实任务的处理过程理清楚，看看它本来就包含哪些离散步骤，哪些是必须做的，哪些是可选的，哪些地方天然存在分支。

### 第二步：定义状态

接下来要明确哪些信息必须长期保留，哪些是中间结果，哪些是最终输出，哪些是错误信息。很多 workflow 设计问题，表面上看像是分支写错了，实际上根源是状态设计得太含糊。

### 第三步：定义节点职责

每个节点最好只负责一类明确动作。不要在一个节点里同时做分类、检索、生成和写库，否则流程虽然看起来短，后续调试和复用都会变得很困难。把节点职责拆清楚，是 workflow 工程化的第一步。

### 第四步：定义路由规则

然后才是定义在什么条件下跳到哪里，什么条件下中断，什么条件下需要人工审批。路由规则其实就是把“业务判断”转化成“执行路径”，它决定了流程是否真的可控。

### 第五步：补全异常路径

只写 happy path 是远远不够的。你需要继续问：超时怎么办，缺参怎么办，失败怎么办，工具返回脏数据怎么办。异常路径是否完整，往往决定一个 workflow 是不是只能演示一次。

### 第六步：再决定哪些节点需要 LLM

最后才决定哪些步骤真的需要交给模型。很多系统设计错误，恰恰在于把原本应该由规则、代码或显式状态解决的问题一股脑交给了 LLM。更合理的顺序始终是：

> **先设计流程，再决定哪些步骤交给模型。**
