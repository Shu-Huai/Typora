# 停机问题

简单说：**停机问题（Halting Problem）就是问：有没有一个算法，能“看代码就知道这段程序会不会跑完”**。结论是：**没有，这样的万能算法不可能存在**。

## 停机问题在问什么？

把问题说白话一点：

> 给你一个程序 `P` 和它的输入 `x`，
>  能不能写一个“超级检查器” `H(P, x)`，
>  保证总是能在有限时间内告诉你：
>
> - `P(x)` 最终会 **停下来**（正常结束），还是
> - `P(x)` 会 **永远跑下去**（死循环、卡死，不停机）？

形式化一点：

- 输入：程序 `P`，输入数据 `x`
- 输出：
    - 若 `P(x)` 会停机，则输出 `"YES"`
    - 若 `P(x)` 不会停机，则输出 `"NO"`
- 要求：
    - `H` 自己必须**总能停机**
    - 结果必须**永远正确，不允许出错**

**停机问题的结论**：不存在这样的万能算法 `H`。

也就是说，这个判定问题本身是**不可判定的（undecidable）**。

## 经典证明思路（对角线 / 自指悖论）

证明思路非常像“理发师悖论”或“说谎者悖论”，核心就是：

> 假设有这么一个完美的判定器，然后构造一个“和自己对着干”的程序，让它自爆。

### 假设：有一个完美的停机判定器 H

假设存在算法 `H(P, x)`：

- 如果程序 `P(x)` 会停机，`H(P, x)` 返回 `YES`
- 如果程序 `P(x)` 不会停机，`H(P, x)` 返回 `NO`
- 并且 `H` 自己总能在有限时间内给出答案

### 构造一个“反其道而行”的程序 D

现在我们用 `H` 来写一个新程序 `D(P)`：

```
D(P):
    if H(P, P) == "YES":   # 如果 P(P) 会停机
        loop forever      # 故意死循环，不停机
    else:                 # 如果 P(P) 不会停机
        halt              # 立刻停机
```

解释一下：

- `D` 把程序 `P` 当作输入
- 它调用 `H(P, P)`，也就是问：“程序 `P` 在输入 `P` 时，会不会停机？”
- 如果 `H` 说会停机，`D` 就偏不，让自己**死循环**
- 如果 `H` 说不会停机，`D` 就**立即停机**

### 关键一步：让 D 自己检查自己

现在我们问：`D(D)` 会发生什么？

- 让 `H(D, D)` 先判断 `D(D)` 会不会停机

分情况讨论：

1. 如果 `H(D, D) == "YES"`
    - 说明 `H` 认为：`D(D)` 会停机
    - 根据 `D` 的定义：如果 `H(D, D) == "YES"`，`D(D)` 将会**死循环**
    - 这就矛盾了：`H` 说它会停机，但实际上它永远不停机
2. 如果 `H(D, D) == "NO"`
    - 说明 `H` 认为：`D(D)` 不会停机
    - 根据 `D` 的定义：如果 `H(D, D) == "NO"`，`D(D)` 会**立即停机**
    - 又矛盾：`H` 说它不会停机，但实际上它停了

无论 `H(D, D)` 输出 YES 还是 NO，都会导致矛盾。

所以，我们一开始的假设——**存在这样完美的停机判定器 `H`**——是错误的。

> 结论：这样的万能算法不可能存在，停机问题是不可判定的。

## 这件事为什么重要？

### 告诉我们算法能力的极限

不是所有“看上去很合理的问题”都能用算法解决，有一类问题在理论上就是**无解**的（不是没找到，而是根本不存在算法）。

### 和很多“不可能实现的功能”有关

例如：

不可能有一个工具，能对“任何程序”做静态分析，保证 100% 正确地告诉你：

- 会不会死锁
- 会不会越界
- 会不会除零
- 会不会永远卡住

这些一般都可以通过把问题“编码”为停机问题来证明不可判定。

### 和 Rice 定理、可计算性理论相关

Rice 定理大致说：

> 只要是关于“程序实际计算的函数性质”的非平凡问题，统统都是不可判定的。
>
> 停机问题是其中最经典的一个例子。

### 和哥德尔不完备定理有内在联系

 都是利用“自指”“对角线”这种技巧，说明：

- 有些真命题在某个形式系统内不可证明
- 有些看似明确的问题用算法永远无法完全解决
