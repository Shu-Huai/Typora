# Superpowers：把 AI 编程关进流程里

Superpowers 不是为了让 AI 更快写代码。AI 已经够快了，甚至有时候快得吓人。真正麻烦的是它太容易在没想清楚的时候动手：需求还没问明白就开写，代码能跑但没有测试，修 bug 靠猜，做完了也没有验收，分支和工作区一堆残留，聊着聊着上下文还会跑偏。

Superpowers 解决的是这些问题。它把设计、计划、隔离开发、TDD、系统化调试、代码审查和收尾这些工程动作，做成 AI 必须遵守的技能流程。这样 AI 不再只是一个会补代码的模型，而是被一套工程纪律约束住的执行者。

我对它的理解很简单：AI 编程缺的往往不是能力，而是纪律。没有流程时，AI 的高效率很容易变成高返工率。Superpowers 的价值就在这里：先想清楚，再写计划；先写测试，再写代码；先找根因，再修 bug；先验证，再说完成。

## 它到底是什么

Superpowers 更像一套 AI 编程方法论，不像普通开发库，也不是 IDE 插件。它不提供运行时能力，也不替代语言框架。它做的事更朴素：把开发过程里本来就该做的动作，变成 AI 助手不能跳过的规程。

普通 AI 编程常见的流程是这样的：用户给一个模糊目标，AI 直接生成代码；能运行就继续推进；出问题再让 AI 修；修完一个地方，可能又把另一个地方弄坏。整个过程里，缺的不是“会不会写代码”，而是闭环：需求没有确认，设计没有记录，计划没有拆开，测试没有先行，调试没有根因分析，审查没有独立视角，完成也没有验收。

Superpowers 要减少的就是这种随机性。它把 AI 的自由生成，改造成受控执行。

## 主流程

Superpowers 可以粗略理解成七步：

1. Brainstorming：先澄清需求，形成设计。
2. Git worktrees：给任务创建隔离工作区。
3. Writing plans：把设计拆成可执行任务。
4. Sub-agent driven development：用新的子代理执行任务，并做审查。
5. Test-driven development：先写失败测试，再写实现。
6. Code review / Verification：代码完成后审查和验证。
7. Finish branch：合并、提 PR、保留或丢弃分支，把工作收尾。

这些步骤听起来多，但每一步都对应一个真实风险。Brainstorming 防止需求误解；计划防止执行时靠猜；worktree 防止污染主线；TDD 防止“能跑但不对”；系统化调试防止盲修；审查防止实现者盲区；最后的收尾防止工作区长期烂在那里。

## Brainstorming：先设计，不急着写代码

Brainstorming 是 Superpowers 里最硬的一道门。用户批准设计之前，AI 不应该写代码、创建项目或执行实现命令。小功能也一样，只是设计可以短一点。

这条规则并不是仪式感。比如用户说“做一个登录功能”，如果 AI 直接开写，很快就能生成一套看起来能跑的代码。但认证方式、密码存储、会话策略、错误处理、安全边界、测试方式，这些都可能没有被确认。等代码写完再发现方向不对，返工成本会高得多。

一个好的 Brainstorming 通常会做几件事：

1. 先看项目结构、文档和现有写法。
2. 判断是否需要 UI 草图、流程图或架构图。
3. 一次只问一个关键问题，尽量让用户容易回答。
4. 如果需求太大，先拆成子项目。
5. 给出多个方案，说明取舍。
6. 分段确认设计，而不是一口气丢一篇长文档。
7. 把设计保存到正式文档里。
8. 自查有没有 TBD、TODO、矛盾和模糊边界。
9. 用户确认后，再进入计划阶段。

重点不是文档多长，而是 AI 真的理解了要做什么。设计至少要说清楚目标、边界、组件职责、数据流、错误处理、测试策略，以及明确不做什么。

已有代码库里还要注意一件事：尊重现有结构。Superpowers 不鼓励借一个小需求顺手重写半个项目。如果当前任务需要局部整理，可以写进设计；但不要把“完成这个功能”变成“重构整个系统”。

## Writing Plans：把想法写成能执行的说明书

设计回答“做什么”，计划回答“怎么做”。Writing Plans 的假设是：执行者可能是一个新的 sub-agent，它没有前文聊天记录，只能看计划本身。所以计划必须自包含。

自包含的意思是，每个任务都要写清楚：

- 创建或修改哪些文件。
- 每个文件要写什么。
- 要运行什么命令。
- 命令的预期结果是什么。
- 测试应该先怎样失败，再怎样通过。
- 完成后如何提交。

最危险的是那些看似合理、其实没法执行的占位表达，比如 TBD、TODO、implement later、handle edge cases、write tests for the above、similar to task 2。它们把没想清楚的地方伪装成了计划。

不合格的计划可能长这样：

```markdown
- Add proper error handling to the login API.
- Write tests for the above.
- Implement validation similar to Task 2.
```

这里的问题很明显：哪些错误？测试叫什么？Task 2 的细节执行者能不能看到？都没说。

更好的写法是：

```markdown
- Modify `src/auth/login.ts` so empty username or password returns HTTP 400 with body `{ "error": "username and password are required" }`.
- Add `tests/auth/login.test.ts` with a test named `returns 400 when username is empty`.
- Run `npm test -- tests/auth/login.test.ts`; the new test should fail before implementation and pass after implementation.
```

计划还要足够小。理想情况下，一个任务只做一件事，几分钟能完成。TDD 的一个循环可以拆成：写失败测试、确认失败原因、写最少实现、确认通过、提交变更。颗粒度越小，失败时越容易定位。

计划写完后要自审三件事：需求有没有全部覆盖；有没有占位词；函数名、类型名、字段名是否前后一致。对 sub-agent 来说，一个名字不一致就可能让它新建一套东西，而不是复用已有代码。

## Worktree：让 AI 在隔离区里动手

设计和计划通过后，才进入执行。这里 Superpowers 通常会先用 Git worktree 创建隔离工作区。

Git worktree 是 Git 自带功能，可以让同一个仓库同时有多个工作目录。比如：

```bash
git worktree add ../my-project-auth feature/auth
```

这样 `../my-project-auth` 就是 `feature/auth` 分支对应的新目录，主目录可以继续停在 `main`。两个目录共享 Git 历史，但文件系统互相独立。

这对 AI 编程很有用。AI 如果在隔离 worktree 里改坏了，可以丢掉；如果改得好，再经过测试和审查合并回来。它减少了主线被临时代码污染的概率。

使用 worktree 时要注意：目录要被 `.gitignore` 忽略；创建后先安装依赖并跑基线测试；目录位置尽量遵守项目已有约定；任务结束后清理，不要留下没人知道状态的工作区。

## Sub-agent：用新的上下文执行任务

Sub-agent driven development 的想法是：每个独立任务交给一个新的 AI 子代理。这个子代理没有前面聊天的惯性，只能依赖任务说明。

这有两个好处。第一，减少上下文污染。长对话里，AI 很容易把上一个任务的临时写法带到下一个任务。第二，倒逼计划质量。因为 sub-agent 看不到你刚刚讨论过什么，任务写得不完整，它就会卡住或者请求更多上下文。

子代理完成后不能直接算完。Superpowers 要求两轮检查：先看规格是否做对，有没有遗漏或越界；再看代码质量，比如命名、重复、边界、性能和测试覆盖。顺序不能反。做错了事，代码再漂亮也没用。

子代理的反馈大致有四类：

- Done：完成，可以审查。
- Done with concerns：完成但有疑虑，需要判断是否影响正确性。
- Needs context：缺关键上下文，要补充后重新派发。
- Blocked：被卡住，可能需要拆小任务、修计划或换模型。

如果它说 blocked，正确做法不是喊它继续试，而是看它卡在哪里。

模型选择也不必一味用最强的。机械实现可以用便宜一点的模型；跨文件集成用标准模型；架构判断、复杂调试和关键审查再用强模型。前提是流程要兜住，尤其是审查和验证不能省。

## TDD：没有失败测试，就别写实现

Superpowers 对 TDD 的要求很硬：没有失败测试，不写生产代码。

这条规则容易让人嫌麻烦，但它的作用很直接。先写测试，是先定义行为；后补测试，常常只是验证已经写出来的实现。两者差别很大。

TDD 的循环是红、绿、重构。

红色阶段写一个明确失败的测试。失败原因必须正确：它应该因为目标行为不存在而失败，而不是因为导入错、拼写错或测试环境坏。

绿色阶段只写最少生产代码，让这个测试通过。不要顺手加未来功能，也不要顺手重构。

测试通过后，才进入重构：改命名、消重复、提函数、理结构。重构时测试必须保持绿色。

如果已经先写了生产代码怎么办？Superpowers 的规则是删掉，用 TDD 重新来。这个规则很严，但有道理：留着旧实现当参考，测试很容易围绕实现写，而不是围绕需求写。

Bug 修复也一样。先写一个失败测试复现 bug，确认失败原因就是这个 bug，再写最小修复，最后跑相关测试和必要的全量测试。这样 bug 修完后，会变成测试集的一部分。

## Systematic Debugging：先查根因，再修

系统化调试的铁律是：没有根因调查，不修 bug。

它针对的是很常见的 AI 失控方式：看到报错就猜，猜完直接改，改完再看运气。Superpowers 把调试拆成四步。

第一步是调查，只收集信息，不提修复方案。记录症状、错误信息、日志、复现步骤、发生时间、影响范围、是否稳定复现、最近有没有相关变更。

第二步是分析，沿着现象往下追根因。报错通常只是症状。比如“数据库超时”可能是连接池满，而连接池满可能是某个异常路径没有释放连接。

第三步才是修复。找到根因后，只做最小改动。修 bug 时不要顺手重构、优化或扩功能，否则验证会变得更难。

第四步是验证。确认原 bug 不再复现，也没有引入新问题。验证可以包括复现步骤、相关测试、全量测试，必要时还要看集成环境。

举个简单例子：React 页面里按钮点了没反应。低质量调试会直接改 `onClick`，加日志，甚至重写按钮。系统化调试会先看事件有没有触发、网络请求有没有发出、控制台有没有输出、DOM 上有没有东西挡住按钮。最后可能发现问题不是按钮逻辑，而是一个透明 overlay 盖在上面。修复就应该集中在层级或 `pointer-events`，不是重写提交逻辑。

## Code Review 和完成前验证

代码审查不是为了挑刺，而是为了打破实现者盲区。人和 AI 都一样，刚写完代码时很容易相信自己的思路。独立审查能帮你看见遗漏。

Superpowers 的审查通常会把问题分成三类：

- Critical：安全漏洞、权限绕过、数据泄露、破坏性数据错误等，必须立刻修。
- Important：边界遗漏、异常路径没覆盖、业务逻辑错误、测试不足，修完才能继续。
- Minor：命名、注释、局部重复等轻问题，可以记录为技术债。

Critical 和 Important 没解决，就不该进入下一阶段。

完成前验证看的是另一件事：任务是不是真的交付了。它通常检查：相关测试是否通过；审查问题是否处理；有没有 TODO、FIXME、临时代码和调试日志；文档是否更新；实现是否符合设计和计划。

这一步防的是“能跑了，所以完成了”的错觉。代码能跑只是条件之一，不等于任务完成。

## Finish Branch：别把半成品留在角落

任务写完、测试通过、审查完成后，还需要收尾。Superpowers 会要求用户选择一种明确动作。

常见选项有四个。

第一，本地合并。适合功能完成、测试通过、不需要团队审查的场景。

第二，推送并创建 Pull Request。适合团队协作、需要 CI 或正式审查记录的项目。

第三，保留。适合任务暂时不能结束，比如等接口、设计稿、业务确认或外部依赖。保留也要标清状态。

第四，丢弃。适合实验方向错了、需求取消或方案不可行的分支。该删就删，别让它长期混在工作区里。

原则只有一个：每次打开的工作，都要有关闭动作。没有合并、没有 PR、没有标记进行中、也没有丢弃的分支，最容易制造混乱。

## Writing Skills：把重复流程做成技能

`writing-skills` 是 Superpowers 里的元技能。它不是用来写某个功能，而是用来创建自己的技能。

如果某类操作在 AI 编程里反复出现，就适合做成技能。比如提交前检查格式、创建接口时生成测试模板、部署前跑固定检查、改数据库结构时同步迁移说明。技能的价值是让这些流程在合适场景自动触发，而不是每次都重新提醒 AI。

一个技能通常包括：

- `SKILL.md`：入口，说明技能是什么、何时触发。
- 平台指令文件：写给 AI 的规则、步骤和禁止事项。
- `references/`：放规范、示例和项目约定。
- `scripts/`：放可执行脚本。

好技能要精确、无歧义、可执行。“代码格式要好看”不是好规则；“提交前运行 `npx prettier --check "src/**/*.{ts,tsx}"`，失败时列出文件但不自动修改”才是规则。

## 适合和不适合的场景

Superpowers 特别适合这些情况：多文件、多模块改动；长期维护项目；有测试、审查、PR 或 CI 要求的团队项目；安全、权限、支付、数据一致性等高风险逻辑；以及 AI 经常改偏、改乱、反复修 bug 的代码库。

这些场景有一个共同点：返工成本高，出错影响大。流程比速度重要。

但这不等于每个小改动都要写很长的文档。非常小的任务可以轻量化。比如改一个配置项，设计只需要写清楚改什么、为什么改、影响范围、怎么验证；计划也可以只有两三步。轻量化不是省略，而是在保留关键门禁的前提下降低文档体量。

Superpowers 也容易被误解成高级提示词。其实它重要的不是某一句提示怎么写，而是流程能否稳定触发、能否约束行为、能否检查结果、能否把工作关掉。它更像工程制度，不像一次性的 prompt 优化。

## 一个真实任务会怎么跑

假设要给已有 Web 项目增加“登录失败次数限制”，Superpowers 风格不会直接让 AI 写代码，而会这样推进：

1. Brainstorming：确认限制维度是 IP、用户名还是两者组合；阈值是多少；锁定多久；错误返回什么；是否影响管理员；是否需要配置项。
2. Design 文档：记录中间件设计、存储方式、错误码、日志策略、测试范围和明确不做的内容。
3. Writing Plans：拆成测试、实现、配置、文档和验证任务，每个任务写清文件、命令和预期结果。
4. Git worktree：创建 `feature/login-rate-limit` 的隔离工作区，安装依赖并跑基线测试。
5. TDD：先写“连续失败后第 N 次返回 429”的失败测试，再写最少实现。
6. Sub-agent execution：把独立任务交给新的子代理，完成后做规格审查和代码质量审查。
7. Systematic Debugging：如果测试异常失败，先查根因，再修。
8. Code Review：独立检查安全、边界、异常路径和测试覆盖。
9. Verification：确认测试通过、审查问题已解决、无临时代码、文档已更新、实现符合设计。
10. Finish Branch：选择合并、创建 PR、保留或丢弃，并清理 worktree。

步骤不少，但不是为了显得专业。每一步都在挡一个具体的坑。

## 最后

我会把 Superpowers 概括成一句话：它不是让 AI 少做事，而是让 AI 在正确的时候做正确的事。

普通 AI 编程像是“让模型帮我写代码”。Superpowers 更像是“让模型在我定义的工程制度里交付代码”。差别就在这里：一个偏随机生成，一个偏专业交付。
