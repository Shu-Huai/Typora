# 关于网络中的文件传输协议

## 概念与边界

**网络中的文件传输协议**，指在计算机网络中，用于**访问、传输、同步或呈现数据**的协议与其实现栈。它们规定了：

- **数据语义层**：对象（Object）、文件（File）、块设备（Block）三种主导范式；是否提供目录、权限、锁、版本、元数据等语义。
- **传输控制层**：连接建立、会话保持、流量控制、加密签名、压缩与断点续传等机制。
- **一致性与可靠性层**：校验、冲突处理、幂等操作、错误恢复与多站点复制。
- **可运维性**：穿越防火墙与代理的难易度、客户端生态成熟度、可观测性与审计能力。

协议的选型，实质是在**语义、性能、安全、可运维**之间进行权衡。

## 发展历程

### 1970s–1980s：传统与奠基

- **FTP** 成为主机间文件传输事实标准（明文控制与数据通道）。
- **NFS** 在 UNIX 体系内形成远程文件系统范式（本文不展开）。

### 1990s：桌面与 Web 崛起

- **SMB/CIFS** 在 Windows 生态普及，形成集成的共享、打印与权限模型。
- **HTTP** 标准化，随后催生基于 HTTP 的文件访问扩展（如 WebDAV）。

### 2000s：安全化与互联

- **SFTP/SCP** 在互联网环境成为安全文件传输常规方案。
- **WebDAV** 作为 HTTP 扩展，用于协作式远程读写与“网络磁盘”。

### 2010s：云与数据中心化

- **SMB 3.x** 引入加密、预认证完整性、多通道与 RDMA 等，显著提升可靠性与吞吐。
- **对象存储接口（S3/OSS）** 成为大规模非结构化数据事实标准。
- **rsync** 与 CI/CD、备份归档、站点镜像深度结合。

### 2020s：云原生与混合场景

- 对象与文件、块级协议在同一系统中共存：**S3 网关挂载**、**NVMe/TCP**、**多活复制**与零信任传输成为常态化技术选项。

## 分类

### 按语义范式分类（首要维度）

#### 块设备（Block）

- 远端呈现裸 LUN（逻辑卷），客户端自行构建文件系统（如 ext4/NTFS）。
- 代表：**iSCSI**。
- 特点：延迟敏感、性能接近本地盘；不原生支持多主并发写，需要集群文件系统或上层锁管理。

#### 文件级（File）

- 远端以目录树形式可挂载访问，具备权限、锁与句柄等语义。
- 代表：**SMB、WebDAV**（以及未纳入本文的 NFS）。
- 特点：适合团队协作与办公共享，语义丰富；跨平台、实现差异会影响互操作性与性能。

#### 对象级（Object）

- 以“桶 + 对象（键）”组织；目录为前缀模拟；强依赖 HTTP API。
- 代表：**S3、OSS**。
- 特点：高扩展性、低成本、跨地域；不具备严格 POSIX 语义，重命名/原地修改并非原生。

#### 传输/同步（Transfer/Sync）

- 以文件拷贝与差量同步为目标，不提供挂载语义。
- 代表：**FTP、FTPS、SCP、SFTP、rsync**。
- 特点：脚本化容易，适合自动化分发、备份镜像；不解决多客户端共享一致性问题。

### 按是否基于 HTTP 分类

#### 基于 HTTP/HTTPS：S3、OSS、WebDAV、HTTP File Server。

- 优势：端口（80/443）通行性高、易与网关/代理集成；
- 劣势：对象存储的非 POSIX 特性、WebDAV 的高时延下元数据操作成本等。

#### 非基于 HTTP/HTTPS：SMB、FTP/FTPS、SCP/SFTP、rsync、iSCSI。

- 优势：各自领域优化充分（如 SMB 的文件语义、iSCSI 的块级性能、SFTP 的单端口安全）；
- 劣势：穿越复杂网络需额外规划（如 FTP 被动端口段、SMB 策略等）。

## SMB

### 基本概念

<img src="https://www.etsme.com/wiki/wp-content/uploads/2024/02/smb-example.png" alt="什么是SMB协议？SMB协议的工作原理详解- etsme百科网" style="zoom: 67%;" />

SMB（Server Message Block）是面向**文件级共享**的远程访问协议。客户端经由网络对服务器上的目录、文件、命名管道与打印队列执行操作。现代实现以 **SMB 2.x/3.x（3.1.1）** 为主，关键能力包括：方言协商、复合请求（Compounding）、信用（Credits）并发控制、租约（Leasing）与机会锁（Oplock）、持久/可恢复句柄（Durable/Persistent Handles）、多通道（Multichannel）、RDMA（SMB Direct）、端到端加密与预认证完整性（3.1.1）。

### 数据结构

> SMB2/3 报文头与复合请求

SMB2/3 的每个 PDU 均以固定 64 字节头部开场，字段为后续机制的“锚点”。

<img src="Z:\Public\images\format,webp.webp" alt="53871b85393eb26a08076ee37c74e2bf0dd1ecfb"  />

#### SMB2/3 头（64B）核心字段

- `ProtocolId`：固定魔数 `0xFE534D42`（即 0xFE + 'S''M''B'）。
- `StructureSize`：固定 64。
- `CreditCharge / CreditRequest / CreditResponse`：并发/流控的信用机制。
- `Command`：操作码（NEGOTIATE、SESSION_SETUP、TREE_CONNECT、CREATE、READ/WRITE、CLOSE、IOCTL、LOCK、QUERY_INFO 等）。
- `MessageId`：请求-响应匹配；支持乱序/流水线。
- `TreeId`、`SessionId`：树连接与会话标识。
- `Flags`：如签名、加密标志位。
- `Signature`：消息签名（如启用）。
- **3.x 扩展**：在多通道语境下使用的 `ChannelSequence`/保留位等。

> SMB2/3 报文头与复合请求
>
> **复合请求（Compounding）** 允许将多条命令串联在一次往返：例如 `CREATE → READ → CLOSE`。这与“信用机制 + 大 I/O”配合，显著降低 RTT，对大吞吐/高时延链路尤为关键。复合请求通过头部的 `NextCommand` 偏移字段串连多条命令体。

### 控制面

> 连接的建立与管理

#### 典型握手流程

![3b9bdee70e94d9c5ddee54cb7d2ddcf145ea54df](Z:\Public\images\format,webp-1760936994137-9.webp)

```
TCP 445 建链
  → NEGOTIATE（方言与能力协商；3.1.1 时携带预认证完整性能力）
  → SESSION_SETUP（SPNEGO：通常 Kerberos/NTLM 完成认证并派生密钥）
  → TREE_CONNECT（绑定具体共享，如 \\server\share）
  → {CREATE/READ/WRITE/...} 正常数据面操作
  → TREE_DISCONNECT / LOGOFF
```

- **NEGOTIATE（协商）**：选择方言（2.0.2/2.1/3.0/3.0.2/3.1.1），交换能力上下文（加密算法族、预认证完整性算法、支持的传输特性等）。
- **SESSION_SETUP（会话）**：完成认证（Kerberos/NTLM），生成会话密钥，后续用于消息签名/加密派生。
- **TREE_CONNECT（树连接）**：对某个共享建立上下文，之后的文件操作均在该 TreeId 下进行。
- **会话维持与断线恢复**：3.x 支持“可恢复/持久句柄”（下节详述），以便掉线重连时延续打开状态。

### 并发与流控

SMB2/3 使用**信用（Credits）**做应用层流控与并发窗口管理。

- **CreditRequest / CreditResponse**：客户端在请求里声明所需信用，服务端在响应中回授额度；额度决定“在途请求”上限。
- **CreditCharge**：对大 I/O（尤其 > 64KB）按比例消耗多个信用，一次请求可拆分占用多份额度。
- **实践建议**：
    - 关注客户端是否“吃满”信用窗口（大流量下请求被服务端限额会降低吞吐）。
    - 启用复合请求与足够大的 I/O 大小；在高 RTT 下效果明显。
    - 结合 **Multichannel** 提升并行通道带宽利用率。

### 缓存一致性问题

SMB 的一致性通过**机会锁（Oplock）与租约（Lease）**协调客户端缓存与写入冲突。

- **Oplock → Lease 的演进**：SMB2.1 起引入 **Lease**，相较传统 Oplock 更细粒度区分数据/元数据缓存许可，并在共享读/写情境下提供更优降级策略。
- **Lease Break（破坏通知）**：当其他客户端需要写入时，服务器向持有租约的一方发送“破坏”通知，要求降级/释放缓存；客户端需在时限内响应。
- **目录租约**：对目录枚举元数据的缓存许可，降低目录遍历往返。
- **工程含义**：在多客户端读多、写少的团队共享中，Lease 提升缓存命中与交互性能；写入竞争激烈时将更频繁地发生降级。

### 高可用性

SMB3 提供**透明故障转移**能力，核心依赖句柄持久化与集群文件服务器。

- **Durable Handle**：客户端在 `CREATE` 时请求“可恢复”句柄（掉线/短时中断后可重连恢复 I/O）。
- **Persistent Handle**：在具备后端持久化/集群支持时，句柄可以跨节点保持（结合 Scale-Out/CA Share）。
- **Transparent Failover**：与 Windows 故障转移群集/Scale-Out 文件服务器配合，计划内迁移或节点故障时，客户端几乎无感，适合虚拟化与备份等连续性要求高的场景。
- **实践要点**：开启 **Continuous Availability（CA）** 共享属性；后端存储与群集心跳需稳定，避免长时间脑裂导致句柄恢复失败。

### 多路能力

SMB3 在链路与传输层引入**多通道（Multichannel）**与**RDMA（SMB Direct）**以提升吞吐与降低延迟。

- **Multichannel**：同一会话可同时使用多条 TCP 连接，自动探测网卡能力（RSS/吞吐）。在多网卡/多路径环境下实现**聚合与容错**。
- **SMB Direct（RDMA）**：利用 iWARP/RoCE/IB 提供零拷贝与内核旁路，显著降低 CPU 与时延，适合万兆/百兆比特级别的数据中心复制、Hyper-V 存储与备份负载。
- **通道序列（Channel Sequence）**：在多通道语境下用于保证请求顺序与重放语义。
- **实践要点**：万兆以上链路建议：
    - 启用 **Multichannel**；为多网卡规划独立子网/VLAN。
    - RDMA 场景：iWARP 可免 PFC；RoCEv2 需配置 DCB/PFC/ECN 与优先级队列，确保无损或近无损。

### 安全性

SMB 3.x/3.1.1 的安全体系涵盖**认证、签名、加密与预认证完整性**。

- **认证**：通过 SPNEGO 选择 Kerberos 或 NTLM；域环境下优先 Kerberos。
- **消息签名**：基于会话密钥的完整性保护，可策略强制；防止篡改与中间人修改。
- **端到端加密（SMB Encryption）**：在会话或共享级启用；常见算法为 AES-GCM/CCM（3.1.1 可协商至 AES-256）。
- **预认证完整性（Pre-auth Integrity, SMB 3.1.1）**：自 NEGOTIATE/SESSION_SETUP 起对握手材料进行连续哈希绑定，抵御方言与能力降级攻击，保证后续密钥派生的正确性。
- **最小化暴露面**：关闭 SMBv1；仅在可信域或零信任通道（VPN/代理/SMB over QUIC）上暴露 445；最小权限 ACL 与访问审计。

## HTTP File Server（基于 HTTP 的文件服务）

### 定位与工作方式

![One Command to Setup HTTP File Server in Linux [Tip] - FOSTips](Z:\Public\images\httpdownloadserver.png)

**HTTP File Server**（下称 HFS）指通过 **HTTP/HTTPS** 暴露服务器上的文件，提供目录浏览、下载，以及有限（或经扩展后的）上传能力。它本质是“**按 URL 访问文件对象**”，与 SMB/NFS 的“挂载式文件系统语义”不同，HFS 更适合**发布与分发**：

- **对象单位**：URL 对应单个文件（或符号化的文件条目），以 `GET/HEAD` 为主，必要时 `PUT/POST` 处理上传。
- **会话模型**：**无状态**请求，应使用缓存/条件请求/范围请求减少重复传输与 RTT。
- **语义边界**：原生 HTTP 不提供文件锁与记录级并发控制，协作编辑需 WebDAV 或应用层协议补齐。

> 典型实现形态：
>
> 1. **通用 Web 服务器**：Nginx/Apache/Lighttpd + 目录索引（autoindex）→ 静态分发。
> 2. **专用 HFS 程序**：如一些 Go/Rust 写的单文件 HTTP 目录服务。
> 3. **应用后端网关**：由应用鉴权与记录下载，再用 **X-Accel-Redirect（Nginx）/X-Sendfile（Apache）** 将大文件回源交给 Web 服务器直传。

### 端口与安全边界

- **端口**：80（HTTP）/443（HTTPS）。生产强烈建议 **仅暴露 443** 并开启 **HSTS**。
- **安全构件**：TLS（证书、OCSP stapling）、反向代理/WAF、鉴权网关（OIDC/JWT/签名 URL）、限速限并、IP 访问控制、目录访问控制。
- **零信任**：面向公网时，优先置于 **反向代理 + 身份前置（IdP/OAuth2 Proxy/OIDC）** 模式，再回源到 HFS。

### 能力与边界（与文件分发强相关的 HTTP 机制）

#### 断点续传与分块下载

- **范围请求（Range Requests）**：客户端在请求头加 `Range: bytes=start-end`；服务端返回 **206 Partial Content** 与 `Content-Range`，实现**断点与多线程下载**。
- **文件探测（HEAD）**：`HEAD` 返回元数据（长度、类型、ETag、Last-Modified），下载器据此计算分片计划。
- **多连接下载**：下载器可并行多个 Range 请求；服务端需合理限并与速率。

#### 条件请求与缓存一致性

- **ETag / If-None-Match** 与 **Last-Modified / If-Modified-Since**：避免重复下载，命中时返回 **304 Not Modified**。
- **Cache-Control / Expires**：指挥浏览器与 CDN 缓存策略；静态不可变资源可用 `Cache-Control: public, max-age=31536000, immutable`。
- **If-Range**：在客户端持有旧 ETag 或日期时，若资源未变更则继续范围下载，变更则回退到 200 全量。

#### 下载呈现与安全头部

- **Content-Type**：准确的 MIME，避免浏览器误判。
- **Content-Disposition**：`attachment; filename="xxx.zip"` 强制“另存为”，防 XSS/HTML 渲染风险。
- **X-Content-Type-Options: nosniff**、**Referrer-Policy**、**Content-Security-Policy (CSP)**：降低前端内容被利用的风险。
- **Accept-Ranges: bytes**：显式告知支持范围请求。

### 上传能力的实现路径

原生 HTTP 并不标准化“断点续传上传”。常见工程做法：

1. **表单上传（POST multipart/form-data）**：适合中小文件；大文件需调优缓冲与超时。
2. **分块/断点协议**：
    - **tus**（开源的断点续传协议）：客户端分片上载，可暂停恢复。
    - **S3 兼容多段上传**：若后端是对象存储，可直接走 **Multipart Upload**。
3. **反向代理直传后端**：应用签名与校验分片，上传内容走反向代理直接落盘/对象存储，应用仅处理元数据（减轻应用层负载）。

> 若只需“接收文件”，而非强协作：**强烈建议把上传落在对象存储（S3/OSS）**，服务端签名直传，减少本地磁盘与并发压力。

### 典型实现与配置示例

#### Nginx：只读镜像/下载站（含目录索引、断点与限速）

```nginx
server {
  listen 443 ssl http2;
  server_name files.example.com;

  # TLS 与安全头（略：证书、HSTS、OCSP）
  add_header Strict-Transport-Security "max-age=31536000" always;
  add_header X-Content-Type-Options nosniff;

  # 静态文件根目录
  root /srv/files;
  autoindex on;                 # 目录索引
  autoindex_exact_size off;     # 显示友好大小
  autoindex_localtime on;

  # 断点续传（Nginx 默认支持 Range）
  # 显式告知
  add_header Accept-Ranges bytes;

  # 大文件直传优化
  sendfile on;
  tcp_nopush on;
  aio threads;                  # 异步 I/O（按内核情况评估）
  output_buffers 4 512k;

  # 合理的类型映射
  types { text/plain txt; application/zip zip; }

  # 下载呈现：强制附件（防止浏览器渲染可疑内容）
  location ~* \.(zip|tar|gz|7z|iso|img|bin)$ {
    add_header Content-Disposition 'attachment';
  }

  # 简单限速与并发
  limit_rate 50m;      # 每连接限速，示例值
  keepalive_timeout 75;

  # 仅允许 GET/HEAD，禁 POST（纯下载站）
  if ($request_method !~ ^(GET|HEAD)$) { return 405; }
}
```

**要点**：

- `autoindex` 适合镜像/制品分发；敏感目录必须**显式关闭**。
- 大文件：开启 `sendfile/aio/tcp_nopush`，必要时配合 `sendfile_max_chunk` 控制内核阻塞。
- 公网暴露：务必仅 443 + HSTS；考虑 WAF 与机器人/爬虫策略。

## S3（Simple Storage Service 接口）

### 语义与接口模型（Bucket / Object / Key）

- **命名空间**：`Bucket` 下以 **Key（字符串）**标识对象；“目录”只是**前缀**约定（如 `logs/2025/10/20/part-0001.gz`）。
- **对象不可变**：每次 `PUT` 等于**创建新版本**（若开了 versioning）或覆盖旧对象（未开 versioning）。**不支持原地修改**；`rename/move` 实为 **Copy + Delete**（服务端侧复制）。
- **API 面**：HTTP/HTTPS 方法
    - 读：`GET`（可 **Range** 分段）、`HEAD`；
    - 写：`PUT`（小对象），**Multipart Upload（分片）** 适合大对象；
    - 列举/前缀检索：`ListObjectsV2`（分页，前缀过滤与 delimiter 聚合“伪目录”）；
    - 元数据：ETag、Content-Type/Encoding、User-Metadata（自定义 header）。
- **选择性读取**：S3 Select（对 CSV/JSON/Parquet 执行投影/过滤，按需返回字节），显著降低网络与解压成本（适用数据湖 ETL 预裁剪）。

### 一致性、可见性与原子性

- **写后读一致性**：对 `PUT`/`DELETE`/覆盖写入，**新对象读**与**现有对象覆盖读取**保证强一致（现代主流云 S3 语义已提供强一致）。
- **列举一致性**：List 通常也提供强一致（视厂商而定）；工程上仍建议**通过索引/清单**驱动处理流程，不以 `List` 作为强制真相源。
- **原子性**：**单对象 `PUT`/`CompleteMultipartUpload` 的可见性是原子的**；要么旧版可读，要么新版本可读，不会暴露“半成品”。
- **幂等性**：以 `PUT` + `If-Match/If-None-Match` 或者带内容哈希/对象锁策略，避免意外覆盖。

### 安全与访问控制（IAM / STS / KMS / 预签名 URL）

#### 身份与授权：

- **IAM Policy**（附到用户/角色）与 **Bucket Policy**（附到桶）共同决定允许/拒绝；
- 临时访问用 **STS**（AssumeRole）发 **短期凭证**（有期、可撤销）；
- **Access Point**（多租户/大规模共享）可简化按路径/前缀隔离。

#### 加密层次：

- **SSE-S3**（服务端、S3 管理 KMS）；
- **SSE-KMS**（服务端、客户 KMS 密钥，细粒度审计/轮换/撤销）；
- **SSE-C**（客户自管密钥，少用）；
- **CSE**（客户端加密，SDK 在本地加密后上传）。

- **URL 授权**：**预签名 URL**（短期 Token 化的 `GET/PUT`），常用于浏览器直传/临时下载。

#### 网络边界：

- **VPC Endpoint（Gateway/Interface）** 让 VPC 内流量走私网；
- **公共端点**时强制 TLS、最小权限、限制来源（CIDR/Referer/签名 URL）。

#### 示例：仅允许某角色在前缀 `tenantA/` 读写

```
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [ "s3:GetObject", "s3:PutObject", "s3:DeleteObject" ],
    "Resource": "arn:aws:s3:::my-bucket/tenantA/*"
  }]
}
```

### 耐久性与可用性（复制、版本、对象锁）

- **耐久性**：标准存储通常宣称 **11 个 9（99.999999999%）级别**对象持久性（多 AZ/区冗余）。
- **可用性**：按存储级别不同（标准/RA-GRS/单区等）给出 SLA（例如 99.9%～99.99%）。
- **版本管理（Versioning）**：开启后每次写入生成新版本，删除会产生删除标记（Delete Marker）；支持**跨区域复制（CRR）**按版本搬运。
- **对象锁/WORM**：合规场景可启用 **Object Lock**（Retention/Legal Hold），实现不可变（Write-Once-Read-Many）。
- **回收与恢复**：版本化 + 生命周期 + 清单（Inventory）使误删/覆盖可回滚。

### 存储级别与生命周期策略

#### 常见级别（示例）：

- **Standard**：热数据，较高可用与低时延；
- **Infrequent Access（IA / One Zone-IA）**：较低成本，取回费/更高最小计费；
- **Intelligent-Tiering**：自动在热/冷之间迁移；
- **Archive（Glacier/Deep Archive）**：超低成本，取回延迟分钟～小时。

#### 生命周期（Lifecycle）：

- 基于**对象年龄/前缀/标签**自动执行：转存到 IA/归档、到期删除、移除过期分段（AbortIncompleteMultipartUpload）。
- 数据湖推荐：**落地 30 天转 IA、180 天转归档、1~3 年删除**（按业务合规调整）。

### 分片上传（Multipart Upload, MPU）内部机制

- **何时用**：对象 **≥ 50–100 MB** 建议分片上传（SDK 多默认阈值 ~ 8–100 MB）；**TB 级**对象必须分片。
- **流程**：
    1. `CreateMultipartUpload` → 得到 `UploadId`；
    2. 并行 `UploadPart`（分片编号 1..N）→ 返回 ETag；
    3. `CompleteMultipartUpload`（提交所有 part 的 ETag/PartNumber）；或 `AbortMultipartUpload`。
- **并发与重试**：分片可并行、多机/多线程上传；失败**仅重传分片**，最终合并原子完成。
- **ETag 语义**：单 `PUT` 的 ETag 通常是对象 MD5；**MPU 的 ETag 不再等于整文件 MD5**（而是与各分片 MD5 及分片数相关）。强校验需使用 **Checksum API（CRC32C/CRC32/SH A1/SHA256）** 或上传额外 `.sha256`。
- **分片大小**：S3 单对象最大 5TB，分片 5MB–5GB；分片越大，请求数越少；分片越小，重试损失越少（折中取 64–256MB 常见）。

## WebDAV

### WebDAV 是什么？

**WebDAV（Web Distributed Authoring and Versioning）** 是在 HTTP/1.1 之上扩展的一组协议（核心 RFC 4918），让客户端可以像操作“远程文件系统”一样，通过 HTTP(S) 对服务器上的资源进行**创建、读取、更新、删除、移动、复制、列目录、读写元数据**与**加锁**等操作。它的设计目标是：用已经被广泛接受的 HTTP 语义与基础设施（端口 80/443、代理/CDN、TLS、鉴权）来支持**跨平台、跨网络的协作编辑与内容管理**。

<img src="Z:\Public\images\what-is-webDAV-800x480.png" alt="What Is WebDAV? Easy 2025 Guide to the Protocol" style="zoom: 67%;" />

> #### 常见实现与客户端
>
> 服务器：Apache httpd (mod_dav)、Nginx（通过第三方模块/网关）、IIS、SabreDAV、Nextcloud/ownCloud、litmus 兼容实现等。
>  客户端：Windows（WebClient）、macOS（访达“连接到服务器”）、Linux（davfs2、gio/gvfs）、移动端与三方工具（WebDAV Drive、rclone、Cyberduck、Mountain Duck、KeePass/Obsidian/备份工具插件等）。

### 核心抽象与“数据结构”

严格来说 WebDAV 是应用层协议，不定义内存结构；下列是其**资源模型与线上的数据结构/对象**：

#### Resource（资源）

- 对应 URL 标识的实体，可理解为“文件”。
- 继承 HTTP 实体语义（有 `ETag`、`Last-Modified`、`Content-Type`、`Content-Length` 等）。

#### Collection（集合）

- 资源的“目录”。可包含子集合与普通资源。
- 通过 `MKCOL` 创建；列出内容通过 `PROPFIND Depth=1`。

#### Properties（属性，元数据）

- 以 **XML（带命名空间）** 表达的键-值元数据，存储在资源或集合上。
- 分为 **live properties**（由服务器维护，如 `getlastmodified`, `getetag`, `resourcetype`）与 **dead properties**（任意自定义属性）。
- 读写：`PROPFIND` / `PROPPATCH`。

#### Locks（锁）

- 为避免并发写冲突，WebDAV提供写锁：**独占锁**或**共享锁**。
- 创建锁：`LOCK`（返回 `Lock-Token`）；续租或释放：`LOCK`/`UNLOCK`；带锁操作需在请求头 `If:` 中携带 token。
- 锁信息可通过 `prop` 查询（`lockdiscovery`）。

#### Multi-Status（多状态响应）

- 当对“集合”或“多资源”做操作时，服务器以 `207 Multi-Status` 返回一份 **XML 响应体**，逐条给出每个目标的状态码与属性（典型于 `PROPFIND`、`PROPPATCH`、`COPY/MOVE` 深度操作）。

#### Depth 与条件请求

- `Depth: 0|1|infinity` 控制操作递归层级（列目录/复制/移动/属性查询等）。
- 结合 HTTP 条件请求：`If-Match`/`If-None-Match`/`If` 头与 `ETag`，用于**乐观并发控制**。

> 扩展族：
>
> - **ACL（访问控制）**：基于 `DAV:` 命名空间的权限模型（RFC 3744）。
> - **DeltaV（版本控制）**：RFC 3253，引入 versioned resource、activity、baseline 等概念（较少通用实现）。
> - **CalDAV/CardDAV**：在 WebDAV 上定义的日历/联系人同步协议（广泛应用于日历、通讯录）。

### 工作原理（请求–响应流程）

WebDAV 完全遵循 HTTP 的请求-响应与无状态特性，通过**新增方法与头部**来表达“文件系统式”的意图。

#### 常用方法

<img src="Z:\Public\images\webdav-protocol-20230727-glossar-beitrag-grafik-kr-EN.png" alt="WebDAV protocol - definition, explanation and applications" style="zoom:67%;" />

- 基础（继承 HTTP）：`GET`（下载/读取）、`HEAD`、`PUT`（上传/覆盖）、`DELETE`（删除）、`OPTIONS`（发现支持的 DAV 类）。
- WebDAV 扩展：
    - `PROPFIND`：读取资源/集合的属性与目录清单（配合 `Depth` 使用）。
    - `PROPPATCH`：修改（增加/删除/更新）属性。
    - `MKCOL`：创建集合（目录）。
    - `COPY` / `MOVE`：跨/同一服务端路径复制或移动；使用 `Destination` 头，并可带 `Overwrite: T/F`。
    - `LOCK` / `UNLOCK`：加锁/解锁（写锁），响应与请求中涉及 `Lock-Token` 和 `If` 条件。

### 一个简单的示例（列目录）

#### 请求

```http
PROPFIND /docs/ HTTP/1.1
Host: webdav.example.com
Depth: 1
Content-Type: application/xml; charset="utf-8"

<?xml version="1.0" encoding="utf-8" ?>
<propfind xmlns="DAV:">
  <prop>
    <displayname/>
    <getcontentlength/>
    <getlastmodified/>
    <resourcetype/>
    <getetag/>
  </prop>
</propfind>
```

**响应（节选）**：

```http
HTTP/1.1 207 Multi-Status
Content-Type: application/xml; charset="utf-8"

<multistatus xmlns="DAV:">
  <response>
    <href>/docs/</href>
    <propstat>
      <prop>
        <displayname>docs</displayname>
        <resourcetype><collection/></resourcetype>
        <getlastmodified>Mon, 20 Oct 2025 06:11:00 GMT</getlastmodified>
        <getetag>"5f2a-..."</getetag>
      </prop>
      <status>HTTP/1.1 200 OK</status>
    </propstat>
  </response>
  <response> ... 子资源 ... </response>
</multistatus>
```

### 并发与一致性

- **乐观并发**：利用 `ETag` + `If-Match`/`If-None-Match`，在 `PUT`/`DELETE` 时确保基于期望版本写入。
- **悲观并发**：`LOCK` 获得写锁（独占/共享），后续更新在请求头 `If: (<Lock-Token>)` 下进行；完成释放 `UNLOCK`。
- **集合操作**：`COPY/MOVE` 可在服务端原地高效执行，减少客户端多次下载/上传成本。

### 使用场景

1. **跨平台“网络磁盘/网盘”与协作编辑**
    - 在 Windows/macOS/Linux 原生挂载为网络驱动器/卷；在办公/家庭网络/NAS 中进行文件共享与多端同步（例如 Nextcloud + WebDAV）。
2. **移动端/三方工具的“通用存储后端”**
    - 许多应用以 WebDAV 作为远程存储适配器（Obsidian/Notability/笔记与文档同步、相册备份、密码库同步等）。
3. **轻量内容管理与发布**
    - 小型 CMS/知识库/静态内容分发，用 WebDAV 统一上传、改名、移动、属性标注（标签、分类等）。
4. **自动化与备份**
    - `rclone/restic/duplicity` 等将 WebDAV 作为后端，进行增量备份、定时同步与脚本化运维。
5. **受限网络环境中的文件访问**
    - 复用 443 端口与企业代理；TLS 友好、方便穿越仅放行 HTTP(S) 的网络边界。

### WebDAV 解决了哪些问题？

- **统一协议与生态**：基于 HTTP 的统一传输、鉴权与安全（TLS），跨平台广泛兼容，降低部署与穿透成本。
- **目录与属性的“网络原语”**：通过 `PROPFIND/PROPPATCH/MKCOL` 等在 HTTP 里原生表达**列目录、读写元数据、创建目录**等操作（这是 FTP/原生 HTTP 不完整或不标准的部分）。
- **并发控制**：提供写锁（悲观）与 ETag 条件请求（乐观），降低多人协作时的冲突与丢写。
- **原子/批量操作**：`COPY/MOVE` 与 `207 Multi-Status` 支持在服务端高效完成复杂目录操作与批量结果汇报。
- **可扩展的元数据模型**：XML + 命名空间 + live/dead 属性，既有标准属性，也允许业务自定义。
- **扩展生态（CalDAV/CardDAV）**：在 WebDAV 之上定义结构化业务（日历、联系人），实现跨系统互操作。

## OSS 对象存储

### 是什么（What）

**OSS 是面向非结构化数据的分布式存储服务**。与本地文件系统或块存储不同，OSS 以“**桶（Bucket）—对象（Object/Key）**”的方式，通过 **HTTP/HTTPS API** 提供高可用、高扩展的读写与管理能力。它适合存放图片、音视频、备份包、日志、模型权重、数据湖文件等，并支持版本管理、生命周期、访问控制、跨区域复制、加密等能力。

<img src="Z:\Public\images\O1CN01MRqQ2o27o93wEIE80_!!6000000007843-2-tps-6667-3168.png_.png" alt="对象存储服务-阿里云" style="zoom: 12%;" />

> 关键词：对象级存取、海量水平扩展、按量计费、与计算解耦、跨地域访问。

### 有哪些数据结构（Data Model）

- **Bucket（桶）**

    全局命名空间的容器，承载对象与默认策略。常见属性：地域、存储类型（标准/低频/归档/冷归档等）、版本控制、加密默认值、跨域（CORS）、日志/审计、访问策略（ACL/Policy）。

- **Object（对象）**

    由 **Key（路径样式的字符串）+ 数据体 + 元数据（Metadata/Headers）** 组成。Key 只是字符串，**没有真正的目录**；“/” 仅用于前缀筛选以模拟层级。

- **Multipart（分片上传）**

    将大对象分片并行上传，完结时合并；可断点续传、提高上传吞吐。

- **Appendable Object（可追加对象，阿里云 OSS 特有）**

    支持尾部**顺序追加写**（如日志/数据采集），天然适配流式生产场景。

- **Symlink（符号链接，阿里云 OSS 支持）**

    对象级“软链接”，便于做别名或灰度切换（例如 `latest` → `v1.2.3`）。

- **Object Tagging / User-Defined Metadata**

    以键值对为对象打标签或携带业务头，便于检索、计费分摊、治理。

- **ACL / Bucket Policy / STS（临时凭证）**

    访问控制的三件套：对象/桶级权限、策略语句、短期密钥授权。

- **Lifecycle / Intelligent Tiering**

    生命周期与（可选）智能分层策略，自动转冷、归档与过期清理。

- **Inventory / Server Access Logging**

    清单与访问日志，支撑审计、对账与数据治理。

### 原理（How it works）

- **对象存取语义**

    通过 RESTful API（PUT/GET/DELETE/HEAD/POST）或 SDK 读写对象；**重命名与就地修改并非原生**——一般用“复制+删除”或覆盖写实现。

- **一致性**

    现代主流 OSS（含阿里云、AWS 等）通常提供 **强一致的读后写/列举可见性**（以官方文档为准），对应用侧简化显著；早期产品多为“最终一致”，现在基本已收敛。

- **高可用与耐久**

    常见做法是 **跨设备/机架/可用区多副本或纠删码（Erasure Coding）** 存储；桶级再配合**跨区域复制（CRR）**实现容灾。耐久度通常宣称 11 个 9 级别。

- **扩展性与性能**

    元数据服务与数据面分离，Key 空间按前缀或哈希分片到多路后端；客户端利用 **并发/分片上传/Range 读取/多线程下载/CDN 回源** 提升吞吐。

- **安全**

    结合 **SSE（服务端加密）/KMS/客户主密钥（CMK）**、**TLS**、**细粒度策略**、**VPC/内网 Endpoint**、**跨域 CORS** 等保障传输与存储安全。

- **数据处理内联化**

    常见能力：**服务端图片样式处理、音视频转码管线、Select/SQL on Object（按条件拉取对象内部字节）**、清单/事件通知（投递到消息队列、函数等）。

### 使用场景（Use Cases）

- **静态网站 / 前端资源**：与 CDN 搭配，低成本高可用发布。
- **备份与归档**：数据库/镜像/日志/模型权重长期保存；生命周期自动转冷。
- **数据湖 / 大数据**：Parquet/ORC/CSV 等湖格式存取，联动计算（EMR、Spark、Flink、MaxCompute、Hadoop 兼容层等）。
- **音视频点播与直播**：作为源站与内容库，结合媒体处理与 CDN。
- **日志与观测**：海量日志落地（Appendable Object 很好用），配合检索或离线分析。
- **AI/ML 数据集**：样本库、特征文件、训练/评测数据、模型发布。
- **跨区域/跨云分发**：CRR 做多活、容灾与近源访问。

## rsync 介绍文档

### 是什么？

![img](Z:\Public\images\ca0e812c8cc1a60855d5a57bc3d9e31f.jpeg)

`rsync` 是一个用于**高效增量同步**文件与目录的工具/协议（最初由 Andrew Tridgell 等人设计）。它可以在本地或通过网络同步两端的数据，只传输**差异块（delta）**，从而显著减少带宽与时间开销。rsync 既是一条命令，也是一套有版本演进的**应用层协议**（常见 protocol ver. 29/30/31）。

### 有哪些数据结构？

为实现“只传变化”的目标，rsync 在同步过程中构建并使用了下列核心数据结构：

#### 文件列表（file list）

- 每个待同步条目包含：路径、大小、mtime、权限/属主、设备号、硬链接键、是否稀疏/符号链接、ACL/xattr（可选）等。
- 发送端与接收端据此决定哪些文件需要比较、创建或更新。

#### 块签名表（block signatures）

- 将大文件切成固定或近似固定大小的**块（block）**，对每块计算两种校验：
    - **弱滚动校验（rolling checksum）**：基于字节和加权和的轻量算法，可 O(1) 更新，便于滑窗扫描。
    - **强校验（strong checksum）**：早期为 MD4，后续多为 MD5（部分实现支持更强散列）；用于消除弱校验碰撞。
- 接收端把“弱校验 → 签名记录”组织为**哈希表/散列表**，实现近似 O(1) 匹配查询。

#### 滑动窗口（sliding window）

- 在“扫描端”（通常是发送端）对整个文件流以 1 字节步长滑动，快速计算弱校验并查表匹配，匹配后再比对强校验。

#### 指令/令牌流（token stream / delta program）

- 差异以两类指令编码：
    - **COPY**：引用对端已有文件的块（按块索引）。
    - **LITERAL**：直接内联发送新增字节。
- 指令流经压缩（可选，如 `--compress`）后传输。

#### 过滤规则集（filter/exclude list）

- 有序规则（`--exclude/--include`、`.rsync-filter`），支持通配符、目录限定与继承；用于在创建文件列表时裁剪目标集。

### 原理（工作机制）

**目标**：最小化传输字节数，同时保持文件内容与元数据一致。

**基本流程**（以“远端目标存在旧版本文件”为例）：

1. **协商与文件列表**

    双方交换选项、协议版本与特性位，发送端生成待同步的**文件列表**并传给对端（或双方协同生成）。

2. **签名阶段（在“持有旧版本”的一侧）**

    对端把旧文件切块，计算每块的**弱/强校验**，构建**块签名表**并发回。

3. **匹配阶段（在“持有新版本”的一侧）**

    发送端以**滑动窗口**扫描新文件字节流：

    - 计算滚动弱校验 → 查表命中 → 用强校验确认 → 生成 **COPY** 指令；
    - 不命中时把窗口中的原始字节聚合成 **LITERAL** 指令。
         得到紧凑的**delta 程序（token stream）**。

4. **重建与校验**

    接收端据 **COPY/LITERAL** 指令在本地重建新文件；完成后可进行**完整性校验**（强散列或大小/mtime）。

5. **元数据同步**

    根据选项更新权限、时间戳、属主、ACL、xattr、硬链接关系、稀疏属性等。

> 关键点：**滚动校验**使得插入/删除造成的“对齐漂移”不会破坏匹配能力；强校验消除碰撞，保证内容正确。

### 使用场景

- **异地备份与镜像**：

    定期把生产数据同步到备份机/对象目录；结合 `--link-dest` 做“近似快照”（硬链接不变块，新增只占用增量空间）。

- **网站/应用部署**：

    代码与静态资源的快速增量分发，比 `scp`/FTP 更省带宽。

- **日志与媒体库同步**：

    大体量文件的日常追加或少量修改，rsync 只传改动部分。

- **跨机房/跨云迁移**：

    首次全量 + 多次增量，最终切换时窗口更短。

- **本地目录对齐**：

    同一台机上两个目录的快速镜像（不走网络）。

### 解决了哪些问题？

- **带宽浪费**：只传变化块，避免整文件重传。
- **时延与中断成本**：支持断点续传（`--partial`, `--append`），传输出错可快速重试。
- **权限/元数据一致性**：可同步权限、属主、时间戳、ACL、xattr、硬链接与设备文件（选项控制）。
- **稀疏文件高效传输**：识别“洞洞”（holes），避免传输与落盘真实零字节。
- **近似快照备份**：配合 `--link-dest` 与目录轮转工具（如 rsnapshot），以硬链接复用未变文件，节省空间。
- **可预览/可控**：`--dry-run` 预演变更；丰富的过滤规则精准控制同步范围。

### 常用工作模式与命令示例

> 均为示例，按需添加 `-a`（归档）、`-v`（详细）、`-h`（人类友好）、`--delete`（删除多余文件）等。

#### 本地目录到目录

```bash
rsync -avh --delete /data/www/ /backup/www/
```

#### 通过 SSH 到远端

```bash
rsync -avz --delete -e "ssh -p 2222" ./site/ user@host:/var/www/site/
```

#### 增量备份（硬链接快照）

```bash
# 以昨天的快照为基准，复用未变文件的硬链接，只为新增/变化写新数据
rsync -a --delete --link-dest=/backup/daily-2025-10-19 /data/ /backup/daily-2025-10-20
```

#### 过滤规则

```bash
rsync -av --exclude '.git/' --exclude '*.tmp' src/ dest/
# 或使用 .rsync-filter 文件管理复杂规则
```

#### 大文件的就地更新（减少 I/O）

```bash
rsync -av --inplace bigfile.img remote:/data/
```

#### 保持扩展属性/ACL（系统需支持）

```bash
rsync -aAX src/ dest/
```

## iSCSI

### 是什么（What）

**iSCSI（Internet Small Computer System Interface）**是把传统 **SCSI 命令**封装在 **TCP/IP** 之上的网络块存储协议。它让服务器（**Initiator**）通过以太网访问远端磁盘/卷（**Target**），像本地块设备一样进行 **读写块 I/O**。

对上层应用（数据库、虚拟化平台、文件系统）而言，iSCSI 呈现的是**块设备**而非文件共享（对比如 NFS/SMB）。

- **Initiator**：发起端（主机上的内核/驱动或 HBA 卡）
- **Target**：存储端（阵列、软件 Target、SAN 设备）
- **LUN**：Target 导出的逻辑单元（逻辑卷/磁盘）

<img src="Z:\Public\images\fc994abbfc5dab7b59a3c4fa1f7599c8.png" alt="在这里插入图片描述" style="zoom:50%;" />

### 核心数据结构（Data Structures）

iSCSI 在网络上传输的最小单元是 **PDU（Protocol Data Unit）**，其主体由以下部分组成：

#### BHS（Basic Header Segment, 48B 固定）

- **Opcode**：PDU 类型（SCSI Command、Data-Out、Data-In、Response、Login/Logout 等）
- **Flags**：立即执行、最终分片（F）、读取/写入方向等
- **TotalAHSLength / DataSegmentLength**：附加头/数据段长度
- **LUN**：8 字节 LUN 标识
- **Initiator Task Tag（ITT）**：由发起端分配，标识一次 SCSI 任务
- **CmdSN / ExpStatSN**：会话顺序控制（Command 序号/期望的状态序号）
- **DataSN / StatSN**：数据/状态序号（流控与重传对齐）

#### AHS（Additional Header Segment，可选）

 承载额外协商信息或扩展字段。

#### Data Segment（可选）

 实际负载（如写请求的数据块或读返回的数据块）。**必须按 4 字节对齐**（Padding）。

#### Digest（可选）

- **HeaderDigest** 与 **DataDigest**（通常 CRC32C），用于端到端校验。

### 会话与连接

- **Session（ISID + Target Portal Group Tag）**：Initiator 和 Target 之间的逻辑会话。
- **Connection（CID）**：一个会话可包含**多条 TCP 连接**（MC/S，Multiple Connections per Session），用于并行与带宽聚合。
- **任务（Task）**：一次 SCSI 命令的生命周期（由 ITT/TTT、CmdSN、StatSN 协同跟踪）。

### 标识与命名

- **IQN（iSCSI Qualified Name）**：`iqn.yyyy-mm.<反转域名>:<可选路径>`（如 `iqn.2003-01.org.linux-iscsi.host:disk01`）
- **EUI**：基于 IEEE EUI-64 的 16 字节标识（较少见）
- **Target Portal**：`IP:Port`（默认 3260），可带 **TPGT**（Target Portal Group Tag）

### 关键序号/标签

- **CmdSN / ExpCmdSN**：命令窗口与顺序控制
- **StatSN / ExpStatSN**：响应回执顺序
- **DataSN**：数据流分片序号
- **ITT/TTT**：Initiator/Target Task Tag，匹配请求与响应

### 工作原理（How）

#### 发现（Discovery）

- **SendTargets**：Initiator 连接到某个 **Portal**，通过文本协商获取可用 Target/LUN 列表。
- **iSNS（可选）**：集中式名称与发现服务。

#### 登录与安全（Login & Security）

- **Login Phase**：分两阶段/三阶段状态机（Security → Operational Negotiation → Full Feature Phase）
- **安全**：
    - **CHAP / Mutual CHAP**：身份认证
    - **IPsec / TLS（少见）**：链路加密
- **参数协商**（Text Key-Value）：
    - **MaxRecvDataSegmentLength**、**FirstBurstLength**、**MaxBurstLength**
    - **ErrorRecoveryLevel（ERL 0/1/2）**
    - **InitialR2T / ImmediateData**（写入路径优化）
    - **DataDigest/HeaderDigest**（CRC32C 开关）

#### 全功能阶段（Full Feature Phase）

- **命令/数据流转**
    - 读：Initiator 发送 **SCSI Command（READ）** → Target 以 **Data-In PDUs** 分片返回数据 → **SCSI Response** 完结
    - 写：可先发 **Immediate Data** 和/或 **Unsolicited Data**，其后依据 Target 的 **R2T（Ready To Transfer）** 令牌发送 **Data-Out PDUs** → **SCSI Response**
- **顺序控制与重传**
    - 通过 CmdSN/StatSN/DataSN、期望序号与 **Status-Class/Detail** 错误码实现有序传输与**选择性重传**（取决于 ERL）。
- **多连接/多路径**
    - **MC/S**：一个会话下多条 TCP 连接并行分担 I/O
    - **MPIO（多路径 I/O）**：操作系统层面对**多条会话或多 Portal** 做路径聚合/故障转移（与 iSCSI 协议解耦）

#### 性能增强

- **Jumbo Frames（MTU 9000）**：减少 PDU/中断开销
- **TOE/iSCSI HBA**：TCP 或 iSCSI 卸载
- **iSER（iSCSI Extensions for RDMA）**：将数据面改走 **RDMA（RoCE/iWARP/InfiniBand）**，降低 CPU/延迟
- **窗口/队列调优**：TCP 窗口、队列深度（Queue Depth）、并发 I/O 数

### 使用场景（Use Cases）

**虚拟化存储**：

- VMware/Hyper-V/KVM 的共享数据存储（VMFS、CSV、LVM 等），支撑 vMotion/HA/DRS 等特性。

**数据库后端块存储**：

- 为 Oracle、MySQL、PostgreSQL、SQL Server 等提供**原始块设备**，便于主机侧文件系统/卷管理。

**容器与编排**：

- 作为 Kubernetes 的持久卷（PV）（在早期与私有环境中仍然常见）。

**备份/归档与二线存储**：

- 备份服务器挂载廉价磁盘阵列的 LUN，做 D2D 备份、冷数据池。

**跨机房/容灾**：

- 在 IP 广域网下提供远程块设备，结合复制/快照实现 DR。

**开发/测试环境的共享块盘**：

- 以较低成本替代光纤通道 SAN。

## FTP / FTPS

### 它们是什么？

- **FTP（File Transfer Protocol）**：互联网早期的文件传输应用层协议，采用**一条控制连接 + 多条临时数据连接**的“双通道”模型；明文传输，默认端口 **21**（控制），数据端口依模式而定。经典规范来自 **RFC 959** 及其扩展（如 IPv6/EPSV/EPRT 的 RFC 2428、MLST/MLSD 的 RFC 3659 等）。
- **FTPS（FTP over TLS）**：在 FTP 之上加入 **TLS 加密**（认证、机密性与完整性），常见两种：
    - **显式 FTPS（Explicit）**：先普通 TCP 连接到 21 端口，再用 `AUTH TLS` 升级为 TLS。
    - **隐式 FTPS（Implicit）**：直接以 TLS 握手起步，历史上常用 **990** 端口（控制通道）。

> 注意：**FTPS ≠ SFTP**。SFTP 是 SSH 子系统（单 TCP 22，完全不同协议与报文）。

### 核心数据结构 / 概念

#### 控制与数据通道

<img src="Z:\Public\images\b50a7b0e-4b81-4a19-8817-00deb57e648f_ftp-server-control-and-data-channels-graphic.jpeg" alt="What is FTP Tutorial: Overview and Business Use Cases | ExaVault Blog" style="zoom: 80%;" />

- **控制通道**：客户端 ↔ 服务器，长期保持；基于文本命令/响应（ASCII 行）。
- **数据通道**：每次文件传输或目录列出时临时建立；传原始字节流（或分块/压缩模式）。

#### 命令与响应（控制面“报文”）

- **命令**（客户端 → 服务器，常见）：
    - 身份认证：`USER`、`PASS`
    - 会话管理：`QUIT`、`NOOP`、`SYST`、`FEAT`
    - 路径与目录：`PWD`、`CWD`、`CDUP`、`MKD`、`RMD`
    - 数据通道协商：`PORT`/`EPRT`（主动），`PASV`/`EPSV`（被动）
    - 传输参数：`TYPE`（A=ASCII，I=Image/Binary，L 8 等）、`MODE`（S/B/C）、`STRU`（F/R/P）
    - 文件操作：`RETR`（下载）、`STOR`（上传）、`APPE`（追加）、`DELE`、`RNFR/RNTO`（重命名）
    - 列表/元数据：`LIST`、`NLST`、`MLST/MLSD`、`SIZE`、`MDTM`、`REST`（断点续传偏移）
- **响应码**（服务器 → 客户端，三位数字 + 文本）：
    - **1xx**：初始正应答（开始传输）
    - **2xx**：完成（OK）
    - **3xx**：需进一步信息（如需密码）
    - **4xx**：临时错误
    - **5xx**：永久错误
    - 常见示例：`220` 服务就绪、`331` 需要密码、`230` 登录成功、`227` 进入被动模式、`150/226` 数据传输开始/完成。

#### 文件/传输相关“结构”

- **数据类型（`TYPE`）**：
    - `A`（ASCII 文本）、`I`（二进制/图像，**工业默认**）、`E`（EBCDIC，较少用）、`L n`（本地字长）。
- **文件结构（`STRU`）**：
    - `F`（File，连续字节流，最常用）、`R`（Record）、`P`（Page）。
- **传输模式（`MODE`）**：
    - `S`（Stream，默认/最常用）、`B`（Block）、`C`（Compressed）。
- **目录列表格式**：
    - 传统 `LIST` 输出是**非结构化文本**（UNIX/Windows 风格不一）。
    - 现代推荐 `MLST/MLSD`（机器可读键值格式：`type=dir;size=...;modify=YYYYMMDDHHMMSS; name`）。

#### 扩展与特性

- **IPv6/防 NAT 指令**：`EPSV`、`EPRT`（替代 `PASV/PORT`），对防火墙/NAT 友好。
- **功能探测**：`FEAT`（列出服务器支持的扩展）。
- **断点续传**：`REST <offset>` + `RETR/STOR`。
- **UTF-8**：`OPTS UTF8 ON`（或默认支持）以避免中文乱码。

#### FTPS 相关结构

- **TLS 升级与参数**：`AUTH TLS` → `PBSZ 0` → `PROT P|C`
    - `PBSZ`：保护缓冲区大小，现代实现常固定 `0`。
    - `PROT`：**P**（保护/加密数据通道）或 **C**（Clear/明文数据通道）。
- **证书与校验**：服务器端证书（公有 CA 或私有 CA），可选双向认证（客户端证书）。
- **会话复用**：部分服务器要求数据通道沿用控制通道的 TLS 会话（或会话票据），以防“FTP-CCC”类攻击与会话劫持。

### 工作原理（握手与数据流）

#### 基本流程（以被动模式 + 二进制为例）

```
TCP 21 建立 → 220 欢迎
C: USER alice
S: 331 需要密码
C: PASS ******
S: 230 登录成功
C: TYPE I                 （二进制）
S: 200 OK
C: EPSV                   （或 PASV）
S: 229 进入扩展被动 (|||54012|)   ← 服务器开放了 54012
C: 建立 TCP 到 54012       （数据通道）
C: RETR /path/file.bin
S: 150 打开二进制数据连接
... 传输字节流 ...
S: 226 传输完成
C: QUIT
S: 221 再见
```

#### 主动 vs 被动模式（与 NAT/防火墙）

<img src="Z:\Public\images\ftp-active-vs-passive-e1638177916888.webp" alt="FTP Active Vs Passive - Which One Is Right To Your Needs?" style="zoom:50%;" />

**主动（PORT/EPRT）**：客户端在本地监听端口，**服务器主动回连**客户指定端口建立数据通道。

- 优点：服务器端配置简单。
- 缺点：客户端常在 NAT/防火墙后，**难以被回连**（不友好）。

**被动（PASV/EPSV）**：服务器告诉客户端一个端口，**客户端主动连接**该端口。

- 优点：穿越 NAT/企业防火墙更容易（单向外连）。
- 最佳实践：启用 **EPSV/EPRT**（对 IPv4/IPv6 统一），并在服务器上**固定 PASV 端口范围**，同时在防火墙放行该范围。

#### 断点续传（大文件可靠性）

- 通过 `REST <offset>` 指定偏移点，再执行 `RETR`（下载）或 `STOR`（上传），可实现**续传**。

### FTPS：安全层的接入方式

![FTPS Client | GoAnywhere](Z:\Public\images\ftps-2021_0.png)

#### 显式 vs 隐式

- **显式 FTPS（推荐）**：连 21 → `AUTH TLS` 升级 → `PBSZ 0` → `PROT P`（数据通道加密）。
- **隐式 FTPS**：连 990，**起始即 TLS**。历史兼容性强，但扩展性差（现代更倡导显式）。

#### 数据通道保护与性能

- `PROT P`：控制与数据**都加密**，最安全，但 CPU/TLS 开销更高。
- `PROT C`：控制通道加密、数据通道明文；在受信内网、大吞吐批量场景可权衡采用（并不建议跨公网）。

#### 证书与兼容

- 使用**受信 CA**签发证书以避免客户端警告；内网可用 **私有 CA**，需部署信任链。
- **TLS 版本与套件**：建议 TLS 1.2/1.3（禁用过时算法与协议版本）。

## SFTP

### SFTP 是什么？

<img src="Z:\Public\images\04pya2amdo.jpeg" alt="img" style="zoom: 80%;" />

- **SFTP（SSH File Transfer Protocol）** 是运行在 **SSH-2**（TCP/22）之上的**二进制文件传输子系统**。与 FTP/FTPS 完全不同，它：
    - 复用 **SSH 单连接单端口**（可多信道），天然穿越 NAT/防火墙；
    - 具备 **机密性、完整性与端点认证**（来自 SSH 的加密、MAC/KEX/主机密钥）；
    - 使用**结构化二进制报文**，跨系统语义更统一（原生支持权限、时间戳、符号链接等）。
- 常见版本：**v3**（事实上的通用兼容，OpenSSH 默认）、v4~v6（少量实现支持更多语义）。

> 术语提醒：`sftp` 既指协议，也常指客户端命令行工具（OpenSSH 套件内）。

### 核心数据结构 / 报文与概念

#### 报文外层框架（SSH 信道内）

SFTP 所有消息都封装在 SSH 的一个 **channel** 上，以二进制格式往返：

```
uint32  packet_length
byte    packet_type   (SSH_FXP_xxx)
uint32  request_id
...     payload (因类型而异)
```

- **packet_length**：后续字节长度（不含自身）。
- **packet_type**：功能分类（如 OPEN、READ、WRITE…）。
- **request_id**：客户端分配的 ID，用于**乱序匹配响应**（支持并发/管线化）。

#### 关键消息类型（常见 v3）

- 会话起始：`SSH_FXP_INIT` ↔ `SSH_FXP_VERSION`
- 路径解析：`REALPATH`
- 文件打开/关闭：`OPEN`、`CLOSE`
- 读写：`READ`（带 `handle` + `offset` + `len`）、`WRITE`（带数据）
- 目录：`OPENDIR`、`READDIR`、`CLOSE`
- 元数据：`STAT`/`LSTAT`/`FSTAT`、`SETSTAT`/`FSETSTAT`
- 链接/操作：`SYMLINK`、`READLINK`、`RENAME`、`REMOVE`、`MKDIR`、`RMDIR`
- 返回：`NAME`（目录列举结果或路径解析结果）、`ATTRS`（属性）、`STATUS`（错误/成功码）

**STATUS 常见码**：`SSH_FX_OK`、`SSH_FX_EOF`、`SSH_FX_NO_SUCH_FILE`、`SSH_FX_PERMISSION_DENIED`、`SSH_FX_FAILURE` 等。

#### 文件句柄与属性结构

- **Handle（文件句柄）**：`OPEN/OPENDIR` 成功返回一个**不透明字节串**，后续 `READ/WRITE/READDIR/CLOSE` 以此标识对象。
- **ATTRS（文件属性）**（按 flag 可选出现）：
    - 大小（`size`）、UID/GID、权限（POSIX mode bits）、访问/修改时间（atime/mtime）、扩展键值对。
- **NAME（目录项）**：条目列表，每个包含 `filename`、`longname`（兼容 ls 风格，可忽略）、`attrs`。

#### 传输语义

- **随机访问**：读取或写入时显式带 `offset`，天然支持**断点续传/并行分块**。
- **目录枚举**：`OPENDIR` → 多次 `READDIR` 直到 `STATUS:EOF` → `CLOSE`。
- **原子重命名与持久化**：通过 `RENAME`（以及扩展 `posix-rename@…`）、`fsync@openssh.com` 增强跨平台稳健性。

#### 常见扩展（vendor extensions）

- `posix-rename@openssh.com`（原子 rename）
- `statvfs@openssh.com`（查询文件系统配额/块大小等）
- `hardlink@openssh.com`、`fsync@openssh.com`
- `copy-data`/`copy-file-range`（零拷贝/服务器端拷贝，较新实现）

### 工作原理（端到端流程与性能要点）

#### 握手与子系统启用

1. **TCP/22 建立** → SSH **KEX**（密钥交换）→ **主机密钥验证** → **用户认证**（密码/公钥/双因子）。
2. SSH **打开会话信道**，执行子系统：`subsystem: "sftp"`（或直接启动 `sftp-server` 程序）。
3. **SFTP 层**：客户端发 `INIT`（声明协议版本），服务端回 `VERSION`（含支持的扩展）。

#### 典型读写时序（并发/管线化）

```
Client                                             Server
  SSH: open channel "sftp"
  SFTP: INIT ------------------------------->       VERSION
  OPEN "file.bin" (flags, attrs) ---------->       HANDLE h
  READ h, off=0, len=64k ------------------>       DATA 64k
  READ h, off=64k, len=64k ---------------->       DATA 64k
  ...（多个 READ 可并发，凭 request_id 乱序匹配）...
  CLOSE h --------------------------------->       STATUS OK
```

- **管线化**：客户端**连续发送多个 READ/WRITE**，不必等待前一条完成，显著降低 **RTT 影响**。
- **最佳 chunk**：常见 32–128 KiB（视端/链路调优）；配合**并发 outstanding**（如 16–64）能拉满带宽。

#### 校验与安全

- 安全性来自 SSH：**对称加密（AES chacha20 等）+ MAC/AEAD（Poly1305/GCM）+ KEX（ECDH/Curve25519）+ 主机密钥（Ed25519/RSA）**。
- **端点认证**：客户端校验**服务器主机指纹**（防中间人）；服务器校验**用户凭据**（密码/公钥/硬件密钥 + U2F/FIDO2）。

### 典型使用场景

- **企业与政府互联数据交换**：对等方只开放 22 端口就能达成安全文件传输，易于合规与审计。
- **自动化批处理/定时任务**：以脚本/SDK 实现**可靠断点续传**、**原子落盘**（写临时名→原子 rename）。
- **跨云/跨机房同步**：在复杂网络/严格防火墙环境中以单端口更稳（比 FTP/FTPS 的动态端口简单）。
- **设备与嵌入式网关**：许多安全基线只允许 SSH；SFTP 自然可用。
- **替代老旧协议**：从明文 FTP/基于 TFTP 的流程迁移到 SFTP，提升安全与语义一致性。

### SFTP 解决了哪些问题？

1. **安全传输的一致基线**：内建加密/完整性/认证，无需额外 TLS/证书栈（与 FTPS 对比）。
2. **NAT/防火墙友好**：单 TCP 端口、单连接多信道，减少网络侧开孔与 ALG 依赖。
3. **跨平台文件语义**：结构化属性（权限、时间、链接），减少“LIST 文本解析”这类不确定性。
4. **稳定与可恢复**：显式偏移读写 + 原子 rename +（可选）fsync 扩展，利于**断点续传/幂等落盘**。
5. **高延迟场景性能可控**：请求 ID + 管线化/并发让**长肥管道**也能跑满。

## SCP

### 是什么？

- **SCP（Secure Copy）** 是基于 **SSH** 的安全文件拷贝工具与协议族，目标是用最简洁的命令行语法完成**主机间文件/目录的复制**。
- 从历史上看有两种“实现路径”：
    1. **传统 scp 协议**（源自 BSD `rcp`，在 SSH 会话中执行远端 `scp` 程序，走自有的轻量文本控制报文）；
    2. **现代 scp over SFTP**：很多 OpenSSH 版本已将 `scp` 的底层默认改为 **SFTP 子系统**，以规避传统协议的一些安全与兼容问题，同时保留 `scp` 的命令行习惯（必要时可用选项切回 legacy）。

> 小结：**SCP 既是一条命令，也是两套可选的底层机制（legacy scp 协议 / SFTP）**。不管哪种，都复用 SSH 的**认证与加密**，单端口（TCP/22），对 NAT/防火墙友好。

### “数据结构”与控制报文

#### 传统 scp 协议（rcp 风格）的最小报文集

在 SSH 登录远端后，本地 `scp` 会在**一端以“发送者（source）”模式**、**另一端以“接收者（sink）”模式**启动远端 `scp`，两端通过 **STDIN/STDOUT** 交换**纯文本控制行 + 二进制数据**：

- **控制字节与行格式**（ASCII 文本）：
    - `C<mode> <size> <filename>\n`：拷贝**普通文件**（`mode` 八进制权限位，如 `0644`；`size` 十进制字节数）
    - `D<mode> 0 <dirname>\n`：进入**目录**（开始递归）
    - `E\n`：**退出目录**（递归回退一级）
    - `T<mtime> <atime> 0 0\n`：设置**时间戳**（修改/访问时间）
- **数据块**：紧随 `C...` 行后发送**原始文件字节流**，长度与 `<size>` 一致，随后发送**单字节 ACK**。
- **应答与错误**（单字节 + 文本）：
    - `\x00`：OK / ACK
    - `\x01<msg>\n`：非致命错误
    - `\x02<msg>\n`：致命错误（会终止）

> 可以把它理解成“**极简的、顺序化的、流式文件宣告 + 原样数据**”。没有目录列表与随机访问能力。

#### 现代 scp over SFTP 的结构

- 数据结构直接复用 **SFTP 的二进制消息集**：`OPEN/READ/WRITE/CLOSE/OPENDIR/READDIR/STAT/RENAME/...`，每条有 `packet_length | type | request_id | payload`，支持**偏移读写、目录枚举、扩展属性**等（详见你之前的 SFTP 文档）。
- `scp` 作为**外层语法糖**：仍然接受 `scp src dst` 的命令行与通配符，但底层用 **SFTP 消息**完成传输。

### 工作原理

#### 连接与认证（两种实现通用）

1. 本地发起 **SSH 连接**（主机密钥校验、KEX、用户认证：密码/公钥/多因子）；
2. 建立 SSH 会话信道：
    - **传统协议**：本地通过 SSH 启动远端 `scp`，组合 `-f`（从远端拉）或 `-t`（向远端推）模式；
    - **SFTP 方案**：本地通过 SSH 打开 **SFTP 子系统**，用 SFTP 消息执行相同的复制语义。

#### 传统 scp 的时序（示意）

**推送目录（-r）** 时序（右侧为远端接收者）：

```
SSH exec: remote `scp -t -r <dest>`
本地：D0755 0 project\n          →   远端：\x00
本地：T 1700000000 1700000000\n  →   远端：\x00
本地：C0644 12 README.md\n       →   远端：\x00
本地：（12 字节数据）            →   远端：\x00
本地：E\n                        →   远端：\x00
```

- 每一步都有 ACK，流程**严格顺序**；失败会返回 `\x01/\x02`。

#### scp over SFTP 的时序（示意）

```
SSH subsystem "sftp" up
OPEN dest/README.md (WRITE, create, trunc) → HANDLE
WRITE offset=0 len=... (可流水线/并发)     → STATUS OK...
CLOSE                                      → STATUS OK
```

- 可利用 **SFTP 的管线化** 减少 RTT 影响；目录递归通过 `OPENDIR/READDIR` 实现。

### 典型使用场景

- **临时/一次性** 的安全文件分发与拉取（开发、运维、值班场景中最常见的“顺手工具”）。
- **自动化脚本** 中的简单推送/拉取（CI/CD 中把构建产物扔到测试机，或从服务器捞日志/快照）。
- **隔离网络/堡垒跳转**：结合 `-J`（ProxyJump）或多跳 SSH，仍能一条命令到达目标。
- **最小依赖环境**：很多系统只装了 OpenSSH，直接 `scp` 即可，无需额外服务端组件。

### SCP 解决了哪些问题？

1. **把明文 rcp/ftp 换成安全链路**：复用 SSH 提供**机密性/完整性/身份认证**。
2. **极低心智负担**：`scp A B` 的**点到点**拷贝心智模型简单，学习成本最低。
3. **单端口 / NAT 友好**：SSH 22 一孔走天下；无需像 FTP/FTPS 那样动态开端口。
4. **跨平台可用性**：几乎所有类 Unix / 大多数网络设备都内置或可安装。
5. **覆盖常见元数据**：借助 `-p` 可保留时间戳/权限（传统协议靠 `T`/`C`；SFTP 方案靠属性）。

### 常用命令与参数（OpenSSH 语法）

#### 基本

- `scp file user@host:/path/`（推送）
- `scp user@host:/path/file .`（拉取）
- `scp -r dir user@host:/dst/`（递归目录）
- `scp -p file user@host:/dst/`（保留时间戳/权限）

#### 连接/跳板

- `scp -P 2222 file user@host:/dst/`（自定义端口）
- `scp -J jump hostA:/a hostB:/b`（经堡垒机转发）

#### 三段拷贝

- `scp -3 userA@hostA:/a userB@hostB:/b`（经本机中转的 A→B）

#### 调试

- `scp -v`（显示 SSH 与 scp 交互细节，定位失败点）
