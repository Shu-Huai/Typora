# 打包压缩

这篇文章主要在讲一件事：`.tar.gz` 之所以有两个后缀，不是因为命名啰嗦，而是因为它真的经历了两道工序。

- `.tar`：把多个文件、目录、权限、路径等信息打成一个归档文件。
- `.gz`：用 gzip 把这个归档文件压缩成更小的字节流。

也就是说，`.tar.gz` 不是一种“单一格式”，而是：

```text
目录 / 多个文件
    ↓ tar 打包
archive.tar
    ↓ gzip 压缩
archive.tar.gz
```

反过来解压时，顺序也要倒过来：

```text
archive.tar.gz
    ↓ gunzip 解压
archive.tar
    ↓ tar 解包
目录 / 多个文件
```

所以 `.tar.gz` 这两个后缀很诚实：它告诉你这个文件先被 tar 打包，又被 gzip 压缩。

这背后也体现了 Unix 世界的一个老思想：一个工具只做一件事，并把这件事做好。tar 负责归档，gzip 负责压缩，中间用管道连起来。

## 打包、压缩、归档格式：先把几个概念分清

很多人平时会把“打包”和“压缩”混着说，比如“把这个目录压缩一下”。日常沟通问题不大，但真正用命令时最好分清楚，因为不同工具负责的事情不一样。

### 打包：把多个东西合成一个东西

打包，也叫归档，英文常见说法是 archive。

它的核心目标不是变小，而是把多个文件、目录结构和相关元数据放进一个文件里。

比如一个目录长这样：

```text
project/
├── README.md
├── src/
│   └── main.c
└── docs/
    └── intro.md
```

用 tar 打包后，会得到：

```text
project.tar
```

这个 `.tar` 文件里面保存的不是单纯的文件内容，还包括：

- 文件路径
- 目录结构
- 文件权限
- 文件所有者和所属组
- 修改时间
- 符号链接
- 有些情况下还可以保存 ACL、扩展属性、SELinux 标签等

但是，tar 本身不负责把文件变小。

如果原目录大约 100 MB，打出来的 `.tar` 往往还是接近 100 MB，甚至可能因为对齐和元数据略大一点。

tar 的名字来自 Tape Archive，也就是“磁带归档”。早期 Unix 系统里，备份常常写到磁带上。磁带适合顺序写入，不适合随机跳来跳去，所以 tar 的工作方式就是把一堆文件按顺序排成一条连续的字节流。

这也是为什么 tar 非常适合管道：

```bash
tar -cf - project/
```

这里的 `-` 表示不写到普通文件，而是把归档内容输出到标准输出。

### 压缩：把一段字节流变小

压缩的目标是减少体积。

gzip、bzip2、xz、zstd、lz4 这些工具，本质上都是把输入的字节流变成更短的字节流。

![What Is GZIP Compression? A Guide to GZIP Compression for Faster Load Times](http://public.file.lvshuhuai.cn/images\Untitled-design-5.jpg)

例如：

```bash
gzip access.log
```

会生成：

```text
access.log.gz
```

注意，gzip 处理的是文件或字节流，不理解“目录”这个概念。

如果你直接对目录执行：

```bash
gzip project/
```

通常会报错，因为目录不是普通文件。

gzip 可以压缩多个文件，但它会分别生成多个 `.gz` 文件：

```bash
gzip a.log b.log c.log
```

结果是：

```text
a.log.gz
b.log.gz
c.log.gz
```

它不会自动把这三个文件合成一个包。

所以 gzip 的定位很清楚：

```text
一个文件 / 一条字节流 → 一个压缩后的文件 / 一条压缩后的字节流
```

### 打包 + 压缩：为什么会有 `.tar.gz`

如果要把整个目录既合成一个文件，又压小，就需要两步：

```bash
tar -cf project.tar project/
gzip project.tar
```

最后得到：

```text
project.tar.gz
```

更常见的写法是用管道一步完成：

```bash
tar -cf - project/ | gzip > project.tar.gz
```

这条命令可以拆开看：

```text
tar -cf - project/
```

把 `project/` 打成 tar 流，并输出到标准输出。

```text
|
```

管道，把左边命令的输出交给右边命令。

```text
gzip > project.tar.gz
```

gzip 读取 tar 流，压缩后写入 `project.tar.gz`。

这就是 `.tar.gz` 的本质：tar 和 gzip 两个工具串起来。

### 格式、算法、工具不是一回事

这几个词也容易混：

| 名称 | 类型            | 说明                                |
| ---- | --------------- | ----------------------------------- |
| tar  | 归档格式 / 工具 | 负责打包，不负责压缩                |
| gzip | 压缩格式 / 工具 | 常用 DEFLATE 算法，压缩单个文件或流 |
| zip  | 归档 + 压缩格式 | 一个格式同时处理打包和压缩          |
| 7z   | 归档 + 压缩格式 | 常见于 7-Zip，压缩率通常较高        |
| rar  | 归档 + 压缩格式 | 常见于 WinRAR / RAR                 |
| xz   | 压缩格式 / 工具 | 常用 LZMA2，压缩率高，速度慢        |
| zstd | 压缩格式 / 工具 | 速度快，压缩率也不错                |
| lz4  | 压缩格式 / 工具 | 极快，压缩率一般                    |

严格说：

- `.tar` 是归档文件。
- `.gz` 是 gzip 压缩文件。
- `.tar.gz` 是 tar 归档再 gzip 压缩。
- `.zip` 自己既能放多个文件，又能压缩每个文件。
- `.7z`、`.rar` 也是归档和压缩一体化格式。

## 常见格式怎么选：不是谁压得小谁就一定最好

不同格式的设计取舍不一样。有的重视兼容性，有的重视压缩率，有的重视速度，有的重视 Unix 元数据保存能力。

### `.tar`：只打包，不压缩

创建 tar 包：

```bash
tar -cf project.tar project/
```

查看 tar 包内容：

```bash
tar -tf project.tar
```

解包：

```bash
tar -xf project.tar
```

解到指定目录：

```bash
mkdir output
tar -xf project.tar -C output
```

tar 适合保留 Unix/Linux 文件结构和元数据，例如：

- 目录结构
- 权限
- 符号链接
- 用户和组
- 修改时间

如果是 Linux 源码包、系统备份、容器层文件、服务器目录迁移，tar 是非常自然的选择。

但 tar 本身不压缩，所以单独的 `.tar` 文件通常不适合网络传输，除非后面再接 gzip、xz、zstd 等压缩工具。

### `.tar.gz` / `.tgz`：最常见的 Unix 源码包格式

`.tar.gz` 也常写成 `.tgz`，两者本质一样。

创建：

```bash
tar -czf project.tar.gz project/
```

解压：

```bash
tar -xzf project.tar.gz
```

查看内容：

```bash
tar -tzf project.tar.gz
```

几个参数含义：

| 参数 | 含义              |
| ---- | ----------------- |
| `c`  | create，创建归档  |
| `x`  | extract，解包     |
| `t`  | list，列出内容    |
| `z`  | 使用 gzip         |
| `f`  | 指定文件名        |
| `v`  | verbose，显示过程 |

例如：

```bash
tar -xzvf nginx-1.27.4.tar.gz
```

可以拆成：

```text
x：解包
z：调用 gzip 解压
v：显示文件列表
f：后面跟文件名
```

很多人背的是 `xzvf`，但实际理解后就不需要死记了。

`.tar.gz` 的特点：

- 兼容性很好，几乎所有 Linux / macOS 环境都能处理。
- 压缩速度较快，压缩率中等。
- 适合源码包、日志包、一般备份包。
- gzip 是流式压缩，适合管道处理。

例如直接打包压缩后传到远程机器：

```bash
tar -czf - project/ | ssh user@server 'cat > project.tar.gz'
```

也可以远程直接解开：

```bash
tar -czf - project/ | ssh user@server 'mkdir -p /tmp/project && tar -xzf - -C /tmp/project'
```

这里没有生成中间文件，数据一路从本机 tar 到 gzip，再通过 ssh 到远程 tar。

### `.tar.bz2`：压缩率比 gzip 好，但速度偏慢

创建：

```bash
tar -cjf project.tar.bz2 project/
```

解压：

```bash
tar -xjf project.tar.bz2
```

查看：

```bash
tar -tjf project.tar.bz2
```

参数 `j` 表示 bzip2。

bzip2 曾经很常见，压缩率通常比 gzip 好，但速度慢不少。今天新项目里它的存在感已经下降，很多场景被 xz 或 zstd 替代。

适合：

- 对兼容性有要求，但希望比 gzip 小一点。
- 老系统或老发布流程里还在使用 `.tar.bz2`。

不太适合：

- 大量日志实时压缩。
- 追求速度的备份场景。

### `.tar.xz`：压缩率高，适合发布包，但不适合着急

创建：

```bash
tar -cJf project.tar.xz project/
```

解压：

```bash
tar -xJf project.tar.xz
```

查看：

```bash
tar -tJf project.tar.xz
```

参数 `J` 表示 xz，注意是大写。

xz 通常压缩率很好，很多 Linux 发行版源码包、软件发布包会用 `.tar.xz`。缺点也明显：压缩慢，内存占用可能比较高。

适合：

- 软件发布包。
- 不频繁生成，但希望下载体积小的文件。
- 存档文件。

不适合：

- 高频日志压缩。
- 低内存机器。
- 需要快速压缩 / 快速解压的场景。

可以指定压缩等级：

```bash
xz -9 project.tar
```

或多线程压缩：

```bash
xz -T0 project.tar
```

`-T0` 表示尽量使用所有 CPU 核心。

### `.tar.zst`：现代服务器场景很常用

zstd 是近些年很常用的压缩工具，特点是速度快，压缩率也不错。很多系统包管理器、日志系统、备份流程已经大量使用 zstd。

创建：

```bash
tar --zstd -cf project.tar.zst project/
```

解压：

```bash
tar --zstd -xf project.tar.zst
```

如果 tar 版本不支持 `--zstd`，可以用管道：

```bash
tar -cf - project/ | zstd -T0 -o project.tar.zst
```

解压：

```bash
zstd -d -c project.tar.zst | tar -xf -
```

常见参数：

```bash
zstd -1 file      # 更快，压缩率低一些
zstd -19 file     # 更小，但更慢
zstd -T0 file     # 使用多线程
zstd -d file.zst  # 解压
zstd -t file.zst  # 测试完整性
```

`.tar.zst` 适合：

- 服务器备份。
- 大目录打包。
- 构建产物归档。
- 日志归档。
- 既关心速度，也关心体积的场景。

如果今天从零设计一个 Linux 内部归档流程，`.tar.zst` 往往比 `.tar.gz` 更舒服。但 `.tar.gz` 的兼容性仍然更强。

### `.zip`：跨平台最方便

创建 zip：

```bash
zip -r project.zip project/
```

查看内容：

```bash
unzip -l project.zip
```

解压：

```bash
unzip project.zip
```

解到指定目录：

```bash
unzip project.zip -d output/
```

排除文件：

```bash
zip -r project.zip project/ -x '*/.git/*' '*.log'
```

zip 的特点是“打包和压缩是一体的”。它不是先把所有文件合成一个大流再压缩，而是通常按文件分别压缩，并在文件末尾保存中心目录。这样 zip 很适合随机访问和单文件解压。

![The structure of a PKZip file](http://public.file.lvshuhuai.cn/images\central-directory-structure.png)

比如你只想从 zip 里拿一个文件：

```bash
unzip project.zip project/README.md
```

zip 适合：

- 发给 Windows 用户。
- 发给不熟命令行的人。
- 需要图形界面直接打开。
- 多平台交换文件。

但 zip 在 Unix 元数据保存方面不如 tar 稳定，尤其是：

- 符号链接
- 执行权限
- 所有者
- ACL
- 扩展属性
- 文件名编码

现代 zip 工具可以保存一部分信息，但跨平台时不一定可靠。所以如果你在 Linux 服务器之间迁移目录，tar 往往比 zip 更靠谱。

### `.7z`：高压缩率和加密常用

创建：

```bash
7z a project.7z project/
```

解压，保留路径：

```bash
7z x project.7z
```

只解出文件，不保留路径：

```bash
7z e project.7z
```

查看：

```bash
7z l project.7z
```

测试：

```bash
7z t project.7z
```

指定高压缩等级：

```bash
7z a -t7z -mx=9 project.7z project/
```

加密内容和文件名：

```bash
7z a -t7z -mx=9 -p -mhe=on secret.7z secret/
```

这里：

- `-p`：输入密码。
- `-mhe=on`：加密文件名。否则别人虽然打不开内容，但能看到里面有哪些文件。

7z 适合：

- 想要较高压缩率。
- 需要加密。
- Windows / Linux 都可能处理。
- 归档一批不常改的文件。

缺点是：在一些最小化 Linux 环境里未必默认安装。

### `.rar`：常见于 Windows 生态

RAR / WinRAR 在 Windows 世界很常见。Linux 上通常需要额外安装 `unrar` 或 `rar`。

查看：

```bash
unrar l archive.rar
```

解压：

```bash
unrar x archive.rar
```

RAR 的压缩率和分卷能力不错，也有加密功能。但它的生态相对封闭，不如 zip、tar、gzip、xz、zstd 这些格式在开源系统里自然。

如果只是自己使用或者对方明确能处理 RAR，可以用。若是公共发布、服务器自动化流程或开源项目，一般优先考虑 `.tar.gz`、`.tar.xz`、`.tar.zst` 或 `.zip`。

## 命令实战：日常该怎么打包、解压、查看、验证

这一节不只列命令，还要说明什么时候该怎么写。压缩解压的坑大多不是概念，而是手一快直接解错目录、覆盖文件、漏掉权限、或者压完才发现不完整。

### tar 常用命令

#### 创建 `.tar`

```bash
tar -cf project.tar project/
```

#### 创建 `.tar.gz`

```bash
tar -czf project.tar.gz project/
```

#### 创建 `.tar.xz`

```bash
tar -cJf project.tar.xz project/
```

#### 创建 `.tar.zst`

```bash
tar --zstd -cf project.tar.zst project/
```

#### 解压 `.tar`

```bash
tar -xf project.tar
```

#### 解压 `.tar.gz`

```bash
tar -xzf project.tar.gz
```

#### 解压 `.tar.xz`

```bash
tar -xJf project.tar.xz
```

#### 解压 `.tar.zst`

```bash
tar --zstd -xf project.tar.zst
```

#### 解压到指定目录

```bash
mkdir -p /tmp/output
tar -xzf project.tar.gz -C /tmp/output
```

这个习惯非常重要。不要总是在当前目录直接解压，尤其是来源不明的包。

#### 查看内容但不解压

```bash
tar -tf project.tar
tar -tzf project.tar.gz
tar -tJf project.tar.xz
```

实际工作中，解压前最好先看一眼：

```bash
tar -tzf nginx-1.27.4.tar.gz | head
```

如果输出类似：

```text
nginx-1.27.4/
nginx-1.27.4/README
nginx-1.27.4/src/
```

说明它有顶层目录，直接解一般比较安全。

如果输出类似：

```text
README
main.c
Makefile
src/a.c
src/b.c
```

说明它没有顶层目录，直接解在当前目录会把一堆文件撒出来。最好先建目录：

```bash
mkdir package
tar -xzf package.tar.gz -C package
```

#### 去掉顶层目录

有时 tar 包里多包了一层目录：

```text
project-1.0/
project-1.0/src/
project-1.0/README.md
```

你想直接解到当前目录，不想要 `project-1.0` 这一层：

```bash
tar -xzf project-1.0.tar.gz --strip-components=1
```

更稳妥的写法：

```bash
mkdir project
tar -xzf project-1.0.tar.gz -C project --strip-components=1
```

`--strip-components=1` 表示去掉路径前面的 1 层。

### gzip / gunzip 常用命令

压缩文件：

```bash
gzip access.log
```

结果是：

```text
access.log.gz
```

默认情况下，gzip 会删除原文件，只留下 `.gz`。

保留原文件：

```bash
gzip -k access.log
```

解压：

```bash
gunzip access.log.gz
```

或者：

```bash
gzip -d access.log.gz
```

解压到标准输出，不落盘：

```bash
gunzip -c access.log.gz
```

查看压缩日志内容：

```bash
zcat access.log.gz | less
```

搜索压缩日志：

```bash
zgrep 'ERROR' access.log.gz
```

测试 gzip 文件是否完整：

```bash
gzip -t access.log.gz
```

压缩等级：

```bash
gzip -1 access.log   # 快
gzip -9 access.log   # 更小但更慢
```

日常默认等级通常够用，不要无脑 `-9`。很多日志用 `-6` 和 `-9` 的体积差距不大，但耗时差距明显。

### xz 常用命令

压缩：

```bash
xz file
```

保留原文件：

```bash
xz -k file
```

解压：

```bash
xz -d file.xz
```

查看：

```bash
xzcat file.xz | less
```

测试：

```bash
xz -t file.xz
```

多线程：

```bash
xz -T0 file
```

压缩等级：

```bash
xz -0 file   # 快，压缩率低
xz -9 file   # 慢，压缩率高
```

xz 的高等级会吃内存。服务器上压大文件时，要注意别把机器内存打满。

### zstd 常用命令

压缩：

```bash
zstd file
```

保留原文件通常是默认行为之一，但不同用法要看命令输出。更明确地写输出文件：

```bash
zstd file -o file.zst
```

解压：

```bash
zstd -d file.zst
```

输出到标准输出：

```bash
zstd -d -c file.zst
```

测试完整性：

```bash
zstd -t file.zst
```

多线程压缩：

```bash
zstd -T0 bigfile
```

高压缩等级：

```bash
zstd -19 bigfile
```

更常用的是在速度和体积之间取平衡：

```bash
zstd -3 bigfile
zstd -6 bigfile
```

对于日志归档，zstd 通常很舒服：

```bash
tar -cf - logs/ | zstd -T0 -o logs.tar.zst
```

### zip / unzip 常用命令

压缩目录：

```bash
zip -r project.zip project/
```

解压：

```bash
unzip project.zip
```

解到指定目录：

```bash
unzip project.zip -d output/
```

查看内容：

```bash
unzip -l project.zip
```

测试完整性：

```bash
unzip -t project.zip
```

排除文件：

```bash
zip -r project.zip project/ -x '*/.git/*' '*.log' 'node_modules/*'
```

更新已有 zip：

```bash
zip -r project.zip project/
```

zip 默认会更新已有压缩包里的同名文件。

如果是 macOS 打 zip，经常会带上 `__MACOSX`、`.DS_Store` 等文件。可以排除：

```bash
zip -r project.zip project/ -x '*/.DS_Store' '__MACOSX/*'
```

### 7z 常用命令

创建：

```bash
7z a archive.7z project/
```

解压并保留目录结构：

```bash
7z x archive.7z
```

解压到指定目录：

```bash
7z x archive.7z -ooutput
```

注意 `-ooutput` 中间没有空格。

查看：

```bash
7z l archive.7z
```

测试：

```bash
7z t archive.7z
```

加密：

```bash
7z a -p -mhe=on archive.7z project/
```

如果你只是想把东西安全发给别人，7z 加密比“zip 普通密码”更可靠一些。但密码本身仍然要通过安全渠道传递，不能和压缩包一起发。

## 压缩包里的细节：路径、权限、符号链接、完整性和安全

压缩解压看起来只是几个命令，但真正出问题的地方常常在细节里。尤其是在服务器、生产环境、备份恢复、CI/CD 里，不能只靠“能解开就行”。

### 解压前先看内容

最值得养成的习惯：

```bash
tar -tf archive.tar | head
tar -tzf archive.tar.gz | head
unzip -l archive.zip | head
7z l archive.7z
```

看什么？

1. 有没有顶层目录。
2. 会不会把大量文件撒到当前目录。
3. 有没有奇怪的绝对路径。
4. 有没有 `../` 这种路径穿越。
5. 有没有符号链接指向敏感位置。
6. 文件数量是否异常。
7. 文件名编码是否明显乱码。

一个安全的源码包通常长这样：

```text
project-1.0/
project-1.0/README.md
project-1.0/src/main.c
```

一个容易污染当前目录的包可能长这样：

```text
README.md
main.c
config.yaml
src/main.c
```

遇到后者，先建目录再解：

```bash
mkdir archive-content
tar -xzf archive.tar.gz -C archive-content
```

### 不要随便用 root 解压来源不明的包

如果用 root 解压 tar 包，可能会恢复文件所有者、权限、甚至覆盖系统路径。来源不明的归档文件里如果有奇怪路径，风险会更高。

普通用户解压通常更安全：

```bash
tar -xzf archive.tar.gz
```

如果必须用 root，至少先查看内容，并考虑：

```bash
tar --no-same-owner -xzf archive.tar.gz
```

`--no-same-owner` 表示不要恢复归档里的原始所有者。

对于系统备份恢复，情况相反：你可能就是想保留所有者和权限。这时要明确知道自己在做恢复，而不是随手解一个包。

### 3. 绝对路径和路径穿越

危险路径示例：

```text
/etc/passwd
../../.ssh/authorized_keys
/home/user/.bashrc
```

正常工具通常会对绝对路径做一定处理，比如去掉开头的 `/`，但不要完全依赖工具默认行为。

可以先检查：

```bash
tar -tf archive.tar.gz | grep -E '(^/|(^|/)\.\.(/|$))'
```

如果有输出，就要谨慎。

zip 也一样：

```bash
unzip -l archive.zip
```

不要把来源不明的压缩包直接解到重要目录。

### 符号链接和硬链接

tar 能保存符号链接。

例如：

```text
project/current -> /etc/nginx
```

如果解压后某些脚本继续操作这个链接，可能会影响链接目标。

查看 tar 包内容时，详细列出：

```bash
tar -tvf archive.tar
```

对于 gzip 压缩的 tar 包：

```bash
tar -tzvf archive.tar.gz
```

输出里如果第一位是 `l`，表示符号链接：

```text
lrwxrwxrwx user/group 0 date project/current -> /etc/nginx
```

符号链接本身不是问题，但来源不明时要看清楚。

### 权限和可执行位

tar 通常能保存 Unix 权限，比如脚本的可执行位：

```text
-rwxr-xr-x build.sh
```

zip 在跨平台时对权限保存不一定稳定。有时你从 zip 解出来的脚本不可执行，需要手动：

```bash
chmod +x build.sh
```

如果你要发布 Linux 工具，里面有可执行文件、符号链接、权限要求，优先考虑 `.tar.gz`、`.tar.xz` 或 `.tar.zst`。

### ACL、扩展属性和 SELinux

普通 tar 命令不一定保存所有高级元数据。系统备份时要注意这些参数：

```bash
tar --acls --xattrs --selinux -cpf backup.tar /path/to/data
```

恢复时也要带上：

```bash
tar --acls --xattrs --selinux -xpf backup.tar -C /
```

这里的 `p` 表示尽量保留权限。

但这类命令更接近系统备份恢复，不适合随便用于普通项目打包。

### 稀疏文件

有些文件看起来很大，但实际占用磁盘很小，比如虚拟机镜像、数据库文件、某些日志文件。

查看：

```bash
ls -lh disk.img
du -h disk.img
```

如果 `ls` 显示 100G，但 `du` 显示 2G，这可能是稀疏文件。

打包时可以用：

```bash
tar --sparse -cf vm.tar disk.img
```

否则可能把空洞也写进去，导致包变得很大。

### 完整性测试

压缩包能列出内容，不代表内容一定完整。传输后最好测试。

tar 本身主要是归档格式，完整性能力有限，通常依赖外层压缩格式的校验。

常见测试命令：

```bash
gzip -t file.gz
bzip2 -t file.bz2
xz -t file.xz
zstd -t file.zst
unzip -t file.zip
7z t file.7z
```

对于 `.tar.gz`：

```bash
gzip -t archive.tar.gz
tar -tzf archive.tar.gz > /dev/null
```

对于 `.tar.zst`：

```bash
zstd -t archive.tar.zst
zstd -d -c archive.tar.zst | tar -tf - > /dev/null
```

如果是重要备份，压完后应该至少做一次测试，不能等到恢复时才发现坏了。

### 加密不是压缩，压缩也不是加密

压缩只是把数据变小，不提供保密性。

这些文件默认都不是加密的：

```text
.tar
.tar.gz
.tar.xz
.tar.zst
.zip
.7z
```

zip 和 7z 可以加密码，但要看加密方式。

普通 zip 的传统加密很弱，不适合保护敏感数据。更可靠的做法是使用 7z 的 AES 加密，或者先用专门工具加密，再压缩 / 传输。

7z 加密示例：

```bash
7z a -t7z -p -mhe=on secret.7z secret/
```

也可以用 GPG：

```bash
tar -czf - secret/ | gpg -c -o secret.tar.gz.gpg
```

解密解压：

```bash
gpg -d secret.tar.gz.gpg | tar -xzf -
```

## 压缩率、速度和场景选择

压缩没有绝对最优。你需要在几个因素之间取舍：

- 压缩后有多小
- 压缩速度
- 解压速度
- 内存占用
- 兼容性
- 是否支持流式处理
- 是否保留 Unix 元数据
- 是否方便 Windows 用户打开
- 是否需要加密

### 不同数据的压缩效果差别很大

文本、日志、CSV、JSON、源码通常压缩效果很好。

例如：

```text
access.log
data.csv
source code
SQL dump
JSON export
```

这些文件里重复模式多，压缩工具很容易找到规律。

但下面这些文件通常已经压缩过，再压一次效果很差：

```text
.jpg
.png
.mp4
.mp3
.pdf
.zip
.gz
.7z
.rar
```

把一个 1 GB 的 MP4 再 gzip 一次，可能只小一点点，还浪费大量 CPU。

所以不要看到大文件就下意识压缩。先判断它本身是不是已经压缩格式。

可以用 `file` 查看：

```bash
file video.mp4
file archive
```

### 常见格式的大致取舍

| 格式  | 压缩率 | 压缩速度 | 解压速度 |     兼容性 | 常见用途                |
| ----- | -----: | -------: | -------: | ---------: | ----------------------- |
| gzip  |     中 |       快 |       快 |       很强 | 源码包、日志、HTTP 压缩 |
| bzip2 |   较好 |       慢 |       中 |       较强 | 老项目、旧归档          |
| xz    |   很好 |       慢 |       中 |       较强 | 发布包、系统包          |
| zstd  |     好 |     很快 |     很快 | 新系统较强 | 备份、日志、构建产物    |
| lz4   |   一般 |     极快 |     极快 |         中 | 临时数据、实时系统      |
| zip   |     中 |       中 |       中 |       很强 | 跨平台文件交换          |
| 7z    |   很好 |       慢 |       中 |         中 | 高压缩率、加密归档      |
| rar   |     好 |       中 |       中 | Windows 强 | Windows 生态、分卷      |

### 压缩等级不是越高越好

大多数工具都有压缩等级。

gzip：

```bash
gzip -1 file
gzip -9 file
```

xz：

```bash
xz -0 file
xz -9 file
```

zstd：

```bash
zstd -1 file
zstd -19 file
```

7z：

```bash
7z a -mx=1 archive.7z dir/
7z a -mx=9 archive.7z dir/
```

压缩等级越高，通常：

- 压缩更慢
- CPU 消耗更高
- 有些工具内存占用更大
- 体积不一定明显下降

例如一个日志文件，用 gzip `-6` 可能压到 120 MB，用 `-9` 压到 115 MB，但耗时多很多。是否值得，要看场景。

一般经验：

- 临时传输：用快一点的等级。
- 长期存档：可以用高一点的等级。
- 大规模日志：优先考虑 zstd。
- 发布包：可以用 xz 或 zstd 的较高等级。
- 给普通用户：zip 更省沟通成本。

### 多线程压缩

传统 gzip 是单线程的。大文件压缩时，可以用 pigz，它生成的仍然是 gzip 兼容格式：

```bash
pigz big.log
pigz -d big.log.gz
```

tar 配合 pigz：

```bash
tar -cf - logs/ | pigz > logs.tar.gz
```

xz 可以多线程：

```bash
xz -T0 bigfile
```

zstd 原生支持多线程：

```bash
zstd -T0 bigfile
```

7z 也通常支持多线程压缩。

如果你在多核服务器上压几十 GB 数据，单线程 gzip 可能很慢。换成 pigz 或 zstd，体验会明显不同。

### 该用什么格式

一些实际选择：

#### 发给不懂命令行的人

用 zip：

```bash
zip -r photos.zip photos/
```

原因：Windows、macOS、Linux 都容易打开。

#### 发布 Linux / Unix 源码包

用 `.tar.gz` 或 `.tar.xz`：

```bash
tar -czf project-1.0.tar.gz project-1.0/
tar -cJf project-1.0.tar.xz project-1.0/
```

原因：Unix 元数据保存好，生态习惯稳定。

#### 服务器备份

用 `.tar.zst`：

```bash
tar --acls --xattrs -cf - /data | zstd -T0 -o data.tar.zst
```

原因：速度快、压缩率好，适合大数据量。

#### 压缩日志

单文件日志：

```bash
zstd -T0 access.log
```

一批日志：

```bash
tar -cf - logs/ | zstd -T0 -o logs.tar.zst
```

如果系统只认 gzip：

```bash
gzip access.log
```

或者更快：

```bash
pigz access.log
```

#### 追求最小体积

可以考虑 xz 或 7z：

```bash
tar -cJf source.tar.xz source/
7z a -mx=9 source.7z source/
```

但要接受压缩慢、内存占用高的问题。

#### 需要加密

用 7z 或 GPG：

```bash
7z a -p -mhe=on secret.7z secret/
```

或者：

```bash
tar -czf - secret/ | gpg -c -o secret.tar.gz.gpg
```

## 把文章里的 `.tar.gz` 问题放回实际工作

`.tar.gz` 要两个后缀，是因为 Unix 世界把“归档”和“压缩”拆成了两件事。

这和 zip、rar、7z 的设计不同。zip、rar、7z 更像一个工具把事情全包了：既负责把多个文件组织起来，也负责压缩。tar + gzip 则是两个工具配合：tar 把目录变成连续字节流，gzip 把这条流压小。

这种设计的好处是组合能力强。

同一个 tar，可以接不同压缩器：

```bash
tar -cf - project/ | gzip > project.tar.gz
tar -cf - project/ | xz > project.tar.xz
tar -cf - project/ | zstd -T0 > project.tar.zst
```

同一个 gzip，也可以压任何字节流：

```bash
cat access.log | gzip > access.log.gz
mysqldump db | gzip > db.sql.gz
tar -cf - project/ | gzip > project.tar.gz
```

这就是 Unix 管道的价值：工具之间不需要知道彼此内部怎么实现，只要都能读写标准输入输出，就能组合。

所以 `.tar.gz` 不是历史遗留的怪名字，而是一个非常清楚的结构：

```text
多个文件
  → tar：合成一个归档流
  → gzip：压缩这个归档流
  → 得到 archive.tar.gz
```

当你看到这些后缀时，可以从右往左理解解压过程：

```text
.tar.gz  ：先 gunzip，再 tar -xf
.tar.xz  ：先 unxz，再 tar -xf
.tar.zst ：先 unzstd，再 tar -xf
```

或者从左往右理解创建过程：

```text
目录 → tar → gzip/xz/zstd
```

这比死记命令可靠得多。
