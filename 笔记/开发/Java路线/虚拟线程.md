# 虚拟线程（Virtual Threads）详解

## 虚拟线程是什么？

虚拟线程（Virtual Threads）是 **JDK 21 中正式引入（JEP 444）的新并发模型**，由 Project Loom 推动。它的核心目标是：

> **用“每个任务一个线程”的简单编程模型，却拥有接近“回调式异步”的高并发能力。**

传统的 Java 线程（`java.lang.Thread`）我们可以叫它 **平台线程（Platform Thread）** —— 它直接映射到底层操作系统线程；而虚拟线程则是：

- 仍然是 `java.lang.Thread` 的实现；
- 但不再一一对应 OS 线程，而是 **完全由 JVM 管理和调度**；
- 创建、切换、销毁的成本极低，可以轻松创建 **几十万甚至上百万** 个并发线程。

你可以把它理解成：

> “JVM 自己实现了一层轻量级线程，把原来昂贵的 OS 线程当作‘载体’，在上面挂很多轻量任务。”

## 为什么需要虚拟线程？（传统线程/异步模型的痛点）

### 平台线程的问题

传统 `new Thread(...)` 或线程池里的线程，是 OS 级别的线程，有几个特点：

1. **创建成本高、数量有限**  
   - 每个线程有独立的栈（几百 KB ~ 数 MB），还要向操作系统申请资源。  
   - 高并发场景下，几千个线程一般还能接受，上万开始就危险，再高就容易 OOM 或上下文切换爆炸。

2. **阻塞调用浪费资源**  
   - 线程在执行阻塞 I/O（访问数据库、调用 HTTP 接口、文件读写）时，其实**啥都没干，只是在等**。  
   - 但这个线程仍然占着 OS 线程和整条调用栈，对系统来说是昂贵的资源浪费。

3. **复杂的异步编程模型**  
   - 为了提高吞吐量，我们被迫使用：回调、`CompletableFuture`、响应式（Reactor、RxJava）、协程风格等。
   - 这会带来复杂的控制流、难以 debug 的调用栈，以及上下文传递（安全上下文、事务、日志 MDC 等）问题。

**结论：**

> 平台线程对“阻塞型 I/O 为主”的后端应用来说，很难同时做到：
>
> “编程简单 + 支持极高并发”。

### 虚拟线程想解决什么？

虚拟线程的设计目标是：

- 你依然写 **同步阻塞风格的代码**（`Result r = client.call();`）；  
- 但当代码阻塞时，**JVM 自动帮你把虚拟线程挂起**，把到底层的 OS 线程还给线程池；  
- 等 I/O 完成后，再把虚拟线程恢复到某个 OS 线程上继续执行。

也就是说：

> **看起来是阻塞代码，实际是“无阻塞”的高并发调度。**

## 虚拟线程的基本工作原理（通俗版）

### “栈切走”的思想

传统平台线程阻塞时：

- 调用栈和线程是绑在一起的，线程卡在那一行直到 I/O 返回；
- OS 无法“把这条栈切下来，晚点再接上”。

<img src="https://seven97-blog.oss-cn-hangzhou.aliyuncs.com/imgs/202404252017484.gif" alt="img" style="zoom: 67%;" />

虚拟线程的关键改进是：

1. JVM 为虚拟线程维护一份 **用户态的栈和状态**；
2. 当虚拟线程遇到“可挂起的阻塞点”（典型如 `Socket.read()`）时：
   - JVM 把这个虚拟线程从当前 OS 线程上“摘下”（park）；
   - 保存其 Java 栈和状态到堆上；
   - OS 线程回到一个调度池，继续执行其他虚拟线程；
3. 当 I/O 完成时：
   - JVM 把对应虚拟线程的栈恢复到某个可用的 OS 线程；
   - 从之前阻塞的那一行继续往下执行。

因此：

- **虚拟线程的阻塞不会阻塞 OS 线程**；
- OS 线程就好比一个“执行器”，不停地轮流执行不同的虚拟线程。

### “N:M” 调度模型

<img src="https://s7.51cto.com/oss/202311/03/7518075737abff1efe82522f7709fce04bcd0e.png" alt="img" style="zoom: 67%;" />

- 传统模型：**1:1**  
  - 1 个 Java 线程 ≈ 1 个 OS 线程。
- 虚拟线程模型：**N:M**  
  - N 个虚拟线程 映射到 M 个 OS 线程（一般 M 远小于 N，比如 100 个 OS 线程跑 10 万个虚拟线程）。

JVM 相当于在用户态实现了一套调度器，而不是完全依赖 OS 的线程调度。

## 怎么用虚拟线程？（基本 API）

> 从 JDK 21 开始，虚拟线程是正式特性，直接在标准库中使用即可。

### 创建一个虚拟线程

```java
Thread startVirtualThread = Thread
        .ofVirtual()
        .start(() -> {
            // 这里是任务逻辑
            String name = Thread.currentThread().toString();
            System.out.println("Running in " + name);
        });
```

特点：

- **每个任务一个虚拟线程**（per-task）；
- 不需要再手动维持复杂的线程池参数（核心线程数、最大线程数等）；
- 创建几万甚至几十万个任务也完全可行。

## 虚拟线程与 Spring / Web 框架

### 对 Spring MVC / Spring Boot 的意义

在传统 Spring MVC 中：

- 每个 HTTP 请求由 Servlet 容器分配一个平台线程；
- 线程阻塞在 Controller 或 Service 层的各种 I/O 调用上；
- 高并发下需要非常小心地调线程池大小，否则容易占满系统资源。

使用虚拟线程后：

- 每个请求仍“看起来”是由一个线程处理；
- 但这个线程是虚拟线程；
- 当执行到数据库/HTTP 等阻塞 I/O 时，JVM 自动挂起虚拟线程、释放 OS 线程；
- 容器可以同时处理大量请求，而不会被线程数量绑死。

这让 “简单的同步编程模型” 和 “高并发” 不再矛盾。

### 与响应式 WebFlux 的关系

- **WebFlux**：基于 Reactor 的响应式模型，本质是“手动管理异步流”。优点是理论吞吐高，缺点是编程模型复杂。
- **虚拟线程 + MVC**：仍然是同步 blocking 风格，但底层调度变聪明了。

两者关系可以这么理解：

> - 如果你已经大量投资在响应式栈（Reactor、WebFlux），虚拟线程并不会立刻取代它。
> - 如果你之前为了高并发“被迫”写异步/响应式，但团队更习惯同步写法，那么虚拟线程 + MVC 是非常有吸引力的替代方案。

## 虚拟线程的适用场景与收益

### 特别适合的场景

- **I/O 密集型** 服务端应用：
    - 大量 HTTP / gRPC 调用；
    - 大量数据库查询；
    - 微服务之间的 RPC 调用；
    - 消息队列 + 外部服务组合。
- 需要同时挂很多“长期悬挂”任务：
    - 长轮询；
    - WebSocket；
    - 等待远程事件等。

在这些场景中，虚拟线程能显著提升：

- **吞吐量**：可支持更多并发请求；
- **资源利用率**：OS 线程数量控制在合理范围，CPU 更专注在实际计算任务上；
- **开发效率**：回到同步写法，逻辑清晰，调试更简单。

### 收益示意（定性）

在一些社区基准测试中，使用虚拟线程往往能：

- 在相同硬件上，将最大并发连接数从几千提升到几万；
- 平均响应时间接近传统异步模型；
- 同时保持“普通同步代码”的可读性与可维护性。

实际提升幅度和你的业务结构、数据库/网络延迟等强相关，需要通过压测来确定。

## 使用虚拟线程时的注意事项

### CPU 密集型任务仍然受限于核心数

虚拟线程并 **不是** 用来提升纯 CPU 运算吞吐的：

- 对于大量 CPU 计算（图像/视频编解码、加密、复杂算法），瓶颈在 CPU，本质上与“有多少线程”关系不大；
- 这时虚拟线程不会带来明显收益，甚至过多任务反而增加调度开销。

**建议：**

- 对 CPU 密集型任务，仍然控制任务数量（如固定大小线程池）；
- 可以在业务层进行分类：I/O 任务用虚拟线程，计算任务用传统线程池。

### 不要在虚拟线程里无意义自旋/忙等

例如：

```java
while (!flag) {
    // 忙等
}
```

这样的代码会占满 CPU，让虚拟线程调度优势消失。正确做法应使用等待机制（`wait/notify`、`LockSupport.park`、`CountDownLatch` 等），让虚拟线程真正“挂起”。

### 关注未适配的底层库

虚拟线程要正常释放 OS 线程，前提是底层 I/O 操作是 **可挂起的**（non-blocking 或经过 JDK 适配）。一般情况下：

- JDK 自带的 Socket、HTTP、File I/O 等都已适配；
- 但某些旧的原生库 / JNI 调用仍可能占用 OS 线程不放。

遇到这类库时，要查文档或做压测，确认是否有对虚拟线程的支持或替代方案。

### 线程本地变量（ThreadLocal）与上下文传递

虚拟线程数量可非常庞大，如果大量使用 `ThreadLocal` 存放大对象，可能会：

- 增加内存占用；
- 难以回收，导致泄漏。

建议：

- 只在必要时使用 `ThreadLocal`；
- 更倾向于显式参数传递或使用框架提供的上下文（如 Spring 的 `RequestContext` 等）。

## 与其他语言并发模型的对比（类比理解）

- **Go 的 goroutine**
    - “几十万 goroutine 挂在少量 OS 线程上”，理念非常接近虚拟线程；
    - 区别在于 goroutine 是 Go 语言内建，而虚拟线程是 Java 在现有生态上演进。
- **Kotlin 协程**
    - 协程是语言与库层实现，需要“可挂起点（suspend）”标注；
    - 虚拟线程则是 JVM 层做切换，对调用者而言是普通阻塞方法；
    - 协程在单个线程内调度，虚拟线程是 N:M 与 OS 线程映射，层级不同。

可以简单记住：

> 虚拟线程 = “Java 版、JVM 原生的 goroutine 风格并发”。
