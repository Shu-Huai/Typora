# 10 工程化实践

前九篇的代码都是能跑的教学例子。从例子走向能上线的服务，还差三块：测试兜住行为、目录结构装下规模、部署方式扛住流量。这篇收尾。

## 测试

FastAPI 的测试体验在 Python 生态里排前列，因为 TestClient 让测试不需要真起服务器：

```python
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)


def test_read_root():
    response = client.get("/")
    assert response.status_code == 200
    assert response.json() == {"message": "Hello, FastAPI"}
```

TestClient 底层是 httpx，请求在进程内直接穿过应用，没有网络开销，测试跑得快。配合 pytest 使用：

```powershell
pip install pytest
pytest
```

![pytest 官方标志](Z:\Public\images\pytest-logo.png)

测试依赖数据库这类外部资源时，conftest.py 里准备 fixture：

```python
import pytest
from fastapi.testclient import TestClient

from database import Base, engine
from main import app


@pytest.fixture()
def client():
    Base.metadata.create_all(engine)
    yield TestClient(app)
    Base.metadata.drop_all(engine)
```

每个测试前后重建表，测试之间互不污染。

依赖覆盖是 FastAPI 测试的杀手锏：测试里不想连真实数据库，把依赖换成假的：

```python
def fake_get_db():
    yield {"users": ["alice"]}


app.dependency_overrides[get_db] = fake_get_db
```

处理函数里声明的 get_db 全部被替换成假实现，测试只关心接口逻辑，不受外部资源影响。记得测完清掉：

```python
app.dependency_overrides.clear()
```

### 完整测试用例

一个创建用户的接口配上测试，覆盖成功和失败两条路径：

```python
def test_create_user(client):
    response = client.post(
        "/users/",
        json={"name": "alice", "age": 30},
    )
    assert response.status_code == 200
    data = response.json()
    assert data["name"] == "alice"


def test_create_user_invalid(client):
    response = client.post("/users/", json={"name": "alice", "age": "abc"})
    assert response.status_code == 422
```

第一条验证正常创建，第二条验证非法年龄被 Pydantic 拦下。测试的价值在第二条这类负向用例上：接口的校验逻辑只有被测试锁住，后续重构才敢动手。

断言清单照着这四条写，覆盖大多数接口场景：状态码对不对、响应体字段对不对、错误分支有没有走到、副作用有没有发生（数据库里的记录变化）。

## 项目结构

教学用的单文件在功能变多后必然撑不住，拆分的标准动作是 APIRouter：

```python
# routers/users.py
from fastapi import APIRouter

router = APIRouter(prefix="/users", tags=["用户"])


@router.get("/")
def list_users():
    return {"users": []}


@router.post("/")
def create_user():
    return {"id": 1}
```

```python
# main.py
from fastapi import FastAPI

from routers import users

app = FastAPI()
app.include_router(users.router)
```

prefix 统一路径前缀，tags 统一文档分组，每个业务域一个 router 文件，main.py 只做组装。

配置用 pydantic-settings，环境变量驱动：

```powershell
pip install pydantic-settings
```

```python
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    app_name: str = "示例应用"
    database_url: str = "sqlite:///app.db"


settings = Settings()
```

配置项写默认值，部署时用环境变量覆盖，密钥类配置绝不进代码库。

### 环境变量注入

```powershell
$env:DATABASE_URL = "postgresql://user:pass@db:5432/app"
uvicorn main:app
```

pydantic-settings 启动时按字段名匹配环境变量，DATABASE_URL 自动覆盖 database_url 的默认值。部署环境改配置不用动代码，密钥类配置只存在于环境变量或密钥管理系统，代码库和镜像里都搜不到明文。

一个能撑起规模的目录结构：

```text
project/
├── main.py            # 应用入口，组装路由和中间件
├── settings.py        # 配置类
├── database.py        # 引擎、Session、Base
├── models/            # SQLAlchemy 表模型
├── schemas/           # Pydantic 请求/响应模型
├── routers/           # 按业务域拆分的路由
├── dependencies/      # 共享依赖（数据库会话、认证）
├── tests/             # pytest 测试
└── requirements.txt
```

各模块职责：

| 目录 | 职责 | 示例内容 |
| --- | --- | --- |
| models | 表结构定义 | User 表模型 |
| schemas | 接口出入参数 | UserCreate、UserOut |
| routers | 路由处理 | users.py、orders.py |
| dependencies | 可复用依赖 | get_db、get_current_user |

表模型和接口模型分层的好处：数据库字段和接口字段各管各的，加个内部字段不用动接口，改接口格式不用动表结构。models 里的东西不出接口边界，schemas 里的东西不进数据库层。

## 部署

![测试与部署拓扑](Z:\Public\images\fastapi-deploy.png)

开发环境的启动方式前面一直在用：

```powershell
uvicorn main:app --reload
```

![uvicorn 官方标志](Z:\Public\images\uvicorn-logo.png)

生产环境去掉 --reload，改用多进程：

```powershell
uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4
```

> --reload 会消耗更多资源，比没有它的时候更不稳定，只能用于开发环境。
>
> —— uvicorn 官方文档

workers 数量通常取 CPU 核数。注意两个点：每个 worker 是一个独立进程，内存状态不共享，会话类数据要放 Redis；worker 数量开得超过核数只会互相抢 CPU。

Linux 上更常见的是 gunicorn 管理进程、uvicorn 干活：

```bash
gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker
```

前面再加 Nginx 反向代理，负责三件事：终结 HTTPS、服务静态文件、把流量均匀分给后端。Nginx 配好 TLS 证书后，应用只和本机通信，不需要自己处理加密。

容器化用 Docker，最小镜像参考：

```dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

容器里必须监听 0.0.0.0 才能被外部访问，这是高频坑。

上线前的检查清单：

- HTTPS 是否全站启用，令牌传输不加密等于裸奔
- 日志是否落到文件或采集系统，多进程日志别用 print
- 健康检查接口是否就绪（返回 200 的 /health)
- 数据库连接池大小是否匹配 worker 数，池太小会排队
- 密钥配置是否走环境变量，代码库里搜一遍硬编码

## 踩坑清单

1. 生产环境开着 --reload：性能损耗加不稳定，监控里看 CPU 占用异常时先查它。
2. 同步阻塞函数放进 async 接口：requests 这类同步调用会卡住整个事件循环，IO 密集场景要么用 httpx 异步版，要么接口声明成普通 def。
3. 依赖里忘关 Session：连接池被耗尽后服务假死，用 yield 依赖让清理自动化。
4. response_model 字段类型写错：响应校验失败返回 500，排查时先看响应模型的类型和实际返回值对不对。
5. 把密码写进 JWT payload：payload 是明文，等于把密码贴在请求头上到处发。
6. 容器里监听 127.0.0.1：宿主机永远访问不到，容器环境一律 0.0.0.0。
7. 测试连着生产数据库跑：fixture 没隔离环境，一条误写的测试数据就上线了。
