# 07 请求生命周期

FastAPI 处理一次 HTTP 请求有固定流程。请求到达 ASGI 应用后，先穿过中间件组成的洋葱外层，再进入路由匹配，随后解析依赖，最后执行路径操作函数。响应沿相反方向返回，再次经过中间件。异常在其中任何环节冒出时，由异常处理器或最外层兜底。理解这条链路，才能说清楚一段代码在哪个位置执行、执行几次、出错时谁负责收尾。

> FastAPI 官方文档对中间件的定义：A "middleware" is a function that works with every request before it is processed by any specific path operation, and also with every response before returning it. 中文大意：中间件是一个函数，它在任何一个具体路径操作处理请求之前运行，也在响应返回之前运行。

## 中间件

**中间件**位于整个应用的外围。每个请求都要先穿过中间件再进入路由，响应返回时再反向穿出。多个中间件叠加时形成**洋葱模型**：先注册的在外层，后注册的在内层。

### 洋葱模型

下图是请求生命周期的整体视图。请求从左向右穿过中间件进入路由，响应从右向左穿回。异常处理器与中间件不在同一层，具体差别在“异常处理”一节展开。

注册两个中间件，观察执行顺序：

```python
from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def first_middleware(request: Request, call_next):
    # 请求进入第一层
    print("第一层：请求进入")
    response = await call_next(request)
    # 响应穿出第一层
    print("第一层：响应返回")
    return response


@app.middleware("http")
async def second_middleware(request: Request, call_next):
    # 请求进入第二层
    print("第二层：请求进入")
    response = await call_next(request)
    # 响应穿出第二层
    print("第二层：响应返回")
    return response


@app.get("/")
async def home():
    print("路由函数执行")
    return {"message": "hello"}
```

启动服务并请求一次，控制台输出顺序：

```
第一层：请求进入
第二层：请求进入
路由函数执行
第二层：响应返回
第一层：响应返回
```

输出说明：请求方向从外到内，第一层先进；响应方向从内到外，第二层先出。`call_next` 是 ASGI 协议定义的调用链函数，作用是把请求交给下一层。中间件如果不调用 `call_next`，请求就停在原地，路由永远等不到。`call_next` 的返回值是 Response 对象，可以修改之后再返回。

### 计时中间件

计时是中间件最典型的用法。要点：`call_next` 之前的代码是前置逻辑，之后的代码是后置逻辑，计时必须拆成两段。

```python
import time

from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def timing_middleware(request: Request, call_next):
    # 前置逻辑：请求进入时记录时间
    start = time.perf_counter()
    # 把请求交给下一层，等待响应生成
    response = await call_next(request)
    # 后置逻辑：响应返回后计算耗时并写进响应头
    cost_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{cost_ms:.2f}ms"
    return response


@app.get("/")
async def home():
    # 模拟一个耗时任务
    time.sleep(0.05)
    return {"message": "hello"}
```

计时函数用 `time.perf_counter()` 而不是 `time.time()`。前者取单调时钟，不受系统改时间影响，适合计算两点的间隔；后者取墙上时钟，会被手动调时间干扰。

验证方式：浏览器开发者工具或 curl 查看响应头，出现一条 `X-Process-Time`。Windows PowerShell 里执行：

```powershell
curl.exe -i http://127.0.0.1:8000/
```

日志中间件把方法、路径、状态码与耗时拼成一行，原理相同：

```python
import logging

from fastapi import Request

logger = logging.getLogger("access")


@app.middleware("http")
async def logging_middleware(request: Request, call_next):
    response = await call_next(request)
    # 输出示例：POST /items 200 12.34ms
    logger.info("%s %s %s", request.method, request.url.path, response.status_code)
    return response
```

`@app.middleware("http")` 装饰器底层等价于调用 `app.add_middleware`。装饰器适合自己写的函数型中间件，`add_middleware` 适合现成的类型中间件，CORSMiddleware 就是典型例子。注册顺序敏感，先注册的在外层。下面两条语句交换位置，执行顺序就反过来：

```python
app.add_middleware(LoggingMiddleware)
app.add_middleware(AuthMiddleware)
```

LoggingMiddleware 在外层，请求先进日志中间件；AuthMiddleware 在内层，鉴权逻辑后执行。外层中间件记录到的耗时包含内层全部开销。鉴权失败抛出的 401 异常同样会被外层日志记录，因为响应终究要穿出外层。

**BaseHTTPMiddleware** 与纯 ASGI 中间件的差异：前者以 Request/Response 对象为单位工作，写法简单，但存在性能开销，对流式响应不友好；后者直接操作 scope、receive、send 三个原始对象，性能最好，代码更繁琐。入门阶段统一用 BaseHTTPMiddleware。

中间件内部抛异常：在 `call_next` 之前抛出的异常不会被异常处理器捕获。异常处理器安装在中间件内侧，中间件抛出的异常会越过处理器，直接落到最外层的 **ServerErrorMiddleware**，最终变成 500 响应。想让中间件里的错误走统一格式，必须在中间件内部自行 try/except，或者把异常放到路由函数里再抛。

中间件的常见用途：

- 日志：记录每个请求的方法、路径、状态码、耗时
- 鉴权：统一校验 Token，校验不通过直接返回 401
- 统计：接口调用量、慢接口排行、错误率
- 跨域：统一处理 CORS 响应头，下一节展开

完整的可运行文件：

```python
"""main.py：中间件演示的完整可运行文件。"""

import time

from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def timing_middleware(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    cost_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{cost_ms:.2f}ms"
    return response


@app.get("/")
async def home():
    return {"message": "hello"}


@app.get("/items/{item_id}")
async def read_item(item_id: int):
    return {"item_id": item_id, "name": "示例条目"}
```

## CORS

浏览器的**同源策略**规定：页面脚本只能读取同源请求的响应。同源指协议、域名、端口三者完全相同。前端开发服务器（如 http://localhost:5173)与后端 API（如 http://127.0.0.1:8000)端口不同，属于不同源，浏览器会拦截跨域响应。跨域问题的解法在服务端：后端在响应头里声明允许的源，浏览器校验通过后放行。

FastAPI 用 CORSMiddleware 统一处理：

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    # 允许的前端源：带协议、域名、端口
    allow_origins=["http://localhost:5173", "https://example.com"],
    # 允许的请求方法
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    # 允许的请求头
    allow_headers=["Content-Type", "Authorization"],
    # 是否允许携带 Cookie 等凭证
    allow_credentials=True,
)
```

四个参数各有分工。**allow_origins** 决定哪些源可以读响应；**allow_methods** 决定允许的 HTTP 方法；**allow_headers** 决定请求可以携带的自定义头；**allow_credentials** 控制 Cookie 与认证头是否随请求发出。

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| allow_origins | 允许的源列表 | [] |
| allow_methods | 允许的请求方法 | ["GET"] |
| allow_headers | 允许的请求头 | [] |
| allow_credentials | 是否允许携带凭证 | False |

allow_credentials 的坑：一旦设为 True，allow_origins 就不能写成 `["*"]`。浏览器规范要求带凭证的响应必须回显具体源，通配符与凭证同时出现时浏览器直接拒绝响应。此时要么列出全部具体源，要么用 `allow_origin_regex` 做动态匹配。不带凭证的场景可以放心用通配：

```python
app.add_middleware(
    CORSMiddleware,
    # 不带凭证时可以用通配符放行所有源
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
    allow_credentials=False,
)
```

**预检请求**：请求带自定义头（如 Authorization)或使用 PUT、DELETE 等方法时，浏览器先发一个 OPTIONS 预检请求，询问服务端是否允许。CORSMiddleware 会拦截 OPTIONS 请求，直接返回 200 响应，不会进入路由。路由层无需写 OPTIONS 接口，也不用 `@app.options` 装饰器，除非中间件没有挂载。

## 异常处理

路由函数抛出的异常沿调用栈向上冒泡。FastAPI 在内层安装了异常处理机制，拦截冒泡上来的异常并转换成 JSON 响应。默认行为分两类：**HTTPException** 返回 `{"detail": "..."}` 结构；校验失败抛出 **RequestValidationError**，返回 422 与错误明细列表。两类默认格式都可以替换成业务格式。

异常从抛出到响应的完整路径：

1. 路由函数或依赖抛出异常
2. 异常沿调用栈向外冒泡
3. 异常处理器按类型匹配，命中则替换为统一格式响应
4. 未命中的异常落到 ServerErrorMiddleware，返回 500

### 统一业务异常格式

先定义异常类，再注册处理器。处理器签名固定为(request, exc)，返回 Response 或可序列化对象。

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


class BusinessError(Exception):
    # 业务异常：message 是对外提示语，status_code 是对外状态码
    def __init__(self, message: str, status_code: int = 400):
        self.message = message
        self.status_code = status_code
        super().__init__(message)


@app.exception_handler(BusinessError)
async def business_error_handler(request: Request, exc: BusinessError):
    # 统一错误响应格式：code 表示业务码，message 表示提示语
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": exc.status_code, "message": exc.message},
    )


@app.get("/items/{item_id}")
async def read_item(item_id: int):
    if item_id <= 0:
        raise BusinessError("资源编号必须是正整数")
    return {"item_id": item_id}
```

注册之后，路由里任何位置 raise BusinessError 都会变成统一格式。处理器自己构造 JSONResponse，状态码与响应体都由处理器决定。同一个异常类型只能注册一个处理器，重复注册会覆盖前面的。

HTTPException 是框架内部统一捕获的常见错误来源，默认响应体固定为 `{"detail": "..."}`：

```python
from fastapi import HTTPException


@app.get("/users/{user_id}")
async def read_user(user_id: int):
    if user_id == 0:
        # 默认响应体：{"detail": "用户不存在"}
        raise HTTPException(status_code=404, detail="用户不存在")
    return {"user_id": user_id}
```

要替换这个格式，注册 `starlette.exceptions.HTTPException` 的处理器即可，注册方式与业务异常相同。

### 覆盖校验异常

请求体或查询参数校验失败时，FastAPI 抛出 RequestValidationError，默认返回 422 与错误明细列表。明细列表每一项包含 loc、msg、type 三个字段，业务系统通常只想要其中的提示语：

```python
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    price: float


@app.exception_handler(RequestValidationError)
async def validation_error_handler(request: Request, exc: RequestValidationError):
    # exc.errors() 返回错误明细列表，取第一条
    first = exc.errors()[0]
    return JSONResponse(
        status_code=422,
        content={"code": 422, "message": "参数校验失败", "detail": first},
    )


@app.post("/items")
async def create_item(item: Item):
    return {"name": item.name, "price": item.price}
```

错误明细示例：请求体缺 price 字段时，errors()[0] 大致是 `{"type": "missing", "loc": ["body", "price"], "msg": "Field required"}`。loc 指示出错位置，msg 是英文原文，可以直接透传给前端，也可以维护一份中文映射。

异常处理器与中间件的区别要分清。中间件包住应用最外层，异常处理器位于中间件内侧、路由外侧。处理器只能捕获从路由层冒泡上来的异常；中间件内部抛出的异常位于处理器上游，处理器看不见。处理器按异常类型精确匹配，中间件按位置全部拦截。

| 异常类型 | 默认状态码 | 处理方式 |
| --- | --- | --- |
| HTTPException | status_code 参数指定 | 默认响应体 {"detail": "..."} |
| RequestValidationError | 422 | 默认返回错误明细列表，可注册处理器覆盖 |
| BusinessError（自定义） | 由类定义 | 必须注册处理器，否则落到 500 |
| 未捕获异常 | 500 | ServerErrorMiddleware 兜底，返回 Internal Server Error |

## 练手题

1. 编写日志中间件，输出请求方法、路径、状态码、耗时，格式如 POST /items 200 12.34ms。
2. 注册两个中间件验证洋葱顺序，确认注册先后与输出顺序的对应关系。
3. 为详情接口注册 BusinessError 处理器，使找不到资源时返回 {"code": 404, "message": "资源不存在"}。
4. 覆盖 RequestValidationError，把 422 响应改成统一格式，保留出错字段信息。
5. 配置 CORSMiddleware 允许 http://localhost:5173 并开启 allow_credentials，用浏览器请求，观察 OPTIONS 预检请求是否由中间件直接应答。
