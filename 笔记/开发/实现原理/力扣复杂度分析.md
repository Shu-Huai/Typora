# 力扣复杂度分析

## 功能介绍

LeetCode 中，有这样一个功能，即给出用户提交的代码的时间复杂度和空间复杂度，结果是输出 $O(N),O(n\log n)$ 这样的数学公式，这个功能是如何实现的？

是否有技术能够直接从代码自动化分析出复杂度，并给出这样的数学公式？还是根据运行时间进行推断的？

![30697de6-6c37-426a-9788-64123f6174ee](http://public.file.lvshuhuai.cn/images\30697de6-6c37-426a-9788-64123f6174ee.png)

## 概要

- 这个功能实际上是接了个 LLM，“请你根据这份代码，给出其空间复杂度”类似这样的 prompt。
- **LeetCode 现在这个“时间复杂度 / 空间复杂度 $O(N)$”弹窗，不是靠测运行时间算出来的，而是一个 AI＋静态分析 的“猜测器”，本质是启发式/LLM 工具。**
- **从理论上讲，不可能（在一般意义上）做一个“对任意代码都精确给出 Big-O”的自动分析器**，最多只能在受限的语言/代码风格里近似推断。
- 现实中确实有一些“自动复杂度分析”的技术和研究工具，但都带有各种限制，LeetCode 的实现可以看成是其中很“工程化＋AI 化”的一种。

## LeetCode 这个功能本身在干嘛？

LeetCode 在 2024 年发布过一条官方更新，说新上线了 **“Analyze Complexity：自动分析提交的时间和空间复杂度”** 的功能。

另外，在 LeetCode 的公开 issue 里，这个功能被明确叫作 **“AI Analyze Complexity 工具”**，而且有用户发现：

> 如果你在代码里自己写了注释 `// TC = O(T * B log B + ...)`，这个工具有时会**直接把你注释里的复杂度原样抄出来**，甚至注释是错的它也照抄。[GitHub](https://github.com/LeetCode-Feedback/LeetCode-Feedback/issues/32223?utm_source=chatgpt.com)

这两点基本说明：

它并不是从底层执行时间推出来的“数学结论”，而是一个**读你代码（甚至读注释）、然后用 AI/规则做静态分析的工具**。

再加上一些博客专门讨论这个功能的“准确性问题”，比如某人写了一个看起来是 $O(N)$ 空间的解法，但 LeetCode 给出 $O(1)$，说明它的判断有偏差。[interviewhelp.io](https://www.interviewhelp.io/blog/posts/how_accurate_is_the_analyze_complexity_feature_on_/?utm_source=chatgpt.com)

这也符合 “LLM + 启发式规则” 的味道——**能对大部分常见写法给出合理答案，但绝对不严谨**。

## 理论上能不能“从代码自动算出 Big-O”？

这里有个非常关键的计算机科学结论：

> 对**一般的、图灵完备的语言（C++/Java/Python 这类）**，想要一个算法**对所有程序都精确给出时间复杂度（甚至判断是不是 $O(n)$、$O(n^2)$ 等）是做不到的**——会和[[笔记/开发/算法/停机问题]]等价，属于不可判定问题。

原因直觉上是：

- 复杂度取决于“这个程序对所有输入会怎么走”，
- 但“对所有输入会不会停”“会不会在某个 input 进入死循环”等问题本身就是不可判定的。

所以：

- **不存在一个“对任意代码都精确”的通用自动复杂度分析器。**
- 能做的只能是：
    - 限制语言/风格（比如：不能有任意递归、不能有复杂指针、不能有动态生成代码……），
    - 或者给出一个**上界/近似估计**，而不是精确的 Big-O。

## 现实里有哪些自动复杂度分析技术？

### 静态分析

这类工具会：

- 解析 AST / 控制流图 / 调用图；
- 分析循环的迭代次数、递归深度、数组访问模式等；
- 用**抽象解释 / 约束求解 / 线性递推**等方法推一个“成本函数”。

很多工业级静态分析器（Astrée 之类）就是这样分析程序的各种性质的，只不过它们更多关注“是否有越界、除以 0、死锁”等安全问题，同样的思想也可以用来分析资源消耗（时间、空间）。

优点：

- 不用真正跑程序；
- 在限制一定编码风格时，可以给出比较可靠的“上界”。

缺点：

- 一旦代码写得很花（多态、虚函数、反射、复杂递归、非线性计算循环次数），精确分析会变得非常难甚至不可能；
- 通常只能说“至多是 $O(n^2)$”、而不是非常精细地区分 $O(n\log n)$ vs $O(n)$。

### 动态 / 经验分析（真跑、拟合曲线）

另一路思路是：

1. 生成不同规模的输入 $n$；
2. 多次运行程序，记录时间/内存；
3. 用回归/统计方法去拟合：更像 $O(n)$、$O(n \log n)$、$O(n^2)$ 还是 $O(2^n)$ 等

学术界有类似的工具，比如 **Empirical Scaling Analyser (ESA)**、最近还有 benchmark 专门提供“通过动态方式推断时间/空间复杂度”的框架，用来评估代码和大模型的复杂度。

优点：

- 不用懂代码结构，只要能跑；
- 对很多算法（尤其是单一主要循环/递归）可以比较好地拟合复杂度类型。

缺点：

- 需要跑很多次、很多不同 $n$，**成本很高**；
- 对常数因子/缓存命中等非常敏感，噪声大；
- 很难在在线评测平台这种高并发场景大量使用。

这一点几乎可以排除“LeetCode 每次帮你跑一堆不同规模的隐藏用例专门做复杂度拟合”的可能性——太贵，也不稳定。

## LeetCode 的做法大概率是什么？

综合官方文案 + 社区反馈，可以合理推断（但注意：LeetCode 没公开源码，所以只能是推测而不是“官方真相”）：

**它是一个 AI／LLM 驱动的静态分析工具：**

- 官方更新里这个功能单独列出，和“AI Code Review”等功能放在类似位置；
- GitHub issue 明确说这是一个 “AI Analyze Complexity tool”，并且会读你写在注释里的复杂度然后复读。

**内部估计过程可能是：**

- 把你的源码（以及语言信息、题目 ID、也许还有题目描述）作为输入；
- 做一些简单的程序分析（提取循环/递归结构、调用关系）；
- 再喂给一个微调过的 LLM，让它输出：
    - Time: $O(n)$、$O(n \log n)$、$O(n^2)$ 等
    - Space: $O(1)$、$O(n)$ 等

这跟现在很多“复杂度分析小助手”Chrome 插件的做法几乎一样，只不过 LeetCode 是内置版。

**它几乎肯定不会是“根据你那一次提交的运行时间”推出来的：**

- 提交时 LeetCode 通常只在固定测试集上跑一次，得到“xx ms、xx MB”；
- 单次运行只能反映“这个 $n$、这个机器、这个数据下的具体时间”，**没法从单点时间反推出 big-O 类型**；
- 真要基于运行时间做推断，也得多组不同 $n$ 做拟合，这对线上 OJ 成本太高，也会让判题时间暴涨。
