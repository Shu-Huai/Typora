# 异常与失败处理

本文逐项说明异常场景下的行为：用户看到什么、接口返回什么、数据怎么写、能否重试。

本文不讨论正常流程，见各模块文档。异常码清单见 [[接口/接口总览|接口总览]]。

## 异常矩阵

### 账单操作

| 场景 | 返回 | 数据写入 | 可重试 |
|---|---|---|---|
| 金额/参数缺失 | 422 | 无 | 改参数后可以 |
| 账本不属于当前用户 | 403 | 无 | 否 |
| 退款金额超过原支出剩余额度 | 422（校验失败） | 无，行锁保证并发正确 | 改金额后可以 |
| 编辑支出单时金额小于已退款总额 | 422 | 无，事务回滚 | 先处理退款单 |
| 删除已被退款关联的支出单 | 正常 | 级联删退款单并回滚余额 | 幂等性见下 |

账单增删改全部在事务里，异常时数据库回滚，余额不会半更新。Redis 缓存更新在事务外，异常时缓存可能是旧值，下一次读会从库刷新（update 后才覆盖）。

删除账单幂等性：删不存在的账单会抛 422 或 404，重复删除不是静默成功。

### 资产操作

| 场景 | 返回 | 说明 |
|---|---|---|
| 新增资产余额负数 | 422 | 信用卡类允许负余额（欠款），其他类型看校验 |
| 编辑不存在的资产 | 404 或 422 | 查不到即失败 |
| 资产余额与实际账单不符 | 无接口 | 只能靠账单反推，没有直接修正入口 |

### AI 记账

| 场景 | 返回 | 日志 |
|---|---|---|
| 文本与记账无关 | 422，提示无关 | ai_bill_parse_log 记 IRRELEVANT |
| 信息不全（缺金额等） | 422 | 记 MISSING_INFO |
| 资产名匹配不到 | 422 | 记 ASSET_NOT_FOUND |
| 分类名匹配不到 | 422 | 记 CATEGORY_NOT_FOUND |
| 多个候选有歧义 | 422 | 记 AMBIGUOUS |
| 限流 | 429 | 不调用模型，不写日志 |
| 模型超时/格式错/服务挂 | 500 | 记对应错误码和原始 JSON |

AI 失败不影响手工记账，前端把解析结果做成可编辑草稿，匹配失败用户自己选。

### 认证

| 场景 | 返回 | 说明 |
|---|---|---|
| token 缺失或格式错 | 401 token无效 | 前端清 token 跳登录 |
| token 超龄（34.7 天） | 401 token过期 | 同上 |
| 密码错 | 401 账户或密码错误 | 不跳登录，留在登录页 |
| 用户名占用（注册/改名） | 400 | 换名重试 |

## 数据一致性边界

- 账单事务只保证数据库内一致，Redis 缓存是最终一致，最大延迟取决于下一次读
- 预算数值是惰性重建，账单改完立刻查预算拿到的就是对的，但中间没有任何"脏"标记
- 资产余额没有独立的对账入口，账单和余额如果历史上有 bug 造成偏差，只能人工修库
- 图片在事务内随账单一起写入和删除，不存在文件与记录分离的问题

## 已知边界

- 并发下两个请求同时修改同一账单：没有乐观锁，后写覆盖先写，余额可能错位。个人单用户场景概率低
- 退款并发：行锁保护原支出单读取，两笔并发退款不会超退，这个场景是安全的
- TokenValidator 的 ThreadLocal 不清理：请求结束后 userId 残留在复用线程里，下一次请求若因异常提前返回可能串号
- AI 限流计数按分钟粒度，边界时刻可能实际超过 5 次
- 缓存写覆盖在事务外，提交前崩溃时缓存是"幽灵新值"，7 天 TTL 内不会自愈（除非该实体再次被写）

## 人工核对方法

怀疑余额和账单不一致时：

1. 导出该资产相关的全部账单（按类型四表分别查 asset 外键）
2. 按时间排序手工重放余额变化，对比当前 balance
3. 或者调 `GET /api/asset/day-statistic` 看历史曲线是否有跳变，跳变点即异常账单

怀疑预算不对时：

1. 确认账本 begin_date 和当前时间算出的预算周期
2. 手工统计周期内支出-退款，对比 budget.used 和 book.used_budget
3. 触发一次 rebuild（读账本接口）后再次对比
