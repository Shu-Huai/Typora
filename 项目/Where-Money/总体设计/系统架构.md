## 系统边界

系统由前端 SPA、后端单体服务、两个基础设施（MySQL、Redis）和一个外部 AI 服务组成。没有消息队列、没有对象存储、没有搜索引擎、没有定时任务。

- 前端与后端：HTTP + JSON，鉴权头 `Authorization: Bearer <token>`
- 后端与 MySQL：MyBatis 手写 XML，10 张表，账单图片以 mediumblob 存表内
- 后端与 Redis：账单/资产/分类的 JSON 缓存（7 天 TTL）+ AI 限流计数器
- 后端与 AI 服务：Spring AI 的 OpenAI 兼容接口，base-url 指向 opencode.ai 代理，模型 deepseek-v4-flash

前端有两条发布路径：普通 Web（静态 dist，可由任意静态服务器托管）和 HarmonyOS 壳（Web 产物内联进 ArkWeb 的 rawfile）。Vercel 部署模式下路由切 hash 模式。

## 组件清单与关键数据流

### 组件清单

| 组件 | 位置 | 职责 |
|---|---|---|
| Vue 3 SPA | 前端仓库 | 登录注册、记一笔、账单、资产、预算、统计图表、主题定制 |
| Controller | `controller/` | 6 个业务控制器 + BaseController（异常处理），全部 @RequestParam 入参 |
| 鉴权拦截器 | `utils/TokenValidator.java` | 拦截 /api/**，JWT 校验、token 续期、ThreadLocal 传 userId |
| Service | `service/impl/` | 账单（1198 行核心）、资产、预算、账本、分类、用户、AI |
| Mapper | `mapper/` + XML | 手写 SQL，含 resultMap、动态更新、统计聚合 |
| AI 模块 | `AiBillServiceImpl` | 提示词构造、调用、JSON 解析、资产分类匹配、限流、日志 |
| MySQL | 外部 | 10 张表，四类账单分表存储 |
| Redis | 外部 | 实体缓存 + 限流计数 |
| OpenAI 兼容接口 | 外部 | 自然语言转结构化账单 |

### 记一笔（以支出为例）

```
用户提交（FormData）
  → POST /api/bill/bill?type=支出
  → BillServiceImpl.addBill @Transactional
  → insert pay_bill + update asset.balance（同事务）
  → budget.used/times 相对更新
  → 写缓存 / 删缓存
  → 前端刷新首页与账单页
```

四类账单的落库路径不同：收入加资产余额，支出减资产余额，转账一减一加并记手续费，退款加回资产并刷新原支出单的 refunded 状态。

### AI 记一笔

```
用户输入文本
  → POST /api/bill/ai/parse
  → Redis 限流（5 次/分钟/用户）
  → 构造系统提示词（时间、类型、资产列表、分类列表）
  → 调用大模型 → 截取 JSON → fastjson 解析
  → 资产/分类精确匹配，模糊兜底，多命中抛歧义
  → 返回草稿字段（金额、分类、资产、备注、时间）
  → finally 写 ai_bill_parse_log
```

### 查询与统计

查询路径统一带 Redis 旁路缓存：先查缓存，未命中查库再回填。列表类查询（按账本、按时间区间）不缓存，直接四表分查后按时间倒序合并。预算数值不存缓存，每次读账本时全量重建。

## 技术选型与方案记录

### 为什么账单按类型拆四张表

四种账单字段差异明显：支出有退款标记、退款有原支出单外键、转账有两个账户和一个手续费字段。拆表后每张表结构贴合业务，统计 SQL 各自清晰。

代价是列表查询要四表分查再内存合并排序，分页没法下推数据库。当前数据量（个人账本级别）下没有压力，如果要做大数据量优化，这是第一个要改的点。

### 为什么预算用全量重建而不是增量更新

早期版本用相对更新方法（`changeCategoryUsedBudgetRelative` 等），每次记账后对预算做加减。这个方法现在还留在代码里但没有任何调用者。

被替换的原因：账单被修改、删除、退款后，要精确倒推预算变化很脆弱；跨预算周期的旧账单还要判断该不该算进本期。全量重建（`rebuildBudgetByBook`）的做法是每次读账本时按 beginDate 算出当前周期，用周期内"支出-退款"重新统计每个分类的 used 和 times。逻辑单一，永远和账单表一致，代价是每次读账本都要跑一遍统计 SQL。详情见 [[模块/预算/预算计算|预算计算]]。

### 为什么 AI 调用要独立一张日志表

大模型输出不可控：格式错、幻觉分类、超时都会发生。日志表记录输入文本、模型名、状态、错误码、原始 JSON、耗时，出问题时能区分"我们的提示词问题"还是"模型的问题"。限流计数用 Redis INCR，分钟粒度 key 带用户和时间戳。

### 图片为什么存数据库

没有引入对象存储，mediumblob 最省事。代价是账单表膨胀、查询要避免把 image 带进缓存（代码里写缓存前显式 setImage(null)）、下载走 JSON base64 返回。当前 100MB/文件的上限对数据库压力很大，是已知边界。

## 主要风险

- 后端配置里有明文数据库密码和 AI API key（本地 application.properties 被 gitignore 排除，example 文件才有加密提示），泄露面取决于机器本身
- 密码 MD5 哈希无盐，弱口令可离线破解
- TokenValidator 不清理 ThreadLocal，线程复用场景有串数据风险（当前 Tomcat 线程池会复用线程，问题真实存在，只是单用户场景影响小）
- 账单图片在库里，备份和迁移成本高
- AI 服务是外部的，挂了只影响 AI 记账，不影响手工记账；但 AI key 泄露会直接产生费用
- CORS 允许任意源且带凭据，配合 token 续期机制存在被跨站利用的窗口
