## rebuildBudgetByBook 的代码路径

![](Z:\Public\images\where-money-budget-rebuild.svg)

触发点只有一个：`BookServiceImpl.getBook` 和 `getBookList` 里调用。所以前端打开预算页、首页拿月统计时都会触发。

实现步骤：

1. `TimeComputer` 按 GMT+8 取今天日期，结合 book.beginDate 算当前周期：如果今天日期 ≥ beginDate，周期从本月 beginDate 开始到下月 beginDate 前一天；否则从本月 beginDate 往后推一个月
2. `BudgetMapper.selectUsedAmountByBook` 等聚合 SQL：按 book_id + 周期时间过滤支出账单，支出金额减去该单已退金额（子查询 refund 表），按 bill_category_id 分组出 used 和 times
3. 对每个有预算的分类执行 update（set used、times）
4. 汇总所有分类 used 更新 book.used_budget

整个过程在 @Transactional 里，重复执行覆盖写，幂等。

## 周期计算与校验

### 周期计算细节

beginDate 是每月第几天（1-28）。周期边界：

- 今天 ≥ beginDate：周期 = 本月 beginDate ～ 下月 beginDate
- 今天 < beginDate：周期 = 上月 beginDate ～ 本月 beginDate

2 月的情况：beginDate 最多 28，2 月一定有 28 号，所以周期不会跨到 3 月错位。这就是 beginDate 上限 28 的原因，而不是随意定的。

### 校验实现

- addBudgetValidated：先查该分类是否已有预算（有则拒绝），再查账本已分配总额 + 新额度 ≤ total_budget（超则拒绝）
- updateBudgetValidated：请求里的 amount/times 非空直接抛异常；只处理 limit，改后重新走总额校验
- updateTotalBudgetValidated：请求里的 usedBudget 非空直接抛异常；新 totalBudget < 已分配总额则拒绝

总额校验的 SQL：按 book_id sum(limit_amount) 对比 total_budget。

## 残留代码与特殊风险

### 残留的相对更新方法

`changeTotalUsedBudgetRelative`、`changeCategoryUsedBudgetRelative`、`changeCategoryTimesRelative` 和对应的 mapper 方法还在代码里，没有任何调用者。它们是全量重建方案落地前的实现，记账时实时增减预算数值。

当时的问题：改账、删账、退款都要精确倒推预算变化，路径多了之后容易漏，且跨周期账单的归属判断重复实现。全量重建后这些方法变成了死代码，删掉可以减维护面。

### 特殊风险

- rebuild 在 getBook 里同步执行：账单量大时每次打开预算页都全表聚合，慢查询会放大到整个账本查询
- rebuild 与记账并发：记账事务还没提交时 rebuild 读到旧账单，算出的 used 略旧；下一次读自动纠正。这是惰性一致，不是 bug
- 分类删除后 budget 行悬挂：rebuild 聚合时按分类 join，悬挂行不会被更新，used 停留在删除前的值；界面上这个分类已经不在列表里，用户看不到，但行还在
- book.used_budget 汇总与分类 used 之和理论上相等，如果分类被删，汇总就不等了，目前没有对账
