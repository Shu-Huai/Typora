# 并发与失败处理

本文说明并发控制手段、异常场景行为和积分修正路径。

本文不讨论正常流程，见各模块文档。错误码与提示见 [[接口/接口总览|接口总览]]。

## 并发控制

系统用两个手段保证并发安全：

### advisory lock（应用级锁）

| 锁 | 作用域 | 保护的场景 |
|---|---|---|
| pg_advisory_xact_lock(hashtext(userId)) | 用户维度 | 计时开始/停止/切换串行，保证"单 RUNNING 会话"约束 |
| pg_advisory_xact_lock(hashtext("goalId:periodStart:periodEnd")) | 目标周期维度 | 结算与修正互斥，防止同一周期重复结算 |
| pg_advisory_xact_lock(hashtext("reward-redeem:<userId>")) + (hashtext("reward-redeem-item:<rewardItemId>")) | 用户 + 商品维度 | 兑换串行，防库存并发扣超 |

锁都在事务内获取（xact），事务提交/回滚自动释放，不需要手动 unlock。用户维度锁意味着同一用户的计时操作全局串行——个人应用没有吞吐问题。

### 数据库约束兜底

- GoalSettlement @@unique([goalId, periodStart, periodEnd])：即使锁失效，重复结算会 P2002
- TimerSession 的"单 RUNNING"没有唯一约束（业务语义复杂），完全靠 advisory lock

## 异常矩阵

### 计时

| 场景 | 返回 | 数据 | 用户看到 |
|---|---|---|---|
| 活动不存在或已停用 | 400 | 无 | 提示活动无效 |
| 已有运行中会话 | 409 ConflictError | 无 | "已有运行中的计时" |
| 开始时间与已有记录重叠 | 409 | 无 | 冲突提示 |
| 停止时结束时间早于开始（时钟回拨） | 自动 +1 秒 | 记录按修正时间写入 | 无感知 |
| 取消计时 | 200 | 会话置 CANCELED，无记录无积分 | 无感知 |

### 记录

| 场景 | 返回 | 修正 |
|---|---|---|
| 补录与已有记录重叠 | 409 | 拒绝 |
| 修改后重叠 | 409 | 拒绝 |
| 修改时长/活动 | 200 | 积分差额流水 + 目标结算修正 |
| 删除记录 | 200 | 负向回滚流水 + 目标结算修正 |

### 目标与奖励

| 场景 | 返回 | 说明 |
|---|---|---|
| 同一周期重复结算 | 幂等（unique 兜底） | P2002 捕获后跳过 |
| 兑换库存不足 | 400 | 限量商品 stock<=0 |
| 兑换余额不足 | 400 | 余额 < 价格 |
| 兑换已删除商品 | 400 | 商品查询为空 |

## 积分修正路径

一条记录变更的完整连锁：

```
修改记录
  → 事务：更新记录 + 重算 pointDelta
  → 差额追加 RECORD_EARN 调整流水 + increment 余额
  → reconcileSettlementsByRecordMutation
      → 找重叠周期的结算 → 重算 → 差额追加 GOAL 调整流水 + increment 余额
  → 提交
```

全部在一个事务内完成。任何一步失败整体回滚，不会出现"记录改了但积分没动"的中间态。

## 已知边界

- advisory lock 是 PostgreSQL 专属：换数据库（如 SQLite/MySQL）并发防护全部失效，但 Prisma 代码能跑
- 单 RUNNING 会话约束只在计时操作串行时成立：直接改库可绕过
- 时钟回拨只做了 +1 秒的最小修正，跨天的回拨（设备时间差）没有检测
- 全局结算接口 /api/goals/settle 无鉴权语义校验：任何登录用户可触发
- 事务失败的错误透传：Server Action 抛异常会被 Next.js 捕获，前端 feedback-banner 显示，但 API route 的 409 等业务错误码依赖前端 fetch 分支处理，两套错误处理路径不一致
- 无死锁重试：advisory lock 等待死锁时由 PostgreSQL 判定，应用层不重试
