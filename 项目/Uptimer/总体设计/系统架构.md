# 系统架构

本文说明系统组成、全栈结构、数据流向和技术选型。

本文不讨论积分与结算的业务细节，见 [[总体设计/积分模型|积分模型]] 和 [[总体设计/目标结算|目标结算]]。不讨论部署，见 [[开发文档/数据库与部署|数据库与部署]]。

源码范围：`src/app/`、`src/actions/`、`src/modules/`、`src/lib/`、`middleware.ts`、`prisma/schema.prisma`。

![](http://public.file.lvshuhuai.cn/images\uptimer-system-architecture.svg)

## 系统边界

Next.js 全栈单体，没有独立的 API 服务器：

- 前端：Server Components（SSR 页面）+ 客户端叶子组件（计时器、表单、选择器）
- 后端：Server Actions（表单提交）+ Route Handlers（计时 API、记录 API、目标结算 API）
- 数据：PostgreSQL 直连（Prisma 7 + pg adapter）
- 外部服务：仅 Iconify 图标 CDN（运行时拉取 SVG），无其他第三方

没有消息队列、没有后台任务、没有缓存、没有对象存储。鉴权是自建 JWT Cookie，没有引入 Auth.js 之类的框架。

## 全栈结构与模块分层

### 页面请求

```
浏览器请求 /records（带 uptimer_session Cookie）
  → middleware 粗查 cookie 存在性
  → 页面 Server Component 调 requireUserId() 验签 JWT
  → recordsService 查询 → 渲染时间轴
```

### 表单提交（Server Action）

```
活动创建表单 → createActivityAction("use server")
  → activityService.create → prisma 事务 → 返回
  → revalidatePath 刷新页面
```

### 计时与结算

```
计时：TimerPanel 每 1 秒本地刷新显示
  → 开始：POST /api/timer/start → timerService.startTimer
  → 停止：POST /api/timer/stop → 事务：建记录+结算积分+会话置 FINISHED
  → 查询：GET /api/timer/current → 运行中会话（用于刷新页面后恢复秒表）

结算（惰性，无定时任务）：
访问 /records → goalService.settleOnRecordsVisit（当前用户）
POST /api/goals/settle → settleExpiredGoals（全部启用用户）
```

### 模块分层（src/modules）

每个业务域一个目录，四层文件：

| 层 | 职责 | 示例 |
|---|---|---|
| schemas.ts | zod 校验 | timer.schemas.ts |
| repository.ts | Prisma 查询封装 | timer.repository.ts |
| service.ts | 业务 + 事务 | timer.service.ts |
| types.ts | 类型定义 | timer.types.ts |

调用方向：action/route → service → repository → prisma。校验在 action 层或 service 层用 zod 完成。

## 技术选型与方案记录

### 为什么 Next.js 16 全栈而不是前后端分离

单人项目的效率选择：一套 TypeScript 类型从数据库（Prisma）贯通到页面（React props），没有 API 契约维护成本。Server Actions 让表单提交不用写 API 层，Route Handlers 只给"需要 fetch 的交互"用（计时器）。

代价：部署必须是 Node 环境（不像纯静态站能扔 CDN），页面和 API 耦合在同一进程。

### 为什么用 advisory lock 而不是唯一约束做并发控制

计时的"单会话"约束本质是业务规则（同一用户同时只能跑一个计时），不是数据唯一性。pg_advisory_xact_lock(hashtext(userId)) 在事务内锁住用户维度的所有计时操作，开始/停止/切换互相串行，比唯一约束更贴合语义，且锁随事务自动释放。

目标结算用 goalId:periodStart:periodEnd 做 advisory lock，另有 @@unique 兜底 P2002。

### 为什么结算做成惰性触发而不是定时任务

没有 cron 环境（自部署，无 Vercel Cron），且个人应用的结算频率低。惰性结算的代价是：用户不访问记录页，过期目标就一直不结算，积分也就一直不到账。当前接受这个代价；如果将来上 Vercel，vercel.json cron 调 /api/goals/settle 是现成的升级路径。

### 为什么记录要存活动快照

活动可以改名字、改回报率、甚至软删除，历史记录如果外键直连，展示和重算都会随活动变化漂移。快照（activityNameSnapshot、activityNatureSnapshot、rewardRateSnapshot）让每条记录自包含当时的结算依据，目标结算修正也能按快照还原历史。

## 主要风险

- 无测试：积分和结算逻辑（余额、回滚、修正）全靠人工验证，改动风险高
- AUTH_SECRET 有开发态缺省值 "dev-auth-secret-change-me"，忘了配置时上线等于裸奔
- /api/goals/settle 是全局结算入口，任何登录用户都能触发（middleware 只查 cookie 存在性），虽然业务上无害但语义不对
- Iconify 图标依赖外部 CDN，离线或 CDN 故障时图标空白（emoji 回退只对无冒号的值生效）
- 单提交大爆炸（116 文件一次提交），没有演进历史可查
