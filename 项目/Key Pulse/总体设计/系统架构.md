# 系统架构

本文说明系统组成、前后端分工、数据流向和多端形态。

本文不讨论加密细节，见 [[总体设计/安全模型|安全模型]]。不讨论各模块内部实现，见 [[模块/认证与会话/认证与会话|认证与会话]]、[[模块/OTP 配置/OTP 配置与协议|OTP 配置]]、[[模块/密码库/密码库与密钥|密码库]]。

源码范围：

- 前端 `src/`
- 前端 `vite.config.ts`、`electron/`、`android-app/`、`harmony-app/`

## 系统边界

系统由多端前端、后端单体、两个基础设施（MySQL、Redis）组成。没有消息队列、没有定时任务、没有外部服务调用、没有对象存储。

- 前端与后端：HTTP + JSON，`Authorization: Bearer` + Cookie `KP_REFRESH`（credentials: include）
- 后端与 MySQL：MyBatis-Plus 注解 SQL + Flyway 迁移
- 后端与 Redis：仅限流计数器，缺省时回退进程内 Map

唯一的外部信任边界是"零知识线"：secret 明文、vault 密钥、验证码计算都在前端一侧，任何情况下不过这条线。后端看到的 secret 形态是 AES-GCM 密文 + 加密元数据。

## 前后端分工与多端形态

### 前后端分工

| 职责 | 位置 |
|---|---|
| OTP secret 加解密 | 前端 vault（Web Crypto） |
| TOTP/HOTP 验证码计算 | 前端（RFC 4226/6238 本地实现） |
| 二维码解析 | 前端（@zxing/browser，摄像头在原生壳） |
| 密文与协议参数存储 | 后端 otp_entries 表 |
| 用户、会话、审计 | 后端 |
| 改密重加密的编排 | 前端逐条重加密，后端批量更新密文 |

改密是两端配合最紧的流程：前端对每条 OTP 解密后用新密钥加密，把新密文集合交给后端；后端在事务里逐条更新（带 user 隔离），任何一条失败整体回滚。

### 多端形态

一套 Vue 代码，四种构建模式：

| 形态 | 构建命令 | 路由 | 差异 |
|---|---|---|---|
| Web | npm run build | history | base `/` |
| Electron | electron:build | hash | base `./`，主进程 480x720 窗口，contextIsolation + sandbox |
| Android | android:build + android:sync | hash | dist 拷入 WebView assets，JS/CSS 内联进 index.html |
| 鸿蒙 | harmony:build + harmony:sync | hash | 同上，拷入 rawfile/www |

原生壳通过 CustomEvent 桥接向前端提供能力：摄像头扫描（startCamera/stopCamera）、剪贴板图片（keypulse-native-paste-image）、系统深色同步（keypulse-system-theme-change）。Web 端没有这些能力时降级为文件上传和手动输入。

## 关键数据流

### 登录

```
输入邮箱密码
  → POST /api/auth/login（限流 email+IP 10次/分）
  → BCrypt 校验 → 签 access token（15 分钟）+ 发 refresh token（180 天，存哈希）
  → 前端 vault.unlockWithPassword（PBKDF2 派生密钥）
  → GET /otp-entries 拉密文 → 本地解密 → 列表展示
```

### 查看验证码

```
OtpListView 每 1 秒 setInterval
  → 本地 HMAC 计算全部条目（不发网络请求）
  → 渲染 6/8 位验证码 + TOTP 倒计时
```

### 刷新会话

```
任意请求 401
  → POST /api/auth/refresh（Cookie KP_REFRESH，限流 IP 30次/分）
  → 轮换：删旧 hash、签新 refresh、签新 access
  → 重放原请求一次；refresh 也失败则清 session 回登录页
```

## 技术选型与主要风险

### 为什么 access + refresh 双 token、refresh 只存哈希

access token 15 分钟短命，泄露影响窗口小；refresh token 180 天长命但只存 SHA-256 哈希、只走 HTTP-only Cookie，前端脚本读不到。轮换机制让每次 refresh 后旧 token 作废，配合"只重放一次请求"避免了并发请求互相踢。

refresh 存哈希意味着数据库泄露时哈希无法还原出可用的 refresh token，攻击者拿不到会话。代价是登出和轮换都要先哈希再查库，多一次 SHA-256 计算，可忽略。

### 为什么 vault 密钥要从主密码派生

随机密钥需要安全存储（又回到钥匙托管问题）；从密码派生意味着"密码就是钥匙"，改密即全库重加密，服务端和本地都不存密钥本体。代价是 PBKDF2 要跑 30 万次，解锁登录有可感知的延迟（前端在解锁时做，一次性成本）。

### 为什么后端不生成验证码

生成验证码需要 secret 明文，一旦后端参与就意味着零知识承诺被破坏，且后端成为攻击高价值目标。全部计算下放前端后，后端就是个"加密数据的保险柜"，即使被攻破也只有密文。TOTP/HOTP 算法本地实现（约百行，RFC 标准），不依赖第三方库。

### 主要风险

- token version 的鉴权校验没实现（见 [[总体实现/异常与失败处理|异常与失败处理]]）：改密后旧 access token 在 15 分钟窗口内仍可用
- 用户忘记主密码：vault 无法解锁，密文无法解密，没有恢复机制（产品决策，但用户会丢数据）
- 前端 localStorage 只有主题设置，无 token 落盘，风险可控；但 IndexedDB vault 材料（包裹的密钥）在本机，设备被物理接触时有离线爆破风险（PBKDF2 成本是主要防线）
- CORS 默认 `*` + allowCredentials 是宽松配置，上线要收窄
- jwt-secret 当前本地配置是弱口令，生产必须更换
