# 安全模型

本文说明 KeyPulse 的完整安全设计：vault 密钥体系、token 双机制、限流、审计和日志脱敏。

本文不讨论各机制的实现代码，见 [[模块/认证与会话/认证与会话|认证与会话]] 和 [[模块/密码库/密码库与密钥|密码库]]。

源码范围：前端 `src/modules/crypto/`、`src/stores/vaultStore.ts`；后端 `security/`、`service/impl/SecurityRateLimitServiceImpl.java`、`service/impl/AuditLogServiceImpl.java`、`log/`。

## vault 密钥体系

前端密码库的密钥派生链：

![](Z:\Public\images\key-pulse-security-model.svg)

```
主密码
  → PBKDF2（SHA-256，300,000 次迭代，随机 salt）→ rawKey（256 bit）
  → 随机 deviceKey（AES-GCM 256，extractable=false）
  → rawKey 用 deviceKey 包裹（wrappedKey）
  → {salt, iv, wrappedKey, deviceKey} 存 IndexedDB（keypulse-vault / materials / current）
```

每一条 OTP secret 用 rawKey 独立 AES-GCM 加密（随机 salt + iv 各一条），密文连同加密元数据（加密算法、KDF 算法、KDF 参数）一起提交后端。

两个关键性质：

- 主密码不上传、不落盘，只存在于内存和派生过程
- 登出/改密后 vault 清空，下次登录要重新输入密码解锁（restore 失败即回登录页）

改密的完整路径：旧密码派生旧密钥 → 逐条解密 → 新密码派生新密钥 → 逐条重加密 → 新密文集合提交后端 → 后端事务内更新 → 前端清 vault。任何一条条目解密失败（比如数据损坏），用户会看到明确失败。

## token 双机制

| | access token | refresh token |
|---|---|---|
| 形态 | JWT HS256 | 随机 32 字节 Base64URL |
| 内容 | sub=userId、tokenVersion、iat、exp | 库中只存 SHA-256 哈希 |
| 时长 | 15 分钟 | 180 天 |
| 载体 | Authorization 头 | HTTP-only Cookie KP_REFRESH |
| 撤销 | 无法（靠自然过期） | 轮换即删旧、登出删当前、改密全删 |

Cookie 属性：HttpOnly、Path=/api/auth；HTTPS（含 X-Forwarded-Proto）时 Secure + SameSite=None，本地 HTTP 时 SameSite=Lax。

改密的全设备失效链路：BCrypt 哈希更新 + tokenVersion+1 + refreshTokenMapper.deleteByUserId。新签发的 access token 携带新 tokenVersion。

设计文档声称"每次鉴权校验 token version"，源码里 JwtAuthenticationFilter 只验签不比对数据库，改密后旧 access token 在 15 分钟内仍有效。这是当前实现与设计的已知差距，见 [[总体实现/异常与失败处理|异常与失败处理]]。

## 限流与审计

### 限流

两个限流点：

| 场景 | key | 限额 | 窗口 |
|---|---|---|---|
| 登录 | kp:rate:{email}:{ip} | 10 次 | 1 分钟 |
| 刷新 | kp:rate:refresh:{ip} | 30 次 | 1 分钟 |

实现是 Redis String INCR + 首次设置 TTL；Redis 不可用或异常时回退到进程内 ConcurrentHashMap 固定窗口计数。回退 Map 没有清理线程，条目只在下次访问时惰性重建，注释承认"bounded"——进程级数据量有限。

### 审计

audit_logs 表记录 8 类事件：USER_REGISTER、USER_LOGIN（成败分记）、USER_LOGOUT、PASSWORD_CHANGED、OTP_CREATED、OTP_UPDATED、OTP_DELETED。

规则：

- OTP 事件的快照只含 issuer 和 accountName（`;` 替换为空格防拼接歧义）
- 密码、secret、密文、验证码、JWT、refresh token 原文一律不入审计
- 登录失败也记录（success=false），便于发现撞库

### 日志脱敏

RequestLoggingFilter 记录每个请求的 requestId（透传 X-Request-Id 或生成 UUID）、方法、路径、状态、耗时、IP、User-Agent。UA 先经 SensitiveDataSanitizer 清洗：正则 `(?i)(password|encryptedSecret|encrypted_secret|token|secret|jwt)\s*([:=])\s*([^\s,;&]+)` 把值替换为 `[REDACTED]`。

审计日志和请求日志之外，设计文档里的"操作日志"（注解/AOP 方式）没有实现。

## 已知边界

- token version 鉴权校验未实现（上）
- 无验证码重试策略之外的反机器人手段（注册接口没有限流）
- 前端 JWT 不验签（只按后端返回使用），信任来自 HTTPS 通道
- 邮箱注册无验证，emailVerified 恒 false
- 审计日志无清理策略，长期膨胀
- CORS 配置默认 `*` + allowCredentials，上线需收窄到具体域名
