# 认证与会话

本文从代码角度说明注册、登录、会话刷新轮换、登出和改密全设备失效的实现。

本文不讨论安全设计的取舍，见 [[总体设计/安全模型|安全模型]]。异常行为见 [[总体实现/异常与失败处理|异常与失败处理]]。

源码范围：`service/impl/AccountServiceImpl.java`、`service/impl/SessionServiceImpl.java`、`security/JwtService.java`、`security/JwtAuthenticationFilter.java`。

## 注册与登录

### 注册

`register(RegisterCommand, RequestMetadata)`：

1. email trim + 小写归一
2. findByEmail 查重，存在抛 EMAIL_EXISTED(409)
3. BCrypt 编码密码，emailVerified=false，tokenVersion=0
4. 写 USER_REGISTER 审计

注册成功不自动登录，前端跳登录页。注册接口没有限流。

### 登录

`login(LoginCommand, RequestMetadata)` 是 @Transactional：

1. 限流：kp:rate:{email}:{ip}，10 次/分钟，超限抛 429
2. 密码不匹配：记 USER_LOGIN(success=false) 审计，抛 401
3. 成功：sessionService.issue（refresh token 哈希入库）+ jwtService.createAccessToken(userId, tokenVersion)，记 USER_LOGIN(true)

access token 的 tokenVersion 取自签发时的用户当前值。

## 会话刷新与轮换

`SessionServiceImpl.refresh(rawToken, metadata)`：

1. 限流 kp:rate:refresh:{ip}，30 次/分钟
2. rotate：SHA-256 哈希 → 查库 → 过期则删并抛 401 → 删旧记录、签新 token（180 天）
3. 查用户当前 tokenVersion，签新 access token

轮换的性质：refresh token 是一次性的，每次使用即作废旧 token。并发场景两个请求同时 refresh，第一个成功第二个必然查不到旧哈希而失败——前端"只重放一次"的策略下第二个请求会回登录页，这是已知行为。

## 登出与改密

### 登出

`logout(rawToken)`：revoke 按哈希删当前设备记录（返回 userId 供审计），清 Cookie（maxAge=0），记 USER_LOGOUT。没有 Cookie 的登出请求（无会话）也返回成功。

### 改密（全设备失效）

`changePassword(userId, command, metadata)` 是 @Transactional：

1. 校验旧密码
2. 逐条 updateCiphertextForUser（密文/salt/iv/算法/KDF 参数，SQL 带 user 隔离），任何一条 0 行即抛 UNAUTHORIZED 整体回滚
3. 更新 BCrypt 哈希、tokenVersion+1、passwordChangedAt
4. deleteByUserId 删除全部 refresh token
5. 记 PASSWORD_CHANGED 审计

效果：所有设备 refresh 立即失效；access token 自然过期（15 分钟）后也无法刷新。前端侧同时清 vault，设备上的本地密钥失效。

## 已知边界

- JwtAuthenticationFilter 只验签不比对 tokenVersion：改密后旧 access token 在 15 分钟窗口内仍可调用接口（见 [[总体实现/异常与失败处理|异常与失败处理]]）
- 登录和刷新的限流 key 与设计文档不一致（实际 kp:rate:*，设计文档是 kp:login-fail/kp:refresh-rate）
- AccountServiceImpl 的多构造函数 null 依赖是重构遗留
- 注册无限流
- refresh token 无"记住设备"列表，用户无法单独踢某台设备
