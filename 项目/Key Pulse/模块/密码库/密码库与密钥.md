# 密码库与密钥

本文说明前端 vault 的密钥派生、加解密、IndexedDB 存储、解锁恢复和改密重加密。

本文不讨论安全设计的取舍，见 [[总体设计/安全模型|安全模型]]。不讨论改密的后端行为，见 [[模块/认证与会话/认证与会话|认证与会话]]。

源码范围：`src/modules/crypto/vaultCrypto.ts`、`src/modules/crypto/vaultStorage.ts`、`src/stores/vaultStore.ts`。

## 密钥派生与加解密

### 密钥派生

解锁时从主密码派生加密密钥：

```
PBKDF2(password, salt, 300000 次, SHA-256) → 256 bit rawKey
```

salt 的来源：登录时先从后端取任意一条 OTP 条目的 secretSalt（otpStore.load 拿第一条）。每条 OTP 有独立的随机 salt，但密码派生的 salt 必须稳定，所以借用了条目自己的 salt 字段——这也是登录流程先拉列表再解锁的原因。

### 加密与解密

每条 OTP secret 独立加密：

```
加密：AES-GCM 256，随机 salt + 随机 iv → {ciphertext, salt, iv}
解密：用该条目的 salt 和 iv 解出明文
```

加密元数据（salt/iv/算法/KDF 参数）随密文一起提交后端存储。解密失败（数据被篡改、密码不对、跨设备改密后旧密钥）会抛异常，前端提示验证码计算失败。

## IndexedDB 设备材料

解锁成功后，为了让本设备下次打开不用重新输密码，把密钥材料存进 IndexedDB：

```
库 keypulse-vault / store materials / key current
值：{version: 1, salt, iv, wrappedKey, deviceKey}
```

deviceKey 是随机 AES-GCM 密钥（extractable=false），rawKey 用它包裹成 wrappedKey。下次访问走 `restore()`：读出材料 → deviceKey 解包 → 恢复 rawKey。deviceKey 不可导出，材料离开这台设备无用。

登出和改密都会 `vaultStore.clear()` 清空 IndexedDB 材料和内存密钥。

## 改密重加密与会话关系

### 改密重加密

`reencryptEntries(newPassword, entries)` 逐条：

1. 用旧 rawKey 解密每条密文
2. 用新密码派生新 rawKey（新随机 salt）
3. 新密钥加密 → 产出 ReencryptedOtpEntry 集合

集合随 changePassword 请求提交后端。中途失败（任一条解不开）直接中断，前端停留在改密页，后端数据未动。

### 会话与 vault 的关系

- access token 过期不影响 vault：refresh 成功后 vault 继续可用
- refresh 彻底失败（回登录页）时 vault 已解锁状态还在内存——authStore.clearSession 只清 token；页面跳转后 OtpListView 卸载，但 vaultStore 的解锁状态在 store 里，重新登录后如果密码没改，理论上仍可解锁。实际上登录流程会重新 unlockWithPassword，覆盖旧状态
- 改密成功必须 clear vault：旧 rawKey 解不开新密文，不清理会导致后续解密失败

## 已知边界

- 忘记主密码 = 数据丢失，无恢复路径
- vault 材料在 IndexedDB，本地浏览器扩展或恶意网页（同源）理论可读取，靠浏览器同源策略兜底
- PBKDF2 30 万次在低端设备上有秒级延迟，登录按钮会卡一会儿
- 跨设备改密后旧设备 restore 会"成功"但解密失败，没有自动检测和引导重新登录
- salt 借用第一条条目的 secretSalt，如果用户删除了该条目不影响（salt 已随材料存 IndexedDB），但新设备首次登录时用户必须至少还有一条 OTP
