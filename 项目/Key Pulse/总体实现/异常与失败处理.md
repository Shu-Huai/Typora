# 异常与失败处理

本文说明异常场景下的行为：用户看到什么、接口返回什么、数据怎么写、能否恢复。

本文不讨论正常流程，见各模块文档。错误码清单见 [[接口/接口总览|接口总览]]。

## 异常矩阵

### 认证与会话

| 场景 | 返回 | 数据写入 | 用户侧 |
|---|---|---|---|
| 注册邮箱重复 | 409 EMAIL_EXISTED | 无 | 提示换邮箱 |
| 参数校验失败（邮箱格式、密码长度） | 400 PARAM_ERROR | 无 | 表单字段级提示 |
| 密码错误 | 401 USERNAME_OR_PASSWORD_ERROR | 审计 LOGIN success=false | 留在登录页 |
| 登录超限（10 次/分） | 429 TOO_MANY_REQUESTS | 无 | 提示稍后再试 |
| access token 过期 | 401 UNAUTHORIZED | 无 | 前端自动 refresh 重放一次 |
| refresh token 过期/被删 | 401 UNAUTHORIZED | 过期时删记录 | 清 session 回登录页 |
| refresh 超限（30 次/分） | 429 | 无 | 同上 |
| 改密旧密码错 | 401 USERNAME_OR_PASSWORD_ERROR | 无 | 留在改密页 |

### OTP 配置

| 场景 | 返回 | 说明 |
|---|---|---|
| 缺加密元数据（salt/iv/算法/KDF） | 400 PARAM_ERROR | Service 层 validate 逐项检查 |
| otpType/algorithm/digits 非法 | 400 | TOTP/HOTP、SHA1/256/512、6/8 位白名单 |
| TOTP 缺 period 或 ≤0 | 400 | |
| HOTP 缺 counter 或 <0 | 400 | |
| 查询/更新/删除他人的条目 | 404 NOT_FOUND | SQL 带 user_id 条件，查不到统一按不存在返回（不暴露存在性） |
| 改密时条目不属于当前用户 | 401 UNAUTHORIZED | 整体事务回滚，密文不变 |

## 会话失效的完整链路

### 登出（当前设备）

revoke 按 hash 删 refresh token 记录，清 KP_REFRESH Cookie（maxAge=0）。access token 不作废，15 分钟内仍可用（这是 JWT 短命设计的固有属性）。前端同时清 vault 解锁状态。

### 改密（全设备）

tokenVersion+1 + 删全部 refresh token。所有设备的 refresh 立刻失效；但旧 access token 的 15 分钟窗口依然存在——这就是 token version 鉴权校验未实现带来的缺口：一个攻击者如果拿到了改密前的 access token，15 分钟内还能调接口。

### 主动防御的边界

- 前端 refresh 失败自动清 session 回登录页，不会卡在死循环（allowRefresh 只允许重放一次）
- refresh 轮换是"删旧插新"，旧 token 重放必然查不到 hash，天然防重放
- 限流在 Redis 挂掉时降级进程内，不影响登录功能本身

## 数据一致性边界

- 改密是唯一的多表事务：密文批量更新 + 哈希 + tokenVersion + 删会话，全部在一个 @Transactional 里，失败整体回滚
- 登录签 token 和写审计也在事务里，但 token 签发本身不可回滚（已发出去了），极端情况下审计失败回滚会导致"登录成功但无审计"或反之
- OTP 增删改的审计与业务操作同事务，要么都有要么都无
- 前端 vault 与后端密文可能不一致：用户在多设备改密后，旧设备 IndexedDB 里的 wrappedKey 仍指向旧密码，restore 会成功但解密新密文会失败——表现为验证码计算失败。当前没有自动检测和引导，只能重新登录解锁

## 已知缺口

- token version 鉴权校验未实现（见上）
- 前端对后端返回的错误信息直接展示（throw new Error(body.message)），后端 message 是中文文案，多语言化时是问题
- 注册无限流，可被脚本刷账号
- 审计日志无清理，长期膨胀
- 忘记主密码无恢复路径：vault 打不开，数据实际丢失（产品决策，但用户要有预期）
