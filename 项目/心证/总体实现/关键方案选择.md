## 运行时核心取舍

### Agent 而非固定工作流

| 项目 | 取舍 |
| --- | --- |
| 要解决的问题 | 病例文字、SVS、知识检索和用户补充信息出现顺序不固定 |
| 未采用方案 | Java 按固定顺序执行“登记→切片→诊断→RAG” |
| 缺陷 | 需要人为预设每轮步骤，无法根据工具观察选择停止、追问或降级 |
| 最终方案 | Spring AI Tool Calling 让 Controller 在每次 Tool Result 后继续决策 |
| 仍保留的硬约束 | Java 限制工具步数、总时限、权限、路径和领域授权 |

[已知边界] LLM 的工具选择具有不确定性，系统提示词和工具描述需要与工具真实能力同步维护；测试只能验证工具契约和运行时治理，不能证明任意上游模型在任意提示下都作出最佳决定。

### 单一 SVS 共享目录

| 项目 | 取舍 |
| --- | --- |
| 要解决的问题 | SVS 体积大，不适合浏览器上传或复制为项目数据集 |
| 未采用方案 | 多数据集仓库、前端文件上传、把绝对路径写入会话 |
| 缺陷 | 权限边界模糊、数据副本不可控、不同运行环境路径不可移植 |
| 最终方案 | Java 与 Python 配置同一共享目录；会话只保存相对路径和哈希 |
| 当前边界 | 两个进程必须访问同一实际目录；不支持每个会话自定义根目录 |

### Python 作为 OpenAI 兼容网关

| 项目 | 取舍 |
| --- | --- |
| 要解决的问题 | Java 需要 Spring AI 的流式 Tool Calling，而 Controller LLM 可能是在线或本地模型 |
| 未采用方案 | Java 直接绑定具体在线供应商；为每种模型重写 Java 客户端 |
| 缺陷 | 配置分散，在线/本地切换会修改后端实现 |
| 最终方案 | Java 固定调用本机 FastAPI 的 `/v1/chat/completions`；Python 选择 online/local 上游并保持 OpenAI 兼容传输 |
| 当前边界 | Python 网关不是 vLLM；本地模型可由 vLLM 或其他 OpenAI 兼容服务提供，但需自行部署 |

## 检索与公开推理展示

本地 RAG 与互联网搜索是不同来源：前者受管理员上传 PDF 和 Qdrant 约束，后者受心脏病理领域守卫约束。两者的结果会成为 Agent 的观察，但不自动成为病例事实。

前端不展示完整思维链。原因不是缺少流式能力：SSE 会显示工具开始、工具结果、模型提供方返回的公开摘要以及回答增量；完整私有推理既不稳定，也可能泄露敏感上下文或诱导用户把中间推断误当结论。
