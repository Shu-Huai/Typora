# 数据模型

本文说明 14 个 SQLAlchemy 模型的字段、关系和存储约定。

本文不讨论业务语义，见 [[总体设计/游戏世界|游戏世界]] 和 [[总体设计/比赛引擎|比赛引擎]]。

源码范围：`models/` 14 个文件、`core/db.py`。

## 模型清单

![](Z:\Public\images\owiviosa-er-diagram.svg)

| 模型 | 业务意义 |
|---|---|
| User | 账号（email 唯一） |
| Save | 存档：一个独立游戏世界 |
| League | 联赛（多级链 upper/lower_league） |
| Club | 俱乐部（资金、声望、职员） |
| Coach | 教练（阵型、5 战术权重） |
| Player | 球员（11 能力、12 位置计数、工资、头像） |
| Calendar | 赛程 |
| Game + GameTeamInfo + GameTeamData + GamePlayerData | 正式比赛记录（4 个类一文件） |
| GamePvE + TeamPvE + PlayerPvE | PvE 比赛临时数据（3 个类一文件） |
| TargetPlayer + Offer | 转会目标与报价（2 个类一文件） |
| UserFinance | 玩家收支流水 |

## 关键字段

| 模型 | 关键字段 |
|---|---|
| Save | date（"2020-08-01" 字符串日期）、season、player_club_id、lineup（JSON 串 {球员id:位置}） |
| League | name、points、cup、upper_league、lower_league |
| Club | name、finance（万）、reputation、assistant/doctor/scout/negotiator（职员等级） |
| Coach | formation（阵型名）、wing_cross/under_cutting/pull_back/middle_attack/counter_attack（Integer） |
| Player | 11 能力值、12 位置出场计数 ST_num 等、wages（周薪）、avatar（JSON 头像参数）、real_stamina、last_game_date、values |
| Game | script（解说全文）、mvp、winner_id、goal_record |
| GamePlayerData | 每场每球员的技术统计（player_id_idx 手工索引） |
| Offer/TargetPlayer | on_sale、谈判状态（nf/r/rr） |

日期用字符串存（"2020-08-01"），不是 DATE 类型。lineup 和 avatar 是 JSON 字符串（String 列），查询时不解析。

## 关系、删除与事实边界

### 关系与约束

- 主链：user → save → league → club → coach/player；calendar、game 挂 save
- email 唯一（user）
- 无显式外键级联规则（以模型定义为准），删除存档不会自动清理子表
- 唯一手工索引：game_player_data.player_id（db.py 启动时创建）

### 删除与生命周期

- 无删除接口：存档、比赛、转会记录只增不删（/test/clear-db 除外）
- PvE 临时表（team_pve/player_pve）随比赛会话生成，结束后转为正式 Game
- Offer/TargetPlayer 状态流转代替删除：on_sale 挂牌、nf 谈判失败、r 被拒、rr 已处理

### 事实边界

- 全部状态在 MySQL，无缓存层
- 队徽图片不在数据库：按队名从独立图床加载
- ML 模型在进程内存（.pkl 启动加载），不落库
- 日志在文件系统（logs/），不落库

## 已知边界

- 无迁移文件：表结构变更靠手工 ALTER，models 与线上库可能漂移
- 日期字符串排序和区间查询依赖格式一致性，跨格式数据会静默出错
- JSON 串字段（lineup/avatar）无结构校验，脏数据写入后解析时才报错
- 球员 values 字段的用途不明（db.py 有历史加列注释）
- 无 created_at/updated_at 统一约定：各模型按需定义 created_time
