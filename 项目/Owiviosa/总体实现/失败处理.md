# 失败处理

本文说明异常场景下的行为、危险调试端点和数据一致性边界。

本文不讨论正常流程，见各模块文档。端点清单见 [[接口/接口总览|接口总览]]。

## 异常矩阵

### 认证

| 场景 | 返回 | 前端行为 |
|---|---|---|
| 密码错误 | 401 "Incorrect username or password" | 提示"账号或密码错误"，留在登录页 |
| token 无效/过期 | 401 "Could not validate credentials" | 清 token/saveId，1 秒后跳登录页 |
| 重复注册邮箱 | 400 "Email already registered" | 提示用户名已存在 |

### 比赛

| 场景 | 行为 |
|---|---|
| 阵容不完整（不足 11 人） | 前端本地校验，"阵容不完整，请补充球员" |
| 战术选择无效（turns 未变） | 前端 warning"战术选择无效！" |
| 比赛不存在 | 404 "Game not found" |
| PvE 会话不存在（直接 next-turn 没 start） | 路由层返回异常，前端表现为比赛数据空 |

### 转会

| 场景 | 返回 | 前端 |
|---|---|---|
| 报价资金不足 | 'can not afford' | 提示 |
| 重复报价 | 'repeat offer' | 提示 |
| 谈判失败两次 | 谈判状态 'nf' | 谈判窗口关闭 |
| 对方拒绝 | 报价状态 'r' → 'rr'（deal-rejected-offers 批量） | 通知 |

## 危险调试端点

/api/v1/test 下的端点全部无鉴权，部署前必须处理：

| 端点 | 风险 |
|---|---|
| GET /test/clear-db | drop_all 清空全部数据 |
| GET /test/all-judge-on-sale2 等 8 个 | 对全部 AI 俱乐部批量执行转会流程，改变游戏世界状态 |
| GET /test/game-process-demo | 跑一场曼城 vs 曼联演示赛 |

这些端点是开发期的批量调试工具。放公网等于把"一键删库"和"一键改档"公开。

## 一致性与已知缺口

### 数据一致性边界

- 世界推进（next_turn）无事务：几十场比赛 + AI 转会的模拟中途异常，会留下部分推进的状态（日期可能没 +1 但部分比赛已写入）
- PvE 比赛用 team_pve/player_pve 临时表：浏览器中断后临时数据残留，再次 start 会重新生成（旧临时数据不清理的确认见 [[模块/比赛/比赛与指挥|比赛与指挥]]）
- 转会成交是多表写入（finance 转移、user_finance 记录、工资调整），无事务保护，中途失败会资金与球员状态不一致
- 度假同步执行：进程重启丢进度，已推进的天数不回滚

### 已知缺口

- 无全局异常处理器：不同路由的报错格式不一致，前端 catch 大量静默（`catch(() => {})`），错误容易被吞
- BackgroundTasks 的任务结果不可查询：下一天返回 state 后，模拟过程失败前端无感知
- 无请求日志中的用户标识：loguru 日志不含 save_id 上下文，排查玩家问题困难
- 前端 400/403/405/408/501/503/504/505 分支是注释占位，实际只处理了 401/404/500/502

## 人工核对方法

怀疑世界推进损坏时：

1. 查 save 表的 date 与 calendar 表当天比赛状态是否一致
2. 查 game 表当天应完成的 AI 比赛是否都有记录
3. 查 user_finance 当天是否有对应的收支流水
4. 必要时用 /test/game-process-demo 单跑一场验证引擎本身可用
