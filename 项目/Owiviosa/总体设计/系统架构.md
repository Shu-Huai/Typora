# 系统架构

本文说明系统组成、比赛引擎的定位、ML 子系统和数据流向。

本文不讨论引擎内部逻辑，见 [[总体设计/比赛引擎|比赛引擎]]。不讨论世界生成，见 [[总体设计/游戏世界|游戏世界]]。

源码范围：

- 后端根平铺包：`core/`、`models/`、`schemas/`、`crud/`、`routers/`、`modules/`、`game_configs/`、`machine_learning/`
- 前端 `src/`

![](http://public.file.lvshuhuai.cn/images\owiviosa-system-architecture.svg)

## 系统边界

前后端分离：

- 前端 Vue 3 SPA（soybean-admin 模板二次开发），开发端口 19232，无代理直连后端
- 后端 FastAPI，端口 8080，前缀 /api/v1
- MySQL 持久化（pymysql 驱动，无缓存、无消息队列、无定时任务）
- 队徽图片来自独立静态服务器（默认 localhost:1451，按队名 .png）

系统是"玩家请求驱动的回合制"架构：没有任何后台调度，世界只在玩家点"下一天"（或度假）时推进，其他俱乐部的比赛和转会行为在那一刻被同步模拟。

### 世界推进（下一天）

```
前端点"下一天" → GET /api/v1/next-turn?save_id
  → FastAPI BackgroundTasks 跑 next_turner.check()
  → 立即返回 {state: null | pve}
  → 后台：日期 +1 → 模拟其他比赛 → AI 转会行动
  → state=pve 表示今天有玩家比赛，前端跳赛前准备
```

### 一场玩家比赛

```
赛前准备（阵容 + 战术权重）→ POST /game-pve/start
  → 生成 team_pve/player_pve 临时数据 → attacker_club_id
比赛进行：GET /game-pve/next-turn?tactic（每回合）
  → 引擎模拟一个进攻回合 → 返回 script 解说 + 比分 + 球员数据
  → 重复至 turns > 51 → GET /game/{game_id} 拿完整结果
或：POST /game-pve/skip 直接跳到终场
```

### 转会

```
挂牌（put-on-sale）→ 其他 AI 俱乐部报价（incoming-offers）
玩家报价（make-offer-by-user）→ 资金校验 → 对方接受/拒绝
接受后薪资谈判（negotiate-wage）→ 成功率公式 → 成交/破裂
"下一天"时 AI 俱乐部之间也会批量转会（test 下 all-* 调试端点可手动触发）
```

## 技术选型与方案记录

### 为什么比赛是回合制文字解说而不是实时引擎

单人项目在有限时间里能做出来的方案：回合制把比赛离散成最多 51 个决策点，每个决策点一次 HTTP 请求，服务端计算后返回"发生了什么事"的文本。玩家有参与感（选战术），引擎有确定性（可测试、可复现），前端不需要游戏渲染管线。

代价：比赛节奏慢，一场比赛 51 次请求；自动模式用 1 秒轮询缓解，跳过比赛接口直接算完。

### 为什么把 sklearn 模型打进项目而不是独立服务

两个 ML 用途都很轻：位置能力是 12 维权重线性回归（小数据量），战术成功率是 5 个随机森林分类器。训练离线完成（base_game 模拟器产数据 → 训练 → joblib 序列化 .pkl），运行时只做 inference：启动时加载 5 个 .pkl，比赛和选人时直接调用。不需要 GPU、不需要模型服务，进程内调用零延迟。

代价：模型是"训练一次冻结"的，模拟器逻辑改动后模型不再匹配数据分布，需要重新跑训练流程（simulate_eve.py + starter.py）。

### 为什么世界推进是 BackgroundTasks 而不是任务队列

"下一天"要模拟几十场比赛和 AI 转会，耗时可能秒级。FastAPI BackgroundTasks 在响应返回后继续执行，前端不用等。代价：任务不可观测（没有进度查询）、进程重启即丢、无重试。度假接口（连续 N 天）是同步执行，天数多了会慢。

### 为什么用 MySQL + create_all 而不是迁移

早期项目的快速迭代选择。代价：表结构演进靠手工 ALTER，db.py 里还留着被注释的"给 Player 加列"的历史语句。上线后改结构风险高，见 [[开发文档/配置与部署|配置与部署]]。

## 主要风险

- /api/v1/test 下有 clear-db（drop_all 清库）和 8 个批量转会调试端点，全部无鉴权：部署到公网等于把删库接口公开
- 无测试：比赛引擎、积分计算、转会逻辑全靠人工验证
- 前端遗留 soybean 模板代码量大（mock、旧登录组件、第二套 axios），维护面宽
- 硬编码散落：前端 BasicLayout 写死 club_id=1，转播奖金按联赛名硬编码，队徽按队名拼 URL
- 随机性：球员生成和比赛模拟用随机数，无随机种子管理，问题难复现
