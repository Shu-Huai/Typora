本文不讨论具体技术实现，实现细节见 [[总体设计/系统架构|系统架构]] 和 [[总体实现/实现总览|实现总览]]。

## 项目目标

解决校园羽毛球馆的约场问题。球馆容量有限，一个时间槽只供一人（一队）使用，热门时段需要"抢"。系统把抢票做成固定开闸时刻的秒杀：提前生成时间槽、提前预热、到点开闸、先到先得、未支付自动释放。

用户预期流程：登录 → 浏览场次 → 看时间槽 → 开闸抢票 → 抢到后支付 → 不想打就取消或退款。

## 用户角色与核心场景

### 用户角色

| 角色 | 谁 | 能做什么 |
|---|---|---|
| USER | 学生 | 注册登录、浏览场次/球场/时间槽、抢时间槽、支付、取消、退款、管理自己的账号 |
| ADMIN | 管理员（内置账号 `root`） | 以上全部 + 系统配置、场次管理、用户管理、手动预热/开闸/生成时间槽、模拟支付成功 |

ADMIN 继承 USER 的全部权限。角色机制见 [[总体设计/权限边界|权限边界]]。

### 核心场景

抢票主线：

1. 管理员提前一天（或当天）配置场次：开抢时间、开始/结束时间、时间槽间隔（如每 30 分钟一段）。
2. 系统在开抢前 N 分钟预热：生成当天全部时间槽，为每个槽在 Redis 建立库存信号量（容量 1）和去重集合，闸门置为关闭。
3. 到达开抢时刻，系统自动开闸。
4. 学生提交预约请求，系统限流、去重、扣库存，请求进消息队列异步落库，订单状态 PENDING_PAYMENT。
5. 学生 15 分钟内支付成功，订单 CONFIRMED。
6. 超时未支付，定时任务取消订单，库存回补，其他人可以再抢。

辅助场景：

- 学生取消待支付订单：库存立即回补。
- 学生退款：订单回到 CANCELLED，库存回补。
- 管理员调整球场数量：只允许在当天第一场预热开始前修改。
- 管理员改系统配置（预热分钟数、支付超时、金额等）：保存后自动做联动补偿。

## 功能范围与明确不做

### 功能范围

已实现：

- 认证：注册、登录、token 自动续期、登出（前端清 token）
- 用户自助：查看信息、改学号/密码、销户
- 浏览：场次、球场、时间槽、订单的条件查询
- 预约：抢时间槽、查询抢票结果、取消
- 支付：创建微信支付单（mock）、模拟支付成功、退款、查支付状态
- 管理：系统配置读写、场次增删改、用户增删改查、手动预热/开闸/生成时间槽
- 后台：定时预热、自动开闸、每日生成时间槽、超时未支付取消、启动球场对账
- 运维：Windows 部署脚本、批量注册用户脚本、k6 压测脚本

### 明确不做（当前版本）

- 真实微信支付：不调微信下单/回调/退款接口，全部 mock（见 [[模块/支付/支付与退款|支付与退款]]）
- 微信/QQ 等第三方登录
- 手机号、邮箱注册
- 消息推送（支付倒计时提醒、预约成功通知）
- 后台可视化运营页面之外的人工审核流程
- 多校区、多球馆的多租户隔离：单球馆，球场即资源
- 团购、包场、季卡等非单次预约的售卖方式

## 非功能要求与数据保留

### 非功能要求（事实，非目标）

从代码里能确认的约束：

- 并发：抢票瞬间高并发，单时间槽容量 1，不超卖是硬约束
- 可靠性：MQ 发布阶段失败必须补偿释放库存；消费失败进死信队列做最终补偿
- 一致性：允许短暂不一致（Redis 已扣库存但数据库未落库），通过补偿闭环收敛
- 幂等：预热、生成时间槽、抢票、支付成功全部幂等，重复调用不产生副作用
- 安全：密码 MD5 存储、JWT 鉴权、管理接口带数据库角色二次校验
- 性能：每用户每分钟限流 5 次，压测脚本目标 p95 < 1200ms、失败率 < 10%

没有 SLA、容量规划、监控告警方面的正式指标。压测脚本在 `scripts/perf/`，说明见 [[开发文档/构建发布与压测|构建发布与压测]]。

### 数据保留

- 所有业务数据在 MySQL 中持久化，无归档策略
- 逻辑删除：所有表用 `is_active` 软删，销户、删球场、删场次都不物理删除数据
- Redis 中的数据全部带 TTL（到当天结束），是可重建的临时状态：库存、去重、闸门、预热标记、补偿上下文（TTL 300 秒）
- 可重建内容：时间槽（按球场和场次配置重新生成）、Redis 全部 key
- 必须永久保存的内容：用户账号、预约记录、支付单（当前没有清理机制，一直保留）
