# 状态机

本文定义预约单和支付单的状态、流转条件和触发者。这是全系统一致性判断的基准。

本文不讨论状态字段在数据库里怎么存，见 [[数据库/数据模型|数据模型]]。不讨论支付模块的代码路径，见 [[模块/支付/支付与退款|支付与退款]]。

源码范围：

- `enm/ReservationStatus.java`、`enm/PayOrderStatus.java`、`enm/ReserveResultStatus.java`
- `service/impl/ReserveServiceImpl.java`（cancel、cancelTimeoutPending）
- `service/impl/PayServiceImpl.java`（mockWechatPaySuccess、refund）

## 预约单状态机

`ReservationStatus` 四个枚举值：`PENDING`、`CONFIRMED`、`CANCELLED`、`PENDING_PAYMENT`。

| 流转 | 触发者 | 条件 |
|---|---|---|
| （无）→ PENDING_PAYMENT | `ReserveConsumer` 落库（redis 模式）/ `ReserveServiceDbImpl.reserve`（db 模式） | 扣库存成功 |
| PENDING_PAYMENT → CONFIRMED | `PayServiceImpl.mockWechatPaySuccess` | 支付单 CAS PAYING→SUCCESS 成功，且预约仍为 PENDING_PAYMENT |
| PENDING_PAYMENT → CANCELLED | 用户主动取消（DELETE /reserve/{id}）或超时任务 | CAS 带 `status = PENDING_PAYMENT` 条件，0 行即失败 |
| CONFIRMED → CANCELLED | 退款（POST /pay/refund/{id}） | 支付单 CAS SUCCESS→REFUNDED 成功 |

关键点：

- 全部流转都是 CAS（条件更新），并发下谁先抢到谁生效，后到者拿到 0 行更新即放弃或报错
- PENDING_PAYMENT → CONFIRMED 和 PENDING_PAYMENT → CANCELLED 是互斥的两条出边，靠 CAS 保证只有一个成功
- `PENDING` 枚举值定义了但主流程不产生：落库直接写 PENDING_PAYMENT。它是预留值
- 订单取消后 `active_slot_id` 生成列变 NULL，唯一约束让位，见 [[数据库/数据模型|数据模型]]

## 支付单状态机

`PayOrderStatus` 五个枚举值：`PAYING`、`SUCCESS`、`REFUNDED`、`CLOSED`、`FAILED`。

| 流转 | 触发者 | 条件 |
|---|---|---|
| （无）→ PAYING | 创建支付单（POST /pay/wechat/{id}） | 预约处于 PENDING_PAYMENT |
| PAYING → SUCCESS | mock 支付成功 | 预约仍为 PENDING_PAYMENT |
| PAYING → CLOSED | 预约取消或超时取消 | 关联的支付单被批量关闭 |
| PAYING → FAILED | 再次创建支付单时发现旧单过期 | 惰性处理：不单独跑任务 |
| SUCCESS → REFUNDED | 退款 | 预约处于 CONFIRMED |

支付单和预约单成对流转：预约取消时关闭支付单，支付成功时确认预约。两步更新不在一个事务里，靠"支付单先 CAS、预约单后 CAS，第二步失败则整个操作报 FAILED"的顺序兜底，避免出现"支付单显示成功但预约没确认"的悬挂状态。

## 结果状态（非持久化）

`ReserveResultStatus` 是轮询接口的返回值枚举：`PENDING`、`SUCCESS`、`FAILED`。它不落库，每次查询实时计算：

- 查 `reservation` 表按 traceId 命中且属于当前用户 → SUCCESS（附 reservationId 和预约状态）
- 查 `bf:reserve:pending:{traceId}` 存在且 userId 匹配 → PENDING
- 都没有 → FAILED

## 状态机边界

- 支付成功和预约确认分两步执行，中途服务重启会出现"支付单 SUCCESS、预约仍 PENDING_PAYMENT"的中间态，之后超时任务会把预约取消掉，形成"支付成功但订单被取消"的矛盾。mock 环境下概率低，接真实支付后回调必须幂等重放
- `PAYING → FAILED` 的惰性关闭意味着超时未支付的旧单会一直躺在 PAYING 状态，直到用户再次发起支付或订单被取消。展示层看到的"支付中"可能已经过期
- 状态字段是 varchar 存枚举 name，没有 CHECK 约束，任何代码都能写入非法值
- `ReservationStatus.PENDING` 预留未使用，前端 types/api.ts 里也定义了它，两边保持一致但都是死值
