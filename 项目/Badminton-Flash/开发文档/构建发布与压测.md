# 构建发布与压测

本文说明后端打包、Windows 部署脚本、前端构建和压测工具的使用。

本文不讨论 Docker（项目没有容器化）。不讨论数据迁移（schema.sql 只建不删，无迁移工具）。

源码范围：`scripts/deploy/deploy.ps1`、`scripts/batch-register.ps1`、`scripts/perf/*`；前端 `package.json` build 脚本。

## 后端打包与 Windows 部署

### 打包

```bash
mvn clean package
java -jar target/Badminton-Flash-Backend-1.0.jar
```

打包产物是 fat jar。历史上有过"主清单属性缺失"问题（提交 a7dc881），现在 pom 里 `spring-boot-maven-plugin` 已显式配置 mainClass，不会再出现。

### Windows 部署

`scripts/deploy/deploy.ps1` 是完整部署脚本，目标机路径硬编码 `C:\Badminton-Flash-Backend\`：

1. git pull
2. 停 Windows 计划任务 `Badminton-Flash-Backend`
3. mvn clean → compile → package
4. 重启计划任务

发布流程：推到 git 远程，在服务器上执行 deploy.ps1。回滚方式：git reset 到旧提交后重新执行 deploy.ps1。

发布时机的约束：

- 抢票期间发布会中断服务（停任务到重启之间有窗口），且 Redis 库存、pending 键在发布窗口内不受影响，重启后恢复
- 定时任务全部是每分钟扫描，重启最多丢一分钟的调度，下次扫描自动补齐
- 不要在当天第一场预热前发布涉及 schema 的版本

## 前端构建

```bash
npm run build   # vue-tsc -b && vite build，产物在 dist/
npm run preview # 本地预览构建产物
```

生产部署方式仓库内没有脚本：README 提到生产跨域用网关反代。构建产物 `dist/` 交给任意静态服务器或 Nginx，并把 `/auth` 等六个前缀反代到后端 25001。

## 压测

### 准备 token

```powershell
# 批量注册 2000 个用户（默认 19120100~19122100）
scripts/batch-register.ps1
# 批量登录，把 {studentId, token} 合并写进 tokens.json
scripts/perf/fetch-tokens.ps1
```

`fetch-tokens.ps1` 有个已知问题：它判断 `$resp.data.token`，而后端 `data` 直接就是 token 字符串，脚本拿到的 token 会缺字段。用之前先确认 tokens.json 的内容格式正确。

### 跑 k6

```bash
k6 run scripts/perf/reserve-flow.js
```

默认参数：constant-arrival-rate 2000 请求/分钟、跑 1 分钟、预分配 200 VU、阈值 `http_req_failed<10%`、`p95<1200ms`。流程是：轮询用户 token → 提交预约 → 轮询结果（最多 20 次）→ 按比例分流：40% 支付、30% 取消、失败按 80% 概率重试最多 3 次。

可调环境变量见 `scripts/perf/README.md`，包括 `SUCCESS_PAY_RATIO`、`SUCCESS_CANCEL_RATIO`、`FAIL_RETRY_RATIO`、slot 轮转方式等。

### 压测注意

- 压测前必须预热并开闸，否则所有请求 UNGATED，测的是错误路径
- 单 slot 库存为 1，2000 个用户跑 1 分钟需要足够多的时间槽，否则大量 OUT_OF_STOCK 是预期行为
- 后端日志把 Reserve 相关类调成 ERROR 级，避免日志本身压垮吞吐
- 压测会真实产生预约单和支付单（mock 支付自动成功），跑完需要清理数据库或接受脏数据

## 数据库变更

没有迁移工具。`schema.sql` 是唯一建表来源，`spring.sql.init.mode=always` 每次启动执行。

变更表的正确做法：

1. schema.sql 里用 `CREATE TABLE IF NOT EXISTS` 或加迁移语句（注意幂等）
2. 数据回填写进 data.sql，用 `WHERE NOT EXISTS` 保护
3. 已有表加列：schema.sql 的 CREATE 不会作用于已存在的表，需要手工在库里执行 ALTER，再把结构同步进 schema.sql 供新环境使用

风险：schema.sql 与线上库结构漂移时，新环境建出来的表和线上不一致。目前没有工具检测这个问题。
