# 实现总览

本文说明后端实际的服务结构、调用链、配置来源、运行时依赖和当前实现边界。

本文不讨论各模块的业务细节，见 [[模块/预约/预约实现|预约]]、[[模块/支付/支付与退款|支付]]、[[模块/认证与用户/认证与用户|认证与用户]]、[[模块/管理端/管理功能|管理端]]。

源码范围：`src/main/java/shuhuai/badmintonflashbackend` 全部包。

## 包结构与实际调用链

### 包结构

| 包 | 内容 |
|---|---|
| `controller/` | 7 个控制器：Auth、User、Browse、Reserve、Pay、Admin、Base（BaseController 实际是全局异常处理，不是端点） |
| `service/` + `service/impl/` | 7 个业务接口，8 个实现（IReserveService 有两个实现） |
| `mapper/` | 7 个空接口 extends BaseMapper，无手写 SQL |
| `entity/` | 7 个实体，对应 7 张表 |
| `model/dto`、`model/vo` | 入参和出参对象 |
| `enm/` | 5 个枚举：角色、预约状态、支付状态、支付渠道、配置键 |
| `config/` + `beans/` | 7 个配置类、3 个 Bean 装配类 |
| `scheduler/` | 5 个定时/启动任务 |
| `mq/` | 消息发布回调、消费者、消息体 |
| `utils/` | Token 校验、请求上下文、Redis 封装、Jasypt、MD5、时区工具 |
| `response/` | 统一返回结构和错误码 |
| `excep/` | BaseException |

主类 `BadmintonFlashBackendApplication` 开启 `@EnableScheduling` 和 `@EnableEncryptableProperties`。

### 实际调用链

抢票：

```
ReserveController.reserve(ReserveDTO)
  → ReserveServiceImpl.reserve (redis 模式)
  → RateLimitServiceImpl.tryConsume（Bucket4j）
  → Redisson RSemaphore / RSet / RBucket
  → rabbitTemplate.convertAndSend（publisher confirm 同步等待）
  → ReserveConsumer.consume（异步）
  → IReservationMapper.insert
  → ReservePublishCallbackHandler.compensateByTraceId（失败时）
```

取消：

```
ReserveController.cancel / ReserveTimeoutScheduler
  → ReserveServiceImpl.cancel / cancelTimeoutPending
  → IReservationMapper 条件更新（status=PENDING_PAYMENT → CANCELLED）
  → IPayOrderMapper 批量关闭 PAYING 支付单
  → 回补 dedup + semaphore
```

配置更新：

```
AdminController.updateSystemConfig
  → AdminServiceImpl.updateConfig
  → 校验 → syncCourts → upsert config
  → TransactionSynchronization afterCommit 补偿（生成 slot / 重建 slot / 预热）
```

所有写操作以 Service 层为事务边界，取消和支付里的 CAS 靠 MyBatis-Plus 的条件更新完成，没有显式锁（除支付单创建和预热等分布式锁场景）。

## 配置来源

配置分四层，加载顺序：

1. `application.yml` + `application-dev.yml`（dev profile 默认启用）。仓库里只有 `.example` 文件，真实文件被 .gitignore 排除
2. 环境变量可覆盖 Spring 标准项
3. 敏感项用 Jasypt 加密（`jasypt.encryptor.password` 本身在 yml 里明文提供，`JasyptComputer` 用 PBEWithMD5AndDES）
4. `config` 表：业务配置（预热分钟数、支付超时、金额、球场数等），由管理员在页面上改，运行时可热更新

config 表的配置项清单和校验规则见 [[模块/管理端/管理功能|管理功能]]。

## 运行时依赖与并发

### 运行时依赖

| 依赖 | 用途 | 故障影响 |
|---|---|---|
| MySQL | 全部持久化 | 系统不可用 |
| Redis | 库存、闸门、去重、限流、分布式锁、补偿上下文 | 预约不可用（db 模式除外），调度器全部失效 |
| RabbitMQ | 预约落库消息 | 抢票请求同步等待 confirm 3 秒后超时返回，库存可能泄漏 |
| 本地时间 | 调度器判断预热/开闸窗口 | 时区错乱会导致提前开闸或永不预热。`TimeZoneInitializer` 启动时强制 `Asia/Shanghai` |

### 锁与并发

| 锁 | 类型 | 作用 |
|---|---|---|
| `bf:warmup:lock:{ymd}:{sessionId}` | Redisson RLock，lease 60s | 预热幂等 |
| `bf:slotgen:lock:{ymd}:{sessionId}` | RLock，lease 120s | 生成时间槽幂等 |
| `bf:pay:create:lock:{reservationId}` | RLock，lease 5s | 支付单创建幂等 |
| `bf:lock:court-bootstrap` | RLock，lease 180s | 启动球场对账互斥 |
| `bf:dedup:{slotId}` | RSet | 抢票用户去重 |
| `bf:sem:{slotId}` | RSemaphore(1) | 库存 |
| DB `active_slot_id` 唯一约束 | 数据库 | 防超卖兜底 |

## 实现边界

- 单体单实例。调度器的幂等键和锁都基于 Redis，从机制上支持多实例，但从未在多实例下运行过
- 生产部署是 Windows 计划任务方式（`scripts/deploy/deploy.ps1`），单机运行，无容器、无反向代理配置
- `RedisConnector`、`RedisBean` 里的 RedisTemplate 系列 Bean 和 `@EnableCaching` 是通用基础设施，业务主链路没有使用
- 日志只到控制台，无文件归档、无日志框架扩展。`BaseController` 做智能日志路由：按异常栈定位业务类 logger，前缀为请求 URL
- 无监控指标暴露（无 actuator、无 Micrometer 业务指标），压测靠 k6 自定义指标
- `src/test/java` 目录为空，无 JUnit 测试
