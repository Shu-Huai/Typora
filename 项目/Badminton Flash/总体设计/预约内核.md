# 预约内核

本文从设计角度说明预约内核的三个原则、请求处理流程和补偿闭环。

本文不讨论定时任务如何预热库存，见 [[模块/预约/库存与预热|库存与预热]]。不讨论代码细节，见 [[模块/预约/预约实现|预约实现]]。

源码范围：

- `service/impl/ReserveServiceImpl.java`（redis 模式，默认）
- `service/impl/ReserveServiceDbImpl.java`（db 模式）
- `mq/ReserveConsumer.java`、`mq/ReserveDlqConsumer.java`、`mq/ReservePublishCallbackHandler.java`
- `controller/ReserveController.java`

## 设计目标

预约内核要同时满足三件事：

1. 一个时间槽只有一个人能约到（不超卖，硬约束）
2. 抢票请求在内存级完成，不碰数据库（快）
3. 任何一步失败后库存能回补，不留死库存（最终一致）

三个目标有冲突：要快就不能同步写库，不写库就存在"扣了库存但库没记录"的中间态，中间态需要补偿。整个内核就是围绕这个矛盾设计的。

## 请求处理流程

一个预约请求按顺序经过 8 步：

```
1. 开闸校验    bf:gate:{sessionId} == "1"，否则 UNGATED
2. 归属校验    bf:slot:session:{slotId} == sessionId，防止拿 A 场次的 slot 抢 B 场次
3. 限流        Bucket4j，每用户每分钟 5 次，否则 TOO_MANY_REQUESTS
4. 去重        bf:dedup:{slotId} 集合 add(userId)，已存在则 DUP_REQ
5. 扣库存      bf:sem:{slotId} tryAcquire()，失败回滚第 4 步并返回 OUT_OF_STOCK
6. 写补偿上下文 bf:reserve:pending:{traceId} = "userId:slotId"，TTL 300 秒
7. 投递 MQ     reserve.direct → reserve.queue，消息体含 userId/slotId/sessionId/traceId
8. 等 confirm  同步等 publisher confirm，超时 3000ms
```

步骤 4 的 `add` 返回 false 表示重复：要么是这个用户重复请求，要么是信号量扣减后 MQ 发布失败的残留。两个语义都用 DUP_REQ 返回，前端统一提示"请勿重复提交"。

confirm 的三个分支：

- 发送异常或明确 NACK：立即按 traceId 补偿（回补去重和库存），返回 FAILED
- confirm 超时（3 秒内没等到）：不补偿，正常返回 traceId。此时消息可能已进队列，也可能丢失。补偿的话如果消息其实在队列里会造成双释放，所以宁可不补
- confirm ACK：正常返回

轮询 `GET /reserve/result/{traceId}` 的三态：查 `reservation` 表命中返回 SUCCESS，查 pending 键存在返回 PENDING，都没有返回 FAILED。

## 补偿闭环与双模式

### 补偿闭环

库存被扣之后有三个环节可能失败，各有一个补偿者：

| 失败点 | 补偿者 | 动作 |
|---|---|---|
| MQ 发布失败/被退回 | `ReservePublishCallbackHandler` | 按 traceId 删 pending 键，回补去重和信号量 |
| 消费失败（重试 3 次后） | `ReserveDlqConsumer`（死信队列） | 同上 |
| 用户放弃支付 | 取消接口 / 超时任务 | CAS 改状态后回补去重和信号量 |

补偿前先查 `reservation` 表：如果这个 slot 已经存在 PENDING_PAYMENT 或 CONFIRMED 的记录，说明落库其实成功了，跳过回补，防止误释放。pending 键的 TTL 是 300 秒，超过这个窗口后补偿上下文消失。

confirm 超时不补偿是个刻意留的口子：宁可让库存偶尔泄漏（一个 slot 一整天没人能抢），也不允许一票多卖。泄漏的影响面是单 slot，超卖的影响面是信任。

### 双模式与选择

`reserve.mode` 配置切换两种实现：

- `redis`（默认，`ReserveServiceImpl`）：上面描述的全套 Redis + MQ 路径
- `db`（`ReserveServiceDbImpl`）：不走 Redis 和 MQ，直接插 `reservation` 表，靠 `active_slot_id` 唯一约束拦截超卖，DuplicateKeyException 区分 DUP_REQ（同用户）和 OUT_OF_STOCK（同 slot 不同用户）

db 模式是 redis 模式的下限验证：没有 Redis 和 MQ 环境时系统仍能跑，但抢票请求直接落库，性能上限低。两个模式共享同一套状态机和取消逻辑。

选择 redis 模式作为默认的理由见 [[总体设计/系统架构|系统架构]] 的方案记录。

## 设计边界

- confirm 超时不补偿：极端情况下库存泄漏，无法自动发现，需要人工比对 Redis 库存和数据库记录
- pending 键只有 300 秒 TTL：发布后超过 5 分钟还没消费的消息，即使最后进了 DLQ，补偿也找不到上下文
- 消费端自动 ack（AUTO 模式）：重试 3 次后靠 `AmqpRejectAndDontRequeueException` 进 DLQ，重试期间同一条消息可能被重复消费，靠落库的 DuplicateKeyException 幂等兜底
- `ReserveResultStatus.PENDING` 和 `ReservationStatus.PENDING` 两个枚举值在主流程未使用，是预留
- `lua/book.lua` 是废弃方案，未删除
