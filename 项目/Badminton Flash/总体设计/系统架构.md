# 系统架构

本文说明系统的整体组成、组件职责、数据流向和关键技术选型，以及选型背后的方案比较。

本文不讨论单个模块的内部细节，那些在 [[模块/预约/预约实现|预约模块]]、[[模块/支付/支付与退款|支付模块]] 等模块文档里。不讨论部署操作，见 [[开发文档/构建发布与压测|构建发布与压测]]。

源码范围：

- 后端 `src/main/java/shuhuai/badmintonflashbackend`
- 后端 `src/main/resources`
- 前端 `src/`
- 前端 `vite.config.ts`

描述以源码为准。微信支付真实接入属于目标设计，见文末。

![](http://public.file.lvshuhuai.cn/images\badminton-flash-system-architecture.svg)

## 系统边界

系统由三个部分组成：前端 SPA、后端单体服务、三个基础设施（MySQL、Redis、RabbitMQ）。没有对象存储、没有搜索引擎、没有其他微服务。

外部依赖只有两个：

- 微信支付（目标设计）：当前代码不调用，全部 mock
- git 远程仓库：与运行时无关

前后端通过 HTTP + JSON 通信。前端开发时经 Vite 代理转发 `/auth`、`/user`、`/browse`、`/reserve`、`/pay`、`/admin` 六个前缀到后端。

## 组件清单与关键数据流

### 组件清单

| 组件 | 位置 | 职责 |
|---|---|---|
| Vue 3 SPA | 前端仓库 | 登录注册、浏览、抢票、订单、支付展示、管理面板 |
| Web 层（Controller） | `controller/` | 7 个控制器，统一返回 `Response<T>` |
| 鉴权拦截器 | `utils/TokenValidator.java` | 拦截所有请求，校验 JWT 与角色注解 |
| 业务层（Service） | `service/` | 预约内核、支付、用户、浏览、管理、限流 |
| 数据层（Mapper） | `mapper/` | MyBatis-Plus BaseMapper，无手写 SQL |
| 调度层 | `scheduler/` | 预热、开闸、生成时间槽、超时取消、球场对账 |
| MQ 层 | `mq/` + `beans/RabbitBean.java` | 预约消息投递、消费、死信补偿 |
| MySQL | 外部 | 7 张业务表，防超卖兜底约束 |
| Redis | 外部 | 库存信号量、去重、闸门、限流、分布式锁、补偿上下文 |
| RabbitMQ | 外部 | 预约落库消息、死信队列 |

所有 Redis key 以 `bf:` 为前缀，全部带 TTL。key 清单见 [[模块/预约/库存与预热|库存与预热]]。

### 抢票主链路

```
学生点预约
  → POST /reserve（同步返回 traceId）
  → 开闸校验 → slot 归属校验 → 限流 → 去重 → Redis 信号量扣库存
  → 写补偿上下文（bf:reserve:pending:{traceId}）
  → 投递 RabbitMQ（reserve.direct → reserve.queue）
  → 消费者落库 reservation(PENDING_PAYMENT)，清理补偿上下文
  → 学生轮询 GET /reserve/result/{traceId} 拿到结果
```

同步请求只做内存级操作（Redis），落库异步走 MQ。这是"快慢分层"：抢票请求不碰数据库，p95 控制在毫秒级。

### 支付与取消链路

```
支付成功（mock）→ pay_order PAYING→SUCCESS + reservation PENDING_PAYMENT→CONFIRMED
取消/超时      → reservation PENDING_PAYMENT→CANCELLED → 支付单 PAYING→CLOSED → 回补库存
退款           → pay_order SUCCESS→REFUNDED + reservation CONFIRMED→CANCELLED → 回补库存
```

完整流转见 [[总体设计/状态机|状态机]]。

### 预热链路

定时任务每分钟扫描，开抢前 N 分钟对每个时间槽建立信号量、去重集合、归属映射，开抢时刻把闸门从 0 翻到 1。细节见 [[总体实现/定时任务|定时任务]]。

## 技术选型与方案记录

### 为什么用 Redis 信号量而不是 Lua 脚本

现状是 Redisson `RSemaphore`（permits=1）+ `RSet` 去重。

探索过程：仓库里有一份 `src/main/resources/lua/book.lua`，是更早的方案，用 `get open → setnx userLock → pexpire → spop availSet → xadd stream` 完成"检查开闸、用户去重、弹出库存、发消息"的原子操作。这份脚本现在没有任何引用，是历史遗留。

Lua 方案的问题：把"扣库存"和"发消息"绑在一个原子步骤里，脚本执行中途失败时补偿困难，且把 Redis Stream 作为消息通道，消费端要做 Stream 游标管理，比 RabbitMQ 的消费模型重。信号量方案把"扣库存"拆成一个可逆操作（`tryAcquire` 失败或发布失败都能 `release` 回补），补偿简单，配合 MQ 的 publisher confirm 和死信队列能闭环。

最终方案保留 Lua 文件的代价：新开发者可能误以为 Lua 在起作用。文档里明确标注它已废弃。

### 为什么落库走 RabbitMQ 而不是同步写库

抢票接口只操作 Redis 并同步等 publisher confirm，落库由消费者完成。

直接同步写库的缺陷：数据库插入在秒杀峰值下成为瓶颈，而且一旦写库失败，Redis 已扣的库存要同步回补，请求链路变长。

MQ 方案的缺陷：发布成功但消费失败时，用户拿到的 traceId 查询结果是 PENDING，最终靠 DLQ 补偿。发布 confirm 超时的场景刻意不补偿（避免误释放），可能出现"Redis 扣了库存但没有任何预约记录"的短暂不一致，5 分钟 TTL 过后补偿上下文消失，该库存彻底丢失。这是已知边界，见 [[总体实现/失败恢复|失败恢复]]。

### 为什么防超卖需要三重保障

信号量是第一层（主路径），MQ 消费端的冲突处理是第二层（同用户同 slot 幂等吞掉，不同用户冲突补偿释放），数据库 `active_slot_id` 生成列唯一约束是第三层（任何绕过 Redis 的路径，包括 DB 模式，都会触发 DuplicateKeyException）。

没有这层数据库兜底时，Redis 数据丢失（比如误 flush）会造成超卖。生成列 `CASE WHEN status IN ('PENDING_PAYMENT','CONFIRMED') THEN slot_id END` 让取消的订单自动让位。

### 为什么支付全 mock

真实微信支付还没接入，但这不影响预约闭环，所以先用 mock 跑通状态机。mock 的边界很清晰：下单只返回假 prepayId，成功靠管理员调 mock-success 或配置 `wechat.pay.autoMockSuccess` 自动触发。wechatpay-java 依赖已在 pom 里，`PayServiceImpl` 注释里有真实调用示例（prepay、验签、解密），后续接线时替换 mock 分支即可。改造点见 [[模块/支付/支付与退款|支付与退款]]。

## 主要风险

- 单实例部署：调度器和库存都在单机上，多实例未验证（见 [[总体实现/实现总览|实现总览]]）
- Redis 是库存事实来源，Redis 故障期间预约整体不可用，且故障窗口内的库存准确性依赖重启后的人工对账
- publisher confirm 超时不补偿的场景会导致库存泄漏（见 [[总体实现/失败恢复|失败恢复]]）
- 密码 MD5 存储，数据库泄露后密码可暴力破解
- 前端管理员 tab 只靠 JWT role 渲染，接口层有二次校验，但前端没有 403 专项处理
