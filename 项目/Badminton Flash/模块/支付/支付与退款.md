# 支付与退款

本文说明支付模块的全部路径：创建支付单、支付成功、退款、查询，以及 mock 与真实支付的边界。

本文不讨论状态流转的完整图景，见 [[总体设计/状态机|状态机]]。不讨论超时取消的调度，见 [[总体实现/定时任务|定时任务]]。

源码范围：`controller/PayController.java`、`service/impl/PayServiceImpl.java`、`config/WechatPayConfig.java`、`entity/PayOrder.java`。

## 支付流程总览

```
创建支付单 POST /pay/wechat/{reservationId}
  → 分布式锁（bf:pay:create:lock:{reservationId}，lease 5s）
  → 校验预约归属 + 状态 PENDING_PAYMENT
  → 复用未过期支付单 / 惰性作废旧单
  → 生成 outTradeNo，插入 pay_order(PAYING)
  → 不调微信，返回 mock 凭据
  → autoMockSuccess=true 时 1.5 秒后自动支付成功

支付成功 POST /pay/wechat/mock-success/{outTradeNo}（ADMIN）
  → 幂等：已 SUCCESS 直接返回
  → CAS pay_order PAYING→SUCCESS
  → CAS reservation PENDING_PAYMENT→CONFIRMED
  → 第二步失败抛 FAILED

退款 POST /pay/refund/{reservationId}
  → 预约 CONFIRMED 且存在最近 SUCCESS 支付单
  → 模拟退款（日志，不调接口）
  → CAS pay_order SUCCESS→REFUNDED
  → CAS reservation CONFIRMED→CANCELLED
  → 回补 dedup + semaphore
```

## 创建支付单的细节

`createWechatPay` 的分支：

- 预约不属于当前用户：失败
- 预约不在 PENDING_PAYMENT：失败（CONFIRMED 会提示已支付，CANCELLED 提示已取消）
- 存在未过期 WECHAT+PAYING 支付单：直接复用返回，不重复创建
- 存在已过期 WECHAT+PAYING 支付单：旧单置 FAILED，创建新单

支付有效期：`expireTime = now + PAY_TIMEOUT_MINUTE`（默认 15 分钟），金额读 `PAY_AMOUNT`（默认 15.00，必须大于 0 否则失败）。

outTradeNo 生成：`"WX" + System.currentTimeMillis() + UUID 前 8 位`。

返回的 `WechatPayCreateVO` 字段（prepayId、nonceStr、timeStamp、packageValue、signType、paySign）是微信 JSAPI 拉起参数的结构，当前值为 mock 拼装（`mock_prepay_id_` 前缀等）。

## mock 与真实支付的边界

当前状态：

- 下单：不调用微信接口，只 log 打印 appId/mchId/notifyUrl
- 支付成功：靠管理员手动 mock-success，或 `wechat.pay.autoMockSuccess=true` 时下单 1.5 秒后 `CompletableFuture` 自动触发
- 退款：log 模拟，不调接口
- 没有微信回调端点

真实接入时：

- 下单改调 wechatpay-java 的 prepay（依赖已引入 0.2.17，`PayServiceImpl` 注释里有调用示例）
- 新增回调端点接收微信支付结果通知，验签、解密、幂等重放
- 回调端点必须加进鉴权白名单（微信服务器没有 token）
- 退款改调微信退款接口，退款结果异步回调处理

## 超时、幂等与已知边界

### 超时取消与支付的关系

超时任务扫描 `status=PENDING_PAYMENT AND create_time <= now-PAY_TIMEOUT_MINUTE` 的预约，取消时顺带把 PAYING 支付单关成 CLOSED。所以：

- 支付单的 expireTime 和预约的超时扫描共用同一个 `PAY_TIMEOUT_MINUTE`
- 支付单过期不等于预约取消：支付单只是 PAYING → FAILED（惰性），预约由定时任务独立取消
- 用户如果在最后 1 秒支付成功，但定时任务先取消了订单：mockWechatPaySuccess 里"预约仍为 PENDING_PAYMENT"的校验会失败，操作报 FAILED。支付单已 SUCCESS、订单已 CANCELLED，需要人工退款处理（当前 mock 环境无真实资金，问题不可见；接真实支付后这是必须处理的竞态）

### 幂等与并发

- 创建支付单：分布式锁 5s + 支付单复用判断，同一预约同一时刻只会有一笔 PAYING 单
- 支付成功：查单幂等（已 SUCCESS 直接返回），CAS 保证并发下只有一次生效
- 退款：预约 CANCELLED 直接返回成功（幂等），CAS 保证支付单只 REFUNDED 一次
- 取消订单关支付单：批量更新 PAYING→CLOSED，与支付成功的 CAS 互斥（CAS 条件不同，天然串行）

### 已知边界

- 支付成功与预约确认非同一事务，中途崩溃产生悬挂态，见 [[总体实现/失败恢复|失败恢复]]
- 支付金额存在 config 表，改 PAY_AMOUNT 后已创建未支付的支付单金额不变，新单用新价
- 一次预约理论上可创建多笔支付单（过期后重新创建），退款只处理最近一笔 SUCCESS 单
- 前端无支付拉起、无倒计时，见 [[前端/页面与流程|页面与流程]]
- 真实微信支付未接线
