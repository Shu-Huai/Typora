# 管理功能

本文说明管理端三大块：系统配置（含校验与联动补偿）、场次管理、用户管理。

本文不讨论调度器如何消费配置，见 [[总体实现/定时任务|定时任务]]。不讨论权限拦截，见 [[总体设计/权限边界|权限边界]]。

源码范围：`controller/AdminController.java`、`service/impl/AdminServiceImpl.java`、`model/dto/ConfigDTO.java`、`enm/ConfigKey.java`。

## 系统配置

6 个配置项（config 表），含义见 [[开发文档/配置说明|配置说明]]。

修改入口两个：`PATCH /admin/system`（批量）和 `PATCH /admin/system/{configKey}`（单值，text/plain body）。

`updateConfig` 的完整流程：

1. 解析候选配置，逐项校验
2. 校验所有场次的时间关系
3. 校验球场配置（模板含 %d、名字唯一）
4. 球场数量变化时检查变更窗口
5. syncCourts（增删改球场）
6. upsert 配置
7. 注册事务 afterCommit 补偿

### 时间约束

所有场次必须满足：

```
generateTime <= warmupTime <= flashTime <= beginTime < endTime
slotInterval > 0 且整除 (endTime - beginTime)
warmupMinutes <= flashTime 的分钟值（预热不跨午夜）
```

违反任意一条整个更新失败。

### 变更窗口

COURT_COUNT 的修改只允许在 `00:00 ≤ now < 当天第一场预热开始` 窗口内。超出抛 COURT_COUNT_UPDATE_WINDOW_CLOSED。理由：预热开始后球场增减会让"已预热 slot"和"实际球场"脱节，抢票中段改球场数量会造成库存混乱。

### afterCommit 补偿

| 变更的配置 | 补偿 |
|---|---|
| GENERATE_TIME_SLOT_TIME | 全部场次重新生成当天时间槽 |
| COURT_COUNT | 重建当天全部时间槽 + 清理相关 Redis key |
| COURT_NAME_FORMAT | 球场重命名 |
| WARMUP_MINUTE | 对已进入预热窗口的场次立即预热 |

补偿在事务提交后执行，配置已生效才动手，避免回滚后补偿了不存在的配置。

## 场次管理

| 操作 | 行为 |
|---|---|
| POST /admin/session | 校验（时间格式、间隔整除、flashTime 早于 beginTime），插入，联动生成当天时间槽 |
| PATCH /admin/session/{id} | 空字段回填旧值，改完先删当天旧槽再按新参数生成 |
| DELETE /admin/session/{id} | 删当天时间槽、清 Redis 相关 key、逻辑删场次 |

行内动作（定时任务的三个手动入口）：

- warmup：生成槽 + 初始化 Redis 库存/去重/闸门
- open：翻闸门为 1
- slot-gen：只生成当天时间槽

手动接口和定时任务共用同一套锁和 done 标记，可以放心重复调用。

## 用户管理与运维要点

### 用户管理

列表、详情、创建（指定角色）、修改、删除。Service 层的权限约束见 [[模块/认证与用户/认证与用户|认证与用户]]。

### 运维要点

- 当天第一场开抢前是配置变更的安全窗口，管理端页面没有提示这个窗口，改了被拒要查 COURT_COUNT_UPDATE_WINDOW_CLOSED 的时间
- 预热前改 WARMUP_MINUTE 无效（还没进窗口）；预热窗口内改会触发立即预热
- 删除场次是敏感操作：进行中的 PENDING_PAYMENT 订单不随之删除，但它们的 slot 被物理删除，取消释放库存时 Redis key 可能已不存在
- 配置 upsert 用 config_key 匹配，config 表没有唯一键，靠代码保证单值

### 已知边界

- 前端管理面板不展示变更窗口和校验规则，用户只能靠接口报错猜测原因
- 场次管理没有复制功能，相似场次要手工逐个建
- 系统配置没有操作审计：谁在什么时间改了什么值，没有记录（config 表只有 create/update 时间，没有操作者）
