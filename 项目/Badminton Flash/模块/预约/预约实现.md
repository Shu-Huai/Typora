# 预约实现

本文从代码角度说明抢票的完整调用链：Controller 到 Service 到 Redis/MQ/数据库，以及 db 模式的实现。

本文不讨论预热和库存的建立，见 [[模块/预约/库存与预热|库存与预热]]。设计层面的取舍见 [[总体设计/预约内核|预约内核]]。

源码范围：`controller/ReserveController.java`、`service/impl/ReserveServiceImpl.java`、`service/impl/ReserveServiceDbImpl.java`、`mq/` 包全部类。

## Redis 模式的 reserve 调用链

`ReserveServiceImpl.reserve(userId, slotId, sessionId)`，按代码顺序：

```java
// 1. 开闸
RBucket gate = redisson.getBucket(RedisKeys.gate(sessionId));
if (!"1".equals(gate.get())) throw UNGATED;

// 2. slot 归属
RBucket<Object> owner = redisson.getBucket(RedisKeys.slotSession(slotId));
if (owner.get() == null) throw UNGATED;          // slot 未预热视为未开闸
if (!sessionId.equals(owner.get())) throw PARAM_ERROR;

// 3. 限流
if (!rateLimitService.tryConsume(userId.toString(), 5, Duration.ofMinutes(1)))
    throw TOO_MANY_REQUESTS;

// 4. 去重
RSet dedup = redisson.getSet(RedisKeys.dedup(slotId));
if (!dedup.add(userId)) throw DUP_REQ;

// 5. 扣库存
RSemaphore sem = redisson.getSemaphore(RedisKeys.semaphore(slotId));
if (!sem.tryAcquire()) { dedup.remove(userId); throw OUT_OF_STOCK; }

// 6. 补偿上下文
redisson.getBucket(RedisKeys.reservePending(traceId))
        .set(userId + ":" + slotId, PENDING_TTL_SECONDS, SECONDS);

// 7. 投递 MQ（messageId=traceId）
rabbitTemplate.convertAndSend("reserve.direct", "reserve", msg,
    new CorrelationData(traceId));
// 8. 同步等 confirm，超时 PUBLISH_CONFIRM_TIMEOUT_MS=3000
```

发布阶段失败的两个分支：异常或 NACK → `compensateByTraceId(traceId, "sync-send-exception")` 然后抛 FAILED；超时 → 不补偿，正常返回 traceId。

步骤 2 有个隐含语义：slot 不存在于 Redis（没预热）直接当 UNGATED 处理。所以"预热完成"是抢票的前置条件，slot 表里有数据但 Redis 没有，也抢不了。

## 结果查询与消费落库

### 结果查询

`getReserveResult(userId, traceId)` 三步：

1. `reservation` 表按 traceId 查（trace_id 唯一），命中且 userId 匹配 → SUCCESS + reservationId + 当前状态
2. `bf:reserve:pending:{traceId}` 存在且 userId 匹配 → PENDING
3. 否则 FAILED

用户只能查自己的 traceId，查到别人的返回 FAILED（不区分"不是你的"和"不存在"）。

### 消费落库

`ReserveConsumer` 监听 `reserve.queue`，自动 ack，容器配置 `defaultRequeueRejected=false` + stateless 重试拦截器（3 次，1s 起、×2、上限 5s）：

1. 插入 reservation（PENDING_PAYMENT，带 traceId）
2. 成功 → clearPending(traceId)（删补偿键）
3. DuplicateKeyException 分两种：
   - 同用户同 slot（active_slot_id 唯一键冲突）：幂等吞掉，clearPending
   - 不同用户同 slot：有 pending 就补偿回补，让库存回给真正该得的人
4. 其他异常：抛出 → 重试 → 进 DLQ

`ReserveDlqConsumer` 监听 `reserve.dlq`，从消息体/messageId/header 三个位置取 traceId，`compensateByTraceId(traceId, "dlq-final-fail")`。

MQ 拓扑定义在 `RabbitBean` 和 `MqNames`：交换机 `reserve.direct`，队列 `reserve.queue`（死信指向 `reserve.dlx`/`reserve.dlq`），路由键 `reserve`。

## 取消与 db 模式

### 取消

`cancel(userId, reservationId)` 只允许本人取消：

1. 事务内 CAS：`UPDATE reservation SET status='CANCELLED' WHERE id=? AND status='PENDING_PAYMENT'`，0 行抛失败
2. `closePayingOrders`：该预约下所有 PAYING 支付单 → CLOSED
3. 事务外回补：dedup.remove + sem.release

`cancelTimeoutPending(reservationId)` 是超时任务用的变体，不带 userId 校验，逻辑相同。

### db 模式

`ReserveServiceDbImpl`（`reserve.mode=db` 时生效）不碰 Redis 和 MQ：

```java
// 查 gate 换成查 Redis？不，db 模式直接查 flash_session 时间判断开闸
// 直接插入 reservation(PENDING_PAYMENT, traceId)
try { insert; } catch (DuplicateKeyException e) {
    // 查现有记录：同用户 → DUP_REQ；不同用户 → OUT_OF_STOCK
}
```

db 模式没有限流和去重（依赖唯一约束天然去重），开闸判断改为查询场次的 flash_time 是否已到。getReserveResult 直接查表。cancel 逻辑相同（CAS + 关支付单，无库存回补，因为没扣过）。

两种模式的差异汇总：

| | redis 模式 | db 模式 |
|---|---|---|
| 限流 | Bucket4j 每分钟 5 次 | 无 |
| 去重 | Redis Set | 唯一约束 |
| 库存 | Redis 信号量 | active_slot_id 唯一约束 |
| 落库 | MQ 异步 | 同步 |
| 性能上限 | 高（内存操作） | 低（每次写库） |
| 依赖 | Redis + RabbitMQ | 仅 MySQL |

## 实现边界

- `ReserveResultStatus.PENDING` 查询态与 `ReservationStatus.PENDING_PAYMENT` 持久态名字相近，联调时容易混淆。前者是"还没落库"，后者是"落库了但没付钱"
- confirm 超时窗口 3 秒固定，MQ 抖动时会有较多"返回成功但结果查不到"的请求，前端轮询 FAILED 后用户会重新抢，可能引发 DUP_REQ 困惑
- db 模式的开闸判断按 flash_time 字符串比较分钟，与 redis 模式闸门语义有细微差别（手动提前开闸在 db 模式下无意义）
