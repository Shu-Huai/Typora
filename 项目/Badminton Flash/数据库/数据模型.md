# 数据模型

本文说明 7 张表的结构、业务键、约束、删除策略，以及数据库与 Redis 的事实边界。

本文不讨论状态的流转规则，见 [[总体设计/状态机|状态机]]。不讨论 ORM 映射细节，见 [[后端/后端分层|后端分层]]。

源码范围：`src/main/resources/schema.sql`、`data.sql`；`entity/` 包。

## 表清单

| 表 | 实体 | 业务意义 |
|---|---|---|
| user_account | UserAccount | 用户与管理员账号 |
| flash_session | FlashSession | 抢票场次（开抢时间、场馆时间段、槽间隔） |
| court | Court | 球场 |
| time_slot | TimeSlot | 具体可抢的时间槽（场次 × 球场 × 时间段） |
| reservation | Reservation | 预约单 |
| pay_order | PayOrder | 支付单 |
| config | Config | 系统业务配置 |

所有表都有 `id` 自增主键、`create_time`、`update_time`（数据库默认 CURRENT_TIMESTAMP / ON UPDATE）、`is_active`（逻辑删除，`@TableLogic(value="1", delval="0")`）。

## 关键约束

### 唯一约束与业务键

| 表 | 唯一键 | 用途 |
|---|---|---|
| user_account | student_id | 学号登录，防重复注册 |
| time_slot | (slot_date, start_time, end_time, court_id, session_id) | 生成时间槽幂等，重复生成不会产生重复槽 |
| reservation | trace_id | 一次抢票请求的全局标识，轮询靠它 |
| reservation | active_slot_id | 防超卖兜底，见下 |
| pay_order | out_trade_no | 支付单号，微信侧对账标识 |

### active_slot_id 生成列

`reservation.active_slot_id` 是数据库生成列：

```sql
generated always as (
  case when status in ('PENDING_PAYMENT','CONFIRMED') then slot_id end
) stored
```

配合唯一约束，效果是：同一个 slot 最多存在一条"有效"预约。订单取消后 status 变 CANCELLED，生成列变 NULL，唯一约束让位，库存回补后别人能抢。

这是数据库层面的最终防线。即使 Redis 和 MQ 全部绕过（db 模式就是这样），超卖也会被 DuplicateKeyException 拦下。代码里 `@TableField(insertStrategy=NEVER, updateStrategy=NEVER)` 保证 MyBatis-Plus 不会碰这个列。

### 外键

`time_slot.court_id → court.id`、`time_slot.session_id → flash_session.id`、`reservation.user_id → user_account.id`、`reservation.slot_id → time_slot.id`、`pay_order.reservation_id → reservation.id`。

全部没有 ON DELETE 行为。删除侧全部走逻辑删除，不触发外键。物理删数据时要注意先删子表。

### 状态字段

`reservation.status`、`pay_order.status`、`user_account.user_role` 都是 varchar 存枚举 name，没有 CHECK 约束。合法性靠代码保证。

## 枚举、删除与事务

### 枚举存储

MyBatis-Plus 默认按枚举 `name()` 存储：

- ReservationStatus：PENDING_PAYMENT / CONFIRMED / CANCELLED / PENDING
- PayOrderStatus：PAYING / SUCCESS / REFUNDED / CLOSED / FAILED
- UserRole：USER / ADMIN
- PayChannel：WECHAT
- ConfigKey：WARMUP_MINUTE 等 6 项

### 删除策略

全部逻辑删除，`is_active` 置 0：

- 用户销户、管理员删用户：数据保留，登录校验只查有效记录
- 删球场、删场次：保留历史数据
- 删场次时联动清理当天时间槽（物理删 time_slot）和 Redis key

没有归档、没有硬删入口。长期运行数据只增不减。

### 事务边界

- 抢票落库：消费者单条 insert，无事务需求（单条语句）
- 取消：状态 CAS + 关支付单 + Redis 回补，CAS 和关单在事务内，Redis 回补在事务外（Redis 无事务）
- 支付成功：支付单 CAS + 预约 CAS，非同一事务，顺序保证兜底，见 [[总体实现/失败恢复|失败恢复]]
- 配置更新：校验 + 球场同步 + upsert 在事务内，联动补偿注册 `afterCommit`

## 事实边界与已知边界

### 与 Redis 的事实边界

| 事实 | 所在 |
|---|---|
| 库存（该 slot 还能抢吗） | Redis `bf:sem:{slotId}`，数据库不存库存 |
| 抢票去重 | Redis `bf:dedup:{slotId}` |
| 开闸状态 | Redis `bf:gate:{sessionId}` |
| 预约单、支付单、用户、场次、球场、时间槽 | MySQL |
| 抢票补偿上下文 | Redis `bf:reserve:pending:{traceId}`（TTL 300s） |

一句话：MySQL 是账本，Redis 是账本前面的柜台。柜台倒了一切暂停，账本不倒数据就不丢。Redis 全部 key 带 TTL，丢失可重建（重新预热）。

### 已知边界

- 无数据迁移工具，schema 演进靠手工，见 [[开发文档/构建发布与压测|构建发布与压测]]
- 无索引优化：除唯一约束自带的索引外没有额外索引，browse 查询按需全表扫。当前数据量下无感，量大了再补
- 状态字段无 CHECK 约束
- 数据库和 Redis 之间没有对账任务，库存泄漏只能人工发现
