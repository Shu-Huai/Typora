# 定时任务

本文说明全部后台任务的触发时机、执行内容、幂等机制和配置联动。

本文不讨论预热写入的 Redis key 细节，见 [[模块/预约/库存与预热|库存与预热]]。不讨论超时取消的状态流转，见 [[总体设计/状态机|状态机]]。

源码范围：

- `scheduler/WarmupScheduler.java`
- `scheduler/DailySlotGenerateScheduler.java`
- `scheduler/ReserveTimeoutScheduler.java`
- `scheduler/CourtBootstrapScheduler.java`

## 任务清单与幂等机制

所有 `@Scheduled` 任务都是 `cron = "0 * * * * ?"`（每分钟）加上 `zone = "${app.timezone}"`，业务逻辑内部再判断是否到了窗口。共 5 个任务：

| 任务 | 触发 | 逻辑 |
|---|---|---|
| 预热扫描 | 每分钟 | 查 `flashTime` 落在 `[当前分钟, 当前分钟 + WARMUP_MINUTE]` 的场次，逐个预热 |
| 自动开闸 | 每分钟 | 查 `flashTime <= now` 的场次：已开闸跳过，未预热先补预热，再置 `bf:gate:{sessionId} = "1"` |
| 每日生成时间槽 | 每分钟 | 当前时间 >= GENERATE_TIME_SLOT_TIME（默认 00:35:00）时，对所有场次生成当天时间槽 |
| 超时未支付取消 | 每分钟 | 扫 `status = PENDING_PAYMENT AND create_time <= now - PAY_TIMEOUT_MINUTE` 的预约，逐条取消 |
| 球场对账 | 启动一次（`@EventListener(ApplicationReadyEvent)`） | 按 config 表对账球场数量和命名 |

多实例（如果未来部署）和手动接口共用同一套幂等标记：

- 生成时间槽：done 标记 `bf:slotgen:done:{ymd}:{sessionId}` + 锁 `bf:slotgen:lock:{ymd}:{sessionId}`（lease 120s）。库层另有唯一键 `(slot_date, start_time, end_time, court_id, session_id)`，重复插入靠 DuplicateKeyException 吞掉
- 预热：slot 级 done 标记 `bf:warmup:done:{slotId}` + session 级 `bf:warmup:done:{ymd}:{sessionId}` + 锁 `bf:warmup:lock:{ymd}:{sessionId}`（lease 60s）
- 开闸：先检查 `bf:gate:{sessionId}` 是否已是 "1"，是则跳过
- 超时取消：CAS 条件更新（`status = PENDING_PAYMENT`），0 行即视为已被处理
- 球场对账：分布式锁 `bf:lock:court-bootstrap`（lease 180s）

手动接口（`POST /admin/warmup/{sessionId}`、`POST /admin/slot-gen/{sessionId}`）和定时任务走同一条 service 路径，天然幂等。

## 预热与开闸的时序

预热在开抢前 WARMUP_MINUTE 分钟启动，早于 flashTime。自动开闸任务看到时间到了才翻闸门。两者之间有一个"已预热未开闸"的窗口，此时闸门是 "0"。

手动开闸接口（`POST /admin/open/{sessionId}`）可以提前开闸，但前提是预热已完成。

生成时间槽默认在每天 00:35，晚于绝大多数场次的预热开始时间（默认早上开抢前 5 分钟预热），因此时间槽实际上在开抢前一天就已经生成。若某天场次配置在 00:35 之前开抢，预热会触发补生成（`warmupSession` 内部先 generateSlot）。

## 配置联动与任务边界

### 配置联动

config 表更新后（`PATCH /admin/system`），事务提交时按配置键做补偿，见 [[模块/管理端/管理功能|管理功能]]：

| 变更 | 补偿动作 |
|---|---|
| WARMUP_MINUTE | 对已进入预热窗口的场次立即预热 |
| GENERATE_TIME_SLOT_TIME | 对全部场次重新生成当天时间槽 |
| COURT_COUNT / COURT_NAME_FORMAT | 重建当天全部时间槽并清理相关 Redis key |

### 任务边界

- 每分钟扫描依赖 `flash_time` 与当前分钟的匹配，秒级精度不足：场次开抢时间只能精确到分钟，抢票提前量不可能小于 1 分钟
- 超时取消是逐条处理，没有分批。若某场次几千单同时超时，单分钟的处理时长会明显增加，后面的单会晚 1 分钟以上才被取消
- 预热跨午夜有约束：warmup 开始时刻不能早于当天 00:00，否则 TTL 计算和 done 标记会错位。配置校验里做了拦截（`warmupMinutes <= flashTime 分钟值`）
- 任务没有失败告警。预热失败、开闸失败只会记日志，没有人收到通知
