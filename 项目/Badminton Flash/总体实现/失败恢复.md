# 失败恢复

本文逐项说明系统在异常场景下的行为：用户看到什么、接口返回什么、数据怎么写、能否重试、谁负责兜底。

本文不讨论正常流程，见 [[总体设计/预约内核|预约内核]] 和各模块文档。不讨论限流规则本身，见 [[模块/预约/预约实现|预约实现]]。

## 异常矩阵

### 抢票请求阶段（同步）

| 场景 | 接口返回 | 数据写入 | 用户看到 | 可重试 |
|---|---|---|---|---|
| 未开闸 | UNGATED(4002) | 无 | "当前场次未开闸" | 开闸后可以 |
| slot 不属于该场次 | PARAM_ERROR(5010) | 无 | 参数错误 | 换正确的组合 |
| 限流超 5 次/分钟 | TOO_MANY_REQUESTS(4101) | 无 | 请求太频繁 | 1 分钟后可以 |
| 重复请求 | DUP_REQ(4003) | 无（set add 失败） | 请勿重复提交 | 若库存被占则无意义 |
| 库存为空 | OUT_OF_STOCK(4004) | 无（去重已回滚） | 已被抢空 | 等别人取消 |
| MQ 发送异常/NACK | FAILED(1001) | 库存和去重已回补 | 预约失败 | 可以直接重试 |
| MQ confirm 超时 | 正常返回 traceId | 库存已扣，pending 键 300s | 轮询显示 PENDING | 不推荐立即重试，见下 |

### 消费与落库阶段（异步）

| 场景 | 行为 | 兜底 |
|---|---|---|
| 消费抛异常 | 重试 3 次（1s 起、×2、上限 5s），仍失败进 DLQ | DLQ 消费者按 traceId 回补库存 |
| 同用户同 slot 重复落库 | DuplicateKeyException 命中 active_slot_id，幂等吞掉，清 pending | 无需处理 |
| 不同用户同 slot 冲突落库 | 回补库存并清 pending | DLQ 不会再来 |
| pending 键已过期（300s）后才进 DLQ | 补偿拿不到上下文，跳过 | 库存泄漏，见边界 |

### 支付阶段

| 场景 | 行为 | 用户看到 |
|---|---|---|
| 创建支付单时预约已被取消 | 校验失败，FAILED | 提示失败，去订单页看状态 |
| 已有未过期支付单 | 直接复用，不重复创建 | 返回同一笔支付单 |
| 已有过期支付单 | 旧单置 FAILED，创建新单 | 得到新支付单 |
| mock 支付成功时预约已不在 PENDING_PAYMENT | 幂等跳过或失败 | 状态不一致会暴露出来 |
| 支付成功但预约确认失败 | 整个操作 FAILED，支付单已 SUCCESS | 需要人工核对 |

### 取消与退款

| 场景 | 行为 | 幂等性 |
|---|---|---|
| 重复取消 | CAS 0 行，静默成功 | 幂等 |
| 取消时库存回补失败 | 回补在取消之后执行，异常会中断整个取消 | 待边界说明 |
| 退款时预约已取消 | 直接返回成功 | 幂等 |
| 退款时支付单不是 SUCCESS | 校验失败 | 不可重试，需查数据 |

## 补偿实现

补偿的核心是 `ReservePublishCallbackHandler` 和 `ReserveDlqConsumer` 共用的 `compensateByTraceId(traceId, reason)`：

1. `getAndDelete` 拿到 pending 键的值（"userId:slotId"），拿不到说明超时或已补偿，直接结束
2. 查 `reservation` 表该 slot 是否有 PENDING_PAYMENT/CONFIRMED 记录。有：说明落库成功过，跳过回补（防双释放）
3. 没有：`dedup.remove(userId)` + `sem.release()`

触发路径有三条：RabbitTemplate confirm 回调（NACK）、returns 回调（mandatory 消息退回）、DLQ 消费。取消和超时取消则走另一条路径：CAS 改状态成功后直接回补。

## 服务重启与已知边界

### 服务重启后的恢复

- 库存、闸门、预热标记在 Redis，TTL 到当天结束。Redis 没重启则预约继续可用
- RabbitMQ 里未消费的消息在服务重启后继续消费，落库幂等
- pending 键在 Redis。若 Redis 也重启，pending 丢失，此时若 MQ 里还有消息，DLQ 补偿拿不到上下文，库存泄漏
- 数据库里的 PENDING_PAYMENT 超时单由定时任务接手，每分钟扫描，重启不丢
- 球场对账在每次启动时自动跑（加分布式锁），配置和球场不一致会被修复或告警

### 已知边界

- confirm 超时不补偿：这是防双释放的取舍。代价是极端情况下库存泄漏，泄漏的 slot 一整天不可抢，无自动发现机制
- pending TTL 300s：超过 5 分钟才失败的消费，补偿拿不到上下文。库存泄漏同上
- 取消接口里"CAS 成功后回补失败"没有重试机制：库存回补（Redis 操作）失败会让预约单已取消但库存没回来
- 支付成功与预约确认非事务：中途崩溃出现悬挂状态，见 [[总体设计/状态机|状态机]] 边界
- Redis 掉线期间 `RSemaphore` 操作抛异常会被 BaseController 转成 DB_ERROR 或 ERROR，具体行为与 Redisson 版本和网络有关，源码无法确定

## 人工核对方法

出现"库存疑似泄漏"时（某 slot 一整天无人能抢但库里无订单）：

1. `GET /browse/slot/{slotId}` 看时间槽是否存在
2. 查 `reservation` 表该 slot_id 的所有记录及状态
3. 用 redis-cli（注意 database 2）查看 `bf:sem:{slotId}`、`bf:dedup:{slotId}` 的实际内容
4. 核对无误后人工回补库存（删 key 或调信号量接口），最好走一次 warmup 重建
