# 开发验证

这份文档规定 Media Center 修改代码时需要留下什么证据。它把“能编译”“单测通过”“接口可用”“浏览器可播放”分开记录，避免用低层通过结果替代高层验收。

## 代码定位

### 模块入口

先根据需求进入对应模块目录，再沿 Controller、Service、Mapper 和配置反向追踪。跨模块能力优先查看 `总体设计` 和 `总体实现`，不要在多个模块复制一套互相矛盾的规则。

### 配置来源

修改前确认配置来自本地 yml、配置中心还是环境变量。文件根目录、缓存根目录、Redis key 前缀、MQ exchange 和 FFmpeg 参数都必须能追溯到实际配置，文档中的示例值不能当成生产值。

### 变更边界

一个修复应能回答三个问题：哪个输入触发问题、哪一层产生错误、哪条最小改动消除错误。不要为了掩盖异常加入未验证的自动回退；失败应保留错误码、日志和原始上下文。

### 文档同步

实现改变实体、接口、配置、Redis key 或文件布局时，同步更新模块实现文档和对应专项文档。若只是重构而行为不变，记录验证结果即可，不要重新发明业务规则。

## 本地运行

### 后端启动

先启动基础设施和 Gateway，再启动被测业务模块。启动日志必须确认端口、配置中心、数据库、Redis、RabbitMQ 和关键外部依赖均已连接；“进程存在”不等于服务可用。

### 前端联调

浏览器测试先记录实际 URL、登录状态、请求方法和响应码。媒体问题要保存 Network 中的 m3u8、init.mp4、m4s、字幕请求以及失败请求的响应体，不能只依据播放器控件显示。

### 文件夹准备

测试 NAS 文件前确认路径可读、文件未被复制程序占用、媒体信息可由 ffprobe 读取。临时输出放在专用缓存目录，避免测试清理器误删源文件。

### 进程清理

结束联调后检查 Java、FFmpeg、Node 进程和监听端口。后台转码、watcher 和消息消费者如果继续运行，会污染下一次测试的缓存和数据库结果。

## 交付证据

### 浏览器证据

播放类改动记录首次播放、暂停继续、seek、切换画质、刷新页面、恢复进度和字幕的 Network 请求与响应；刷新类改动记录全量刷新、重复点击、两个实例、文件新增、文件删除、文件移动和服务重启的状态变化。

### 证据格式

```text
场景：Movie SOURCE 从 00:05:30 seek 到 00:18:10
接口：POST /movie/playback/prepare -> 200
媒体：master.m3u8 200，init.mp4 200，m4s 200
结果：currentTime 单调，无重复，无跳跃，字幕时间轴一致
```

## 提交标准

### 改动检查

- `git diff --check` 无空白错误；
- 新增文档链接全部可解析；
- H2、H3 层级满足项目约定；
- 生成文件、个人配置和无关模块没有混入提交。

### 变更说明

提交说明要写根因、改动文件、已观察到的运行结果和仍未覆盖的真实环境。浏览器手工通过只能说明当前环境可用，不能替代多实例、NAS 权限和外部服务验证。

### 发布前检查

```powershell
git status --short
git diff --check
```

确认工作区只包含本次任务，才进行提交、合并或推送。
