# 剧集刷新数据库

本文说明 `Media-Center-Series` 如何扫描 NAS 剧集并建立 Series、Season、Episode File 的数据库身份。整体刷新规则见 [[总体设计/刷新数据库设计|刷新数据库设计]]，播放链路见 [[模块文档/Series/模块设计|剧集模块设计]] 和 [[模块文档/Series/模块实现|剧集实现]]。

## 刷新入口

### 管理请求

`AdminServiceImpl` 接收管理刷新请求。请求先经过 `SeriesRefreshRequestManager` 的 admission，再发布 `SeriesRefreshCommandMessage`；调用方获得任务状态，不等待整个 NAS 遍历。

### 监听选主

`SeriesFolderWatcher` 只由 `SeriesLeaderCoordinator` 选出的 leader 注册。leader 锁失效或实例重启后，新的 leader 必须重新注册监听并进行一次校准扫描。非 leader 不应各自消费文件事件，否则同一新增文件会被多个进程解析。

### 消息生命周期

`SeriesRefreshCommandListener` 执行刷新，`SeriesRefreshStatusListener` 广播状态。重复 command 可能来自 ack 重试，必须由任务键、路径唯一约束和 upsert 共同消化；WebSocket future 只负责通知发起实例，不能当作持久任务记录。

### 配置读取

扫描根目录来自 `seriesBaseLocate`，季集模板来自应用配置。刷新开始时固定本轮配置快照，避免用户在扫描中间修改模板导致同一批文件使用两套解析规则。

## 扫描入库

### 模板解析

`AdminServiceImpl.PatternParser` 读取目录和文件名，生成 `SeasonMatch`、`EpisodeMatch` 等中间结果。解析失败的文件进入诊断结果，不应按标题猜测集号。

```text
series root
  -> category / title
  -> season match
  -> episode match
  -> canonical episode file path
  -> media metadata
```

### 身份顺序

先按 `category + title + season_no` upsert Series，再按 `series_id + episode_no` upsert SeriesEpisode，最后按规范化 local path upsert SeriesEpisodeFile。播放、字幕、segment plan 和用户进度都必须指向 episode file，不能只用剧集标题。

### 关系同步

Series source、genre、person 和 info 在主实体提交后同步。一个文件识别出新来源时不能覆盖其他来源；迟到的外部元数据响应需要按 source/version 判断，旧响应不得覆盖新值。

### 事务边界

季、集、文件身份和同一文件的关系写入应在可控事务内完成。ffprobe、Spider、封面下载和摘要生成属于事务外派生任务，提交成功后再投递，失败时保留可重试状态。

## 删除恢复

### 文件集合

全量扫描结束后比较本轮发现的规范化路径与数据库记录。缺失文件先进入待确认状态，避开 NAS 短暂掉线造成全季误删；连续确认后再删除或软删除 EpisodeFile，并按策略处理空 Season、空 Series。

### 路径移动

移动文件按旧路径删除、新路径创建处理。若业务需要保留观看进度，必须通过 fingerprint 或人工映射迁移 progress；不能因为标题和集号相同就把新路径强行视为旧文件。

### 派生缓存

EpisodeFile fingerprint 改变后，旧的 SeriesSegmentPlan、fMP4 global 分片、字幕和 session 均视为失效。缓存清理必须限定在 Series 缓存根目录，不能因为集数删除源 MKV。字幕 URL 至少包含 episode file 身份，避免集间串字幕。

### 异常处理

模板不匹配、媒体探测失败、权限不足和外部服务超时要分别记录原因。失败文件不得从数据库静默消失；下一轮扫描成功时应可恢复。全量任务部分失败时状态应能表达失败数量和路径清单，而不是只返回一个笼统成功。

## 验证证据

### 运行检查

`SeriesSegmentPlan*` 只说明播放计划身份隔离，运行检查仍需确认刷新写入的 episodeFileId、路径和 fingerprint 正确。

### 扫描场景

准备两季、同名集、缺集、重命名、移动、重复事件、不可读文件和模板不匹配文件。检查 Series、Episode、EpisodeFile 数量及唯一键，确认第 1 集和第 2 集不会共用 local path、字幕或播放计划。

### 多实例场景

两实例同时点击刷新，只有一个 command 执行；停止 leader 后由新 leader 接管 watcher；重复投递 command 后数据库不重复。运行记录同时保存 Redis leader key、MQ messageId、任务状态和数据库结果。

### 运行回归

刷新完成后再从某集的中间位置 prepare 播放，检查返回的 episodeFileId、duration、字幕 URL 和 segment-plan 指纹。Movie 的刷新通过不能替代 Series 的季集解析验证。
