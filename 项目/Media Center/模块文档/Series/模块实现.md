# 剧集实现

本文对应 `Media-Center-Series` 的当前源码。业务规则见 [[模块文档/Series/需求分析|剧集模块]]，播放协议与 Movie 保持同一套 fMP4/HLS 约定，但剧集多了一层 series、season、episode、episode file 的身份解析。本文只写实现链路和已验证边界。

## 请求入口

### 剧集查询

Series 查询由 `SeriesController` 进入 `SeriesServiceImpl`，使用 `SeriesMapper`、`SeriesEpisodeMapper`、`SeriesEpisodeFileMapper` 及 genre/person/source 关系 mapper 组装列表、详情、季和集。剧集标题不能直接作为播放文件身份，播放入口最终需要 episodeFileId。

```text
GET /series/**
  → SeriesController
  → SeriesServiceImpl
  → Series / SeriesEpisode / SeriesEpisodeFile mappers
  → 详情或选集 VO
```

数据库唯一身份由 `category + title + season_no`、`series_id + episode_no` 和 `local_file_path` 等约束共同形成。扫描时必须先解析季号、集号和文件路径，再执行 upsert，不能因为两个文件标题相同就复用错误分集。

### 播放准备

`PlaybackController` 接收 `PreparePlaybackDTO`，调用 `PlaybackServiceImpl`。参数核心是 episodeFileId、variant、音轨和起始时间；返回 `PreparePlaybackVO`，包含 sessionId、master.m3u8、duration、resumePosition 和字幕轨道。

```text
POST /series/playback/prepare
  → PlaybackController
  → PlaybackServiceImpl
  → SeriesEpisodeFile
  → Redis session / active session
  → initial fMP4 window
  → PreparePlaybackVO
```

Series 的播放 session key 必须包含 episode file 身份，不能只按 seriesId，否则同一剧集切换集数时会复用错误的时长、分片计划或字幕。

### 媒体请求

`HlsController` 返回 master、variant、init.mp4、m4s 和字幕内容；准备状态不足时区分 410、503 和 404。`PlaybackController` 的 heartbeat/close/replace 更新 Redis session，并将进度写入公共 `user_progress`，媒体类型固定为 SERIES，mediaId 采用产品定义的剧集/集文件身份，不能和 Movie 共用错误 ID。

前端切集时应先关闭旧 session，再准备新 episode file；清晰度切换仍可在同一 episode session 中重新生成清单，但不能把旧集的 segment plan 留在新 session 里。

### 管理入口

`AdminController` 进入 `AdminServiceImpl`，负责配置、全量刷新和文件变更。刷新命令经 `SeriesRefreshRabbitConfig` 发布，`SeriesLeaderCoordinator` 竞争 `series:watcher:leader:lock`，leader 启动 watcher 和 command listener，状态由 `SeriesRefreshStatusListener` 广播给各实例。

## 核心服务

### 季集扫描

全量扫描读取 `seriesBaseLocate`，由 `AdminServiceImpl.PatternParser` 按配置模板解析目录和文件名，先建立 Series，再建立 SeriesEpisode，再关联 SeriesEpisodeFile。测试类 `SeriesPatternParserTest` 直接验证季号、集号和可选 variant。外部来源绑定、genre、person 和 info 关系在相应 mapper 中写入。

新增文件事件调用 `handleFileCreate`，删除事件按规范化相对路径处理。Series 的唯一约束是重要的最终防线：

```text
series(category, title, season_no)
series_episode(series_id, episode_no)
series_episode_file(local_file_path)
series_source(series_id, source)
```

扫描是可重复操作；重复事件不应创建第二个 episode file。文件路径改变要先识别为删除旧路径和创建新路径，不能把新文件直接挂到旧 episode 上而留下幽灵记录。

### 元数据同步

`SeriesServiceImpl` 负责剧集详情和 summary，Spider/豆瓣调用在 AdminService 或对应同步链路中执行。源数据落库需要以 series/episode/source 业务键 upsert，迟到的旧响应不能覆盖更新的 source version。

摘要属于 series 级资源时使用 series summary lock；若产品将来支持分集摘要，锁键必须切换为 episode file/episode 级，不能沿用 seriesId 造成不必要阻塞。

### 分片计划

Series 播放使用 `SeriesSegmentPlanResolver`、`SeriesSegmentPlanner`、`SeriesSegmentPlanStore` 及 lazy fMP4 组件。规划输入是实际 episode file，不是整个剧集；计划文件和缓存路径必须带 episode file fingerprint、variant 和 planVersion。

```text
episodeFileId + source fingerprint
  → ffprobe / keyframe analysis
  → SeriesSegmentPlan
  → segment index + start/end microseconds
  → plan store
```

Movie 与 Series 共享思想，不共享物理文件和 Redis key。Series 的一集可能比电影短，也可能存在不同编码轨道，不能因为 windowStart 相同就复用 Movie 或另一集的分片。

### 媒体输出

Series 的 `PlaybackTranscodeManager`、`LazyFmp4MediaGenerator`、`LazyFmp4PlaybackEngine` 和 cache/coordinator 负责按需生成窗口。SOURCE 视频沿用 copy，音频按 AAC 生成；HIGH1080/LOW1080 使用视频编码，但三档都输出同一时间单位和 fMP4 结构。

字幕按 episode file 提取并缓存；切换集数时必须换 subtitle URL 和 track identity。字幕文件不能只用 seriesId 命名，否则第 1 集和第 2 集会互相覆盖。

## 数据状态

### 领域实体

```text
Series 1 ── * SeriesEpisode 1 ── * SeriesEpisodeFile
Series 1 ── * SeriesSource
Series 1 ── 1 SeriesInfo
Series / Person / Genre 通过关系表连接
User 1 ── * user_progress  (media_type=SERIES)
```

`SeriesEpisodeFile` 是播放和文件物理路径的交汇点。播放准备、segment plan、字幕和缓存都应从它取得 source path、duration、codec 和文件版本，不要从 Series 标题反查文件。

### Redis 状态

Series Redis key 结构与 Movie 对齐，但模块前缀和资源身份不同：

```text
series:watcher:leader:lock
series:refresh-database:request-gate
series:playback:session:<sessionId>
series:playback:window:<episodeFileId>:<variant>:<window>
series:playback:subtitle:<episodeFileId>:<trackId>:lock
```

session/active session/window status 是短状态；最终的 Series、episode、episode file、用户进度仍在 MySQL。Redis 清空后允许重建播放 session，但不能丢失已入库的集信息。

### 刷新消息

`SeriesRefreshCommandMessage` 通过 durable command queue 传递，`SeriesRefreshStatusMessage` 通过 fanout status exchange 传递。`SeriesRefreshRequestManager` 只在发起实例中保存 future，实例重启后无法依靠该 future 找回历史终态。

leader listener 在非 leader 实例上重新投递 command，选主切换期间可能出现重投。没有持久 inbox/task 时，消息重投仍可能重复执行扫描；数据库唯一约束可以防重复实体，但不能避免重复 NAS 读取和外部元数据调用。

### 播放缓存

Series global 缓存可以被不同用户复用，session 缓存绑定单次播放。共享 Redis 不代表各实例本地缓存共享；如果缓存目录在本地盘，Gateway 任意转发会出现 Redis READY 但 B 实例找不到 m4s 的问题。生产部署必须使用共享缓存或 owner instance 路由。

## 运行边界

### 扫描边界

运行记录覆盖文件名和季集解析、计划生成和定位、计划加载、指纹校验、持久文件、扫描、文件变更、配置、刷新生命周期和 request-gate。

### 播放边界

运行记录覆盖 session、窗口、HLS 和字幕；还需确认不同 episodeFileId 不会读到同一份计划，切集后字幕和 duration 都更换。

### 浏览器验收

```powershell
真实浏览器回归至少使用两集：从第 1 集中间 seek、暂停再播放、切换画质、进入第 2 集，再返回第 1 集，检查请求 URL 的 episodeFileId、m3u8、m4s、字幕和进度均未串集。Movie 能播放不等于 Series 链路正确，必须核对 Series 自己的 controller、Redis key、文件路径和计划解析。

### 已知边界

Series 当前实现与 Movie 的播放主链高度相似，但不能把相似误写成共享同一状态。必须继续关注 episodeFile 版本、路径可见性、刷新消息持久幂等和多实例缓存拓扑；若发生播放失败，应先看 `PreparePlaybackVO.status/errorCode`、HlsController 返回码、计划文件和实际 episode 路径，再决定是否修改前端。
