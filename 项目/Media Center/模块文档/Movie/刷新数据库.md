# 电影刷新数据库

本文说明 `Media-Center-Movie` 当前源码如何把 NAS 电影文件同步到 MySQL。总体准入、leader、消息和一致性规则见 [[总体设计/刷新数据库设计|刷新数据库设计]]；本文只保留电影模块的对象身份、扫描顺序、删除边界和验证证据。

## 刷新入口

### 手工请求

管理接口进入 `AdminServiceImpl`。request-gate 保证同一实例正在刷新时再次点击不能创建第二个并行任务。准入成功后发布 Movie refresh command，HTTP 响应表达“已接收”或“已拒绝”，不应把整库扫描放在请求线程中。

### 启动任务

服务启动后由管理服务触发一次校准刷新，目的是恢复进程重启期间丢失的文件事件。启动刷新要使用与手工刷新相同的 admission 和状态链，不能绕过锁直接调用扫描器。

### 文件事件

`MovieFolderWatcher` 监听 `movieBaseLocate`。`MovieLeaderCoordinator` 竞争 `movie:watcher:leader:lock`，只有 leader 注册 watcher 并消费 refresh command；其他实例仍可查询状态。watcher 只发送增量提示，不承担最终一致性，`OVERFLOW`、断电和 NAS 短暂不可用都需要下一轮全量刷新纠正。

### 消息执行

`MovieRefreshCommandListener` 在 leader 上执行扫描，`MovieRefreshStatusListener` 广播结果。重复消息不能靠内存 future 去重；数据库唯一键、文件规范化路径和任务键共同保证重放不会生成第二条 MovieFile。

## 扫描入库

### 文件识别

扫描器从 `movieBaseLocate` 遍历受支持的 `MovieFileType`，跳过临时文件和缓存目录。每个候选文件先做规范化绝对路径、大小、mtime 和媒体探测，再进入业务解析。路径必须仍在配置根目录下，符号链接和越界路径不能写入数据库。

```text
root locate
  -> supported extension
  -> canonical path + fingerprint
  -> ffprobe metadata
  -> MovieFile identity
```

### 电影身份

`Movie` 表保存标题、封面和摘要等业务对象，`MovieFile` 保存源文件路径、时长、视频音频信息和文件版本。扫描时应先按规范化路径查找已有 MovieFile，再根据目录、标题和外部来源关联 Movie；不能仅凭标题把两个同名文件合并。

### 关系写入

电影来源、类型和人物通过 `MovieSource`、`MovieGenre`、`MoviePerson` 及对应 mapper 写入。推荐顺序是先 upsert 主对象，再同步文件，再同步关系，最后触发摘要、封面等派生任务。关系删除要以本次扫描结果为边界，不能把一次探测失败当成“全部关系为空”。

### 事务边界

单个文件的身份和关系写入应具备原子性；外部 Spider、图片下载和播放缓存不应放在同一数据库事务里。事务提交后再发布派生任务，避免下游读取到尚未提交的 movieFileId。

## 删除恢复

### 删除判断

全量扫描结束后，将数据库中的 MovieFile 路径与本次发现集合比较。确认文件不存在且不在临时不可用窗口后，标记或删除文件记录，并清理失效的关系。用户进度和电影主对象是否删除要依据产品保留策略，不能和播放缓存使用同一个 TTL。

### 文件变化

路径相同但大小、mtime 或 fingerprint 改变时，更新媒体信息并使旧 segment plan 失效；路径移动通常处理为旧路径删除、新路径创建。不要把新文件直接覆盖旧 MovieFile 的所有播放身份，否则旧 session 可能继续读取错误源文件。

### 派生资源

播放的 segment plan、SOURCE 音频、1080p 分片、字幕和 session 缓存属于派生数据。源文件版本变化后禁止继续使用旧计划；清理失败应留下可重试状态。字幕可以长期保留，但其 fingerprint 必须与源文件或字幕轨道绑定，避免换片后复用旧字幕。

### 异常恢复

ffprobe 失败、权限不足或 NAS 超时只能把当前文件标为失败并记录路径、异常和重试信息，不能删除上一次成功的数据库记录。下一次刷新再次看到可读文件时，应允许从失败状态恢复。

## 验证证据

### 运行检查

检查源文件 fingerprint 变化是否使旧计划失效；不要把播放页面可见误认为刷新已经正确完成。

### 文件场景

使用临时目录覆盖新增 MKV、重复事件、删除文件、移动文件、不可读文件和同名电影。每个场景都检查 MovieFile 数量、local path、fingerprint、关系数量和任务状态；不要只看管理页面的总数。

### 消息场景

发布两次相同 command，重启消费者后再次发布，模拟非 leader 收到 command，以及 watcher 收到 OVERFLOW。期望只有一个有效刷新任务，实体不重复，状态最终收敛到成功或明确失败。

### 运行证据

记录请求响应、RabbitMQ messageId、leader 日志、数据库查询和 NAS 文件 mtime。若同时验证播放，先确认 MovieFile 已提交，再执行 prepare；播放失败时区分源文件不存在、计划过期和缓存不可见，不能把刷新问题归咎于浏览器。
