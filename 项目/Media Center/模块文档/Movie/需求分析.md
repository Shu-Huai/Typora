# 电影模块


电影模块包含两部分：电影库管理和浏览器播放。电影库回答“有哪些电影、每部电影有哪些文件和资料”；播放系统回答“怎样让 NAS 上的高码率 MKV 在浏览器中稳定播放”。后者已有独立专题，本文着重说明两部分怎样连接以及完整验收边界。

## 电影库

### 数据模型

`Movie` 是内容主体，`MovieFile` 指向实际影片文件。类型、人物、外部来源和扩展资料分别由 `MovieGenre`、`MoviePerson`、`MovieSource`、`MovieInfo` 等实体维护。

```text
Movie
 ├──< MovieFile                 实际可播放文件
 ├──< MovieGenre >── Genre      类型
 ├──< MoviePerson >── Person    导演、演员等人物关系
 ├──< MovieSource               豆瓣等来源 ID
 └── MovieInfo                  简介、年份、海报等扩展资料
```

一部电影可以有多个文件，例如不同分辨率、剪辑版或不同封装。播放进度、转码缓存和字幕上下文都以具体 `MovieFile` 为基础，不能只用 movieId，否则两个时长不同的版本会共享错误时间。

### 扫描规则

管理员配置电影根目录和允许扩展名，刷新任务扫描普通文件并维护数据库。相对路径是文件的直接定位依据；电影主体则依据目录结构、规范化名称和已有关系识别。

刷新按差异更新：

- 新路径创建 `MovieFile`，再关联已有或新建 `Movie`。
- 文件大小、修改时间等变化时更新文件属性，并让依赖文件指纹的播放缓存失效。
- 路径缺失时停止对外播放该文件；只有主体没有其他文件且没有需保留的数据时才考虑清理主体。
- 单文件解析失败记录原因，继续扫描其余电影。

不能用“清空全部电影表再重新插入”的实现。那会改变 movieId/movieFileId，切断用户进度、豆瓣绑定、总结以及缓存目录的关联。

### 内容查询

用户可查看电影总数、分页列表、详情和总结。列表至少包含封面、名称、年份等识别信息，分页采用稳定排序。详情页展示简介、类型、人物及可播放文件。

从详情页进入 `/movie-play/:movieId/:movieFileId` 前，应验证文件确实属于该电影。后端 prepare 同样再次验证，不能相信路由参数组合。

总结生成属于异步能力。状态从 `/ws/movie-summary-status` 返回；已有总结优先读取，重复生成需显式发起。总结失败不能影响详情和播放。

### 豆瓣同步

管理端支持单部与批量同步。第一次同步按名称、年份等条件查找豆瓣 ID，确认后保存为 `MovieSource`；后续优先按已绑定 ID 更新。

自动匹配的基本规则：

1. 标题必须经过有限规范化后相符。
2. 年份存在时应参与判断，重名电影不能只取第一条。
3. 候选不唯一或明显冲突时不自动写入。
4. 外部失败只影响本次同步，本地 Movie 和 MovieFile 保持可用。
5. 更新来源负责的字段，不无条件覆盖人工修订。

批量同步记录每个 movieId 的结果，最终汇总成功、跳过、待确认和失败数量。WebSocket 刷新状态与豆瓣同步状态若共用通道，消息中必须包含操作类型，避免前端把同步误显示成扫描。

## 播放业务

### 三个画质档位

系统不是为了把所有电影预先转成网页格式。原画 4K 文件很大，完整重编码耗时且浪费存储。三个档位承担不同目标：

| 档位 | 视频 | 音频 | 使用场景 |
| --- | --- | --- | --- |
| SOURCE | 必须 stream copy | AAC 48 kHz，通常双声道 | 局域网、保留原画和 HEVC/H.265 |
| HIGH_1080P | H.264 1080p 高码率 | AAC | 公网质量优先 |
| LOW_1080P | H.264 1080p 低码率 | AAC | 公网流量和带宽优先 |

浏览器能解码源视频但不能解码杜比、全景声等音频，是 SOURCE 存在的主要原因。HEVC/H.265 不能放入自动回退列表；否则明明可播放的视频会被无故重新编码。若具体浏览器不能解码视频，应返回可理解错误并让用户选择 1080p，而不是静默改变档位。

### 按需准备规则

播放使用短分片，但后端只生成当前位置附近的有限范围：

```text
用户请求分片 n
  → 若缓存完整，直接返回
  → 若正在生成，短暂等待或返回 503 让 hls.js 重试
  → 若未生成，提交 n，并按预热规则提交 n+1
  → 当前任务完成后停止，不自动排到电影结尾
```

暂停或关闭页面不会强杀已经接近完成的短 FFmpeg 任务，但心跳停止后不再产生新预热。拖动到远处时，调度重心转到新分片；旧缓存保留供本用户回看或其他用户复用。

缓存键基于电影文件、文件版本/指纹、画质、轨道和分片。用户不属于缓存键。A 用户生成的分片可被 B 用户使用，但两人的 session、进度和心跳互不共享。

### 播放清单

主链路是 HLS + fragmented MP4。`master.m3u8` 描述视频 variant 和独立音频轨道；视频、音频各有媒体清单、`init.mp4` 和 `.m4s` 分片。浏览器通过 hls.js/MSE 在同一媒体时间轴中组合轨道。

```text
master.m3u8
 ├── source/video/index.m3u8 → video/init.mp4 + video/seg/*.m4s
 └── audio/index.m3u8        → audio/init.mp4 + audio/seg/*.m4s
```

SOURCE 视频按真实关键帧计划做 copy。对外约 6 秒分片和 60 秒调度窗口是请求与预热粒度，不是把源文件强行按整数秒截断。音频 AAC 根据同一段计划生成，并通过时间戳修整与清单时长保持同步。

前端的 `currentTime` 是小数秒，后端转为整数微秒查找覆盖该时间点的计划段，避免十进制比较和浮点边界误差。详情见 [[模块文档/Movie/播放业务|Movie 播放]]。

### 字幕进度

字幕从原始文件的目标轨道提取，通过 session 下的字幕 URL 提供。字幕以原媒体时间为准，不参与每个视频分片的转码。文件小、提取成本有限，可以作为长期派生结果保存，播放缓存 TTL 不应顺带删除它。

心跳包含 session、当前位置、播放/暂停状态和画质等上下文。它有两个职责：

- 按保存间隔持久化当前用户、当前 MovieFile 的播放进度。
- 在实际播放时触发当前位置及下一小段的准备。

暂停心跳可以继续用于保存 session 活跃状态，但不得不断推动下一窗口。距离结尾小于配置阈值时标记完成，下次从头开始。

## 运行实现

### 播放准备

前端先调用 `/playback/prepare`，后端探测文件、加载或建立分段计划、选择字幕和恢复进度，返回 sessionId、playUrl、variant、时长、恢复位置、心跳间隔及状态。

prepare 的状态不能含糊：

```text
READY       清单及起播所需内容可请求
PREPARING   已接受，前端等待/轮询
FAILED      返回稳定 errorCode 和可读提示
```

同一用户默认只允许一个活跃视频会话，冲突策略为 replace。替换旧 session 只终止其调度上下文，不删除全局分片。session 超时由心跳控制，不能用浏览器是否正常执行 unload 作为唯一依据。

### 任务生命周期

Lazy fMP4 生成使用有界线程池。当前配置限制并发任务、排队任务和单轨在途数；分片 HTTP 请求只等待几秒，FFmpeg 任务有独立超时。

同一目标分片用 single-flight 语义合并并发请求：第一个请求创建任务，后续请求观察同一个 future/状态。失败状态短期保留，防止播放器毫秒级重试形成进程风暴；TTL 到期后允许重新生成。

缓存默认保留 72 小时，定时清理。删除条件同时考虑文件最后使用时间、任务是否仍在执行以及 session 是否仍活跃。清理失败只记录并延后，不能终止整个调度器。

### 转码配置

SOURCE 视频使用 `copy`，音频 AAC；1080p 使用 NVENC 或 CPU H.264 编码参数。配置中 `copy-unsafe-codecs` 可以包含 AV1、VP9 等按项目验证为不适合当前链路的编码，但不包含 HEVC/H.265。

关键运行参数包括：

```yaml
segmentDurationSec: 6
windowDurationSec: 60
preheatAheadWindowCount: 1
session.timeout-sec: 180
lazy.segment-request-wait-sec: 3
lazy.ffmpeg-timeout-sec: 180
cache.ttl-hours: 72
```

配置值不是越大越稳。加大预热会增加磁盘与转码浪费；加大请求等待会占用 Tomcat 线程；提高并发可能让多路 FFmpeg 抢占磁盘和 GPU。调优必须结合实际 4K 文件和硬件测量。

### 前端播放器

前端负责：调用 prepare、加载 HLS、恢复 currentTime、发送心跳、选择清晰度、加载字幕并显示明确状态。播放器不能自行在 SOURCE 失败时自动切换 1080p。

画质切换流程应保存旧 currentTime，在新清单可播放后 seek 回同一媒体时间。切换期间抑制旧实例事件写回，避免旧 `timeupdate` 把新播放器位置覆盖。暂停恢复不重建整个会话，除非发生不可恢复的媒体错误。

## 验收诊断

### 媒体库验收

- 新增、移动、删除电影文件后刷新，Movie/MovieFile 关系符合预期。
- 一部电影多个文件可见，进入播放时参数关系经过校验。
- 重名不同年份电影不会被豆瓣匹配成同一条。
- 豆瓣不可用时本地列表、详情和播放仍工作。
- 刷新不会删除播放进度、总结和有效来源绑定。

### 播放行为验收

使用真实 4K MKV、HEVC/H.265、非 AAC 音频和内嵌 ASS 字幕，分别验证 SOURCE、HIGH_1080P、LOW_1080P：

1. 从 0 开始，检查只生成起播和下一段附近内容。
2. 连续播放跨过多个边界，不重复、不跳跃、不循环、无明显卡顿。
3. 暂停至少一个心跳周期再恢复，音频、视频、字幕位置一致。
4. 拖到多个随机位置及分片边界两侧，实际落点合理且不回旧窗口。
5. 三档画质来回切换，时间轴不乱飘，SOURCE 确认视频为 copy。
6. 关闭页面后观察缓存目录，不继续生成直到结尾。
7. 第二个用户请求已完成分片，不再启动重复 FFmpeg。
8. 缓存过期后能重建，用户进度不受影响。

### 时间轴诊断

发生问题时不靠肉眼猜测，采集同一操作下的四组时间：

```text
前端：seeking/seeked/timeupdate/waiting/playing 的 currentTime
清单：EXTINF、MEDIA-SEQUENCE、MAP 与请求分片编号
媒体：ffprobe 的 packet/frame PTS、DTS、duration、key_frame
后端：请求时间、命中计划段、FFmpeg 输入输出边界、缓存状态
```

字幕准确而音视频跳跃，通常说明视频/音频媒体时间映射或播放器重载有问题；音视频同步但一起偏离目标，通常检查 seek 锚点和播放起始偏移；固定位置循环则检查清单序列、分片内容和缓存键。

### 成功标准

接口返回 200 或生成 `.m4s` 不是成功。通过标准是用户行为与时间轴都正确，并且资源使用符合按需设计。关键帧原理、TS 方案失败原因和 fMP4 决策见播放专题，不在本文重复实现记录。
