# Movie 播放

![](http://public.file.lvshuhuai.cn/images\movie-playback-state-machine-1786601764741-10.svg)

本文是 Movie 播放功能的综合技术文档，内容包括需求、架构、实现、方案演进和运行验收。适用代码：

```text
后端：E:\JetBrains\IDEA\Media-Center-Backend\Media-Center-Movie
前端：E:\JetBrains\WebStorm\Media-Center-Frontend
```

文档讨论的源文件是 NAS 上的电影原片，常见形式为 4K MKV。目标是在浏览器中播放，同时控制转码计算量、磁盘占用和公网流量。

## 需求定义

### 使用场景

典型使用过程如下：

1. 用户将电影原文件保存在 NAS；
2. 在 Media Center 中选择电影；
3. 使用浏览器播放；
4. 在局域网中选择原画，在公网中选择 1080p；
5. 暂停、拖动或切换设备后继续播放；
6. 一段时间不再观看后，系统删除转码缓存。

原文件通常包含多条轨道：

```text
MKV 容器
├── 视频：HEVC/H.265、H.264 等
├── 音频：DTS、TrueHD、Dolby 等
└── 字幕：ASS、SRT、PGS 等
```

实际观察中，目标浏览器能够显示相关 4K HEVC/H.265 电影的画面，但原始音轨没有声音。问题不是“MKV 一定不能播放”，而是浏览器对容器内各轨道的支持不同。

基于这个事实，SOURCE 模式不应重新编码视频。它只需要把原视频压缩数据重新封装，并把音频转换为 AAC：

```text
视频：demux → stream copy → fMP4
音频：demux → decode → AAC encode → fMP4
字幕：完整提取一次 → ASS/VTT
```

如果 SOURCE 连视频一起重编码，会产生以下成本：

- 4K 视频重新编码占用大量 CPU 或 GPU；
- 首次播放等待时间增加；
- 二次有损编码降低画质；
- 生成文件比只转换音频更慢、更贵。

### 功能需求

系统提供三种播放清晰度：

| 清晰度 | 视频处理 | 音频处理 | 用途 |
|---|---|---|---|
| `SOURCE` | 原视频码流 copy | AAC | 局域网、原画播放 |
| `HIGH_1080P` | H.264 1080p 高码率 | AAC | 公网、画质优先 |
| `LOW_1080P` | H.264 1080p 低码率 | AAC | 公网、流量优先 |

播放功能包括：

- 从电影开头播放；
- 从历史小数时间恢复播放；
- 暂停和恢复；
- 向前或向后拖动；
- 在三种清晰度之间切换；
- 选择和显示字幕；
- 通过心跳保存播放进度；
- 多个用户共享已生成媒体；
- 缓存过期后自动清理。

按需生成规则固定为：

```text
首次或 seek 到分片 N：准备 N 和 N+1
播放处于分片 N：只确保 N+1 已存在
暂停：保存进度，不安排新片段
关闭页面：停止心跳和媒体请求，不安排新片段
```

例如：

```text
从开头播放     → 生成 0、1
进入分片 1     → 生成 2
拖到分片 18    → 生成 18、19
缓存实际存在   → 0、1、2、18、19
```

中间的 3～17 不需要生成。

### 质量约束

以下规则不能被自动回退或临时修复破坏：

- SOURCE 的 HEVC/H.265 视频必须 copy；
- HIGH 和 LOW 必须重编码视频；
- 三种清晰度使用同一套电影时间和分片编号；
- 音频和字幕使用同一条电影绝对时间轴；
- 暂停和关闭后不能继续转码到结尾；
- 已启动的短任务可以执行完，但不能自动串联后续任务；
- session 不能拥有或删除共享媒体文件；
- 不完整的 FFmpeg 输出不能发布到公共缓存。

下列现象视为播放失败：

| 类型 | 失败表现 |
|---|---|
| 连续性 | 相邻片段重复、缺帧、固定位置卡顿 |
| 时间 | 非主动 seek 时倒退或大幅前跳 |
| 同步 | 音画不同步、字幕与媒体不同步 |
| 暂停 | 暂停后无法恢复或恢复位置改变 |
| 切换 | 清晰度切换后进度改变 |
| 资源 | 暂停后后台继续生成到电影结尾 |
| 缓存 | 不同编码配置的 init 和 m4s 被混用 |

时间精度要求如下：

```text
接口：允许 Double 小数秒
内部计划：整数微秒
播放器：整部电影的绝对 currentTime
分片区间：[startUs, endUs)
```

整数微秒比视频帧和 AAC frame 的时间粒度更细，并且适合比较、排序、二分查找和序列化。系统不使用整数秒定位分片。

### 范围之外

本功能不负责：

- 将 SOURCE 自动降级到 1080p；
- 永久保存所有清晰度的完整电影；
- 在用户未播放时主动转码整部电影；
- 对字幕进行分段提取；
- 用图像识别判断是否重复播放；
- 修改字幕时间来补偿错误的媒体时间轴。

字幕文件很小，完整提取一次即可。文本字幕和分片计划可以长期保留；视频和 AAC 分片按 TTL 回收。

## 总体设计

### 组件职责

![](http://public.file.lvshuhuai.cn/images\movie-playback-architecture-1786601764741-9.svg)

后端组件划分如下：

| 组件 | 输入 | 输出 | 职责 |
|---|---|---|---|
| `PlaybackController` | HTTP DTO | HTTP VO | prepare、heartbeat、字幕入口 |
| `PlaybackServiceImpl` | 用户、电影、时间、清晰度 | session、播放地址 | 会话、进度和状态并发控制 |
| `MovieSegmentPlanResolver` | 源文件 | `MovieSegmentPlan` | ffprobe 探测和计划持久化 |
| `LazyFmp4PlaybackEngine` | 绝对时间 | 分片请求、HLS 清单 | 定位 N，准备 N/N+1 |
| `LazyFmp4SegmentCoordinator` | 流和分片范围 | 共享 future | 并发合并、队列和预算 |
| `Fmp4PlaybackSupport` | 计划、profile | FFmpeg 命令 | seek、边界和编码参数 |
| `LazyFmp4MediaGenerator` | FFmpeg 请求 | 已校时片段 | 执行、验证和 `tfdt` 修正 |
| `LazyFmp4SegmentCache` | init、m4s | 全局缓存文件 | 路径、兼容检查、原子发布 |
| `HlsController` | session、资源路径 | m3u8/init/m4s | 授权后提供全局媒体 |
| `PlaybackCacheCleaner` | 缓存目录、TTL | 删除结果 | 清理过期媒体代际 |

前端主要由两个文件负责：

```text
src/views/movie-play/index.vue
  播放器、Hls.js、交互、字幕、心跳

src/utils/movie/playbackTimeline.ts
  绝对播放时间计算
```

组件之间的边界是：

- `PlaybackServiceImpl` 管用户状态，不直接操作媒体文件；
- `LazyFmp4PlaybackEngine` 决定需要什么，不直接运行进程；
- `Coordinator` 决定任务能不能运行，不计算媒体时间；
- `Generator` 生成一个有界单元，不继续调度下一单元；
- `Cache` 发布结果，不决定生成哪些分片；
- `HlsController` 提供文件，不保存播放进度。

### 文件结构

播放 session 存放在 Redis，结构可以简化为：

```json
{
  "sessionId": "86e80f7e-a809-45df-bd56-4e416b8db697",
  "userId": 12,
  "movieFileId": 838,
  "variant": "SOURCE",
  "currentTimeSec": 65.734281,
  "paused": false,
  "lastHeartbeatAt": "..."
}
```

session 保存：

- 用户和电影；
- 当前清晰度；
- 播放进度；
- 暂停状态；
- prepare 请求 token；
- session TTL。

session 不保存：

- `.m4s` 文件归属；
- FFmpeg 进程所有权；
- 窗口相对时间 offset；
- 私有的 `init.mp4`。

磁盘缓存按源文件和逻辑流组织：

```text
movie-file-838/
└── lazy-fmp4-v1/
    └── <source-fingerprint>/
        ├── segment-plan.json
        ├── video/
        │   ├── source/<stream-revision>/
        │   │   ├── init.mp4
        │   │   └── segments/
        │   │       ├── seg-000000.m4s
        │   │       ├── seg-000001.m4s
        │   │       ├── seg-000018.m4s
        │   │       └── seg-000019.m4s
        │   ├── high-1080p/<stream-revision>/...
        │   └── low-1080p/<stream-revision>/...
        ├── audio/<stream-revision>/
        │   ├── init.mp4
        │   └── segments/...
        └── subtitles/...
```

缓存身份由这些字段组成：

```text
movieFileId
+ sourceFingerprint
+ streamRevision
+ segmentIndex
```

`sourceFingerprint` 区分源文件版本，包括路径、大小、修改时间和计划版本。`streamRevision` 区分生成配置，包括 codec、实际编码器、分辨率、码率、滤镜和管线修订。

这样可以阻止以下组合：

```text
旧 init.mp4 + 新版 m4s
GPU init.mp4 + CPU m4s
旧 AAC profile + 新 AAC segment
修改前的源文件计划 + 修改后的源文件
```

### HLS 资源结构

浏览器首先请求 master playlist：

```text
/file/hls/{sessionId}/{variant}/master.m3u8
```

master 将一条视频 rendition 与 AAC 音频组关联：

```m3u8
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-MEDIA:TYPE=AUDIO,GROUP-ID="audio",NAME="AAC",DEFAULT=YES,AUTOSELECT=YES,URI="../audio/index.m3u8"
#EXT-X-STREAM-INF:BANDWIDTH=24192000,RESOLUTION=3840x1600,AUDIO="audio"
video/index.m3u8
```

媒体资源包括：

```text
/file/hls/{sessionId}/{variant}/video/index.m3u8
/file/hls/{sessionId}/{variant}/video/init.mp4
/file/hls/{sessionId}/{variant}/video/seg/{segmentIndex}.m4s

/file/hls/{sessionId}/audio/index.m3u8
/file/hls/{sessionId}/audio/init.mp4
/file/hls/{sessionId}/audio/seg/{segmentIndex}.m4s

/file/hls/{sessionId}/subtitle/{trackId}
```

视频和音频 media playlist 从一开始就描述整部电影：

```m3u8
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-MEDIA-SEQUENCE:0
#EXT-X-MAP:URI="init.mp4"

#EXTINF:6.208000,
seg/0.m4s
#EXTINF:6.101333,
seg/1.m4s
#EXTINF:6.186667,
seg/2.m4s

#EXT-X-ENDLIST
```

清单是整部电影的时间地图，`.m4s` 是按需生成的实际内容。清单可以列出 0～500，磁盘上暂时只有 0、1、18、19。seek 到 18 不要求先生成 2～17。

每条逻辑流在一个缓存代际内使用一个稳定 `init.mp4`：

```text
SOURCE 视频      → 一个 video init
HIGH_1080P 视频  → 一个 video init
LOW_1080P 视频   → 一个 video init
共享 AAC         → 一个 audio init
```

FFmpeg 每次工作会在临时目录生成候选 init，但缓存只发布兼容版本，不会给每个准备单元永久保留不同 init。

### 播放生命周期

![](http://public.file.lvshuhuai.cn/images\on-demand-playback-sequence-1786601764741-12.svg)

首次播放或恢复进度：

```http
POST /playback/prepare
Content-Type: application/json

{
  "movieFileId": 838,
  "variant": "SOURCE",
  "positionSec": 65.734281
}
```

后端按以下顺序处理：

1. 验证用户和电影文件；
2. 创建或更新 session，并写入本次 prepare token；
3. 计算源文件指纹；
4. 加载或生成 `segment-plan.json`；
5. 将小数秒转换为整数微秒；
6. 找到当前位置所属分片 N；
7. 确保当前视频流的 N、N+1；
8. 确保共享 AAC 的 N、N+1；
9. 提取或复用字幕；
10. 再次检查 prepare token，防止旧请求覆盖新状态；
11. 返回 session、HLS URL 和原恢复时间。

响应示意：

```json
{
  "sessionId": "86e80f7e-a809-45df-bd56-4e416b8db697",
  "playUrl": "/file/hls/86e80f7e-a809-45df-bd56-4e416b8db697/source/master.m3u8",
  "variant": "SOURCE",
  "resumePositionSec": 65.734281,
  "playbackStartPositionSec": 0,
  "durationSec": 3378,
  "status": "READY",
  "heartbeatIntervalSec": 5
}
```

`playbackStartPositionSec = 0` 表示 playlist 的时间轴从电影 0 秒开始，不表示前端必须从 0 播放。前端使用 `resumePositionSec` 设置 `video.currentTime`。

播放中的心跳：

```json
{
  "sessionId": "86e80f7e-a809-45df-bd56-4e416b8db697",
  "currentTimeSec": 71.028416,
  "paused": false,
  "variant": "SOURCE"
}
```

心跳保存进度并刷新 session TTL。`paused=false` 时确保下一缺失分片；`paused=true` 时不调度。

seek 的顺序是：

```text
记录 targetTime
→ prepare(targetTime)
→ 等待目标 N/N+1 可用
→ video.currentTime = targetTime
→ 恢复加载和播放
```

清晰度切换记录原 `video.currentTime`，准备新 rendition 的相同位置。视频 codec 改变时可以重建 Hls.js/MediaSource，但恢复位置仍是原绝对时间。AAC 不随清晰度重复生成。

缓存生命周期与 session 分开：

- session 过期后，用户状态失效；
- 媒体缓存保留到媒体 TTL；
- 当前媒体 TTL 配置为 72 小时；
- 分片被访问后更新使用时间；
- 清理器保留计划、字幕、新鲜任务和未过期媒体；
- seek 和暂停不清空全局缓存。

## 详细实现

### 分片定位

`ffprobe` 从视频轨读取 packet 的时间和关键帧标志：

```powershell
ffprobe `
  -v error `
  -select_streams v:0 `
  -show_packets `
  -show_entries packet=pts_time,dts_time,duration_time,flags,pos `
  -of json `
  movie.mkv
```

这里使用 packet 数据，不完整解码视频画面。规划器依赖 ffprobe 提供的关键帧标志和时间戳，不假设一个 packet 永远对应一个 frame。

计划结构近似如下：

```json
{
  "version": 3,
  "sourceFingerprint": "...",
  "sourceVideoCodec": "hevc",
  "durationUs": 3378123456,
  "targetDurationUs": 6000000,
  "segments": [
    {
      "index": 10,
      "startUs": 59200000,
      "endUs": 65700000,
      "startDecodeUs": 59116667,
      "seekAnchorUs": 53000000,
      "seekAnchorDecodeUs": 52916667,
      "inputSeekUs": 56000000
    }
  ]
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `startUs` | 分片在电影展示时间轴上的开始 |
| `endUs` | 分片结束，不属于当前片 |
| `startDecodeUs` | 第一个待发布 sample 的绝对解码时间 |
| `seekAnchorUs` | 选中边界前面的真实关键帧展示时间 |
| `seekAnchorDecodeUs` | 该锚点的解码时间 |
| `inputSeekUs` | 提交给 FFmpeg 的输入 seek 位置 |

所有时间保存为整数微秒。接口的 `Double` 秒只转换一次：

```java
long positionUs = Math.max(
        0,
        Math.round(currentTimeSec * 1_000_000.0)
);

MovieSegment current = plan.segmentAtUs(positionUs);
```

查找使用左闭右开区间：

```text
segment 10 = [59.200000, 65.700000)
segment 11 = [65.700000, 71.300000)

65.699999 → segment 10
65.700000 → segment 11
65.734281 → segment 11
```

找到 segment 11 后，后端准备 11、12，但前端仍播放 `65.734281`。浏览器从 segment 11 的关键帧开始解码，再呈现目标时间。

SOURCE 不能直接把选中关键帧时间作为输入 seek。demuxer 可能回退到更早的随机访问点。计划保存前置关键帧 anchor，生成时读取 anchor 到目标边界的内容作为 guard；guard 不发布，只用于让 FFmpeg 稳定地产生目标片段。

### 媒体生成

SOURCE 视频命令必须包含 `-c:v copy`，并且不能包含视频编码器。命令结构如下：

```powershell
ffmpeg -y `
  -ss <input-seek> `
  -i <source.mkv> `
  -t <bounded-duration> `
  -map 0:v:0 `
  -an -sn -dn `
  -c:v copy `
  -tag:v hvc1 `
  -f segment `
  -segment_format mp4 `
  -segment_header_filename init.mp4 `
  -segment_format_options movflags=frag_keyframe+empty_moov+default_base_moof+skip_trailer+negative_cts_offsets `
  -segment_times <anchor-relative-boundaries> `
  -segment_start_number <number> `
  seg_%06d.m4s
```

HIGH/LOW 视频增加缩放、H.264 编码、码率和 GOP 参数。重编码可以强制关键帧，但强制位置来自同一份规范计划，不能单独建立 1080p 时间表。

AAC 单独生成：

```powershell
ffmpeg -y `
  -ss <aac-frame-aligned-start> `
  -i <source.mkv> `
  -t <bounded-duration> `
  -map 0:a:0 `
  -vn -sn -dn `
  -c:a aac `
  -b:a 192k `
  -ac 2 `
  -ar 48000 `
  -af "aresample=async=1:first_pts=0" `
  -f segment `
  ...
```

AAC-LC 一帧通常包含 1024 个采样。48 kHz 下：

```text
1024 / 48000
= 0.021333333 秒
= 21.333 毫秒
```

视频边界 `6.200000` 秒附近可能存在这些 AAC 边界：

```text
6.186667
6.208000
```

音频不能从 AAC frame 中间切开。普通边界四舍五入到最近完整 frame，最大偏差约半帧；电影结尾向上取整，防止丢失尾音：

```java
double framePosition = movieTimeUs * sampleRateHz
        / (1_000_000.0 * 1024.0);

long frameIndex = isMovieEnd
        ? (long) Math.ceil(framePosition)
        : Math.round(framePosition);
```

![](http://public.file.lvshuhuai.cn/images\av-timeline-alignment-1786601764741-1.svg)

音频边界早于视频时，剩余声音由下一音频片承载；晚于视频时，当前音频片多覆盖几毫秒。音频自己的相邻片段仍首尾相接。音频 playlist 使用 AAC 实际边界计算 `EXTINF`，不照抄视频时长。

### fMP4 发布

fMP4 分为初始化信息和媒体数据：

```text
init.mp4
└── moov
    └── trak/mdia/mdhd → timescale

segment.m4s
├── moof
│   └── traf/tfdt → baseMediaDecodeTime
└── mdat → 压缩 sample
```

独立 FFmpeg 任务可能把电影第 372 秒附近的局部输出写成从 0 开始：

```text
实际电影范围：372.200s ～ 385.000s
局部输出 tfdt：0
应发布的 tfdt：372.200s 对应的 timescale ticks
```

后端不能把“真实位置”只写在 JSON 里，因为浏览器不读取该 JSON。发布前需要修改媒体片段中的 `tfdt`：

1. 从候选 init 的 `mdhd` 读取 timescale；
2. 从 guard m4s 的 `tfdt` 读取局部 decode time；
3. 从计划读取 guard 的绝对 decode time；
4. 计算两者的 offset；
5. 给本次所有待发布 fragment 的 `tfdt` 加相同 offset；
6. 检查单调性、box 边界和整数溢出。

它只整体平移时间，不改变 packet 之间的间距。不能通过累计 m3u8 的 `EXTINF` 重新制造 decode time，因为 `EXTINF` 已经是舍入后的十进制时长。

一次生成任务先写临时目录：

```text
task-<uuid>/
├── init.mp4
├── seg_000018.m4s
├── seg_000019.m4s
└── segments.txt
```

发布条件：

- 候选 init 存在并可读取 timescale；
- guard 存在；
- 所有请求片段存在；
- `tfdt` 修正成功；
- init 与缓存代际兼容；
- 文件能原子移动到最终路径。

任何一步失败都不发布部分结果。临时目录最终清理，孤儿任务目录由缓存清理器兜底。

两个用户请求同一冷分片时，协调器按以下键共享 future：

```text
(movieFileId, sourceFingerprint, streamRevision, segmentIndex)
```

HTTP 请求只等待有限时间。任务仍在执行时可以返回：

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 1
```

Hls.js 稍后重试。HTTP 按需补片是恢复路径，正常情况应由 prepare 和 heartbeat 提前准备。

### 播放字幕

前端只使用电影绝对时间：

```ts
const currentMovieTime = video.currentTime;

await heartbeatMoviePlaybackApi({
    sessionId,
    currentTimeSec: currentMovieTime,
    paused: video.paused,
    variant: currentVariant
});
```

暂停时不销毁 Hls.js 和 MediaSource。恢复时继续使用原 `video.currentTime`。如果暂停时销毁播放器再按窗口 offset 重建，会重新引入 session 相对时间问题。

seek 需要防止旧请求覆盖新请求。例如用户依次拖到 300、900、1200 秒，300 秒的 prepare 可能最晚返回。后端使用 prepare token 条件更新 session，前端也只接受当前操作对应的结果。

质量切换步骤：

1. 记录 `video.currentTime`；
2. 请求新 variant 的相同绝对位置；
3. 等待新视频 N/N+1；
4. codec 不兼容时重建 Hls.js；
5. 设置原绝对时间；
6. 继续使用共享 AAC 和原字幕 cue。

字幕从源文件完整提取，保留原始时间：

```text
视频 PTS/tfdt   → 电影绝对时间
AAC PTS/tfdt    → 电影绝对时间
字幕 cue        → 电影绝对时间
video.currentTime → 电影绝对时间
```

如果字幕准确而画面不准确，应该修复视频时间轴；不能移动字幕去匹配错误画面。

## 方案验证

### 方案取舍

第一版使用约 6 秒一个 TS、60 秒一个 FFmpeg 窗口。目的包括：

- 单片较短，首播和 seek 等待时间可控；
- 60 秒批量处理，减少进程启动次数；
- 当前窗口播放时预热下一窗口。

预期流程：

```text
从 05:30 播放
→ 生成 05:00～06:00
→ 预热 06:00～07:00
→ 播放进入 06:00 后生成 07:00～08:00
```

SOURCE stream copy 无法在任意 6 秒位置制造关键帧。若目标位置没有关键帧，segment muxer 只能在附近真实关键帧处分割。因此理论切点和实际 packet 边界不一致。

旧命令还把窗口结束时间放进 `-segment_times`：

```powershell
ffmpeg `
  -ss 0 `
  -i movie.mkv `
  -t 60 `
  -c:v copy `
  -f segment `
  -segment_times 6,12,18,24,30,36,42,48,54,60 `
  seg_%06d.ts
```

最后的 `60` 可能让前一窗口在下一个关键帧处多产生一个尾片；下一窗口又生成相同范围。临时目录复现中，带窗口末尾会多出 `seg_000020.ts`，移除后不再产生该跨窗尾片。

出现过的方案和结论：

| 方案 | 能解决什么 | 为什么没有作为最终方案 |
|---|---|---|
| SOURCE 视频重编码 | 可以强制关键帧 | 违反原画 copy，4K 成本高 |
| 只删除 TS 窗口尾边界 | 消除明确的额外尾片 | 仍有固定切点和独立 seek 问题 |
| 每次 prepare 生成独立 fMP4 run | 片段格式适合 MSE | init 和 decode time 每次重置 |
| 前端维护 run offset | 能把局部时间换算成电影时间 | 暂停、seek、切换时容易重复换算 |
| 暂停时杀 FFmpeg 并删 session 缓存 | 立即停止当前任务 | 文件锁、半成品、无法共享 |
| 规范计划 + 全局 fMP4 + `tfdt` 修正 | 保留 copy，支持稀疏共享 | 当前采用 |

![](http://public.file.lvshuhuai.cn/images\ts-vs-fmp4-evolution-1786601764741-16.svg)

最终方案解决的是三个独立问题：

```text
边界问题 → 整部电影唯一的真实关键帧计划
所有权问题 → 媒体属于全局缓存，不属于 session
时间问题 → 每个 fragment 发布前写回绝对 tfdt
```

### 实现验收

真实媒体验收使用电影 837、838 等文件，不依赖图像识别：

1. 检查 SOURCE 输出 codec 仍为 HEVC/H.265；
2. 比较源文件与发布片段的视频 packet payload/hash；
3. 验证连续片段的 PTS/DTS 单调，无重复区间；
4. 验证跨两个独立 FFmpeg 任务的片段仍连续；
5. 验证跳跃生成的 18、19 可以组合解码；
6. 检查 AAC 相邻片没有重复 terminal frame；
7. 比较 SOURCE、HIGH、LOW 的 segment index 和边界；
8. 用 FFmpeg 将视频和音频分别解码到 null，检查错误和时间戳警告。

SOURCE 是否真的 copy，不能只检查命令字符串。最终证据应是：

```text
源视频压缩 packet payload
           ==
发布 SOURCE 分片对应 packet payload
```

### 浏览器验收

人工验收表：

| 场景 | 操作 | 通过条件 |
|---|---|---|
| 首次播放 | 从 0 播放 | 请求 0、1；音画字幕一致 |
| 恢复进度 | 从小数历史位置开始 | 不吸附到分片起点 |
| 短暂停 | 暂停数秒后恢复 | 时间不跳，音画不漂 |
| 长暂停 | 等当前任务完成后恢复 | 后端没有继续生成后续片 |
| 向前 seek | 跳到冷分片中间 | 只生成目标 N、N+1 |
| 向后 seek | 返回热缓存位置 | 缓存命中，不重复生成 |
| seek storm | 连续快速拖动 | 最终位置正确，旧请求不覆盖 |
| 清晰度切换 | 三种模式双向切换 | currentTime 和字幕不变 |
| 双客户端 | 同时请求同一冷片 | 只有一个共享任务 |
| 页面关闭 | 播放中关闭 | 当前任务后不再调度 |

浏览器记录项：

- `video.currentTime`；
- `video.buffered`；
- `video.seekable`；
- `readyState` 和 `networkState`；
- `waiting`、`stalled`、`seeking`、`seeked`、`playing`；
- Hls.js fatal/network/media error；
- m3u8、init、m4s 请求顺序与 HTTP 状态；
- 当前字幕 cue；
- 对应后端任务和缓存命中日志。

浏览器控制台可使用：

```js
console.table({
  currentTime: video.currentTime,
  duration: video.duration,
  readyState: video.readyState,
  networkState: video.networkState,
  paused: video.paused,
  seeking: video.seeking
});

console.log([...Array(video.buffered.length)].map((_, i) => ({
  start: video.buffered.start(i),
  end: video.buffered.end(i)
})));
```

除主动 seek 外，`currentTime` 不应明显倒退或大幅前跳。短暂 `waiting` 可以由冷转码造成，但必须能够恢复，且不能伴随重复区间或永久 buffer hole。

验证结论分开记录：构建、媒体时间轴检查、浏览器行为和真实 NAS 访问分别记录，不能用其中一项代替其他项。

### 故障排查

出现问题时先保存现场，不要首先清缓存：

- movieFileId、源文件路径和 sourceFingerprint；
- variant、sessionId；
- 故障前后的 `currentTime`；
- 是否发生暂停、seek 或清晰度切换；
- 冷缓存或热缓存；
- 请求过的 playlist、init 和 segment；
- `segment-plan.json`；
- FFmpeg 命令和 stderr。

源文件信息：

```powershell
ffprobe -v error `
  -show_entries format=duration:stream=index,codec_type,codec_name,profile,time_base,start_time `
  -of json `
  input.mkv
```

关键帧和 packet 时间：

```powershell
ffprobe -v error `
  -select_streams v:0 `
  -show_packets `
  -show_entries packet=pts_time,dts_time,duration_time,flags,pos `
  -of csv=p=0 `
  input.mkv
```

生成片段时间：

```powershell
ffprobe -v error `
  -show_packets `
  -show_entries packet=stream_index,pts_time,dts_time,duration_time,flags `
  -of csv=p=0 `
  generated-fragment.mp4
```

症状与检查位置：

| 现象 | 首先检查 |
|---|---|
| 重复一小段 | 相邻视频 packet 范围和 payload |
| 大幅跳跃或循环 | fragment `tfdt`、前端 offset |
| 持续等待 | `buffered` 空洞、m4s 的 503 重试 |
| 音频正确、画面错误 | SOURCE anchor、视频 `tfdt` |
| 画面正确、音频错误 | AAC 边界、terminal frame、音频 `tfdt` |
| 字幕正确、媒体错误 | 视频或音频绝对时间轴 |
| 冷缓存失败 | FFmpeg、临时文件、原子发布 |
| 热缓存失败，清理后恢复 | 缓存代际和 init 兼容性 |

PTS 和 DTS 不能混用：

- PTS 表示呈现时间；
- DTS 表示解码时间；
- 有 B frame 时两者可能不同；
- 分片展示区间使用 PTS 语义；
- `tfdt` 是 base decode time，使用 DTS 语义。

Edge 可以播放而嵌入式浏览器失败时，依次检查服务、HTTP 请求、MSE/codec 支持、Hls.js 错误和缓存代际。不能直接得出“HEVC 不能播放”并增加 SOURCE→1080p 自动回退。
