# 电影媒体探测

这份文档只处理一个问题：原始电影文件如何变成可靠的媒体时间轴。它不讨论电影资料、豆瓣同步或播放器界面。Movie 的播放页面能否连续播放，首先取决于这里生成的源信息、关键帧锚点和分片计划是否正确。

## 输入事实

### 文件身份

探测入口必须从已入库的 `MovieFile` 得到路径，再经过配置根目录校验。请求参数中的文件名不能直接进入 FFmpeg。计划键至少包含：

```text
movieFileId
sourceFingerprint = canonicalPath + size + lastModified + media signature
variant = SOURCE | HIGH1080 | LOW1080
planVersion
```

同一物理路径替换文件后，旧计划不能继续使用。仅比较文件名不够，因为用户可能用新版本覆盖原 MKV。

### ffprobe 结果

`ffprobe` 负责读取容器、轨道和 packet/frame 时间信息，不负责输出播放文件。需要保留的事实包括：容器格式、视频 codec、音频 codec、宽高、帧率、时长、time base、start_time、音轨语言、字幕轨道和关键帧 PTS。

```text
container
  ├─ video stream: codec, width, height, time_base, start_time
  ├─ audio streams: codec, language, channels, sample_rate
  └─ subtitle streams: codec, language, disposition
```

### 时间单位

前端的 `currentTime` 是小数秒，计划内部使用整数微秒。浮点值只在 HTTP DTO 边界存在，进入查找逻辑后立即转换，并用半开区间 `[startUs, endUs)` 选择唯一 segment。这样 60.000 秒不会同时命中前后两个分片。

### 探测失败

探测失败要区分文件不存在、权限失败、FFmpeg 不存在、容器损坏和没有视频轨道。不能统一返回“格式不支持”，因为处理动作不同：权限问题应修配置，容器损坏应换文件，浏览器不兼容才需要用户主动选择 1080p。

## 计划生成

### 关键帧锚点

SOURCE 使用视频 copy，不能把墙钟时间当作切点。计划应从视频流的实际关键帧和可解码起点建立锚点，并记录原始 PTS、DTS、segment start、segment end 和是否需要前置解码上下文。

```json
{
  "planVersion": 3,
  "durationUs": 3378000000,
  "segments": [
    {"index": 0, "startUs": 0, "endUs": 5984000, "anchorUs": 0},
    {"index": 1, "startUs": 5984000, "endUs": 11968000, "anchorUs": 5984000}
  ]
}
```

这里的 6 秒只是近似目标，不是强制切割长度。实际边界由源文件关键帧决定。若关键帧间隔是 2.1 秒或 9.4 秒，计划必须接受实际长度，不能为了整齐而重新切出重叠内容。

### variant 规则

三档画质共享时间坐标，但生成策略不同：

| variant | 视频 | 音频 | 计划用途 |
| --- | --- | --- | --- |
| SOURCE | copy | AAC | 最大限度保留原视频，浏览器兼容音频 |
| HIGH1080 | 1080p 编码 | AAC | 公网高码率 |
| LOW1080 | 1080p 编码 | AAC | 公网低码率 |

SOURCE 不把 HEVC/H.265 放进 unsafe 自动回退列表。用户已经验证浏览器能播放源视频时，服务不能无提示地把它改成另一档画质。

### 计划持久化

计划先写临时文件，完成 JSON 校验、segment 单调性校验和 duration 校验后原子移动到 global。正在生成的计划不能被 HLS Controller 发布。计划文件和缓存文件都要带 fingerprint，避免旧文件覆盖新文件。

### 跳播范围

prepare 根据 currentTime 找到当前 segment，再按配置预热后续有限范围。拖动到第 18 个分片时只准备 18、19 等必要窗口；暂停后不继续扫描到结尾。segment 请求可以补充单片，但不能把一次播放器重试扩大成整部电影任务。

## 诊断方法

### 计划检查

```powershell
ffprobe -v error -select_streams v:0 -skip_frame nokey `
  -show_entries frame=pts_time,pkt_dts_time `
  -of json input.mkv
```

检查计划时关注：第一段是否从合法起点开始、相邻段是否满足 `endUs == next.startUs`、是否存在负时长、最后一段是否覆盖 duration、segment index 是否连续。

### 媒体检查

对生成的 `init.mp4` 和 `.m4s` 逐段执行 ffprobe，记录 codec、start_time、duration 和 stream id。m3u8 返回 200 只能证明清单存在，不能证明分片时间轴连续。

### 浏览器检查

Network 中按顺序保存 master、video/audio playlist、init、video segment、audio segment 和字幕请求。播放器出现重复时，优先比较相邻 m4s 的媒体时间；出现跳跃时，比较 playlist 的 DISCONTINUITY、EXTINF 和实际 segment duration。

## 不采用的方案

### 固定 TS 切割

固定 6 秒 TS 再按 60 秒窗口切割，对重编码的 1080p 尚可，对 SOURCE copy 不可靠。FFmpeg 为满足 seek 可能回退到前置关键帧，导致两个 TS 重复同一段，或中间缺少可解码上下文。问题不在 TS 文件扩展名，而在切点没有服从源视频的随机访问边界。

### 整片转码

整片转码会提前消耗 CPU、磁盘和时间，用户只看十分钟却生成两个小时的文件。按需计划把成本推迟到真实播放位置，并通过 global 缓存让其他用户复用已经完成的分片。

### 静默回退

SOURCE 失败后自动改 HIGH1080 会隐藏真实错误，用户也无法判断是权限、FFmpeg、音频还是浏览器问题。正确做法是返回稳定错误码和诊断日志，由用户主动选择其他 variant。
