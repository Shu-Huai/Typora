# 图片实现

本文对应 `Media-Center-Picture`。业务说明见 [[模块文档/Picture/需求分析|图片模块]]。Picture 同时处理 NAS 文件系统、数据库索引、缩略图、EXIF 元数据、Qdrant 向量和 AI 重绘，不能用普通 CRUD 文档替代实现说明。

## 请求入口

### 图片查询

`PictureController` 负责目录浏览、分页、文件详情、缩略图 URL、元数据、语义搜索和 AI 重绘入口。它调用 `IPictureService` 的 `PictureServiceImpl`，并通过 `PicturePageDTO`、`PictureSearchDTO`、`PictureFileVO`、`PicturePageVO` 等模型返回结果。

```text
GET /picture/**
  → PictureController
  → PictureServiceImpl
  → PictureFileMapper / PictureFolderMapper
  → Picture VO
```

`PicturePathResolver` 是所有文件系统操作的边界组件。任何来自前端的 folder id、relative path、filename 或目标目录，都必须先解析为根目录内的规范化 Path；Controller 不应自行拼接磁盘路径。

### 目录操作

创建目录、重命名目录、移动目录、删除目录，以及文件重命名、移动、删除使用 DTO：`CreatePictureFolderDTO`、`RenamePictureFolderDTO`、`MovePictureFolderDTO`、`RenamePictureFileDTO`、`MovePictureFilesDTO`、`DeletePictureFilesDTO`。

服务层先验证父目录、目标路径、文件归属和根目录边界，再执行磁盘操作和数据库更新。数据库保存 `PictureFolder.relativePath`、`PictureFile.relativePath`、filename、folder id 和文件元信息，不能只更新数据库而不处理磁盘，亦不能把用户输入当作绝对路径直接传给 Files。

### 语义搜索

普通分页按 folder、filename、extension、修改时间等字段查询；语义搜索由 `PictureSearchDTO` 进入 `PictureServiceImpl`，调用 `PictureEmbeddingSyncService`/`QdrantPictureVectorClient` 生成查询向量并搜索 collection，再回查 MySQL 的 PictureFile，最后组装 `PictureSearchVO`。

Qdrant 返回的是 point id 和相似度，不是完整图片事实。结果必须回查数据库确认文件仍有效、路径仍存在或能生成可用 URL；不能把 Qdrant 中已经删除的 point 直接展示给用户。

### AI 重绘

`PictureController.generateIllustration(fileId, requestId, style)` 调用 `PictureServiceImpl.generateIllustration`。服务读取原图、校验 style、调用 LLM 图像服务，再写入 `PictureIllustration`，结果通过 `PictureIllustrationStatusListener` 和 WebSocket handler 广播。

当前 `picture:illustration:generating:user:<userId>` 是用户级并发锁，主要控制昂贵模型的配额；生成前会查询 `picture_file_id + style` 的已有记录并复用 URL，但表没有模型版本和完整业务唯一键，两个用户仍可能并发生成同一意图。

## 核心服务

### 目录扫描

`PictureLibraryScanner` 遍历配置根目录并生成 `ScannedPictureFile`；`PictureLibraryIngestionService` 将扫描结果写入 `PictureFolder`、`PictureFile`，并触发元数据、缩略图和 embedding 处理。全量刷新由 `AdminServiceImpl` 编排，扫描前停止 watcher，扫描完成后重新启动。

```text
PictureLibraryScanner
  → ScannedPictureFile
  → PictureLibraryIngestionService
  → PictureFolder / PictureFile
  → PictureMetadataService
  → ThumbnailServiceImpl / PictureEmbeddingSyncService
```

扫描结果应以 relative_path、文件大小和 lastModified 作为变化判断。Picture 的目录结构会变化，单靠 filename 不能识别稳定文件；移动/重命名需要在服务层同步 folder id、relative path 和派生缓存。

### 文件操作

`PicturePathResolver` 负责：

- 将配置根目录和请求相对路径都转为 normalized absolute Path；
- 检查目标路径 `startsWith(basePath)`；
- 拒绝 `..` 穿越、空路径、根目录外的符号链接和不允许的扩展名；
- 生成数据库相对路径和本地文件路径的双向转换。

路径安全检查必须使用临时目录和越界样例，不能只观察一个正常文件名。文件删除、移动和缩略图读取都要复用 resolver，不能在某个 service 中重新实现一份不一致的安全判断。

### 派生文件

`PictureMetadataService` 读取 EXIF/图片头信息，写入 `PictureMetadata`；`ThumbnailServiceImpl` 按 `PictureThumbnailProperties` 生成缩略图到独立缓存目录。缩略图是可重建派生物，不能与原图使用同一清理根目录。

缩略图生成应使用临时文件，写完并确认尺寸/格式后原子 rename。浏览器请求缩略图时，如果缓存不存在，可以排队生成或返回明确准备状态；不能把半写文件作为成功响应。

### 向量索引

`PictureEmbeddingSyncService` 调用 LLM image embedding，成功后让 `QdrantPictureVectorClient.ensureCollection(dimension)` 检查 collection；404 时创建 `media_center_picture_embedding`，距离函数为 Cosine，再 upsert point。`PictureEmbeddingIndex` 保存 pictureFileId、collection、pointId、模型名、维度、状态、文件大小和修改时间。

当前 collection 不在应用启动时自动创建，也不在普通搜索前盲目创建；首次成功 embedding 时才通过 ensureCollection 创建。全量 Picture refresh 会删除 collection，后续第一张成功 embedding 的图片再创建它。embedding 失败会写失败状态和 retry 信息，不能因为 Qdrant 失败而删除原图或数据库文件索引。

```text
encodeImage(file)
  → ensureCollection(dimension)
  → PUT/UPSERT pointId
  → update PictureEmbeddingIndex=READY
```

pointId 应由 pictureFileId 或稳定文件身份派生。文件大小、lastModified、模型版本变化时，需要使旧 embedding 失效并重新生成；MySQL 状态和 Qdrant point 必须允许重试收敛。

`PictureServiceImpl` 负责业务校验，具体文件操作使用 `Files.move`、`Files.delete`、目录创建等 JDK API。推荐顺序是先验证所有输入和目标，再执行磁盘变更，最后在短事务中更新数据库；如果跨系统步骤中途失败，记录 source、target 和操作状态，由刷新扫描补偿。

重复操作的语义要先区分：确保文件已删除可以重复调用；重命名到已经存在的目标应报冲突；移动请求重复到同一目标可以视为已完成，但源路径和目标路径都要重新检查。不能简单把所有 `NoSuchFileException` 都变成成功，因为它可能表示客户端给错了资源。

## 数据状态

### 领域实体

```text
PictureFolder 1 ── * PictureFile
PictureFile 1 ── 1 PictureMetadata
PictureFile 1 ── * PictureIllustration
PictureFile 1 ── 1 PictureEmbeddingIndex
PictureFile 1 ── * Qdrant points by collection/model version
```

`PictureFolder.relativePath` 和 `PictureFile.relativePath` 是文件系统索引；`PictureMetadata`、`PictureIllustration`、`PictureEmbeddingIndex` 都是派生或外部结果。删除或移动文件时必须明确这些派生记录是更新、失效还是异步清理，不能只删主文件行。

### 实时刷新

`PictureLeaderCoordinator` 使用 `picture:watcher:leader:lock` 选出唯一 `PictureFolderWatcher`。Picture watcher 监听 create、modify、delete，递归注册子目录；全量刷新和实时事件使用 maintenance lock 协调。`OVERFLOW`、WatchKey 失效或 NAS 不可达时应触发 reconciliation，不能静默忽略。

刷新 command/status 使用 `PictureRefreshCommandMessage`、`PictureRefreshStatusMessage`、request manager 和 WebSocket handler。当前状态 future 是实例本地的；RabbitMQ 重投和实例重启仍需要持久 task/inbox 才能完整恢复。

### 外部状态

Picture Redis key 包括 watcher leader、refresh request-gate、library maintenance 和用户级 illustration generating。它们只保存协调状态，不能替代 PictureFile、embedding index 和 illustration 的数据库事实。

Qdrant collection 可重建，但重建前应保存 MySQL embedding index 状态。collection 被全量刷新删除后，搜索可能暂时无结果；服务应返回空结果/准备状态，而不是把 collection 不存在误报成图片文件损坏。

### 外部结果状态

AI 重绘、元数据、embedding 和缩略图都跨越数据库事务之外的副作用，建议按状态管理：

```text
PENDING → RUNNING → READY
              └──→ RETRYABLE_FAILED
              └──→ FINAL_FAILED
```

写对象、写 Qdrant 或调用模型成功后，数据库状态更新失败时必须能通过确定性 key 找回结果。不能只依赖 WebSocket 成功消息；客户端重连后仍应能从 PictureIllustration/EmbeddingIndex 查询当前事实。

## 运行边界

### 路径边界

运行记录覆盖根目录、相对路径、越界和非法输入、创建/移动/重命名/删除/目标冲突，以及 watcher 启停和事件处理。

### 派生边界

运行记录覆盖扫描和入库、元数据读取、缩略图生成、collection、point upsert 和失败状态。

### AI 接口边界

运行记录覆盖参数委托、搜索和生成接口、已有风格图复用、模型调用、用户并发锁、requestId 状态消息和刷新前后 watcher 生命周期。
