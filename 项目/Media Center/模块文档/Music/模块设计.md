# Music 模块设计

Music 的核心是把一个音频文件稳定归属到曲目、歌手、专辑和来源。文件名解析只能提供候选，最终身份必须结合歌手关系、文件路径和外部来源确认。歌单和进度属于用户数据，与曲库刷新分开处理。

## 领域边界

### 曲目身份

`MusicTrack` 是逻辑曲目，`MusicFile` 是物理音频文件，`MusicTrackArtist` 保存歌手关系，`MusicAlbum` 保存专辑。相同标题不同歌手不能复用同一 track。

### 用户数据

Playlist、PlaylistTrack 和 user_progress 属于用户域。曲库刷新可以更新 track/file/source，但不能删除用户歌单或清空进度。歌单重复曲目是否允许，必须由产品语义决定。

### 外部来源

QQ 音乐匹配、歌词、专辑图和 summary 都是派生来源。source type/source id 是外部数据幂等键，匹配失败要保留 NOT_MATCHED，不得用 title-only fallback 绑定错误结果。

## 组件协作

### 入库链路

`MusicLibraryScanner → MusicFilenameParser → MusicLibraryIngestionService → MusicMetadataSyncService → Track/Artist/Album/File mapper`。扫描、解析、入库和外部同步分层，便于在外部服务不可用时保留本地索引。

### 用户链路

`MusicPlaylistController → MusicPlaylistServiceImpl`；`MusicProgressController → MusicProgressServiceImpl`；`FileController → FileServiceImpl`。三个 service 都通过当前用户 id 做资源所有权和进度隔离。

### 刷新链路

`AdminController → AdminServiceImpl/MusicServiceImpl → watcher or scanner → ingestion`。Music 存在直接执行刷新路径，不能仅凭 RabbitMQ 配置认为所有请求都走统一 command listener。差异见 [[模块文档/Music/刷新数据库|音乐刷新数据库]]。

## 运行约束

### 文件解析

`MusicFilenameParser` 对 `菲道尔 _ DIOR大颖` 识别多歌手，对 `G_E_M_ 邓紫棋` 保留别名整体。解析规则改变必须保留对应回归测试。

### 歌单写入

添加、删除、重排需要明确 entry identity。若允许重复曲目，不能用 playlistId + trackId 作为删除目标；若不允许重复，应恢复数据库唯一约束并捕获重复键。

### 外部匹配

先匹配标题，再确认 artist relation；artist 不匹配时停止复用。歌词、封面和 metadata 的失败不应让音频文件从曲库消失。

## 设计验收

验证同名不同歌手、多个歌手文件名、歌单并发添加、进度心跳、QQ 匹配失败和刷新重投，确保曲库事实和用户数据互不覆盖。
