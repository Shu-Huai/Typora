# Music 数据表

Music 数据库最重要的事情是保持 Track、File、Artist、Album 和用户 Playlist 的边界。曲目资料可以更新，物理音频可以替换，用户歌单和进度不应因为一次曲库刷新被重写。

## 表关系

### Track File

`music_track` 是逻辑曲目，`music_file` 是物理文件。一个 Track 可以有多个格式和码率的 File；播放接口需要明确最终选择的 musicFileId。

### Artist Album

`music_artist`、`music_album` 和 music_track_artist、music_album_artist 保存多对多关系与 role_type。合作歌手、作曲者和演奏者不能压成一个 displayName。

### 外部资料

`music_source` 使用 entity_type/entity_id/source/source_id 保存 QQ Music 等来源；`music_lyric` 保存歌词格式和内容。来源失败不影响本地 Track/File。

### 用户歌单

`music_playlist` 属于 user，`music_playlist_track` 保存 Track 和 sort_order。歌单关系不应该直接引用物理文件，除非产品明确支持固定版本播放。

## 身份规则

### Track

标题不是唯一身份。标题、Artist relation、Album、track number、目录和来源共同决定归并；同名不同歌手必须能落成不同 Track。

### File

local_file_path、Track 关系、ext、duration 和媒体指纹构成 File 版本。路径覆盖新音频时，旧歌词和 source 不能自动沿用。

### Source

source_id 的唯一范围包含 source 和 entity_type。Track、Album、Artist 使用相同数字 source_id 不应互相覆盖。

### Playlist

当前表以 playlist_id、track_id、sort_order 组织关系。若要支持重复曲目，需要新增 entry identity 或调整删除语义，不能只让前端临时允许重复。

## 播放关联

### Range

MusicFile 的 ext、codec、bitrate 和 sample rate 决定 MIME、Range 和浏览器能力。数据库不保存整段音频，只保存读取所需的文件事实。

### 歌词

歌词绑定 Track 和 source/format，时间轴是否适用于当前 File 需要检查版本和时长。无时间歌词不能在数据库层标记成逐句同步。

### 进度

产品若按 Track 共享进度，切换 File 时需定义 duration 映射；若按 File 保存，user_progress key 必须包含 File 身份。两种语义不能在不同接口混用。

### 刷新

文件缺失先影响 MusicFile，不直接删除 Track、Playlist、Lyric 或用户 progress。Track 只有在没有有效 File 且策略允许时才进入清理。

## 迁移要点

### 唯一键

修改 music_source、music_file 或 playlist 关系索引前先统计现有重复数据。先清理或建立兼容唯一键，再启用数据库约束。

### Artist 解析

新增 artist role 或 alias 字段时保留原始名称和关系。历史解析反例需要重新归一化，但不能无证据合并艺人。

### Lyric 版本

歌词增加 language、offset、file fingerprint 或 source version 时使用新增列，旧歌词仍可展示为未版本化结果。

### 兼容发布

schema、ingestion、metadata sync、Music API、Playlist API 和前端 Track 类型必须一起核对。
