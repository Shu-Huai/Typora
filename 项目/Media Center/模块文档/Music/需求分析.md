# 音乐模块


音乐模块把音频文件组织成曲目、歌手和专辑，提供流式播放、歌词、进度和歌单。这里最容易出错的不是“能否读出一个 MP3”，而是身份识别：歌名相同并不代表同一首歌，文件夹中的下划线也不一定是分隔符。

## 曲库资料

### 数据模型

`MusicTrack` 是曲目，`MusicFile` 是实际音频。曲目与歌手是多对多关系，由 `MusicTrackArtist` 保存；专辑通过 `MusicAlbum` 管理，`MusicAlbumArtist` 表达专辑艺术家。歌词、外部来源、歌单和歌单曲目分别使用独立实体。

```text
MusicArtist >── MusicTrackArtist ──< MusicTrack
      |                                    |
      └── MusicAlbumArtist ──< MusicAlbum  ├──< MusicFile
                                           ├── MusicLyric
                                           ├──< MusicSource
                                           └──< MusicPlaylistTrack >── MusicPlaylist
```

这种拆分允许一首歌有多个歌手、一个歌手参与多个专辑，也允许同一曲目存在 FLAC 和 MP3 等多个文件。歌单只引用曲目，不拥有或复制原文件。

### 文件解析

配置定义音乐根目录和允许格式。扫描优先使用音频内嵌标签；标签缺失时再从目录和文件名推断。推断规则必须保守并记录原始值。

建议的优先级：

1. 内嵌 title、artist、album 和 track number。
2. 已约定的目录结构，例如 `歌手/专辑/曲目文件`。
3. 仅在分隔符语义明确时解析文件名。
4. 都无法确定时以文件名作为曲目名，歌手和专辑留空，不编造数据。

`菲道尔 _ DIOR大颖` 一类带空格的分隔符可以按规则拆分；`G_E_M_ 邓紫棋` 中的下划线是艺名的一部分。解析器不能对所有 `_` 做 split。任何规则修改都要添加反例测试，防止修复一种命名又破坏已有艺名。

### 曲目归并

禁止使用“标题相同”作为跨文件、跨外部来源的唯一合并条件。至少要同时比较规范化标题与歌手集合；如果专辑、时长或版本标签明显不同，还要保留为独立曲目。

```text
可合并候选：标题一致 + 主要歌手一致 + 版本信息不冲突
不能合并：  标题一致 + 歌手不同
需要判断：  标题一致 + 歌手一致 + Live/伴奏/Remix 不同
```

规范化可以处理大小写、首尾空格、常见标点和全半角，但不能删除会改变艺名的字符。多个歌手的顺序有时是展示差异，不应因此判成两首歌；比较时可使用集合，展示时保留原顺序和角色。

### QQ 音乐同步

单曲或批量同步通过 Spider 查询 QQ 音乐。业务服务把本地标题、歌手等条件传给 Spider，收到候选后再次执行本地身份校验，再更新来源负责的字段。

同步规则：

- 没有歌手信息时不使用标题唯一候选自动写入。
- 候选歌手与本地歌手不相符时拒绝。
- 已有本地歌词或封面时，是否覆盖由来源优先级决定。
- 外部 ID 保存到 `MusicSource`，后续同步优先按已绑定 ID 获取。
- 批量同步中一首失败不终止全部任务，最终汇总成功、跳过和失败数量。

## 音频播放

### 音频流

模块提供按 `musicFileId` 播放指定文件和按 `trackId` 选择默认文件两种入口。前者用于用户或系统已经确定版本；后者适合列表快速播放。

浏览器拖动音频依赖 HTTP Range。后端应根据 `Range: bytes=start-end` 返回 `206 Partial Content`、正确的 `Content-Range`、`Content-Length` 和音频 MIME 类型。若没有 Range，可返回完整资源，但仍使用流式读取。

```http
GET /music-file/audio/812
Range: bytes=1048576-

HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 1048576-7340031/7340032
Content-Length: 6291456
```

不能先把完整 FLAC 读成 `byte[]` 再返回。那会让并发播放直接消耗 JVM 堆，并延长首包时间。路径解析同样从数据库文件记录出发，再校验位于音乐根目录内。

### 默认文件选择

一首曲目可能关联多个文件。按 track 播放必须有稳定选择规则，例如优先无损格式、其次较高码率，再按文件 ID 兜底。规则一旦改变，时长和用户进度可能变化，因此应在详情中允许用户看到实际选择的文件。

无法播放的格式应返回明确错误。当前音乐模块是原文件流式播放，不应偷偷转码成另一个文件；如将来需要浏览器兼容转码，应单独设计缓存、MIME 和进度映射，不能照搬电影 HLS 方案而不说明原因。

### 歌词时间轴

歌词查询以曲目为入口。若存在时间标记歌词，前端根据音频 `currentTime` 高亮当前行；纯文本歌词则只展示，不伪造时间。

LRC 时间通常使用 `[mm:ss.xx]`。解析要处理多标签同一行、偏移标签、空行和无效时间。前端寻找当前歌词行时使用“最后一个时间不大于 currentTime 的条目”，而不是要求时间完全相等。

歌词来自外部同步时仍要绑定正确曲目。相同歌名不同歌手是必须保留的回归用例，否则最直观的表现就是音乐正确、歌词却来自另一首歌。

### 播放进度

进度按用户和 track 保存，接口提供查询和更新。上报内容至少包括秒数和必要的总时长，后端校验非负且不明显超出文件时长。

推荐上报时机：

- 正常播放时每隔若干秒。
- 暂停、切歌、关闭页面前。
- 用户拖动并稳定落点后。
- 播放完成时写入完成状态或归零规则。

如果默认文件发生变化且时长不同，直接恢复旧秒数可能落到错误位置。服务端可以同时保存进度比例和记录时长，在差异超出阈值时由前端提示或按比例近似恢复。

## 歌单任务

### 歌单生命周期

歌单属于用户。创建时保存名称等信息；更新与删除必须校验拥有者。删除歌单只删除歌单与关系，不删除曲目、文件、歌词和外部资料。

`MusicPlaylistTrack` 保存曲目顺序。常见操作包括：

```text
创建歌单
添加 trackId
按本地路径解析并添加曲目
移动曲目位置
从歌单移除曲目
删除歌单
```

添加路径时不能让用户传任意磁盘路径。服务端只在已配置音乐根目录和已入库文件中解析。重复曲目是否允许需要固定规则；若不允许，重复添加返回幂等成功或明确提示，不能产生两条关系。

重排可以使用目标索引或完整有序 ID 列表。无论采用哪种协议，都要在一个事务中验证所有曲目属于该歌单，再更新连续顺序，避免中途出现两个相同序号。

### 曲库刷新

管理接口触发刷新，RabbitMQ 执行，`/ws/refresh-music-status` 通知前端。刷新要维护 Track、File、Artist、Album 的关系，而不是只更新单表。

文件移动后如果能通过稳定标签和文件特征识别，应更新 `MusicFile` 路径并保留 trackId；无法可靠识别则新增文件，再清理缺失记录。移除最后一个文件后是否保留曲目，取决于它是否仍被歌单、歌词或人工资料引用，不能直接级联清空。

### 音乐总结

总结通过 `/music/summary/{trackId}` 获取，生成状态从 `/ws/music-summary-status` 返回。输入可以包含曲目、歌手、专辑、歌词与可用外部资料，但不能因歌词缺失阻止任务。

同一曲目只能有一个活跃生成任务。WebSocket 消息用 requestId 与 trackId 对应前端，失败不影响播放。已存在的总结默认直接读取，重新生成应有显式操作而不是每次打开详情自动调用模型。

### 技术依赖

- Spring Resource 与 HTTP Range：音频流。
- MyBatis-Plus、MySQL：曲目关系、歌词、歌单和进度。
- RabbitMQ、Redis/Redisson、WebSocket：刷新、总结和元数据同步状态。
- OpenFeign、Spider：QQ 音乐调用。
- Vue、Pinia：当前曲目、播放队列和跨页面播放器状态。

Pinia 中的播放队列只是客户端状态，歌单和进度的最终记录仍在后端。用户刷新页面后可恢复持久化歌单，但临时播放队列是否恢复由产品体验决定。

## 故障验收

### 身份回归用例

至少准备以下数据：

| 输入 | 预期 |
| --- | --- |
| 两首同名、不同歌手的歌曲 | 两个 Track，QQ 资料互不串写 |
| 同歌手同标题的 FLAC 与 MP3 | 按规则关联同一 Track 的两个 File |
| `菲道尔 _ DIOR大颖` | 只按约定分隔符解析 |
| `G_E_M_ 邓紫棋` | 保留艺名中的下划线 |
| Live 与录音室版本 | 不因标题规范化错误合并 |

扫描、单曲同步和批量同步都运行这些用例。只测试字符串解析函数还不够，还要验证最终数据库关系。

### 播放歌单用例

1. 播放 MP3、FLAC 等已支持文件，检查首包和 MIME。
2. 从中间字节发 Range 请求，响应范围与文件总长度正确。
3. 浏览器拖动到多个位置，不会从头重新下载或播放错误曲目。
4. 歌词随 currentTime 正确切行，暂停和拖动后恢复正确。
5. 歌单添加、去重、删除、重排后刷新页面，顺序保持。
6. 设备 A 保存进度，设备 B 恢复；用户 B 不受影响。

### 故障边界

QQ 音乐不可用时，本地曲库照常刷新和播放；LLM 不可用时只影响总结；RabbitMQ 暂时不可用时管理端应明确显示任务未被接受，不能假装刷新已经开始。

磁盘文件在播放中被移走时，本次流返回可诊断错误，并把该文件留待下次刷新确认。服务端不应因为一次读文件异常崩溃，也不应立即删除仍可能只是 NAS 短暂离线的全部曲库记录。
