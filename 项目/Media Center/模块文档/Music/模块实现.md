# 音乐实现

本文对应 `Media-Center-Music` 的当前源码。业务规则见 [[模块文档/Music/需求分析|音乐模块]]。实现重点不是播放器外观，而是文件如何变成稳定的 MusicTrack、元数据如何匹配、歌单和进度如何写库，以及刷新监听在多实例下如何运行。

## 请求入口

### 曲库查询

`MusicController` 负责曲目分页、详情、专辑/歌手信息和音频相关查询，调用 `IMusicService` 的 `MusicServiceImpl`。实体由 `MusicTrackMapper`、`MusicAlbumMapper`、`MusicArtistMapper`、`MusicFileMapper` 以及关系 mapper 组合，返回 `GetMusicTrackVO`、`MusicPageTrackVO`。

```text
GET /music/**
  → MusicController
  → MusicServiceImpl
  → track / album / artist / file mappers
  → music VO
```

曲目身份不能只用标题。`MusicTrack` 与 `MusicFile` 分离，歌手通过 `MusicTrackArtist` 关系表连接，专辑通过 `MusicAlbum` 和 album-artist 关系连接。相同标题的不同歌手必须保持不同候选，不能在匹配失败后退化为 title-only 复用。

### 歌词播放

`FileController` 委托 `IFileService` 的 `FileServiceImpl` 读取音频文件。路径来自 `musicBaseLocate`，服务必须在根目录边界内解析相对路径。歌词由 `MusicLyric` 和 `MusicLyricMapper` 读取，`MusicLyricFormat` 区分歌词格式；歌词时间不参与音频流的解码，只负责前端当前播放时间的文本匹配。

### 播放进度

`MusicProgressController` 从 `SecurityUtils` 取得用户，强制 DTO 的 media type 为 MUSIC 后调用 `MusicProgressServiceImpl.updateProgress`。当前实现按用户、媒体类型和 track id 读取 `user_progress`，再执行插入或更新。由于表结构缺少对应业务唯一键，首次并发心跳仍需要数据库约束或 upsert 改造。

### 歌单接口

`MusicPlaylistController` 处理歌单创建、修改、删除、曲目添加、移除和排序，所有 service 调用都传入当前用户 id。`MusicPlaylistServiceImpl` 每个方法先校验 playlist owner，再访问 `MusicPlaylistMapper` 和 `MusicPlaylistTrackMapper`。

歌单操作的身份是 playlist id 和 entry id/track id 的组合。当前添加曲目先查询关系再插入；`sql/alter_music_non_unique_indexes.sql` 还删除了原有关系唯一索引，因此产品必须先决定是否允许同一曲目重复出现，再决定唯一键和 API 的幂等语义。

`AdminController` 调用 `AdminServiceImpl` 处理配置和刷新。Music 有 `MusicRefreshRabbitConfig`、command/status message、`MusicRefreshRequestManager` 和 WebSocket handler。`MusicSummaryHandler`、`MusicSummaryStatusListener` 处理曲目 summary 的实时状态；刷新状态由 `MusicRefreshStatusListener` 广播。

Music 的刷新实现与其他模块并不完全相同：`MusicServiceImpl` 仍有直接执行刷新任务的路径，不能只根据 RabbitMQ 配置推断所有入口都经过统一 command wait 流程。维护代码时要同时检查 AdminService、MusicServiceImpl 和 command listener。

## 核心服务

### 文件名解析

`MusicFilenameParser` 把文件名解析为 `ParsedMusicFilename`，提取标题、歌手、专辑或编号等字段。解析规则必须保守：只把明确的带空格下划线形式识别为分隔符，不能把歌手名中的普通下划线全部切开。

已验证的回归边界包括：

```text
菲道尔 _ DIOR大颖  → 两位歌手
G_E_M_ 邓紫棋      → 作为歌手别名整体保留
```

解析器只负责从文件名得到候选，不负责证明外部匹配正确。后续由 ingestion 使用标题、歌手关系和文件身份共同选择或创建曲目。

### 曲库扫描

`MusicLibraryScanner` 枚举 `musicBaseLocate` 下的支持文件，生成 `ScannedMusicFile`；`MusicLibraryIngestionService` 再把扫描结果转成数据库实体并返回 `MusicLibraryIngestionResult`。`MusicServiceImpl` 或 AdminService 负责全量刷新编排。

```text
MusicLibraryScanner
  → ScannedMusicFile
  → MusicFilenameParser
  → MusicLibraryIngestionService
  → MusicTrack / MusicFile / Artist relation
  → MusicMetadataSyncService
```

入库时优先依据稳定文件路径和已有关系定位 `MusicFile`；创建曲目时必须匹配歌手关系。相同 title 但歌手不匹配时保持未匹配或创建独立实体，不能复用另一位歌手的 track。

### QQ 元数据同步

`MusicMetadataSyncService` 调用 Spider/QQ metadata client，使用本地解析出的 title、artist 和文件上下文进行匹配。`MusicArtistNameMatcher` 负责标点、空格和别名归一化，GEM/邓紫棋等别名在这里处理，不应在调用方散落特殊判断。

匹配流程应保留失败原因：

```text
文件候选
  → 标题归一化
  → 歌手候选归一化
  → 外部搜索
  → 标题 + 歌手关系确认
  → MATCHED / NOT_MATCHED
```

如果歌手不匹配，不能再发起不带 artist 的 title-only fallback。那会把同名歌曲写到错误的 MusicTrack。外部结果写回 `MusicSource`、歌词、专辑和歌手关系时，要以 source type/source id 作为稳定来源键。

### 歌单服务

`MusicPlaylistServiceImpl` 的创建、修改和删除都先验证用户所有权。添加曲目会检查 track 是否存在，再查 playlist-track 关系；排序通常根据现有最大 `sortOrder` 追加，重排则遍历 DTO 更新每条关系。

当前实现的并发风险：

- 两个请求同时追加，可能得到相同 sort_order。
- 两个请求同时添加同一 track，普通索引不能阻止重复关系。
- 重排逐行更新，中途异常会留下部分新顺序。
- 删除接口的“确保关系不存在”语义与“删除一个具体 entry”语义尚未完全区分。

后续若产品允许重复曲目，关系实体必须有稳定 entry id，移除和重排都操作 entry id；若不允许重复，恢复 `(playlist_id, track_id)` 唯一约束并把 DuplicateKeyException 转为可解释响应。

`MusicServiceImpl.getSummary` 使用曲目级 Redis summary lock，调用 LLM 后把摘要写回 `MusicTrack.summary`，`MusicSummaryStatusListener` 和 `MusicSummaryHandler` 推送 requestId 状态。与 Book/Movie 一样，当前摘要字段没有 prompt/model 版本，锁只解决同一资源的瞬时并发。

## 数据状态

### 领域实体

```text
MusicAlbum 1 ── * MusicTrack * ── * MusicArtist
MusicTrack 1 ── * MusicFile
MusicTrack 1 ── * MusicLyric
MusicTrack 1 ── * MusicSource
User 1 ── * MusicPlaylist 1 ── * MusicPlaylistTrack ── 1 MusicTrack
User 1 ── * user_progress  (media_type=MUSIC)
```

`MusicFile` 是实际音频路径和文件类型的载体；`MusicTrack` 是用户展示、播放、总结和外部 metadata 的逻辑曲目。不要用 MusicTrack id 直接拼 NAS 路径，也不要用文件名变化直接创建新的逻辑曲目而不检查稳定身份。

### 刷新状态

Music 使用 watcher leader、refresh request-gate、library maintenance、summary generating 等 key。`MusicLeaderCoordinator` 持有 `music:watcher:leader:lock` 时启动 `MusicFolderWatcher`，follower 不监听文件。

RabbitMQ command/status 使用 `MusicRefreshCommandMessage` 和 `MusicRefreshStatusMessage`。状态队列是实例临时队列，`MusicRefreshRequestManager` 是本 JVM future；实例重启和消息重投仍需要持久 task/inbox 才能完全恢复。

### 文件监听

`MusicFolderWatcher` 当前监听单个配置目录的 create/delete，事件直接调用 AdminService。与 Movie/Picture 的递归能力不完全相同，不能在文档中笼统写成所有模块都递归监听。目录监听只提供变更提示；全量扫描和文件指纹负责校正漏事件。

### 路径配置

`ConfigKey` 校验 `musicBaseLocate`、支持格式等配置。路径处理必须经过绝对化、normalize 和根目录 startsWith 检查。服务账号看到的映射盘可能和桌面用户不同，部署验收要使用实际运行账号检查读权限。

## 运行边界

### 入库边界

运行记录覆盖多歌手、下划线和别名、目录扫描、文件到曲目/专辑/artist relation 的写入，以及 QQ 匹配、歌手不匹配和 NOT_MATCHED 行为。

### 歌单边界

运行记录覆盖用户进度及 media type、歌单所有权/添加/移除/排序/删除，以及音频文件读取和路径边界。

### 状态边界

运行记录覆盖刷新和 watcher 事件、request-gate、leader command、状态 future和总结状态广播。

### 必须保留的规则

- `菲道尔 _ DIOR大颖` 仍解析为多歌手。
- `G_E_M_ 邓紫棋` 不被错误拆成多个 artist token。
- 同标题不同歌手不会复用错误 MusicTrack。
- 两个用户同时编辑同一歌单时，所有权校验不能串用户。
- 同一进度首次并发写入不能产生多行有效记录。
- refresh command 重投不会重复外部 metadata 同步。
