# 音乐曲目身份

Music 最容易产生“看起来能用、实际串歌”的问题。文件名、标签、外部搜索结果和数据库实体不是同一个身份来源；匹配策略必须先保护本地文件，再逐步补充艺术家、专辑和外部资料。

## 输入来源

### 文件名

`MusicFilenameParser` 从文件名和目录提取标题、艺术家、专辑、盘号、轨道号。解析结果是候选，不是最终真相。目录层级可以提供艺术家线索，但不能覆盖文件标签而不留证据。

### 标签

音频 metadata 可能包含多个 artist、feat、作曲者和发行版本。解析时保留原始字符串和清洗结果，避免只保留一个“主歌手”导致关系丢失。

### 外部来源

QQ Music 返回的 songId、albumId、artistId 和歌词是外部事实。外部匹配必须存 source type、source id、匹配输入和版本；调用失败或限流不能改变本地曲目身份。

### 文件指纹

同一路径覆盖另一首歌曲时，路径不再足够。MusicFile 应根据大小、mtime、媒体标签和必要时 hash 识别版本，旧歌词、封面和外部 source 需要重新确认。

## 匹配策略

### 标题归一化

只做有证据的归一化：空白、大小写、常见括号和已定义的合作符号。`G_E_M_ 邓紫棋` 等合法艺名不能被通用下划线规则拆成多个字段。每次规则变化都要有反例测试。

### 艺术家确认

```text
title candidate
  -> artist relation candidate
  -> album / track number check
  -> external source query
  -> confidence decision
```

相同标题但歌手不同，必须创建或关联不同 MusicTrack。禁止无艺术家条件的 title-only fallback，因为它会把同名歌的歌词、封面和播放进度串在一起。

### 版本选择

一个 Track 可以有 MP3、FLAC、M4A 等多个 MusicFile。默认播放文件需要稳定规则，例如用户明确选择优先，系统再按格式/码率/文件 ID 兜底，并把实际 musicFileId 返回给播放器。

### 不确定结果

匹配置信度不足时保留 `NOT_MATCHED` 或待确认状态，仍允许本地音频播放。宁可没有 QQ 资料，也不能把错误资料写成成功后再难以修复。

## 数据写入

### 主对象

先写 MusicTrack、MusicFile 和本地 artist relation，再写外部 source、歌词和封面。数据库唯一键保护路径和业务关系，消息重投只更新同一版本。

### 艺术家关系

多人合作要保存多个关系和角色，不能把原始合作串只存进一个 displayName。删除文件时只删除不再被任何 Track 引用的关系，避免影响其他歌曲。

### 歌词绑定

歌词以 track/file/source 组合绑定。不同版本录音可能时长不同，歌词时间轴不能只按标题复用；来源变化后重新获取并记录版本。

### 进度关联

用户进度至少指向 Track 和实际 File 的约定身份。用户切换 FLAC 到 MP3 时，是否共享进度必须由产品决定，服务端不能隐式把两个时长不同的文件混在一起。

## 回归用例

### 名称反例

```text
G_E_M_ 邓紫棋 - 光年之外.flac
菲道尔 _ DIOR大颖 - 在加纳共和国离婚.flac
同名歌曲 - 歌手 A.mp3
同名歌曲 - 歌手 B.flac
```

检查 title、artist relation、album 和 source 是否正确。

### 解析回归

`MusicFilenameParserTest` 保留带空格下划线、多人歌手、括号版本、缺专辑和大小写扩展名。`MusicLibraryIngestionServiceTest` 验证重复扫描不重复建 Track；`MusicMetadataSyncServiceTest` 验证同名不同歌手不会命中同一外部结果。

### 人工确认

对 NOT_MATCHED 项展示原始文件名、候选艺术家和外部结果，让用户明确选择。确认操作要有幂等 requestId，不能每次打开详情都重新调用 QQ Music。
