# 图书实现

本文对应 `Media-Center-Book` 模块的当前源码。业务目标、格式范围和验收口径见 [[模块文档/Book/需求分析|图书模块]]；本文只记录 Spring 入口、服务调用、数据库写入、文件监听、生成任务和测试边界。类名以 `Media-Center-Book/src/main/java` 为准，未在源码中出现的能力不写成已实现。

## 请求入口

### 书籍查询

`BookController` 负责书籍列表、详情以及书籍相关的读取接口。Controller 不直接访问 Mapper，而是调用 `IBookService`，实现类为 `BookServiceImpl`。返回对象使用 `BookVO`、`BookDTO` 等模块模型，数据库实体是 `Book`、`Author`、`Publisher` 和 `BookFile`。

典型调用链：

```text
HTTP /book/**
  → BookController
  → IBookService
  → BookServiceImpl
  → BookMapper / BookFileMapper / AuthorMapper / PublisherMapper
  → BookVO 或 BookFileDTO
```

文件读取由 `FileController` 和 `FileServiceImpl` 处理。它根据配置中的 `bookBaseLocate` 解析本地路径，再返回文件内容或流；数据库保存的是书籍与文件关系，不把 PDF、EPUB 或 TXT 本体放进 MySQL。

### 阅读进度

`ProgressController` 从当前认证用户取得 userId，把请求交给 `IProgressService` 的 `ProgressService`。进度对象使用公共 `UserProgressDTO`，模块通过 `MediaType.BOOK` 固定媒体类型，避免客户端伪造为电影或音乐进度。

当前写入逻辑是按 `userId + mediaType + mediaId` 查询 `user_progress`，查到则更新，查不到则插入。这个流程在单线程下符合预期，但数据库脚本没有对应业务唯一约束，两个实例同时首次上报仍可能产生重复行；实现文档因此把它记录为当前行为，而不是宣称已经具备集群级幂等。

### 管理入口

`AdminController` 负责配置读写和媒体库刷新。刷新请求由 `AdminServiceImpl` 接收，先通过 Redis request-gate 判断是否已有刷新，再生成 requestId、注册本实例的 `BookRefreshRequestManager` future，并发布 `BookRefreshCommandMessage`。

配置对象由 `ConfigMapper` 持久化。`ConfigKey` 对 `bookBaseLocate`、`bookFileType` 等值做校验；路径类配置在启动 watcher 或执行扫描前还会转成 `Path` 并检查目录是否存在。配置修改不是简单字符串覆盖，调用链会先停止旧监听、更新配置、再按新路径启动监听。

### WebSocket 状态

`WebSocketConfig` 注册刷新、总结和插图的 handler。`BookRefreshHandler`、`BookSummaryHandler`、`BookIllustrationHandler` 保存本实例的 WebSocket session，并向前端推送 requestId 对应的状态。

刷新状态不是由 HTTP 请求直接推送，而是由 RabbitMQ status exchange 广播到 `BookRefreshStatusListener`，listener 再完成 request future 并调用 handler。客户端断线后，当前实现没有历史消息补发；WebSocket 只作为实时通知，不能当任务最终状态存储。

## 核心服务

### 书库扫描

`AdminServiceImpl` 承担全量刷新、文件创建和文件删除的编排。全量刷新通常先停止 `BookFolderWatcher`，扫描 `bookBaseLocate`，解析书籍目录和文件，再写入书籍、作者、出版社、文件关系，最后重新启动 watcher。

`BookFolderWatcher` 使用 JDK `WatchService` 监听目录创建与删除。它不是持久事件队列，事件只在当前 JVM 中存在；Leader 竞争由 `BookLeaderCoordinator` 完成，只有持有 `book:watcher:leader:lock` 的实例才启动 watcher。扫描和 watcher 共享维护锁，防止同一文件被全量扫描和实时事件同时处理。

### 书目入库

`BookServiceImpl` 负责书籍查询、总结和插图等书籍级业务；`FileServiceImpl` 负责文件类型、路径和文件内容读取。文件解析先依据 `BookFileType` 判断 PDF、EPUB、TXT，再把稳定路径写入 `BookFile`。

处理新增文件时，`AdminServiceImpl.handleFileCreate(File)` 先确认扩展名和文件存在，再调用书籍服务或文件服务完成入库。删除时通过相对路径查找 `BookFile` 并标记或删除对应关系。当前代码的最终重复防线仍依赖数据库现有索引和服务层查询，新增文件事件必须能够重复执行。

### 总结生成

书籍总结由 `BookServiceImpl` 调用 LLM Feign 客户端。生成前使用 `RedisKeys.bookSummaryGenerating(bookId)` 获取书籍级 RLock，锁内再次查询 `Book.summary`：已有结果则直接返回，未生成才调用模型并写回数据库。

```text
BookController.summary
  → BookServiceImpl.generateSummary(bookId)
  → RLock(book:summary:generating:<bookId>)
  → 查询已有 summary
  → LLM client
  → 更新 book.summary
  → 释放锁
```

当前摘要结果直接保存在 `book.summary`，没有 prompt/model 版本字段；模型版本变化时不能自动区分旧结果。锁能限制并发，不等于跨版本幂等，版本化摘要属于后续改造项。

### 插图生成

`BookServiceImpl.generateIllustration(bookId, requestId, description)` 组合书名、用户描述和默认提示词，调用 LLM 图像生成服务，再把 URL 写入 `BookIllustration`。当前使用 `book:illustration:generating:user:<userId>` 控制用户级并发，状态 listener 通过 requestId 推送 WebSocket。

用户锁解决的是单用户同时占用模型资源，不是同一本书、同一描述的资源级幂等。两个用户可以同时生成相同意图，表结构也没有输入哈希和模型版本；重复生成是否应该复用必须由后续任务表和业务键决定。

## 数据状态

### 领域实体

主要实体关系如下：

```text
Author 1 ── * Book * ── 1 Publisher
Book   1 ── * BookFile
Book   1 ── * BookIllustration
User   1 ── * user_progress  (media_type=BOOK)
```

`Book` 保存书名、作者、出版社、封面和 summary；`BookFile` 保存文件路径、文件类型及书籍关联；`BookIllustration` 保存生成描述与对象 URL。大文件位于配置目录，数据库只保存索引和派生结果引用。

### 刷新消息

刷新消息由 `BookRefreshRabbitConfig` 声明 command exchange、durable queue 和 status exchange。`BookRefreshCommandMessage` 至少携带 requestId；leader 实例的 `BookRefreshCommandListener` 调用 AdminService 执行扫描，然后发布 `BookRefreshStatusMessage`。

非 leader 收到 command 时会重新投递或等待 leader，具体 listener 行为以 `BookRefreshCommandListener` 为准。status fanout 为每个实例创建独立临时队列，因此发起请求的实例可以收到其他实例执行的终态，但 request future 仍是本地内存结构。

### Redis 状态

Book 当前使用的 Redis key 包括：

```text
book:summary:generating:<bookId>
book:illustration:generating:user:<userId>
book:refresh-database:lock
book:refresh-database:request-gate
book:watcher:leader:lock
```

锁释放放在 finally，leader 使用 watchdog，生成和刷新使用短时互斥。Redis 清空会丢失 request gate、锁和 session 类短状态，但不应删除 MySQL 中的书籍、文件和用户进度。

### 失败处理

模型调用失败时，服务应释放生成锁并通过 status listener 推送失败；不能把空 URL 写成成功结果。刷新过程中 watcher 重启失败时，测试已经覆盖“扫描成功但 watcher 重启失败”的状态边界：扫描结果仍要按实际结果报告，watcher 失败必须进入日志和运维处理。

当前刷新等待依赖 requestId future。实例在发布 command 后重启，future 会消失；RabbitMQ 可能重投 command。持久化 operation task、inbox/outbox 和结果引用是解决该问题的方向，当前模块尚未具备。

## 运行边界

### 接口边界

运行记录覆盖 HTTP 参数到 service 的委托、书籍查询、总结锁、插图提示词构造和 WebSocket 状态消息路由。

### 刷新边界

运行记录覆盖 request-gate 拒绝重复刷新、扫描、配置变更、文件创建/删除和 watcher 生命周期。文件检查使用临时目录，不依赖机器上的固定映射盘。

### 集群运行

两个 JVM 竞争同一 Redis 锁时，集群验收至少包括：

- 两个 Book 实例同时启动，只有一个日志显示 watcher started。
- leader 强制退出后，另一个实例取得锁并重建 watcher。
- WatchService `OVERFLOW` 后触发目录校正，而不是静默忽略。
- 两个实例同时首次写同一用户书籍进度，数据库只有一个业务事实。
- LLM 超时后 HTTP 重试不重复产生同一业务键的插图任务。
