# 幂等规则

幂等不是“接口返回成功就算完成”，而是同一个业务意图被重复提交、消息被重复投递、客户端超时重试或两个实例同时执行时，最终只产生一次应有的业务效果。Media Center 既有进度更新、歌单编辑这种短事务，也有媒体库刷新、AI 生成、转码和对象存储写入这种跨系统长任务，不能用同一种锁笼统处理。

本文把当前代码、数据库脚本和消息链路放在一起检查。表格中的“已有保护”表示源码已经存在；“缺口”表示仅凭当前实现仍可能产生重复、覆盖或半完成状态；“目标做法”是后续实现要求，不能当作已经上线的能力。

## 幂等模型

### 先定义业务意图

判断两次调用是不是“同一件事”，不能只看 URL。应先为操作选择稳定的业务键：

| 操作 | 推荐业务键 | 重复调用期望 |
| --- | --- | --- |
| 保存播放进度 | `userId + mediaType + mediaId` | 更新同一行，较新的有效进度生效 |
| 歌单添加曲目 | `playlistId + trackId` | 曲目最多出现一次；若允许重复，必须另加 entryId |
| 生成影片摘要 | `movieId + promptVersion + modelVersion` | 已有同版本结果时直接返回 |
| 图片风格化 | `pictureFileId + style + modelVersion` | 返回同一结果或明确创建新版本 |
| 全量刷新媒体库 | `module + refreshScope + generation` | 同一时段只执行一个任务，重复请求订阅同一结果 |
| 准备播放分片 | `fileId + variant + streamSelection + segmentIndex + planVersion` | 只生成一份可发布的完整分片 |
| 上传对象 | `namespace + logicalObjectId + contentHash` | 同内容得到同一对象，或返回既有对象 |

`requestId` 与业务键不是一回事。前端每次点击都可以产生新 requestId，它适合串联日志、WebSocket 状态和 HTTP 等待者；业务键才负责识别“这是不是同一个效果”。如果客户端超时后重新生成 requestId，系统仍要靠业务键或持久化任务记录避免重复执行。

需要明确区分三类语义：

- **自然幂等**：把资源设置成目标状态，例如把名称设置为“旅行照片”。执行两次结果相同。
- **条件幂等**：带版本或前置条件更新，例如“只有 version=7 才写入 version=8”。重复请求只有一次成功。
- **非幂等动作**：追加一条记录、扣减配额、调用一次计费模型。必须额外提供幂等键与结果存储。

### 四层防线各管什么

可靠写操作通常不是“加一个 Redis 锁”，而是多层共同收口：

```text
请求/消息
  │
  ├─ 请求层：校验 idempotencyKey，复用已完成结果
  │
  ├─ 协调层：Redisson 控制同一业务键的并发执行
  │
  ├─ 数据层：唯一约束、事务、条件更新决定最终真相
  │
  └─ 副作用层：outbox、对象确定性命名、补偿任务保证跨系统收敛
```

各层不能互相替代：

- Redis 锁会过期、失联或在进程暂停期间发生所有权变化，因此数据库仍需要唯一约束。
- 数据库唯一约束能阻止重复行，却不能阻止两次昂贵的 AI 调用或两次 FFmpeg 任务。
- HTTP requestId 能关联一次请求，却不能处理 RabbitMQ ack 丢失后的重投递。
- `@Transactional` 只覆盖同一数据库事务，不能回滚已经上传到 MinIO 的对象或已经调用的外部模型。

### 任务标识

长任务应有持久化任务表，而不是只把 `CompletableFuture` 放在当前 JVM：

```sql
create table operation_task (
    id                bigint primary key auto_increment,
    idempotency_key   varchar(255) not null,
    request_id        varchar(64) not null,
    operation_type    varchar(64) not null,
    status            varchar(24) not null,
    owner_instance    varchar(128) null,
    result_reference  varchar(1024) null,
    error_code        varchar(64) null,
    version           bigint not null default 0,
    create_time       timestamp not null,
    update_time       timestamp not null,
    unique key uk_operation_task_key (operation_type, idempotency_key)
);
```

接收请求时按以下规则处理：

1. 用 `operationType + idempotencyKey` 查询任务。
2. 已 `SUCCEEDED`：直接返回保存的结果引用，不重新调用外部系统。
3. 为 `RUNNING`：把新 requestId 关联到既有任务，返回“处理中”。
4. 为可重试的 `FAILED`：通过版本条件把任务转为 `RUNNING`，只有一个实例获得执行权。
5. 不存在：插入任务；并发插入由唯一约束决出唯一任务。

当前刷新流程生成 UUID requestId，并用本机 `RefreshRequestManager` 保存等待中的 future；状态通过 fanout exchange 广播到所有实例。这能让原实例收到终态，但实例重启后 future 和请求关联会消失，也没有一份可查询的历史终态。任务表是为了解决这个恢复问题，而不是为了替代 RabbitMQ。

### 响应语义也要稳定

幂等不要求每次 HTTP 状态码完全相同，但业务结果必须可理解。建议统一：

| 场景 | 响应 |
| --- | --- |
| 首次创建成功 | `201`，返回资源 ID |
| 重复创建且业务键相同 | `200`，返回同一资源与 `replayed=true` |
| 同一幂等键却参数摘要不同 | `409 IDEMPOTENCY_KEY_CONFLICT` |
| 任务正在执行 | `202`，返回 taskId、状态查询地址 |
| 条件更新版本落后 | `409 VERSION_CONFLICT`，返回当前版本 |
| 删除不存在的目标 | 对“确保删除”语义返回成功；对“删除指定现存版本”返回 `404/409` |

不能把数据库重复键异常原样抛给用户。服务应在捕获唯一约束冲突后查询既有结果，判断是可复用的重复请求，还是业务参数冲突。

## 常见写入模式

### 写入动作

**创建**最容易被重试放大。正确顺序是“业务键查询只是优化，唯一约束才是裁判”：

```java
try {
    return repository.insert(newEntity);
} catch (DuplicateKeyException duplicate) {
    return repository.findByBusinessKey(key)
        .filter(existing -> samePayload(existing, command))
        .orElseThrow(() -> new IdempotencyConflictException(key));
}
```

只写 `selectOne()` 再 `insert()` 存在经典竞态：实例 A、B 同时查不到，随后都插入。当前 `user_progress` 没有 `(user_id, media_type, media_id)` 唯一约束；进度服务采用先查再增改，因此并发心跳可能生成重复行。它需要唯一索引加 upsert 或条件更新。

**更新**要先决定冲突策略：

- 配置修改通常可采用最后写入者生效，但应记录更新时间和操作者。
- 用户进度不能简单比较服务器到达顺序。并行设备上报时应携带 `playbackSessionId`、媒体时间和客户端事件序号；服务拒绝同 session 的旧序号。
- 歌单重排是一个整体命令，需要事务和 playlist version。逐行更新时中途失败会形成两个相同 sortOrder 或部分新顺序。
- 元数据同步适合“来源版本/文件修改时间较新才覆盖”，避免迟到的旧任务覆盖新扫描结果。

**删除**先明确 API 是命令还是事件：

```text
DELETE /playlists/12/tracks/20
含义：确保关系不存在 → 重复调用可返回成功

POST /playlists/12/remove-entry
含义：移除 entryId=880 的一次具体条目 → 第二次应报告条目已不存在
```

文件删除还要处理数据库与磁盘跨系统一致性。推荐先将数据库状态改为 `DELETING`，提交后执行文件操作，再标记 `DELETED`；失败由恢复任务重试。不能在长事务里持有数据库锁等待 NAS。

### 数据库约束

基于当前建表脚本，可确认的保护并不均匀：Series 已有季、集、文件路径、来源和关系表的多个唯一约束；Picture embedding 已有文件唯一约束和 collection/point 唯一约束。另一方面，下列表只有普通索引或没有业务唯一键：

```sql
-- 当前缺少的关键约束示意，落库前必须先清理存量重复数据
alter table user
    add constraint uk_user_name unique (user_name);

alter table user_progress
    add constraint uk_user_media_progress
        unique (user_id, media_type, media_id);

alter table music_playlist_track
    add constraint uk_playlist_track
        unique (playlist_id, track_id);

alter table picture_illustration
    add constraint uk_picture_style_version
        unique (picture_file_id, style, model_version);
```

最后两项要先确认产品语义：如果歌单允许同一曲目出现多次，就不能建 `(playlist_id, track_id)` 唯一键，而应让客户端创建稳定 `entryId`；如果图片允许同风格生成多个版本，唯一键应包含用户明确提供的 generationId，而不是阻止版本历史。

事务边界应包住一个数据库事实的全部写入：

- 新建剧集、分集、文件和关系可分阶段提交，但同一个阶段不能只写一半。
- 歌单重排应验证全部 track entry 属于目标歌单，再在一个事务内更新，并在 playlist 行上做版本条件。
- 刷新扫描不能用覆盖十万文件的单个长事务；可以写入 refresh generation，分批落库，最后一次原子切换当前 generation。
- AI 结果入库和对象上传跨越数据库与 MinIO，应使用 `PENDING → READY/FAILED` 状态，而不是幻想数据库事务能够回滚对象存储。

### 后台任务

RabbitMQ 的可靠消费应按“至少一次”设计。消费者执行成功但 ack 未送达时，消息可能重投；即使配置 `default-requeue-rejected=false`，连接中断或实例终止仍可能造成重新交付。

刷新消息建议包含：

```json
{
  "messageId": "f5b90a70-...",
  "requestId": "e2cb9f51-...",
  "operation": "MOVIE_LIBRARY_REFRESH",
  "scope": "default-library",
  "requestedBy": 7,
  "createdAt": "2026-08-13T12:30:00+08:00",
  "payloadHash": "sha256:..."
}
```

消费者先向 inbox 表插入 `consumer + messageId`。唯一键冲突说明消息已被接收；若对应任务已经成功，直接 ack。任务完成和业务数据库写入在同一事务时，inbox 状态也在该事务内变更。状态消息由 outbox 表发布，避免“数据库已成功但状态消息没发出”。

定时任务分成两类：

- **单领导者任务**：目录监听、缓存清理。Redisson leader lock 保证大部分时间只有一个执行者，但每个动作本身仍要可重试。
- **分片任务**：为大量记录补嵌入、生成缩略图。按稳定资源键分片，每条记录条件更新，多个实例可以并行认领。

当前目录监听协调器会让非 leader 停止监听，命令监听器在非 leader 收到消息时会重新发布。这能跨过短暂选主窗口，但如果 leader 长时间不可用，可能形成反复发布。更稳定的方式是让所有消费者正常取消息，仅由任务表的条件认领决定唯一执行者；或者使用单活队列并配置明确的重试/死信策略。

### 外部副作用

外部 AI、Spider、MinIO、NAS 和 FFmpeg 都在数据库事务之外，需要为每种副作用定义“如何识别已经做过”：

| 副作用 | 幂等办法 | 失败恢复 |
| --- | --- | --- |
| 调用文本摘要模型 | 业务键含资源、prompt/model 版本；保存输入哈希和结果 | 已有 READY 结果直接复用；超时任务可人工/自动重试 |
| 调用图像生成模型 | 先创建 generation 记录，使用 generationId 调用 | 查询供应商任务或按 generationId 恢复，避免再次计费 |
| 上传 MinIO | 确定性 object key，写入 content hash | HEAD 校验同内容；临时对象完成后原子发布逻辑引用 |
| 移动 NAS 文件 | 保存 source/target 和操作状态 | 同时检查源与目标；目标正确即视为已完成 |
| FFmpeg 生成分片 | 写临时目录，校验后 rename 到最终目录 | 最终文件存在且校验通过时复用；残缺临时目录可清理 |
| Qdrant upsert | pointId 由 pictureFileId 稳定派生 | 重试 upsert；MySQL 记录 collection、pointId 和状态 |

FFmpeg 不能直接把最终文件作为持续写入目标。另一个请求看到文件存在时，文件可能还没写完。正确发布过程为：

```text
获取 segment 业务锁
  → 再次检查最终目录和完成标记
  → 写 session/tmp/<taskId>
  → ffprobe 校验时长、轨道和时间戳
  → 原子移动到 global/<segmentKey>
  → 写完成状态
  → 释放锁
```

## 模块操作矩阵

### Book Picture

| 操作 | 当前已有保护 | 当前缺口 | 目标做法 |
| --- | --- | --- | --- |
| Book 保存阅读进度 | 按用户和媒体查询后增改 | `user_progress` 无业务唯一键，并发可能重复；旧事件可能覆盖新事件 | 唯一键；upsert；同 session 事件序号 |
| Book 生成摘要 | `bookId` 级 Redisson 锁；锁内再次检查已保存摘要 | 模型/prompt 变更没有版本化；锁失效后仍靠单行字段 | 摘要结果表；资源+版本唯一键；READY 结果复用 |
| Book 生成插图 | 用户级生成锁，限制同一用户并发；requestId 关联通知 | 不是 book+描述级幂等；重复请求会生成新图；多用户可同时生成同一意图 | generation 任务表；输入哈希；明确“新版本”或“复用”语义 |
| Book 刷新 | request-gate、执行锁、leader lock、RabbitMQ 状态广播 | request future 只在 JVM；消息去重和终态未持久化 | task/inbox/outbox；按 refresh scope 唯一认领 |
| Picture 新建目录 | 路径检查和文件系统结果提供部分保护 | 表只有普通路径索引；并发同名目录可能竞态 | 父目录+名称或 relative_path 唯一键；以最终路径状态收敛 |
| Picture 移动/重命名 | 服务校验根目录边界 | DB 与文件系统可能半完成；重复调用的源路径可能已不存在 | 操作状态；目标状态检测；补偿扫描 |
| Picture 生成缩略图 | 缓存命中可复用 | 同资源并发生成和半文件发布需确认 | 文件版本业务键；临时文件+原子 rename |
| Picture 生成风格图 | 先查 `fileId+style`；用户级锁；已有结果直接返回 | 两个用户仍可穿透；表无对应唯一键；模型版本未入键 | 资源+style+modelVersion 锁和唯一键；重复键后回查 |
| Picture 嵌入/Qdrant | embedding index 对 fileId、collection+point 有唯一约束；Qdrant upsert 可重试 | 文件变化与模型变化时的版本切换需受控 | 记录内容哈希和模型版本；条件更新索引状态 |
| Picture 刷新 | maintenance/request-gate/leader locks | 与其他刷新模块相同，状态只在内存等待 | 持久任务、消息去重、generation 切换 |

Book 插图“用户锁”和 Picture 风格图“用户锁”的职责主要是限制单用户同时占用昂贵模型，它们不是严格的资源幂等锁。若要同时满足配额和幂等，应保留用户并发控制，再增加资源业务键约束，二者职责不能混成一个 key。

### Movie Series

| 操作 | 当前已有保护 | 当前缺口 | 目标做法 |
| --- | --- | --- | --- |
| 元数据/文件库刷新 | request-gate、refresh lock、watcher leader、命令与状态消息 | 无持久 inbox/task；实例重启后原请求等待关系丢失 | scope 任务唯一键；持久状态；重复消息直接复用终态 |
| 摘要生成 | 资源 ID 级锁并在锁内检查已有 summary | 单字段不能区分 prompt/model 版本 | 版本化摘要表及唯一业务键 |
| 创建播放 session | 用户级锁；active session 和 session 写入 Redis TTL | Redis 丢失后会话消失；不同实例本地资源是否可读仍受部署影响 | session 明确为可丢短状态；客户端可重建；共享路径检查 |
| 准备 fMP4 分片 | final 目录检查、window status `setIfAbsent`、分布式 window lock、本机 in-flight 合并 | 本机 in-flight 不能跨实例；本地缓存若不共享，状态与文件可能分离 | 以全业务键锁定；共享缓存或实例粘性；完成标记与 ffprobe 校验 |
| 提取字幕 | 分布式 subtitle lock；已有文件复用 | 固定租约可能短于异常大文件；半文件可见性需控制 | watchdog 或合理超时；临时文件原子发布 |
| SOURCE 预转码 | Redis active job/job 状态和资源锁 | 进程死亡后的任务状态与临时目录需要恢复 | task lease、心跳、可认领失败任务、残留扫描 |
| 缓存清理 | cache-cleanup leader lock；清理时检查状态/锁 | 本地缓存下只清本机；共享盘下需避免删除正在被其他实例读取的文件 | access lease/最后访问记录；两阶段过期；共享盘全局清理 |
| 播放进度心跳 | 按用户资源查询更新 | 同 `user_progress` 缺少唯一键；多个设备乱序覆盖 | 唯一键；session 序号或客户端时间；合理防倒退策略 |

Movie 与 Series 的播放幂等键不能只写 `segmentIndex`。同一文件切换 SOURCE/HIGH1080/LOW1080、音轨、分段计划版本或编码配置时，编号相同不代表内容相同。完整键至少包含：

```text
<module>:<fileId>:<fileFingerprint>:<variant>:<audioTrack>:<planVersion>:<segmentIndex>
```

当源文件大小、修改时间或关键帧计划变化时，生成新的 fileFingerprint/planVersion，不覆盖旧缓存正在服务的文件；旧版本由 TTL 清理。

| --- | --- | --- | --- |

| 删除歌单 | owner 校验，删除后目标消失 | 第二次可能返回“歌单不存在”，与“确保删除”语义不一致 | DELETE 采用目标状态语义；关系清理由事务/外键保证 |
| 添加曲目 | 先查询关系再插入 | 建表脚本明确将原唯一索引改成普通索引；并发可重复；产品是否允许重复不清楚 | 若不允许重复则恢复唯一键；若允许则用稳定 entryId |
| 调整顺序 | 按最大 sortOrder 追加；重排逐条更新 | 并发追加可得到相同序号；中途失败部分重排 | 歌单级锁只降冲突；事务+version 才保证整体顺序 |
| 摘要/歌词/元数据同步 | 资源锁或按来源更新提供部分收敛 | 外部结果版本、迟到任务覆盖需要约束 | source version/input hash；条件更新；持久任务 |

`sql/alter_music_non_unique_indexes.sql` 主动删除了 `uk_music_playlist_track`，说明不能擅自把“同一曲目只能出现一次”写成既定需求。文档和实现必须先确认歌单是否允许重复曲目。如果允许，删除和排序 API 必须操作 playlist entry ID，而不是只使用 trackId，否则无法准确选择第几个重复项。

### Auth OSS LLM Spider

| 模块/操作 | 当前已有保护 | 当前缺口 | 目标做法 |
| --- | --- | --- | --- |
| Auth 注册 | 先按用户名查询 | user_name 无唯一约束；两个实例可同时注册相同用户名 | 数据库唯一键；重复键转业务冲突；密码哈希只保存一次 |
| Auth 登录 | 读校验并签发 JWT | 重复登录本来可产生多个 token，不应误判为重复写 | 明确多 token/单会话策略；需要撤销时引入 session/jti |
| OSS 上传 | 对象存储 PUT 本身可覆盖同 key | 若 key 每次随机生成，超时重试会产生孤儿对象 | 客户端/业务生成稳定 uploadId；content hash；记录对象状态 |
| OSS 删除 | 删除不存在对象通常可收敛 | DB 引用与对象删除可能不同步 | 先标记待删，重复删除安全，完成后清引用 |
| LLM 文本调用 | 服务通常无业务落库 | 重复调用会重复计费且结果可能不同 | 幂等责任放在调用业务模块；generationId/inputHash |
| LLM 图像调用 | requestId 可用于跟踪 | requestId 变化就无法识别同一生成意图 | 上游持久 generation；供应商若支持则透传幂等键 |
| Spider 元数据查询 | GET/查询可重复 | 外部数据会变化；重试结果不保证字节一致 | 缓存来源版本和抓取时间；写库使用来源业务键 upsert |
| Feign 内部调用 | 超时可配置 | 框架级自动重试若用于 POST 会扩大副作用 | 只自动重试明确幂等调用；非幂等调用必须带业务键 |

## 改造顺序

### 先修数据库最终约束

第一批应处理“两个实例同时写就会产生错误事实”的表：

1. 统计 `user.user_name`、`user_progress`、Picture 路径/插图等潜在重复。
2. 明确歌单重复曲目与 AI 多版本的产品语义。
3. 清理或合并已有重复数据，并保存迁移审计结果。
4. 增加唯一约束，再把服务改为 upsert/捕获重复键回查。
5. 为整体编辑增加 version 字段和条件更新测试。

迁移前查询示例：

```sql
select user_name, count(*)
from user
group by user_name
having count(*) > 1;

select user_id, media_type, media_id, count(*)
from user_progress
where is_active = 1
group by user_id, media_type, media_id
having count(*) > 1;
```

不能先建唯一索引再观察生产报错；要先定义重复记录的合并规则，例如进度选择最新 update_time 的记录，而不是简单保留最大主键。

### 持久任务

第二批统一 Book、Movie、Series、Music、Picture 的刷新骨架：

- 一张公共 operation_task 表，或每模块同结构任务表。
- inbox 保存消费过的 messageId；outbox 保存待发状态事件。
- requestId 只做一次请求关联，taskId/idempotencyKey 标识业务任务。
- WebSocket 断线后，前端用 taskId 主动查询，不依赖错过的广播。
- leader 切换时新实例认领租约过期的 RUNNING 任务，而不是创建第二个任务。

这一步完成后，才能把“RabbitMQ 重投”“发起实例重启”“状态监听断开”纳入可重复测试。

### 最后治理跨系统副作用

第三批聚焦成本高、恢复难的动作：AI 调用、MinIO 对象、NAS 写操作、Qdrant 和 FFmpeg。每个动作建立状态机和扫描恢复器：

```text
PENDING → RUNNING → READY
              └──→ RETRYABLE_FAILED → RUNNING
              └──→ FINAL_FAILED
```

状态更新必须带 version 或 owner token。任务 A 的租约过期后任务 B 接管，A 即使迟到完成，也不能用旧 token 把 B 的状态覆盖为 READY；这就是需要 fencing token/版本条件的地方。

### 完成标准

不能用“加了 Redisson”作为验收。每个操作至少回答下面的问题：

- 重复的业务键是什么，参数不同如何报冲突？
- 最终真相存在哪里，是否有数据库约束？
- 进程在副作用前、后、ack 前分别崩溃会怎样？
- Redis 清空、RabbitMQ 重投、两个实例同时执行时是否仍收敛？
- 用户如何查询既有任务和结果，WebSocket 消息错过后如何恢复？
- 临时文件、孤儿对象和长时间 RUNNING 记录由谁清理？

只有并发测试、重投测试和故障注入都证明结果唯一，才能把矩阵中的“目标做法”改成“已有保护”。具体演练步骤见 [[总体实现/分布式能力/故障演练|故障演练]]。
