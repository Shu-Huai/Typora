# 分布式锁模型

分布式锁的目的不是让代码“显得支持集群”，而是为一个明确的冲突资源建立排他访问。锁 key、持有范围、等待策略、租约和失败行为必须与业务操作对应。

## 锁的职责

### 锁的作用域

`ReentrantLock` 只能协调同一 JVM 中的线程，`RLock` 通过 Redis 协调多个 JVM。部分刷新链路同时使用两者：

```text
refreshMutex.lock()       本实例公平排队，避免本地线程交错
  → RLock.tryLock()       集群内只允许一个实例写库
  → 扫描和数据库同步
  → RLock.unlock()
refreshMutex.unlock()
```

双层锁不是天然必要。若分布式锁采用立即失败，外层本地公平锁只会串行化当前实例的请求；它可以减少 Redis 竞争和保护 watcher 回调，但也可能延长本地等待。每处保留前都要说明本地资源是什么。

`ConcurrentHashMap`、`CompletableFuture` 和进程内 registry 属于 single-flight/状态合并，不是分布式锁。它们适合降低同一实例重复工作，但跨实例必须另有 Redis、数据库或共享文件机制。

### 请求准入

三种锁不能混为一个：

| 类型 | key 示例 | 获取者 | 释放时机 | 重复时行为 |
| --- | --- | --- | --- | --- |
| 请求准入 | `book:refresh-database:request-gate` | HTTP 请求实例 | 收到终态或请求结束 | 返回 updating，不入队 |
| 执行互斥 | `movie:refresh-database:lock` | 实际任务执行者 | 扫描/同步完成 | DUPLICATE/失败终态 |
| Leader | `music:watcher:leader:lock` | 协调线程 | 实例关闭或失去所有权 | 其他实例不启动 watcher/listener |

准入锁改善用户行为，执行锁保护数据。即使准入代码有 bug、MQ 重投或旧请求超时，执行锁仍需存在。Leader 决定谁消费，不应代替执行锁，因为领导权切换可能和任务边界交错。

### 资源生成锁

总结锁按 bookId/movieId/seriesId/trackId，符合“同一内容只有一个总结”的业务键。获得锁后必须 double-check 已持久化结果，原因是等待期间其他实例可能已经完成。

Book/Picture 插图当前主要按 userId 加锁。这只限制“每个用户同时生成一个”，并不严格保证“同一资源和参数只有一份”：两个用户可同时为同一本书同一描述生成；同一用户换 requestId 也可能在第一次完成后重复生成。目标幂等键应包含资源和生成参数哈希，并另设用户并发配额。

```text
并发限制 key：illustration:quota:user:<userId>
业务去重 key：illustration:generate:<resourceId>:<parameterHash>
```

Picture 已在加锁前查询 `fileId + style` 的结果，但查询与插入之间如果锁不是同一业务键，跨用户仍有竞态；数据库唯一约束是最终兜底。

### 播放锁

Movie/Series 当前 key 分为：

- `playback:user:lock:<userId>`：串行化用户会话修改。
- `playback:window:lock:<fileId>:<variant>:<start>`：保护窗口生成。
- `playback:window:status:...`：Redis bucket 记录 IN_PROGRESS/READY/FAILED。
- `playback:subtitle:lock:<fileId>:<trackId>`：保护字幕提取。
- `playback:source:pretranscode:lock:<fileId>`：保护 SOURCE 预转码 job 创建。
- `playback:cache:cleanup:leader:lock`：每次只运行一个共享缓存清理器。

窗口认领还使用 `RBucket.setIfAbsent(IN_PROGRESS, TTL)`。它是原子状态声明，能让未获得实际生成权的请求快速返回 PREPARING。最终仍以完成文件存在且校验通过为 READY。

## Redisson 使用规则

### 锁键设计

统一结构为：

```text
<module>:<domain>:<operation>:<scope...>[:lock|status]
movie:playback:window:lock:<fileId>:<variant>:<windowStart>
picture:library-maintenance:lock
```

key 中的 scope 必须等于冲突范围。太粗会阻塞无关任务，太细会让冲突操作同时运行。文件派生任务建议包含 fileVersion/fingerprint；仅 fileId 无法区分原路径内容被替换的情况。

锁 key 和状态 key 分开。不能用 `isLocked()` 代替任务状态：锁释放可能表示成功、失败或实例死亡。状态记录给调用方解释结果，锁只表达当前互斥所有权。

### 等待策略

项目中存在几种用法：

```java
lock.tryLock();                    // 立即竞争，不等待
lock.tryLock(1, TimeUnit.SECONDS); // 最多等待 1 秒，watchdog 续期
lock.lock();                       // 阻塞等待，watchdog 续期
lock.tryLock(0, 2, MINUTES);       // 不等待，固定 2 分钟租约
```

用户重复操作和后台任务准入适合立即失败。短临界区如用户 session 更新可以等待约 1 秒。阻塞 `lock()` 只适用于确定最终应排队的内部维护操作，并需要线程中断和服务关闭策略。

固定 lease 适合有明确上限、超时后允许接管的短任务；任务可能超过 lease 时，锁提前释放会产生两个写者。长转码使用不指定 lease 的 watchdog 模式更合理，但进程暂停、网络分区仍需结果版本校验。

### 锁租约

Redisson 不指定 lease time 时，持锁客户端定期续期。只要 JVM 和 Redis 连接正常，长任务不会因固定 30 秒过期。实例崩溃后停止续期，锁最终释放。

Leader 使用 `tryLock(0, -1, MILLISECONDS)` 明确启用 watchdog。长转码窗口也使用 watchdog。字幕锁使用固定两分钟，意味着提取必须在租约内完成；若大文件可能超过，应改 watchdog 或把输出发布设计成可并发验证。

所有解锁采用：

```java
if (locked && lock.isHeldByCurrentThread()) {
    lock.unlock();
}
```

`isLocked()` 只能说明某线程持有，不能证明当前线程有权解锁。误用会抛 `IllegalMonitorStateException` 或破坏别人的任务。

### Redis 状态对象

`RBucket` 适合保存小型 session、job 和窗口状态。每个临时 key 都需要 TTL：

- session TTL 随 heartbeat 刷新。
- IN_PROGRESS 不能永久存在，实例死亡后允许接管。
- FAILED 保留较短时间，避免播放器重试风暴。
- READY 的 TTL 与缓存文件 TTL 对齐。
- active job 与 job detail 的生命周期相互校验。

写多个 bucket 不是事务。例如保存 session 后再更新 active session，进程可能在中间崩溃。读取时应处理孤立 session/active 指针；若必须原子，可用 Lua、Redisson transaction 或把两个字段合成一个结构。

## 当前锁模型

### 媒体库锁

| 模块 | 请求 gate | 实际维护锁 | watcher leader |
| --- | --- | --- | --- |
| Book | refresh request gate | refresh database lock | watcher leader lock |
| Movie | refresh request gate | refresh database lock | watcher leader lock |
| Series | refresh request gate | refresh database lock | watcher leader lock |
| Music | refresh request gate | library maintenance lock | watcher leader lock |
| Picture | refresh request gate | library maintenance lock | watcher leader lock |

Music/Picture 使用 maintenance lock 是因为除全量刷新外，还有元数据同步或文件结构变更会修改同一库。Movie/Series 的豆瓣同步复用 refresh database lock，达到类似效果。Book 的新增、更新、删除与 watcher 回调是否全部进入同一分布式维护锁，需要继续审计；仅 `refreshMutex` 无法防止跨实例管理操作冲突。

### 生成任务锁

Book/Movie/Series/Music 总结采用资源锁 + 持久结果 double-check，基本符合幂等生成。结果不存在且未获得锁时返回 GENERATING，不把竞争当错误。

外部元数据同步采用模块级维护锁，确保它不与全量刷新同时改关系表。单资源同步也被全库锁串行化，正确但粒度较粗；未来可拆成文件结构维护锁和 `<source>:<resourceId>` 同步锁，同时依赖数据库唯一约束。

插图/重绘当前以用户并发锁为主。它解决配额，不完全解决相同业务请求去重，详见操作矩阵。

### 播放缓存锁

播放 session 锁的临界区应只包含 Redis/MySQL 状态更新，不在锁内等待 FFmpeg。窗口生成先原子声明状态，再异步执行；读取请求短暂等待或重试。

segment plan resolver 和 lazy coordinator 的本地 Map 需要防内存泄漏：future 完成后移除，异常也移除。跨实例只依赖本地 Map 会重复生成，因此必须和 Redis/最终文件检查配套。

Cache Cleaner 获取 leader lock 后扫描；删除前检查 status bucket 和生成锁。检查与实际删除之间仍可能有 TOCTOU 窗口，生成器必须使用临时目录，清理器跳过最近更新目录，并让删除失败可重试。

### 数据库最终防线

源码中已有多处唯一约束，例如 Series 的 `(category,title,season_no)`、`(series_id,episode_no)`、文件路径、来源和关系表，Picture embedding 的 fileId 与 collection/point。它们能阻止并发“先查都不存在、随后各自 insert”产生重复行。

所有先查再插的业务都应有对应唯一约束，并捕获 DuplicateKey 后回查现有记录。没有唯一约束时，Redisson 锁只能覆盖遵守该锁的代码路径，数据库脚本、旧实例或遗漏路径仍可制造重复。

## 正确性边界

### 数据库边界

锁保证某段时间只有一个持有者，不保证代码成功，不记录执行结果，也不自动回滚文件和数据库。事务保证数据库原子性，但不能覆盖 NAS、MinIO、Qdrant 和模型调用。幂等保证重复执行的最终结果与一次执行相同。

三者组合：

```text
幂等键/任务记录 → 判断是否需要执行
分布式锁        → 防止同一时刻并发执行
数据库事务/唯一约束 → 保证写入原子与最终唯一
补偿记录        → 处理外部资源部分成功
```

### 过期写者

实例 A 获得锁后长时间停顿，锁因 Redis 故障或租约过期释放；B 获得锁并完成新结果；A 恢复后继续写，可能覆盖 B。普通 RLock 不能阻止这种过期写者。

严格场景使用单调递增 fencing token：每次获得执行权取得更大的 epoch，数据库/任务记录只接受不小于当前 epoch 的写入。Media Center 的全库刷新多为可重建 upsert，可用刷新版本达到类似效果；Picture 破坏性文件操作更应使用状态机和补偿，而不是只靠租约。

### Redis 故障策略

获取锁异常和“锁已被别人持有”是不同结果。前者返回依赖不可用，后者返回 GENERATING/UPDATING/DUPLICATE。不能 catch 全部异常后当成 `false`，否则用户会误以为只是重复操作。

Redis 故障期间：只读请求按依赖降级，写库/文件、生成和播放 session 变更应失败关闭。恢复后清理过期 RUNNING 状态，并通过最终文件、数据库结果和任务超时决定是否接管。

### 锁监控

记录 lock key、wait time、held time、结果、requestId 和 instanceId。不要 INFO 打印每个心跳锁，但刷新、leader 变更、超时和异常解锁应有结构化日志。

需要监控：leader 数是否恰为一、锁等待分位数、长期存在的 IN_PROGRESS、DuplicateKey 数、队列重投、任务接管和缓存状态/文件不一致次数。
