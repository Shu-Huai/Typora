# 文件监听选主

Media Center 的媒体根目录位于 NAS、映射盘或本地目录。Book、Movie、Series、Music、Picture 都需要在目录发生新增、删除或变化时更新数据库索引。单实例时可以直接启动一个 Java `WatchService`；多实例时，如果每个实例都监听同一个目录，同一文件事件会被多个 JVM 同时处理，可能造成重复扫描、重复写入、重复下载元数据，甚至互相覆盖删除结果。

当前项目已经实现了“一个模块只允许一个实例启动 watcher”的骨架：每个模块有独立的 `*LeaderCoordinator`，通过 Redisson 的 watcher leader lock 竞争，成为 leader 后启动对应 `*FolderWatcher`。本文专门说明这套竞争的真实边界、监听事件为什么仍可能丢失，以及应该怎样设计接管和补偿。

## 当前实现

### Leader 锁的竞争范围

五个模块各自使用独立的 Redis key，竞争不会跨模块互相阻塞：

| 模块 | 当前锁语义 | 获胜后的本地资源 |
| --- | --- | --- |
| Book | `book:watcher:leader:lock` | `BookFolderWatcher`、Book refresh command listener |
| Movie | `movie:watcher:leader:lock` | `MovieFolderWatcher`、Movie refresh command listener |
| Series | `series:watcher:leader:lock` | `SeriesFolderWatcher`、Series refresh command listener |
| Music | `music:watcher:leader:lock` | `MusicFolderWatcher`、Music refresh command listener |
| Picture | `picture:watcher:leader:lock` | `PictureFolderWatcher`、Picture refresh command listener |

每个实例在 `ApplicationReadyEvent` 后启动一个本地选举线程。选举线程大约每 3 秒检查一次：

```text
ApplicationReadyEvent
  → 尝试 tryLock(0, -1, MILLISECONDS)
  → 成功：leader=true，启动 watcher 和 command listener
  → 失败：保持 follower，不启动 watcher
  → 已是 leader：检查锁仍由当前线程持有
  → 锁丢失：停止 watcher、停止 listener、释放本地 leader 状态
```

`tryLock(0, -1, ...)` 使用 Redisson watchdog，不设置固定的短租约；只要持锁线程和 Redisson 客户端仍然正常，Redisson 会续期。`leader` 的 `AtomicBoolean` 只是本机快速判断，真正的集群竞争依据是 Redis 中的 RLock。

### 获胜后如何启动 watcher

成为 leader 后，协调器从数据库读取模块的媒体根目录配置，规范化为绝对路径，并检查目录是否存在。配置缺失、路径不可读或不是目录时，实例仍可以持有 leader 锁，但不会启动 watcher，并在日志中记录原因。

以 Movie 为例，启动顺序是：

```java
leaderLock = lock;
leader.set(true);
startCommandListener();
startWatcherIfConfigured();
```

`MovieFolderWatcher.startWatching()` 会先停止自身旧 watcher，然后创建新的 JDK `WatchService`，递归注册目录，启动名为 `movie-folder-watcher` 的 daemon 线程。Book、Series、Music、Picture 使用相同的总体模式，但递归注册、支持的文件扩展名和事件类型略有差异。

当实例退出 leader 身份时，协调器先调用 `stopWatching()`，关闭 WatchService、打断监听线程并清理本地 `WatchKey`，再停止 RabbitMQ command listener，最后尝试解锁。正常释放可以让其他实例尽快竞争；进程崩溃则依赖 watchdog 停止和 Redis 锁过期。

### 文件事件如何到达业务层

监听线程从本地 `WatchService` 取出 `WatchKey`，把相对事件路径拼接到当前根目录，然后调用模块的 AdminService：

```text
WatchService.take()
  → WatchKey.pollEvents()
  → ENTRY_CREATE / ENTRY_DELETE / ENTRY_MODIFY
  → 解析绝对路径或相对路径
  → handleFileCreate(...) / handleFileDelete(...)
  → 文件解析、数据库 upsert 或删除
```

Movie 的监听主要处理创建和删除；Picture 还处理修改事件；部分 Book/Music 实现使用单层目录监听，Movie/Series/Picture 支持递归目录。Windows 下 Movie 会优先尝试 `ExtendedWatchEventModifier.FILE_TREE`，不可用时回退为逐目录注册。

这说明“一个 leader”解决的是监听者数量，不是事件处理的持久性。事件从操作系统队列进入当前 JVM 后，才有机会被业务代码处理；Redis leader lock 不会保存事件内容。

## Leader 接管

### 为什么同一时刻通常只有一个监听节点

同一模块的实例使用同一个 Redis lock key。Redisson 的互斥语义保证同一时刻只有一个客户端线程成功持有该 key；其他实例的 `tryLock(0, ...)` 立即失败，继续作为 follower。只有 leader 调用 `startWatcherIfConfigured()`，所以正常情况下同一共享目录不会被多个实例各自注册一套 watcher。

```text
Movie A ── tryLock(movie:watcher:leader:lock) ── 成功 ── 启动 watcher
Movie B ── tryLock(movie:watcher:leader:lock) ── 失败 ── 不监听
Movie C ── tryLock(movie:watcher:leader:lock) ── 失败 ── 不监听
```

这个保证成立有几个前提：

- 所有实例连接的是同一个 Redis 数据平面，而不是各自的开发 Redis。
- 所有实例使用相同的模块锁 key 和相同的逻辑媒体根目录。
- watcher 只能由协调器启动，不能另有 `@PostConstruct`、手工接口或 refresh 代码绕过 leader 直接启动。
- 文件监听事件的处理不会被其他路径绕过，例如管理员刷新和 watcher 同时写库时仍需维护锁/幂等。

如果两个实例的配置指向不同目录，共用一个模块 leader key 仍然只会选出一个监听者；这不是“重复监听”，但会造成另一个目录没人监听。因此监听锁的粒度必须和部署拓扑一致：一个模块一个共享根目录时用模块级 key；一个服务需要监听多个互不相关根目录时，应改为 `module + normalizedRoot` 的根目录级 key。

### leader 锁丢失时发生什么

选举线程每轮检查 `leaderLock.isHeldByCurrentThread()`。如果 Redis 连接异常、watchdog 无法续期或锁被判定失效，协调器会降级：

```text
检测锁丢失
  → leader=false
  → stopWatcherQuietly()
  → stopCommandListener()
  → 不再处理新的本地文件事件
  → 其他实例在锁可竞争后成为 leader
```

这里的“停止”不是瞬间完成。监听线程可能正在 `handleFileCreate()` 中解析一个文件，Rabbit listener 也可能已经取出一条 refresh command。旧 leader 的线程不会因为 `leader=false` 自动回滚已经开始的数据库写入；因此业务层还需要维护操作级锁、事务、唯一约束和 owner/version 条件，防止旧执行者迟到写入覆盖新执行者的结果。

另一个细节是：当前代码的锁获取和释放在选举线程中进行，`isHeldByCurrentThread()` 使用的是 Redisson 的线程所有权语义。不能把锁对象传给任意线程释放，也不能把“本地 AtomicBoolean 仍为 true”当成锁仍然有效的证据。

### leader 宕机后的接管

正常停机和异常宕机是两条不同路径：

| 场景 | 旧 watcher | Redis 锁 | 新 leader |
| --- | --- | --- | --- |
| Spring 正常关闭 | `@PreDestroy` 主动 stop | 主动 unlock | 很快可竞争 |
| JVM 被杀死 | 没有机会 stop | watchdog 停止后过期 | 等待锁失效后竞争 |
| Redis 短时不可用 | 线程可能仍在本地运行 | 续期失败，存在过期风险 | 连接恢复后竞争 |
| 网络分区/长暂停 | 旧线程可能继续 I/O | 新旧实例对锁状态的观察可能不同 | 需要数据库 fencing 防旧写入 |

新 leader 获得锁后当前实现会重新启动 watcher，但不会自动知道旧实例已经从操作系统事件队列中取走了哪些事件。对于一个在切换窗口中创建的文件，可能出现三种结果：

1. 事件仍在系统队列中，旧 watcher 或队列恢复后处理成功。
2. 事件只存在旧 JVM 内存中，旧 JVM 崩溃后事件丢失。
3. 新 watcher 启动后只收到未来事件，历史文件已经存在但没有触发新的 create 事件。

因此“锁成功后启动 watcher”不能单独保证最终一致。

## 事件可靠性

### WatchService 不是持久消息队列

JDK `WatchService` 适合通知“目录可能发生了变化”，不适合当作数据库级事件日志。当前实现中存在以下特征：

- 事件队列属于当前 JVM，进程退出后不会恢复。
- `OVERFLOW` 在 Movie 等监听器中被直接忽略，没有触发全量或增量重扫。
- 同一个文件可能快速产生多次 create/modify/delete，代码没有统一的事件 ID 和去重表。
- 文件刚 create 时可能仍在被复制，立即解析可能读到不完整文件。
- 目录 rename、跨目录移动、临时文件改名发布，在不同文件系统和 WatchService 实现上可能表现为不同事件组合。
- leader 停止和新 leader 注册之间存在窗口，窗口内事件不能依赖本地 watcher 保证不丢。

所以 watcher 只应作为“尽快触发同步”的信号源，而不是唯一事实来源。数据库索引最终应由目录扫描、文件指纹和幂等 upsert 校正。

### 文件变化的正确处理边界

一个文件创建事件至少要经过稳定性检查：

```text
收到 CREATE
  → 判断扩展名和根目录边界
  → 等待文件大小/最后修改时间在短窗口内稳定
  → 确认仍可打开、读取头部或 ffprobe 成功
  → 计算相对路径 + size + lastModified/content fingerprint
  → 取得资源级处理锁
  → 数据库 upsert
  → 记录已处理指纹
```

删除事件也不能只依据文件名。服务应根据规范化相对路径定位数据库文件，并再次确认源文件确实不存在；NAS 短暂不可达时不能把整棵库当成被删除。对于 OVERFLOW、WatchKey 失效或根目录重新挂载，应该标记“需要 reconciliation”，由扫描任务重新比较目录和数据库，而不是静默跳过。

### 监听入口

手工刷新、定时扫描和 watcher 都可能调用相同的 `handleFileCreate`/`handleFileDelete`。它们不应互相假设“自己是唯一入口”，而应共享以下资源级规则：

```text
事件来源：watcher / manual refresh / startup reconciliation
  → 规范化资源键
  → 资源处理锁（短时）
  → 根据文件指纹判断是否真的变化
  → 事务内 upsert 或标记删除
  → 重复事件直接收敛到同一行
```

刷新期间当前模块还会使用 maintenance/refresh lock，使 watcher 事件等待或被暂存。这个锁主要防止扫描和单文件处理同时修改同一索引；它不保存事件。刷新完成后必须进行一次差异扫描或消费暂存事件，避免等待期间的新增文件永久漏掉。

## 实施验收

### 保留单 leader，但把接管做成可恢复流程

“一个监听节点”本身是合理的，原因是操作系统目录监听通常是实例本地资源，不适合让多个服务实例重复注册。建议保留当前 leader 竞争，但增加四个强制步骤：

1. **取得 leader 后先做 reconciliation**：读取共享根目录，按文件指纹与数据库索引比对，补上 leader 切换期间漏掉的事件。
2. **reconciliation 成功后再进入持续监听**：或者 watcher 与 reconciliation 并行，但要把事件按路径去重，不能扫描一次写一次、事件再写一次。
3. **WatchService 的 OVERFLOW、WatchKey 失效、根目录断开都转换成待重扫状态**：日志和指标必须可见，不能 `continue` 后无声恢复。
4. **业务处理使用资源幂等**：路径/指纹唯一键、数据库 upsert、操作状态和短时资源锁共同保证重复事件不会重复产生事实。

推荐的 leader 生命周期如下：

```text
follower
  → acquire watcher leader lock
  → 验证根目录与配置版本
  → reconciliation(scan generation N)
  → 标记 watcherReady=N
  → 启动 WatchService
  → 处理事件并周期性校正
  → 锁丢失/配置变化/关闭
  → 停止 watcher，结束当前批次，回到 follower
```

如果 reconciliation 失败，不应把实例标记成健康 watcher leader。可以继续持有锁并重试，也可以释放锁让其他实例尝试，但必须把原因和重试状态写入指标，避免所有实例因 NAS 不可用而频繁抢锁。

### 两种可选的事件持久化方式

对于当前项目，建议先采用“单 leader watcher + 接管后 reconciliation”，不要马上把每个操作系统事件都改造成复杂消息系统。两种方案的取舍如下：

| 方案 | 优点 | 代价 | 适用性 |
| --- | --- | --- | --- |
| Leader watcher + 周期/接管扫描 | 改动小；适合 NAS；天然修复 OVERFLOW 和宕机漏事件 | 不是实时到毫秒；需要可靠扫描和指纹 | 当前 Media Center 的首选 |
| Watcher 事件写入 DB/outbox 再异步消费 | 事件可查询、可重试、可审计 | 写入链路复杂；事件爆发时需要限流和合并 | 对文件变更审计要求很高时 |
| 每个实例都 watcher，资源锁去重 | 事件覆盖面大 | 仍然重复读取；事件顺序复杂；锁竞争放大 | 不建议作为默认方案 |

无论选择哪种，都不能把“Redis lock 存在”当作事件持久化。第一种方案的关键是扫描可重复、upsert 可重复；第二种方案的关键是 inbox/outbox 和资源指纹；第三种方案即使最终写库只有一行，也会浪费 NAS、ffprobe 和外部元数据调用。

### 最小验收矩阵

文件监听至少要做双实例实测，不能只测试 `PictureFolderWatcherTest` 这种单 JVM 生命周期：

| 场景 | 操作 | 必须观察到的结果 |
| --- | --- | --- |
| 初始竞争 | 同时启动 A/B | Redis 中只有一个 leader；只有一个 watcher 启动日志 |
| 新增文件 | 在共享根目录复制一个完整文件 | 数据库只出现一条文件事实，不能重复解析 |
| 大文件复制 | 先写入临时名，再 rename；或持续写入 | 不在文件未稳定时建立错误索引 |
| 删除文件 | 删除已收录文件 | 只删除对应相对路径，不误删同名其他目录文件 |
| leader 正常退出 | 停止 A | A 停止 watcher；B 取得锁并启动 watcher |
| leader 异常退出 | 强制结束 A | B 等待锁失效后接管，并通过 reconciliation 补齐切换窗口事件 |
| OVERFLOW | 批量制造大量文件事件 | 出现重扫指标/任务，不是静默忽略 |
| NAS 短断 | 暂时撤销目录访问 | 不把整个媒体库批量标记为删除；恢复后能重扫 |
| 双入口 | watcher 与手工 refresh 同时执行 | 资源指纹和数据库唯一约束收敛为一条事实 |
| 配置变化 | 修改媒体根目录 | 旧 watcher 停止，新根目录重新竞争/校正，旧目录不再继续写入 |

日志至少应包含 `module`、`instanceId`、`leaderEpoch`、根目录、事件路径、文件指纹、事件来源、处理结果和耗时。Redis 指标要记录 lock acquire/release、持有时长和接管次数；数据库要能查询最近 reconciliation generation 和失败原因。

### 当前结论

当前代码已经实现了“每个模块一个 watcher leader”的基本竞争，因此在 Redis、配置和正常进程生命周期都正常时，不会因为多实例而默认启动多个监听线程。这个结论可以写进现状文档。

但当前代码还不能承诺“文件事件绝不丢”：WatchService 事件不持久、OVERFLOW 被忽略、leader 接管后没有明确的自动 reconciliation、文件稳定性和跨入口幂等也不完全统一。正确的产品承诺应是：

> 同一模块同一共享根目录在任意时刻最多一个持续监听节点；监听节点故障或事件队列溢出后，通过可重复的目录校正和资源级幂等最终恢复索引一致性。

这比宣称“有 leader 锁所以不会重复、不会漏文件”准确得多。Leader 解决的是监听节点竞争；reconciliation 解决的是监听故障后的补偿；数据库约束和幂等处理解决的是重复事件；三者缺一不可。
