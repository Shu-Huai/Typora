# 多实例部署

![](http://public.file.lvshuhuai.cn/images\media-center-multi-instance-topology-1786601764741-7.svg)

多实例指同一个 Media Center 服务同时运行两个或更多进程，并注册为同一 Nacos 服务名。Gateway 可以把相邻请求转发到不同实例。多实例提高可用性和并发能力，同时也会破坏许多单 JVM 下默认成立的假设。

本文先说明系统在多实例下共享什么、哪些状态仍是本地的，再分析刷新、WebSocket 和播放链路。锁的具体 API 见 [[总体实现/分布式能力/分布式锁模型|分布式锁模型]]，各操作的幂等结论见 [[总体实现/分布式能力/幂等规则|幂等规则]]。

![](http://public.file.lvshuhuai.cn/images\media-center-multi-instance-topology-1786601764741-7.svg)

## 部署模型

### 请求会落到任意实例

Nacos 中存在两个 `Media-Center-Movie` 实例时，Gateway 对每次请求独立选择目标。除非专门配置粘性会话，不能假设 prepare、heartbeat、`.m3u8` 和 `.m4s` 一定到同一个 JVM。

```text
POST /movie/playback/prepare  → Movie A
POST /movie/playback/heartbeat → Movie B
GET  /movie/file/hls/...m3u8  → Movie A
GET  /movie/file/hls/...m4s   → Movie B
```

因此，请求后续需要的状态必须满足以下之一：

- 存在 Redis、MySQL、共享磁盘等所有实例都能访问的位置。
- 客户端携带足够信息让任意实例重建。
- 明确配置粘性路由，并承认实例宕机后会话需要重新建立。

当前 Movie/Series 的播放 session 与 active session 已保存到 Redis `RBucket` 并设置 TTL，heartbeat 可以落到其他实例。仅做到 session 共享仍不够，分片计划和实际缓存文件也必须可见。

### 状态归属

| 状态或资源 | 当前载体 | 多实例可见性 |
| --- | --- | --- |
| 媒体实体、进度、歌单 | MySQL | 共享 |
| 分布式锁、播放 session、窗口状态 | Redis/Redisson | 共享 |
| 刷新命令与状态 | RabbitMQ | 共享分发 |
| NAS 原媒体 | NAS/映射目录 | 取决于每个实例是否挂载同一路径 |
| Movie/Series 分片缓存 | 配置的文件目录 | 只有共享盘或同一主机目录才共享 |
| `RefreshRequestManager` future | `ConcurrentHashMap` | 仅当前 JVM |
| Lazy fMP4 `inFlight` | `ConcurrentHashMap` | 仅当前 JVM |
| WebSocket session 列表 | `CopyOnWriteArrayList` | 仅当前 JVM |
| `ReentrantLock` | JVM 内存 | 仅当前 JVM |

所谓“支持多实例”不能只看有没有 Redis。必须沿完整请求链检查：身份、任务状态、结果数据和派生文件是否都能被下一实例读取。

### 多实例成立的存储前提

所有实例应连接同一 MySQL、Redis、RabbitMQ 和 Nacos namespace。媒体根目录在每个实例上解析到同一批文件，且文件 ID 对应的相对路径具有相同含义。

Movie/Series 有三种部署选择：

| 方案 | 缓存可见性 | 适用范围 |
| --- | --- | --- |
| 同一 Windows 主机，多 JVM，共用同一本地目录 | 可见 | 当前最简单的多实例方式 |
| 多主机，缓存目录挂载共享存储 | 可见，但需验证文件锁、原子移动和性能 | 可横向扩展 |
| 多主机，各自本地缓存 | 不可见 | 需要内容寻址复制、定向路由或每实例生成，不能只用全局锁 |

如果实例 A 获得 Redis 分片锁并把文件写在 A 的本地 D 盘，实例 B 会因锁/READY 状态认为结果已经生成，却无法读取那个文件。这不是偶发问题，而是架构矛盾。

### 多实例不等于所有工作并行

列表查询、详情、原图读取和已存在分片读取可以在多个实例并行。下面工作需要集群级协调：

- 全量媒体库刷新和可能修改同一索引的目录 watcher。
- 同一资源的总结、插图、向量和字幕生成。
- 同一 MovieFile/SeriesEpisodeFile、画质、轨道、分片的转码。
- 同一用户播放 session 的 replace、heartbeat 和关闭。
- 扫描同一缓存目录的定时清理。

目标不是把整个模块锁成单线程。锁粒度应贴近冲突资源：全库刷新用模块级锁，单个总结用资源 ID，播放分片用文件版本、variant、轨道和分片编号。

## 后台任务

### Leader 负责什么

Book、Movie、Series、Music、Picture 通过 `watcherLeaderLock` 选出 leader。当前 leader 启动目录 watcher 和 refresh command listener，非 leader 停止这些资源。竞争、接管和 WatchService 事件丢失边界详见 [[总体实现/分布式能力/文件监听选主|文件监听选主]]。

这解决两个问题：

1. 避免多个 watcher 对同一文件变化重复写库。
2. 让持久 command queue 只由当前 leader 执行。

Leader 锁采用 Redisson watchdog 模式持有，实例存活时自动续期。协调线程还会检查 `isHeldByCurrentThread()`；失去锁后停止 watcher 和 listener。新实例获得锁后再启动。

Leader 只是“谁负责执行”的选择，不是幂等证明。旧 leader 在网络分区后仍可能继续进行已经开始的 I/O，新 leader也可能接管。数据库唯一约束、任务记录或 fencing token 才能防止过期执行者覆盖新结果。

### 刷新命令

刷新命令使用持久 DirectExchange/Queue，状态使用 FanoutExchange。每个实例创建独立、自动删除的状态队列：

```text
任意实例 A 接收 HTTP
  → 注册本地 requestId future
  → command queue
  → leader 实例 B 执行
  → status fanout
  → A、B、C 各自状态队列收到结果
  → A 完成本地 future，所有实例向自己的 WebSocket 广播
```

这个设计能解决“请求在 A、任务在 B”的回传问题。`RefreshRequestManager` 虽是本地 Map，但状态 fanout 会送回 A。若 A 在等待期间宕机，本地 future 丢失；任务仍可完成，但客户端的原 HTTP 连接已经失败，需要依靠状态查询或再次提交得到结果。

当前 request gate 在 HTTP 方法结束时释放，它阻止同一时刻第二个刷新请求入队。实际执行还有 refresh/library maintenance lock 兜底。两层锁职责不同：前者给用户快速返回“正在更新”，后者保护真正写库阶段。

### 消息重投

RabbitMQ 不能被当作“消息绝对只消费一次”。消费者执行完成但 ACK 丢失、连接中断、人工重发，都可能造成同一 requestId 再次到达。

当前刷新执行锁防止两个任务同时运行，但第一个完成并释放锁后，同一 command 再投递仍可能重新全量刷新。刷新过程本身大量采用 upsert，降低了重复数据风险，但没有持久化的 `requestId → terminal result` 去重表时，不能称为严格的消息幂等。

目标设计应在消费前执行：

```text
查询 operation + requestId
  SUCCESS/FAILED → 返回已保存终态，不再执行业务
  RUNNING        → 不再启动第二份
  不存在         → 原子创建 RUNNING，再执行
```

终态记录设置合理保留期。全库刷新还可用模块级业务键限制，即使用户每次点击都生成不同 requestId，也不能并发运行。

### 状态恢复

WebSocket 推送是通知，不是任务事实。当前 handler 的 session 列表只在本实例内，状态 fanout 让每个实例都广播，所以连接落在哪个实例都能收到实时消息。这依赖每个实例的临时状态队列正常存在。

客户端断线或实例重启后，单纯 WebSocket 无法补发历史状态。目标设计需要可查询任务记录，至少保存：operation、business key、requestId、status、owner instance、开始/结束时间、response code 和统计结果。

## 播放资源

### Session 已共享，文件未必共享

Movie/Series 把 session JSON、用户 active session 和 SOURCE 预转码 job 放在 Redis。`playbackUserLock(userId)` 使不同实例中的 prepare、heartbeat 等用户状态修改串行化。

分片与 init 文件仍位于缓存目录。多实例部署必须回答：

- 所有实例是否看到同一 `segment-plan.json`？
- 实例 B 能否看到实例 A 完成的 `init.mp4/.m4s`？
- 共享目录上的临时文件和原子 rename 是否可靠？
- 清理任务判断正在写入时，能否看到另一主机进程的状态？

Redis READY 只是一条状态记录，文件存在才是播放结果。读取时应以文件完整性验证为最终判断；状态与文件冲突时，删除/纠正过期状态并重新生成。

### 两层 single-flight

Lazy fMP4 coordinator 使用本地 `ConcurrentHashMap<SegmentKey, CompletableFuture<Path>>`，把同一 JVM 的并发请求合成一个 future。跨实例由 Redisson window/segment 锁和 Redis 状态协调。

```text
同一实例 10 个请求 → 本地 inFlight → 1 个任务
两个实例各 10 个请求 → 各自本地 inFlight → Redis 竞争 → 集群 1 个写者
```

本地合并减少 Redis 和线程池压力，分布式锁负责集群互斥。两者都不能替代完成文件的原子发布：FFmpeg 写临时目录，验证后 rename/移动成最终路径，读取者只认最终文件。

### Cache Cleaner

Movie/Series 缓存清理通过 `playbackCacheCleanupLeaderLock` 保证每轮只有一个实例扫描。清理器还检查 Redis 状态 bucket 和相关 lock 是否活跃，以免删除正在生成的窗口。

如果缓存是各实例独立本地盘，一个全局 cleanup leader 只会清理 leader 自己能看到的目录，其他实例缓存不会被清理。此时应改成每实例本地清理锁（key 含 instanceId），或使用共享缓存后保留全局 leader。锁模型必须和存储拓扑一致。

### 播放预热

字幕锁按文件和 trackId，窗口锁按文件、variant 和 windowStart，预转码锁按文件。锁 key 还应包含文件版本；原文件在同一路径被替换后，旧锁、状态和缓存不能继续代表新内容。

计划解析器中的本地缓存可以在各实例重复计算，只要输出由同一源文件确定且最终文件原子写入。昂贵预转码必须复用 Redis active job 与持久结果；实例死亡后 job 超时允许接管，接管前检查最终文件是否已完成。

## 故障边界

### Leader 宕机

预期过程：旧实例停止续期，Redis 释放 leader 锁，另一实例获得锁，启动 watcher 和 command listener。测试不能只看 `isLeader=true`，还要确认旧 listener 已停、新 listener开始消费、目录事件没有重复执行。

正在执行的刷新若随进程死亡，会在 MQ 重投或用户重试后重新开始。没有持久任务阶段和 fencing token 时，系统通常只能做到“最终重新刷新”，无法从扫描中点精确续作。

### Redis 故障

Redis 不可用时不能安全获得刷新、写目录、生成内容和播放 session 的集群互斥。系统应拒绝这些写/生成操作，而不是退回 `ReentrantLock` 假装集群安全。只读 MySQL 查询和可直接读取的原媒体可以按模块降级继续。

Redis 主从切换存在极短窗口，已返回成功的锁写入可能尚未复制。对破坏性文件操作或要求严格互斥的任务，单个 Redis 锁不是绝对一致性系统，需要数据库状态、唯一约束和可补偿操作共同兜底。

### 路径校验

所有实例配置同一个相对媒体根并不保证实际内容相同。启动检查应记录根目录标识、抽样文件和可写性。某实例看不到 NAS 时应从 Nacos 下线或健康检查失败，不能继续接受文件请求。

Windows 映射盘通常属于登录会话。服务 A 以桌面用户运行能看到 `Z:`，服务 B 以系统账号运行可能看不到。多实例上线前用每个实际进程身份验证。

### 当前结论

当前代码已经具备多实例协调的主要骨架：leader、Redisson locks/buckets、MQ command/status 和 Redis 播放 session。仍需特别关注：MQ command 的持久幂等记录、用户进度与歌单的数据库竞态、WebSocket 历史状态查询、播放缓存的跨主机可见性，以及锁失效后的过期写入者。
