# 故障演练

多实例、分布式锁和幂等不能靠代码走读验收。正常路径只证明“一次请求通常能成功”，而需要验证的是：请求重复、消息重投、实例退出、Redis 抖动、NAS 断开以及任务接管时，系统是否仍保留一个正确结果，并且用户能查到任务的真实状态。

本文给出可重复搭建的演练环境、故障注入点和验收证据。当前代码尚未具备的持久任务、inbox/outbox 或数据库唯一约束，应先记录为发布风险，修复后再纳入运行门槛。

## 演练环境

### 实例布置

最低有效环境不是一个服务进程，而是同一模块的两个实例：

```text
Gateway :23000
Movie A :23003     Movie B :24003
Series A:23010     Series B:24010
Redis / RabbitMQ / MySQL / Nacos：两实例共享
NAS：A、B 必须以服务账号访问同一逻辑路径
转码缓存：分别验证“共享目录”和“各实例本地目录”两种部署
```

实例端口用命令行或 profile 覆盖，application name 保持相同，使 Nacos 和 Gateway 把它们视为同一服务：

```powershell
$env:SPRING_PROFILES_ACTIVE='local-multi-instance'
java -jar Media-Center-Movie.jar --server.port=23003 --management.server.port=23303
java -jar Media-Center-Movie.jar --server.port=24003 --management.server.port=24303
```

实际执行时分别开终端，并为每个实例设置唯一 `instance-id`。日志格式至少打印 instanceId、requestId、taskId、messageId、lockKey、resourceId。没有这些字段时，即使最终数据正确，也很难证明到底执行了几次。

建议准备独立测试资源：

- 一个很小的电影/剧集文件，用于快速刷新和播放分片测试。
- 一个包含字幕、AAC 之外音轨且关键帧分布真实的视频，用于完整转码验证。
- 一个临时 Picture 根目录，允许创建、移动、删除，不触碰正式图库。
- 一个测试用户和专用歌单，不污染日常进度。
- 可替换的假 LLM/Spider 服务，记录调用次数并支持延迟、超时和固定响应。

### 观测基线

每个用例开始前保存基线，结束后比较业务事实，而不是只看 HTTP 200：

```sql
select count(*) from user_progress;
select user_id, media_type, media_id, count(*)
from user_progress
group by user_id, media_type, media_id;

select playlist_id, track_id, count(*)
from music_playlist_track
group by playlist_id, track_id;

select operation_type, idempotency_key, status, version
from operation_task
order by id desc limit 20;
```

同步采集：

| 证据 | 要看什么 |
| --- | --- |
| 应用日志 | 哪个实例取得锁、执行副作用、发布终态、释放锁 |
| Redis | 锁 owner、TTL、任务状态、active session 是否按预期过期 |
| RabbitMQ | publish/deliver/redeliver/ack、队列深度、死信数量 |
| MySQL | 业务键是否只有一行、task/inbox/outbox 状态是否收敛 |
| NAS/缓存盘 | 最终文件、临时文件、完成标记、孤儿目录 |
| 假外部服务 | 相同业务键的实际调用次数 |
| 前端 Network | requestId/taskId、状态查询、WebSocket 重连恢复 |

执行前确认两个实例真的参与流量。连续调用实例信息接口，或在响应头加入 `X-Media-Center-Instance`：

```powershell
1..20 | ForEach-Object {
    Invoke-WebRequest 'http://localhost:23000/movie/actuator/info' |
        Select-Object -ExpandProperty Headers
}
```

如果请求始终落到同一实例，并发测试只能证明单 JVM 行为。

### 并发工具

简单重复调用可以用 PowerShell 7 的并行管道：

```powershell
$targetUrl = 'http://localhost:23000/movie/admin/refresh-database'
$accessToken = '<test-token>'

1..40 | ForEach-Object -Parallel {
    Invoke-RestMethod -Method Post -Uri $using:targetUrl -Headers @{
        Authorization = "Bearer $using:accessToken"
        'Idempotency-Key' = 'movie-refresh-test-20260813'
    }
} -ThrottleLimit 20
```

更稳定的回归应写集成测试，由 Testcontainers 启动 MySQL、Redis 和 RabbitMQ，再启动两个 Spring context。需要检查跨进程锁或进程退出时，再用两个真实 JVM；单测试进程中的两个 bean 不能覆盖网络分区、进程终止和 Redisson watchdog 停止等情况。

长任务测试不要依赖真实大模型是否恰好很快。假服务应提供控制接口：

```text
POST /test-mode/delay?milliseconds=15000
POST /test-mode/fail-next?count=1&status=503
GET  /test-mode/calls?businessKey=picture:19:PIXEL:model-v2
```

### 通用断言

每个用例同时断言四层结果：

1. **响应层**：重复请求得到同一 resource/task，冲突参数有明确错误。
2. **执行层**：昂贵副作用只执行一次，或按设计只存在一个有效 owner。
3. **数据层**：业务键对应一条有效记录，没有部分事务或倒退状态。
4. **恢复层**：断线/重启后通过查询接口获得终态，临时资源最终被清理。

不得把以下现象当作通过：

- 第二个请求返回“正在处理”，但后台实际上启动了第二份任务。
- 数据库只有一行，但外部 AI 被计费两次。
- Redis 中锁已消失，但数据库任务永久停在 RUNNING。
- WebSocket 显示成功，但文件仍是半成品或另一实例无法读取。
- 两次写入互相覆盖，碰巧最终值看起来合理。

## 重复请求

### 短事务

为注册、进度、歌单关系、Picture 路径等操作写屏障并发测试：所有线程先完成查询，再同时尝试插入，这比普通循环更容易稳定复现“先查再插”的竞态。

伪代码：

```java
var ready = new CountDownLatch(concurrency);
var fire = new CountDownLatch(1);

for (int i = 0; i < concurrency; i++) {
    executor.submit(() -> {
        ready.countDown();
        fire.await();
        client.updateProgress(sameUser, sameMedia, samePayload);
        return null;
    });
}

ready.await();
fire.countDown();
```

断言清单：

- 40 个相同用户名注册请求最终只有一个 user；其余响应为同一业务冲突，不出现 500。
- 100 个相同媒体进度首写最终只有一行有效记录。
- 100 次同一曲目添加按产品定义得到一条 entry，或得到 100 个各自有稳定 entryId 的条目。
- Picture 两实例同时创建同一路径，磁盘与数据库各有一个目录。
- 唯一约束冲突后服务回查的是相同 payload；相同 key 不同 payload 返回冲突，不能静默复用。

还要覆盖乱序更新：先发送 eventSequence=11，延迟后发送 sequence=10。最后数据库必须保留 11。对于允许跨设备独立进度的业务，先定义合并规则再断言，不能武断地使用最大 currentTime——用户主动回看时 currentTime 下降是合法行为。

### 长任务

针对刷新、摘要、插图和转码，强制让任务执行 10～30 秒，在此期间从 A、B 实例各提交多次：

```text
T0  A 接受 businessKey=movie-refresh:default
T1  A 取得执行权，进入假扫描延迟
T2  B 以新 requestId 提交相同 businessKey
T3  A 再次收到客户端超时重试
T4  任务完成
```

预期：

- 所有调用返回同一个 taskId，requestId 可以不同。
- 只有一次扫描/模型调用/FFmpeg 进程。
- task 从 PENDING/RUNNING 只到达一次终态。
- 所有等待者最终查询到同一结果引用。
- 参数哈希不同但复用同一 idempotency key 的请求返回冲突。

摘要要分别测试“同模型同 prompt 复用”和“模型版本变化产生新任务”。图片生成要核对假服务调用次数；只查数据库记录数不够，因为第一次生成可能成功上传却在入库前崩溃。

播放分片测试要核对：

```powershell
Get-CimInstance Win32_Process -Filter "Name='ffmpeg.exe'" |
    Select-Object ProcessId,CommandLine

Get-ChildItem 'D:\Media-Center\movie-hls-cache' -Recurse -File |
    Select-Object FullName,Length,LastWriteTime
```

同一 segment key 同一时刻只允许一个对应 FFmpeg。最终目录只能在校验成功后出现；失败时允许保留带 taskId 的临时目录供诊断，但恢复器必须在 TTL 后清理。

### 消息重投

构造相同 messageId 的重复投递，以及不同 messageId 但相同业务键的重复命令：

| 用例 | 注入方式 | 预期 |
| --- | --- | --- |
| 完全相同消息 | 同一 payload 发布 10 次 | inbox 仅一条，副作用一次 |
| ack 前断开 | 业务提交后、ack 前终止消费者 | 新实例收到 redelivered，查到已完成并 ack |
| 同业务不同 messageId | 模拟客户端超时重新发命令 | task 唯一约束合并到同一任务 |
| 终态重复 | SUCCESS 状态发布多次 | 前端/监听器状态不倒退，不重复弹出副作用操作 |
| 终态乱序 | 先 SUCCESS 后延迟 RUNNING | 条件更新拒绝从终态回退 |
| 毒消息 | 缺字段或不支持的 operation | 有限失败后进入死信，不循环 requeue |

测试 ack 窗口时需要可控钩子：业务事务提交后写入日志/测试 latch，暂不 ack。此时终止进程，再启动 B。若只有 Redisson 锁而没有 inbox/task，B 很可能重新执行，这个预期失败正好证明持久去重的必要性。

状态机更新使用条件 SQL：

```sql
update operation_task
set status = 'SUCCEEDED', result_reference = ?, version = version + 1
where id = ?
  and status = 'RUNNING'
  and version = ?
  and owner_token = ?;
```

影响行数为 0 说明执行权已经变化，迟到实例不能继续发布成功终态。

### 文件副作用

对每个跨系统动作，在以下三个时间点各杀一次进程：

1. 数据库写 PENDING 后、外部调用前。
2. 外部调用/文件生成成功后、数据库 READY 前。
3. 数据库 READY 后、状态消息发布前。

验收结果：

- PENDING 无副作用：恢复器可安全重试。
- 已有对象无 READY：按确定性 object key 或 generationId 找回并补记，不重复生成。
- READY 未通知：outbox 重发事件，查询接口始终能看到 READY。
- 临时 fMP4 存在：不会被 HLS 清单引用；恢复或 TTL 清理后消失。
- 文件移动中断：根据 source/target 的实际存在状态继续，不再次把目标套入子目录。

MinIO 可通过代理或假服务在 PUT 完成后主动断开响应，模拟“服务端成功、客户端认为失败”。NAS 测试可在专用临时共享目录撤销权限或断开映射，不能对正式媒体路径执行破坏性演练。

## 依赖故障

### Leader 切换

分别在 leader 的目录监听、缓存清理、消息执行三个阶段结束进程。Windows 上先确认 PID 与命令行，再只终止测试实例：

```powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.CommandLine -like '*Media-Center-Movie.jar*' } |
    Select-Object ProcessId,CommandLine

Stop-Process -Id <verified-test-pid>
```

验收：

- watchdog 停止续期后，另一个实例在预期时间取得 leader lock。
- 同一时刻观察不到两个有效 leader；若发生短暂双主，资源操作仍由数据库版本/业务锁收口。
- 新 leader 不重扫并重复写入已完成 generation。
- leader 离开期间到达的命令不会无限互相重新发布。
- 原实例恢复后作为 follower，不立即再次抢跑同一任务。

还要测试 JVM 长时间暂停而不是正常退出。可用调试器暂停线程超过预期租约，观察旧 leader 恢复后是否还会继续写。只有 owner token/fencing 条件才能阻止“锁已经属于 B，A 却迟到写入”的情况。

### Redis 租约

Redis 故障分为连接失败、短暂超时、主从切换和数据清空，语义不同。测试期间使用独立 Redis，不能清空开发者正在使用的实例。

| 故障 | 应有行为 |
| --- | --- |
| 请求前 Redis 不可用 | 需要协调的写操作快速失败，不能无锁继续；普通只读按依赖情况降级 |
| 持锁中短暂断开 | 任务检测失去协调能力；可暂停/失败，最终写仍受 DB owner token 保护 |
| 锁自然过期 | 新 owner 接管；旧 owner 的条件提交失败 |
| Redis 数据清空 | session/临时状态可丢并重建；业务主数据不丢；不能把 RUNNING 当作从未执行 |
| Redis 恢复 | 不自动并发重启全部未知任务；从持久 task 状态逐项认领 |

固定 lease 的锁要把任务时间拉长到超过 lease，确认是否出现并发执行。使用 watchdog 的锁要暂停 Redisson 续期线程/进程，确认接管时间。测试日志记录 acquireTime、lease/watchdog、releaseTime 和 owner token。

锁释放只允许 owner：

```java
finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

这一判断防止误解锁，但不能解决迟到写入；数据库条件仍不可少。

### 基础服务

RabbitMQ 不可用时，刷新接口不应先返回“已接受”再把命令静默丢掉。若使用 outbox，HTTP 事务可以先记录待发任务并返回 202，由发布器恢复；未实现 outbox 时应明确失败。

MySQL 故障按事务点测试：连接池耗尽、事务提交失败、死锁重试、提交成功但客户端连接断开。只对具备幂等键的事务自动重试。死锁重试前保留同一业务键，不能重新生成 generationId。

Nacos/服务发现故障主要影响新实例和路由：

- 已启动实例使用已加载配置能否继续处理现有任务。
- Gateway 是否还持有可用实例列表，恢复后是否移除死亡实例。
- Feign 超时重试是否把非幂等 POST 发给另一个实例。
- 配置更新期间两个实例短暂使用不同参数时，业务键是否包含 plan/model/config version。

### 缓存路径

多主机测试必须主动制造路径不一致：A 能访问源文件和缓存，B 只能访问 Redis 中的“已完成”状态但看不到实际文件。预期系统应在启动健康检查或任务执行前发现，而不是向浏览器返回一个随后 404 的 m3u8。

验证两种合法部署：

```text
共享缓存：A/B 使用同一 UNC/NAS 缓存目录
  → 全局 segment 状态和文件确实对应同一物理对象

本地缓存：A/B 各有缓存
  → 播放 session 粘到创建实例，或媒体 URL 明确路由到 owner instance
```

不允许的组合是“Redis 全局宣称 READY + 各实例本地缓存 + Gateway 任意转发”。这时 B 会认为无需生成但拿不到 A 的文件。测试需反复请求同一 `.m4s`，确认响应头 instanceId 和文件可用性。

缓存清理测试让一个实例持续读取分片，另一个实例触发 TTL/高水位清理。清理器不能只看文件 mtime 就删除正在服务的内容；应使用访问租约、活跃 session 引用或延迟两阶段删除。

### 媒体任务

| 能力 | 必测场景 | 通过标准 |
| --- | --- | --- |
| 五模块刷新 | A/B 同时点击、命令重投、leader 中途退出 | 同 scope 一个任务；扫描结果无重复；重连可查终态 |

### 用户写操作

| 操作 | 并发量 | 核心断言 |
| --- | ---: | --- |
| 注册同用户名 | 40 | 一个用户；无 500；冲突响应稳定 |
| 首次写阅读/播放进度 | 100 | 一个业务键一行；无重复 |
| 同 session 乱序心跳 | 100 | 旧序号不覆盖新序号 |

每项都要从两个实例分别发起。仅 Mock mapper 的单元测试适合校验分支，不足以证明唯一索引、事务隔离和跨实例竞争。

### 自动化层次

建议把验证分为四层，控制反馈速度：

1. **单元测试**：业务键构造、状态机、payload hash、版本冲突、锁 key。
2. **容器集成测试**：真实 MySQL 唯一约束/事务、Redis 锁、RabbitMQ inbox/outbox。
3. **双 JVM 端到端**：Nacos/Gateway 路由、实例退出、共享或本地缓存策略。
4. **真实媒体浏览器回归**：播放时间轴、切清晰度、暂停/seek 与多设备进度。

CI 中每次运行第一、二层；涉及分布式协调、MQ 或播放缓存的改动运行第三层；发布候选版本运行第四层。故障演练可能较慢，但不能永久只靠人工记忆，至少把命令、测试数据和 SQL 断言固化到脚本或测试类。

建议输出一份机器可读报告：

```json
{
  "case": "movie-refresh-redelivery-after-commit",
  "instances": ["movie-a", "movie-b"],
  "requests": 20,
  "taskIds": ["task-831"],
  "sideEffectCount": 1,
  "businessRowCount": 1,
  "terminalStatus": "SUCCEEDED",
  "orphanFiles": 0,
  "passed": true
}
```

### 发布门槛

以下任一情况存在时，不应宣称多实例幂等完成：

- 只验证了两个请求串行调用，没有并发屏障。
- Redis 锁存在，但关键业务表没有唯一约束或版本条件。
- RabbitMQ 重投仍可能再次调用外部服务。
- 发起实例退出后，用户无法查询原任务状态。
- 共享状态标记 READY，但另一实例读取不到实际缓存文件。
- 任务可以永久停在 RUNNING，没有租约、恢复器和人工处置入口。
- 测试只看成功响应，没有统计副作用次数和孤儿资源。

通过发布门槛需要保留：测试版本、Git commit、配置摘要、实例数量、数据库迁移版本、Redis/RabbitMQ 版本、执行日志和最终报告。这样下一次修改锁 key、任务状态或缓存目录时，能够复用同一套证据做回归，而不是重新凭感觉判断。
