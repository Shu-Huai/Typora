# 刷新数据库设计

![](http://public.file.lvshuhuai.cn/images\refresh-leader-sequence-1786601764741-14.svg)

刷新数据库是 Media Center 的共同基础流程：从媒体根目录读取文件，解析业务身份，写入 MySQL，再处理删除、变更和派生数据。它不是简单的“重新执行一次 insert”，而是一个可重复、可中断、可由其他实例接管的同步任务。

各模块的具体表、解析规则和外部副作用分别写在模块目录的刷新文档中：Movie、Series、Book、Music、Picture。本文只定义五个模块都必须遵守的任务边界。

## 任务入口

### 触发来源

刷新有四类来源：管理员手工刷新、应用启动后的首次校正、Leader watcher 发现文件变化、运维恢复任务。它们最终都应进入同一套扫描和写入服务，不能为每个入口复制一份 upsert 逻辑。

```text
HTTP refresh / watcher event / startup reconciliation
  → request gate
  → refresh task
  → leader execution
  → scanner
  → ingestion
  → derived work
  → terminal status
```

文件监听只负责尽快触发局部处理；`OVERFLOW`、WatchKey 失效、NAS 短暂不可达和 Leader 切换后的漏事件，都必须由完整或增量 reconciliation 修复。

### 准入规则

每个模块有独立的 request-gate。收到刷新请求后先判断是否已有任务：

| 状态 | 新请求行为 |
| --- | --- |
| 没有运行任务 | 创建任务并进入执行流程 |
| 已有运行任务 | 返回 `STATUS_UPDATING`，不再发布第二条命令 |
| 上一次失败且可恢复 | 复用 task 或创建新的 retry generation |
| 参数范围不同 | 根据 scope 形成不同业务键，不能无条件合并 |

当前代码的 request manager 和 future 在 JVM 内存中，RabbitMQ status 用于实时通知；要支持实例重启后查询，目标实现应持久化 `operation_task`，并用 operation + scope + generation 作为业务键。

### Leader 选择

同一模块同一媒体根目录同时只能有一个持续刷新执行者。Leader lock 负责选择执行实例，不能代替数据库幂等：旧实例在锁丢失后可能仍完成已经开始的 I/O，最终写入仍要经过唯一约束、版本条件或资源锁。

```text
follower
  → watcher/refresh leader lock
  → verify root and config version
  → scan generation
  → write database
  → publish status
  → release or renew
```

## 同步流程

### 扫描阶段

扫描器不直接向前端返回实体，而是先产生带来源信息的扫描结果：

```text
absolute path
  → normalized relative path
  → file type and fingerprint
  → parsed business identity
  → Scanned* DTO
```

指纹至少包含相对路径、大小、最后修改时间；对会被替换但路径不变的媒体，可增加内容头或 hash。扫描根目录不可访问时，任务失败并保留旧索引，不能把所有数据库记录标记为删除。

### 入库阶段

入库按“主实体 → 文件实体 → 关系 → 派生状态”的顺序进行。每个模块的批次可以不同，但一个业务事实的写入必须在明确事务边界内完成。

```text
read scanned item
  → find by stable business key
  → insert or update
  → reconcile relation rows
  → record source fingerprint
  → enqueue derived work
```

先查再插只能作为优化，最终唯一性由数据库约束决定。重复消息、重复 watcher 事件和刷新重跑都应该收敛到同一行，不因主键变化产生重复实体。

### 删除阶段

删除必须基于“扫描确认不存在”，不能基于一次目录访问失败。推荐状态：

```text
seen in current generation → ACTIVE
not seen after complete scan → MISSING_CANDIDATE
confirmed absent           → INACTIVE / DELETED
```

用户进度、人工元数据、歌单关系和生成记录是否级联删除由模块规则决定。派生文件可以异步清理，源媒体不可由刷新清理器删除。

### 派生阶段

缩略图、字幕、embedding、外部 metadata、摘要和播放分片不应阻塞主索引事务。主索引先提交稳定文件事实，再通过任务或状态表触发派生工作。派生失败要能单独重试，不得回滚已经正确入库的媒体文件。

## 一致性边界

### 事务范围

单个媒体事实的数据库写入适合短事务；全库扫描不适合使用覆盖数十万文件的长事务。可以使用 refresh generation：批量写入新 generation，全部扫描成功后切换当前 generation；切换前旧索引继续可读。

跨系统操作不能假设一个数据库事务可以回滚：

- FFmpeg 先写临时目录，校验后原子发布。
- MinIO 使用确定性 object key 和状态记录。
- Qdrant upsert 使用稳定 pointId，MySQL 保存同步状态。
- LLM 调用先创建 generation 任务，避免超时重试重复计费。

### 事件扫描关系

watcher、手工刷新和启动校正可能同时发现同一文件。它们共享资源键和 ingestion 服务，事件只作为触发，不拥有独立事实。`OVERFLOW` 必须产生 reconciliation 请求；静默丢弃会让数据库永远停在旧状态。

### 失败恢复

任务状态建议使用：

```text
PENDING → RUNNING → SUCCEEDED
              ├──→ RETRYABLE_FAILED
              └──→ FINAL_FAILED
```

任务带 owner token、lease 和 heartbeat。实例退出后，其他实例只能接管 lease 已过期的任务；迟到旧 owner 通过版本条件提交失败。状态消息可重复发布，前端以 taskId 和状态版本拒绝回退。

### 验收口径

每个模块刷新必须证明：

- 相同文件重复扫描不会重复创建业务实体。
- 同一时间只有一个模块 Leader 执行全量刷新或监听。
- NAS 不可访问时不误删全库。
- 消息重投不会重复外部副作用。
- 中途崩溃后能恢复任务或通过下一次扫描收敛。
- WebSocket 丢失后仍可通过状态查询得到终态。

## 模块差异

### 内容库

Book 以文件类型、作者、出版社和 BookFile 关系为核心；PDF/EPUB/TXT 可以共享同一书籍，但路径和格式不能丢失。阅读进度不因刷新重置。

### 视频库

Movie 以 MovieFile 的稳定路径和媒体探测结果为核心。Series 以 Series、Episode、EpisodeFile 三级身份为核心；季号、集号、路径和来源约束必须一起校验。两者的文件版本变化都必须使播放计划和派生缓存失效，但不能删除原始媒体或用户进度。

### 音乐库

Music 以文件名解析、曲目/歌手关系和外部来源匹配为核心。标题相同而歌手不同的文件不能复用一个 MusicTrack；歌词和音频文件是独立派生数据。

### 图片库

Picture 以目录树、相对路径和 PictureFile 为核心。EXIF、缩略图、embedding、Qdrant point 和 AI 插图都是派生结果，主索引成功后单独处理。
