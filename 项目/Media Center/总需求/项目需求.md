# Media Center 项目需求

Media Center 是部署在个人服务器上的私有媒体管理系统。用户已经拥有图书、电影、剧集、音乐和图片文件，这些文件通常保存在 NAS、机械硬盘或映射盘中。项目不负责出售或分发内容，而是把零散目录变成能在浏览器中检索、阅读、播放和维护的媒体库。

这份文档规定项目级需求。模块内部的目录规则、数据模型和消费流程由各模块文档说明；电影播放的时间轴与转码实现另有专题文档。

## 产品范围

### 使用前提

系统建立在几个实际前提上：

- 原始媒体已经存在，文件可能很大，移动到云端或重复保存并不现实。
- 文件名和目录包含一部分语义，但不等同于完整的媒体资料。
- 浏览器适合做统一客户端，却不能直接读取服务器磁盘，也不能解码所有音视频组合。
- 用户可能在局域网和公网使用同一套系统，两种环境对带宽的要求不同。
- 数据库可以重建媒体索引，但用户进度、歌单和人工修订不能随扫描丢失。

项目交付的结果不是一个更漂亮的文件浏览器。用户看到的是五类内容库，能够按内容实体而不是纯路径使用自己的文件。例如，一部电影可以关联多个文件版本、类型和人物；一首曲目可以关联多个歌手和一个专辑；一本书可以有 PDF、EPUB 和 TXT 版本。

```text
原始目录              Media Center                    浏览器
电影/五十度灰.mkv  →  电影 + 文件 + 人物 + 进度  →  详情、播放、续播
音乐/歌手/歌曲.flac →  曲目 + 歌手 + 专辑 + 歌词  →  播放、歌单
图片/旅行/照片.jpg  →  文件夹 + 图片 + EXIF + 向量 →  浏览、搜索
```

### 包含的能力

项目范围按“业务模块”和“公共能力”划分。

| 范围 | 包含内容 |
| --- | --- |
| 图书 | 书库刷新，PDF/EPUB/TXT 阅读，阅读进度，书籍总结，AI 插图 |
| 电影 | 电影库刷新，豆瓣资料，详情，SOURCE/1080p 播放，字幕，播放进度 |
| 剧集 | 按季与集整理，豆瓣资料，单集播放，字幕与单集进度 |
| 音乐 | 曲目、歌手、专辑、歌词、音频流、播放进度与歌单 |
| 图片 | 文件夹浏览，文件管理，缩略图，元数据，语义搜索与 AI 重绘 |
| 账号与平台 | 注册登录、统一网关、服务发现、异步任务、对象存储和智能服务 |

配置页面负责各媒体根目录、允许扩展名及模块运行参数。全量扫描和第三方同步属于管理行为；阅读、播放、查看和个人进度属于普通用户行为。

### 明确不做的事情

下列能力容易和媒体中心混在一起，但当前项目不承担：

- 不提供影视、音乐或电子书资源下载站。
- 不向陌生用户开放投稿、内容审核、评论社区和版权结算。
- 不对原媒体进行永久格式迁移。视频转码产物和图片缩略图只是缓存。
- 不把外部网站资料当作不可替代的主数据。豆瓣或 QQ 音乐不可用时，本地内容仍须可使用。
- 不保证任何浏览器都能原生解码任意视频编码；服务端只在定义好的播放档位中处理兼容问题。
- 不实现跨家庭实例的数据同步。本文中的“跨设备”指同一个服务实例和账号。

这些边界直接影响设计。例如，既然原文件不能丢，缓存清理只能碰派生文件；既然外部资料不是主数据，抓取失败不能删除本地影片或曲目。

## 用户流程

### 访问角色

当前至少有普通用户和管理用户两类行为。系统可以用角色字段或部署约定实现，但接口边界必须清楚。

普通用户需要：

1. 注册、登录和维护自己的账号。
2. 浏览五类媒体，查看列表、详情与统计。
3. 阅读、播放或查看原内容。
4. 保存个人进度、维护个人歌单。
5. 发起允许普通用户使用的总结、插图或图片重绘任务。

管理用户额外需要：

- 配置媒体根目录和支持格式。
- 发起全量刷新并看到执行结果。
- 发起单项或批量第三方元数据同步。
- 处理路径错误、解析失败和外部匹配不确定的条目。

权限必须在后端生效。前端隐藏按钮只是交互处理，不能替代 Controller 或 Service 的授权检查。

### 媒体入库

各业务模块的细节不同，但入库遵循同一条主流程：

```text
读取模块配置
  → 校验根目录存在且可访问
  → 遍历允许的文件类型
  → 按模块规则识别内容实体与实际文件
  → 解析可获得的本地元数据
  → 与数据库现有记录比对
  → 新增、更新、标记缺失记录
  → 发布刷新结果
```

刷新不是简单的“全部删除再插入”。全删会改变主键，导致播放进度、阅读进度、歌单关系、第三方资料和生成内容失去关联。合理的刷新需要为内容与文件定义稳定身份：常见依据包括受管根目录下的相对路径、规范化名称、季集编号，以及模块特有的关联字段。

刷新过程还要处理变化：

- 新增文件：建立文件记录，必要时创建内容主体。
- 路径移动或改名：在能够可靠识别时更新现有记录，否则按删除和新增处理。
- 文件删除：停止对外提供内容，清理可重建派生索引；不要误删其他文件共享的主体。
- 文件损坏：记录错误并跳过，不能让几万项扫描因一个文件失败。
- 重复文件：保留多个文件版本或按模块规则合并，不凭文件名草率覆盖。

### 内容消费

列表页解决“找到什么”，详情页解决“这个内容包含什么”，阅读或播放页解决“如何使用具体文件”。前端不应绕过内容实体直接把磁盘路径暴露给浏览器。

一次典型电影访问为：

```text
电影列表 → 电影详情 → 选择 MovieFile
         → prepare 播放会话 → HLS 播放
         → 心跳保存进度 → 下次继续
```

图书、剧集和音乐采用相同的内容/文件分层，但消费协议不同。PDF 按页读取，EPUB 由阅读器解释资源，音乐使用 HTTP 流式响应，图片提供原图与缩略图。系统应让差异停留在模块内部，而不是让所有页面都自己处理服务器文件路径。

### 异步操作

全量扫描、AI 生成、批量外部同步和预转码可能持续数十秒到数小时。调用方不能依靠一个长时间挂起的 HTTP 请求判断结果。

标准交互包含以下参与者：

```text
前端                    业务服务                RabbitMQ/工作线程
 | 建立状态监听             |                           |
 | 提交 requestId -------->|                           |
 | <---- 已接受/已在执行 ----|                           |
 |                         | -------- 执行命令 -------->|
 |                         | <------- 状态消息 ----------|
 | <====== WebSocket: RUNNING/SUCCESS/FAILED ==========|
```

requestId 用于把一次点击和后续状态对应起来，不是资源主键。服务端还要按“任务类型 + 资源”做幂等和互斥，防止用户换一个 requestId 就重复执行同一任务。

## 全局业务规则

### 数据归属

必须区分四类数据：

| 数据 | 权威来源 | 丢失后的处理 |
| --- | --- | --- |
| 原始媒体 | NAS/本地文件系统 | 无法自动恢复，禁止缓存清理触碰 |
| 媒体索引 | MySQL + 文件扫描规则 | 可通过刷新重建，但主键关联要谨慎 |
| 用户数据 | MySQL | 必须备份，不随刷新和缓存清理删除 |
| 派生数据 | 缩略图、HLS/fMP4、向量、生成内容 | 按类型决定重建或长期保存 |

数据库和文件系统不可能天然具备同一事务。只读媒体模块主要通过扫描实现最终一致；Picture 允许改名、移动和删除原文件，因此必须先完成全量参数与路径校验，再执行文件操作和索引更新，并为中途失败保留可补偿信息。

所有路径都以模块配置的根目录为边界。数据库保存相对路径更利于根目录迁移；读取时解析为绝对路径并再次校验，拒绝 `..`、不受管绝对路径和利用链接逃逸的结果。

### 播放进度

进度是用户数据，不属于播放缓存。其标识至少包括用户和被消费的具体内容：

- 图书进度要区分书籍或具体文件格式，并保存阅读器能够恢复的位置。
- 电影进度关联实际 MovieFile，避免不同剪辑版本共用错误时间。
- 剧集进度关联 SeriesEpisodeFile，不能跨集串用秒数。
- 音乐进度关联 Track；若不同文件版本时长差异明显，还需明确默认文件策略。

频繁上报会产生大量写入，因此前端按稳定间隔上报，后端按最小保存间隔限流。在暂停、页面关闭、切换文件等边界事件上应尽力提交最后一次位置。媒体接近结尾时可标为完成，下次从头开始；阈值必须由模块配置统一决定。

播放会话是短期状态，用于当前用户、所选文件、清晰度和心跳。会话超时不删除用户进度，也不立即删除其他用户可复用的媒体缓存。

### 状态反馈

HTTP 响应使用统一业务结构。状态码和消息要区分这些情况：

- 参数不合法或资源不存在。
- 用户没有权限。
- 同类任务已经执行。
- 外部依赖暂时不可用。
- 文件存在但格式或内容无法解析。
- 派生结果尚未完成，可以稍后重试。
- 操作已经失败，需要重新发起或人工处理。

长任务至少有 `PENDING/RUNNING/SUCCESS/FAILED` 四种语义。对播放分片这类短任务还需要表达“正在生成，请播放器重试”，不能把暂未准备好当成永久失败。

用户消息要说明下一步，例如“图片向量服务不可用，仍可按目录浏览”；日志则记录 requestId、资源 ID、依赖响应和异常栈。两者用途不同。

### 资源约束

- 列表、筛选和详情优先查询数据库，不在每次请求中重新遍历 NAS。
- 大文件使用流式响应和 Range，不一次性读入 JVM 堆。
- 视频转码、图片嵌入和 AI 生成都有明确并发上限和有界队列。
- 相同资源、相同参数产生的派生结果尽量共享，不能按用户重复生成。
- 缓存具备 TTL、容量观察和清理规则，磁盘不足时能指出哪个缓存占用空间。
- 外部调用设置连接、读取和任务级超时。长超时不是无限等待的替代品。

## 交付标准

### 功能验收矩阵

每个模块至少准备以下样本：

| 样本 | 目的 |
| --- | --- |
| 正常中文路径 | 验证 Windows/NAS 路径和字符编码 |
| 空目录 | 验证刷新能正常完成并给出 0 条结果 |
| 不支持扩展名 | 验证忽略规则而非误入库 |
| 损坏文件 | 验证单项隔离和错误报告 |
| 同名不同内容 | 验证身份规则不会错误合并 |
| 移动或删除文件 | 验证索引、关联和派生数据处理 |

业务验收按真实路径执行“配置、刷新、浏览、消费、保存进度、重新进入”全链路。只调用 Controller 单接口不能证明前端路由、网关转发、文件权限和浏览器能力正常。

电影和剧集另有播放矩阵，必须覆盖暂停恢复、连续跨分片、随机拖动、清晰度切换、字幕、缓存过期和多人复用。Music 要覆盖 Range 拖动和同名不同歌手；Book 要覆盖三种格式和字符集；Picture 要覆盖目录写操作和 Qdrant 故障降级。

### 非功能验收

性能不规定脱离硬件的绝对数字，而采用可测的运行目标：

- 普通分页请求不随全部媒体文件数量线性遍历磁盘。
- 用户关闭播放后，不再持续生成后续窗口直到结尾。
- 重复刷新请求不会产生两个全量扫描消费者。
- 队列满时快速拒绝并给出可识别状态，不把服务器拖到失去响应。
- 删除缓存后功能可以重新生成；删除缓存前后用户进度保持不变。
- Redis、RabbitMQ、Qdrant、LLM、Spider 或 MinIO 单项故障时，受影响范围符合各模块的降级说明。

### 交付证据

“编译通过”“单元测试通过”和“功能通过”不能混为一句话。每次交付按实际完成情况提供：

```text
静态证据：后端编译、前端构建、类型检查
自动证据：单元测试、集成测试、时间轴/清单检查脚本
运行证据：服务监听、Nacos 注册、依赖连接
浏览器证据：实际页面、真实文件、播放或阅读行为
```

涉及真实 NAS、浏览器解码或 GPU 的场景如果没有执行，应明确标为未验证，不能用 Mock 测试代替结论。

### 需求变更规则

模块实现会继续变化，文档更新遵循两个原则：

1. 已实现行为写成当前设计，并标明实际配置和边界。
2. 尚未实现但已经决定的行为写成需求，注明与现状的差距。

新增公共能力时先判断它属于某个业务模块还是共享服务。只有被多个模块复用、拥有稳定协议的能力才放入 Framework、LLM、Spider 或 OSS，避免为了“微服务化”拆出只有一次调用的空壳服务。
